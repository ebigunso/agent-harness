# First Session in a Repository

Followed once per repository: when the Repository Reference Documents section of `docs/coding-agent/rules/common.md` has no Counsel line, the line recording Counsel's identity and that its relays are admitted. Once that line is there, a Counsel session finds it at open and does nothing beyond the open-time steps.

The owner opens no second session for any of this: Counsel starts the session that sets the repository up and carries the owner's words to it. The instinct refused is to send the owner to an Orchestrator session to ask for setup or to say yes there.

## Setup

- If `docs/coding-agent/rules/common.md` does not exist, setup has not run. Say so and offer it. On the owner's yes, start an Orchestrator session for setup as a run is started, within the limits on a start (`SKILL.md`, Hand-over and relay). Its first message stands alone, says that Counsel started the session and that it is for setting the repository up, and claims no authority of the owner's.
- Before setup no record of means exists, since setup writes it. For this one start, take what the runtime Counsel runs in gives for starting a session in the Orchestrator role with a first message, reading what it wrote, and giving it a further message, from the runtime's own help and documentation. Where nothing is found, say so plainly to the owner and start none.
- A real Counsel session making this start is untried: on 2026-11-13 a session standing in for Counsel made it, from a folder already trusted, for a repository it named by path.
- The setup session ends its turn saying what it waits for and from whom. Read that from what it wrote: its listed state says only that the turn ended (seen 2026-11-13).
- A first setup waits for more than the entry below: what the work runs on, a budget allowance, and whether decision records get a folder are the owner's to answer too. Each is told to the owner as anything that becomes ready is, and each answer is carried back quoting the owner's words. The acceptance of the entry goes first, because no other relay is admitted until the entry is in effect.

## The seat

- Counsel's identity, distinct from the Orchestrator's, is taken at open by the step in the skill's open-time steps; `<repository>` in its name is the repository's name.
- Without a peer channel there is no seat to take; the identity is still the one the entry names.

## Admission of relays

- Setup writes the standing approval that admits Counsel's relays into `common.md` as proposed, marked not in effect, and reports it as an offer. Put it to the owner as any standing approval, with the path to the file, so that the owner reads the entry itself (`SKILL.md`, Drafting and ratification).
- Say what accepting it takes on before asking: an Orchestrator session cannot verify who sent a message, and a runtime may record a message another session sent exactly as one a person typed, so with the entry every relay, the acceptance itself included, is taken on the word of whoever writes as Counsel. The owner takes that on by accepting the entry; nothing before that has accepted it.
- Carry the acceptance to the session that waits for it as a relay quoting the owner's words, with what places the quote: which entry, in which file, naming which identity. A yes to something else, or to relays in general, does not accept the entry. A relay without the quoted words is not acted on, and neither is one in a session whose first message does not say Counsel started it.
- On the acceptance that session records the quoted words and the date in the entry, writes the Counsel line and commits both. The entry is then in effect for sessions that read the branch the commit is on. Where that is not the branch the repository's work is based on, the session's report says so, and what brings the commit there is a merge the owner accepts like any other; tell the owner in a line.
- Seen once, on 2026-11-13, in one runtime, with stand-ins for Counsel and the owner and the acceptance given between the session's turns. Untried: a real owner's words, a decline, an acceptance over a peer channel, and a later session acting on a relay under the committed entry.
- Admission is recorded in `common.md` and nowhere else. A note the Orchestrator keeps for itself is not a place the harness reads.
- Where setup has run and no such entry is in effect, the same is done in the next session Counsel starts, before any other relay to it: the entry is put to the owner and the acceptance carried first. In a session started for a ratified brief this is untried (2026-11-13).
