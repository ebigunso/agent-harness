1. **`src/Bookings.java` — `BookingService.reserve`: Concurrent duplicate reservations remain possible.** Two callers can both observe `count(slot) == 0` and then insert, because these are separate autocommit statements with no uniqueness constraint. A nightly sweep cannot prevent duplicates from being used immediately. Require an atomic capacity check and reservation, enforced through a database uniqueness constraint or equivalent concurrency control, with the losing caller receiving `SlotFull`. Verify this with a concurrent booking test.

2. **`src/Bookings.java` — `NightlyMaintenance.run`, `deleteDuplicatesKeepingEarliest()`: Silently deletes accepted reservations.** Customers and downstream systems already rely on these bookings; keeping the earliest does not make deleting the others safe. Transactional deletion only makes the sweep atomic—it does not undo those commitments. Remove automatic deletion and require an explicit reconciliation process for existing conflicts, including handling affected customers and downstream effects.
