### Gate 4: Explicit Interface Contracts

**Expectation**
- Boundaries between components are explicit, minimal, and stable.
- Inputs, outputs, and failure semantics are intentionally modeled.

**Evidence expectations**
- Plan states contract-impact scope (none/additive/breaking).

- Failure modes are explicit and not silently swallowed.

**Anti-patterns**
- Implicit contracts communicated only by call-site assumptions.
- Breaking contract changes shipped without migration or compatibility notes.
- Returning ambiguous success/failure signals.

- **`query.ts:3` — The exported query has an implicit, UI/database-coupled contract.** `options: any` requires callers to supply an ID, a connection with `lookup`, and a view with `render`, while the query returns whatever the view renders. Neither the required inputs nor the output are explicitly typed, and exposing these internals makes callers depend on details beyond the requested account lookup. Require a narrow, typed API such as `query(id: string): Account`, keep the account source behind that API, and move rendering into `screen()`. If lookup can fail or find no account, explicitly define those outcomes in the contract.
