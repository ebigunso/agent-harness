**Cause (workspace/environment, not code):** `localhost` resolves to `::1` first, and the gRPC channel commits to `[::1]:50051`. The TCP handshake succeeds because Docker Desktop's host-side port proxy is listening on the IPv6 loopback, but the h2c stream is never delivered to the service — the interceptor log shows no invocation, and no HTTP/2 headers come back before the 2 s deadline, so the probe reports `DEADLINE_EXCEEDED` (exit 2). The identical call to `127.0.0.1:50051` completes (`pong`, exit 0, `invoked=true completed=true`), so the service, method, payload, and probe logic are all fine; only the IPv6 loopback path through the published port is broken. The `curl` health check on 50080 isn't a counterexample: it's a different port/proxy path and HTTP/1.1, and curl will fall back between addresses, whereas the gRPC probe does not.

**Smallest safe remediation:** pin the target to the IPv4 loopback — no container, service, or code changes:

```powershell
php probes/unary.php --target 127.0.0.1:50051 --timeout 2
```

(Equivalently `--target ipv4:127.0.0.1:50051` if you want gRPC to skip the resolver entirely.) If you must keep `localhost` in scripts, the next-smallest fix is to publish the port explicitly on IPv4 in the compose/run config (`127.0.0.1:50051:50051`) so `::1` isn't a listening target at all — but that touches Docker config, so do the target pin first.
