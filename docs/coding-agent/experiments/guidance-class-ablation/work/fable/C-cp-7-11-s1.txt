## Findings

**1. `schedule.cpp:5` — `due()` reads `Clock::now()` directly; there is no seam, so the decision can't be tested deterministically.**
The function hard-wires the global clock into the comparison. The only way to test it is to race real time, which is exactly what `test_due` does. This is the root cause of finding 2.
*Require:* make "now" an input to the decision, e.g. `bool due(Clock::time_point deadline, Clock::time_point now)` (a `now()`-defaulting overload or a clock template parameter is fine for callers). The threshold logic is a pure comparison and should be tested as one.

**2. `schedule.cpp:6–11` — `test_due` is timing-dependent and will flake in CI.**
`assert(!due(deadline))` on line 8 assumes less than 20 ms elapses between line 7 and line 8. Per the reviewer note, CI may pause the process between consecutive lines; any GC/scheduler stall, debugger attach, or loaded runner longer than 20 ms turns this into a spurious failure that has nothing to do with the code under test. The spin loop on line 9 then burns a core to reach the "after" case. This is fragile setup that doesn't match the risk — the risk is the comparison operator, not the clock.
*Require:* with the seam from finding 1, replace with fixed timepoints:
```cpp
const auto d = Clock::time_point{} + std::chrono::seconds(100);
assert(!due(d, d - std::chrono::nanoseconds(1)));
assert( due(d, d));                        // boundary: >= not >
assert( due(d, d + std::chrono::nanoseconds(1)));
```
No sleeps, no yields, no dependence on the host clock.

**3. `schedule.cpp:6–11` — the actual threshold boundary (`now == deadline`) is never exercised.**
The task is "check scheduled dispatch threshold", i.e. whether the edge is inclusive. The current test can only ever observe strictly-before and strictly-after; it cannot reliably land on `now == deadline`, so a regression from `>=` to `>` would pass. The equality case in the snippet above covers this.

**4. `schedule.cpp:6` — `test_due` is dead code and uses `assert` for test checks.**
Nothing calls `test_due`, and `assert` is compiled out under `NDEBUG`, so in a release build the test body is empty even if it were called. Neither state gives any evidence the threshold works.
*Require:* wire the test into whatever harness the project uses (or at minimum a `main` that runs it and returns non-zero on failure) and use a check that isn't disabled by `NDEBUG`.

Minor: once the spin loop is removed, drop `#include <thread>`.

**Verdict:** not acceptable as-is. The production function is trivial and probably correct, but the change offers no reliable evidence of that — the test is both flaky and blind to the one case that matters. Findings 1–3 are blocking; 4 is required before merge but is a smaller fix.
