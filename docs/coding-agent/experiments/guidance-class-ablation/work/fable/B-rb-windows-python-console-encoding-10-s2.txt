**Verdict:** It is a workspace/environment problem (stream encoding), not a bug in the script's logic. The scan itself completed; the crash is purely at the print site.

**Cause**

`sys.stdout` is bound to `cp932` even though stdout is a pipe. On Windows, when stdout is *not* a console, Python doesn't use the console code page at all — it falls back to the locale's ANSI code page (`locale.getpreferredencoding(False)`), which on a Japanese-locale machine is CP932. `sys.flags.utf8_mode = 0` confirms UTF-8 mode isn't on, and no `PYTHONIOENCODING` override is set. The status string contains `🧪` (U+1F9EA), a supplementary-plane emoji that no legacy code page can represent, so `print` raises `UnicodeEncodeError` regardless of console vs. pipe. The `flush=True` change was a red herring — flushing doesn't change the encoder.

(Minor note on the reference material: its "inherits the console code page" framing applies to interactive consoles; the piped case here is the locale/ANSI code page path. Same fix applies.)

**Smallest safe remediation**

Override the stream encoding for this invocation, no code change:

```powershell
$env:PYTHONIOENCODING = 'utf-8'; python progress.py
```

(`$env:PYTHONUTF8 = '1'` is an equivalent, slightly broader switch that also fixes file-handle defaults.)

No cleanup is needed: the script is read-only, and the failure happened at print time, so there are no partial writes to check.

If you own `progress.py`, the durable fix is to make the output site explicit at startup rather than relying on the environment:

```python
import sys
sys.stdout.reconfigure(encoding="utf-8")
```

(If the consumer of the pipe can't accept UTF-8, `reconfigure(errors="replace")` or dropping the emoji from `status` are the alternatives — but the default should be UTF-8 output.)

**Confirmation**

1. Rerun with the override: exit code should be `0`, stderr empty, stdout shows `Working 🧪` (byte-check it as UTF-8 if the receiving side re-decodes — e.g. `python progress.py | Out-File -Encoding utf8 out.txt` and inspect).
2. Sanity-check the diagnosis in the same piped environment: `$env:PYTHONIOENCODING='utf-8'; python -c "import sys; print(sys.stdout.encoding)"` should print `utf-8` (vs. `cp932` before).
3. If you applied the `reconfigure` fix, rerun *without* the env var and confirm the same clean output — that proves the script no longer depends on the caller's environment.
