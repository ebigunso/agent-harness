## Findings

**1. `Inventory.java`, `schedule(LocalDateTime input, List<Instant> queue)` — public API hardcodes UTC interpretation of a zone-less value (blocking)**

`LocalDateTime` carries no zone. The method silently assumes every caller's value is wall-clock UTC via `input.toInstant(ZoneOffset.UTC)`. The reviewer notes confirm this is a public adapter fed by callers in other zones. A caller passing `LocalDateTime.of(2026, 9, 9, 2, 0)` meaning 02:00 in Tokyo gets a snapshot scheduled at 02:00 UTC — nine hours off, with no error and no compile-time signal. The task says "schedule at supplied time"; this implementation cannot honor that because the supplied time is ambiguous by type. The one internal caller (`nightly`) happens to be correct only because it constructs the value with `now(ZoneOffset.UTC)` — which is exactly the pattern that makes the bug invisible in the current codebase and lands later.

Required change: encode the zone contract in the signature. Preferred: `schedule(Instant at, List<Instant> queue)` — the queue already stores `Instant`, so the adapter should just take one and stop converting. Acceptable alternative: `schedule(ZonedDateTime at, ...)` / `schedule(OffsetDateTime at, ...)` and call `.toInstant()`. If `LocalDateTime` must be kept for compatibility, add a `ZoneId zone` parameter (`input.atZone(zone).toInstant()`) and do not provide a zone-less overload. `nightly` then becomes `schedule(Instant.now(), queue)`.

**2. `Inventory.java`, `nightly(List<Instant> queue)` — name does not match behavior (flag)**

`nightly` schedules a snapshot for the current instant, not for a nightly time. Either it's a placeholder that will be wrong when someone wires it to a cron, or the name is misleading now. If the intent is "schedule tonight's run", it needs an actual target time (and a zone in which "night" is defined — which again argues for finding #1). If the intent is "schedule immediately", rename it (`scheduleNow`) or drop it.

**3. `Inventory.java`, both methods — no argument validation (flag, minor)**

`input == null` throws an unhelpful NPE from inside `toInstant`; `queue == null` throws from `add`. For a public adapter, `Objects.requireNonNull` with parameter names is cheap and makes misuse diagnosable. Not blocking on its own.

## Not raised
- Wildcard `java.time.*` import and single-line method formatting — style; defer to project conventions.
- Thread-safety of `List<Instant>` — the queue's ownership/synchronization is the caller's, outside this diff's scope.

## Verdict
Not acceptable as-is. Finding #1 is a correctness defect in the public contract that the current test surface (one UTC caller) cannot catch; it must be fixed before merge by changing the parameter type so the zone is explicit.
