**Findings**

1. **`job.cpp`, `finish()` — ordering bug: completion flag is persisted before the result.**
   `markCompleted(id)` runs first, then `writeResult(id, result)`. Per the notes, the two persist independently, `writeResult` can fail, and the process can stop between the calls. If either happens, the store ends up with `completed = true` and no result. Since "complete flag implies retrievable durable result", every consumer of that flag is now allowed to read a result that doesn't exist. Worse, the retry path *checks persisted completion* — so on retry the worker sees "completed", skips the job, and the missing result is never written. This is a permanent, silently corrupted record, not a transient failure.

   **Required:** invert the order — write the result first, then mark completed:
   ```cpp
   void finish(Store& store, const std::string& id, const std::string& result) {
       store.writeResult(id, result);
       store.markCompleted(id);
   }
   ```
   With this order, a failure/crash after `writeResult` leaves an orphaned result but `completed = false`; the retry sees "not completed" and re-runs `finish`, which rewrites the result (must be idempotent — see below) and then marks it. The invariant is never observable-violated. If `Store` ever gains a transactional API, use that instead; but with the interface as given, order is the only tool available and it must be this way round.

2. **`job.cpp` — `writeResult` must be safe to re-execute for the same `id` (follow-on to #1).**
   The corrected ordering relies on retrying `finish` after a partial write. That only works if `writeResult(id, result)` is idempotent (overwrite / put semantics) rather than insert-only. The interface doesn't say. I'd require either a comment on the `Store` contract stating that `writeResult` overwrites for an existing `id`, or a check with the store implementer. This is a documentation/contract ask, not a code change in this diff, but I'd block until confirmed because the retry story depends on it.
