## Diagnosis

**This is not a workspace problem, and it is not the Docker/`localhost` IPv6 issue described in the reference material.**

The reference scenario is ruled out by the evidence:

- **The call reached the service.** The server policy interceptor recorded the request (`method=Private invoked=true`) and the response came back in ~15 ms. A stalled HTTP/2 transport would produce a hang ending in `DEADLINE_EXCEEDED` (exit 2), not a fast, deterministic rejection.
- **No address asymmetry.** `localhost:50051` and `127.0.0.1:50051` return identical results (exit 3, `PERMISSION_DENIED: role required`). The IPv6 hypothesis depends on IPv4 working while `localhost` hangs — that asymmetry is absent.
- **The sibling REST port is healthy**, which here just confirms the machine/network path is fine; it isn't the discriminator.

**Cause:** The gRPC call completed successfully at the transport and application layers. The service's authorization interceptor rejected it because the request carried no credential granting the role required by the `Private` method (`policy=role-required status=PERMISSION_DENIED`). This is expected, correct behavior — an authorization gap, not a connectivity, port-publishing, or resolution fault.

## Smallest safe remediation

Supply the required authorization to the probe call — attach the credential/token metadata that grants the role `Private` demands (e.g., the probe's auth/metadata flag, or calling a method your current identity is authorized for). Do **not** change `localhost` → `127.0.0.1`; that has no effect here and would mask nothing. Do not touch service config, ports, or Docker.

If you believe the caller *should* already be authorized, the fix belongs on the caller's credential wiring or the server's role assignment — still an auth-configuration change, not a workspace change.

## How to confirm

Rerun the same command with the credential attached:

- **Success criterion:** exit code `0`, and response values printed to stdout (the probe only prints on success).
- **Server-side:** the interceptor log flips from `status=PERMISSION_DENIED` to a permitted/OK status for `method=Private invoked=true`.
- **Negative control:** without the credential you should still see exit `3` / `PERMISSION_DENIED`, confirming the change—not chance—produced the difference.

No credential values should appear in stdout/stderr or logs during confirmation.
