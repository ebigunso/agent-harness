**Verdict:** This is an environment (host networking) problem, not a defect in the probe, the service, or the gRPC library. It's the classic Docker Desktop / Windows IPv6-loopback black hole.

**Cause**

`localhost` resolves to `::1` first, and the Ruby gRPC channel takes that first address and sticks with it. On this host, Docker Desktop's port-publishing proxy accepts a TCP connection on `[::1]:50051` (so the connect succeeds and you don't get `UNAVAILABLE`), but the connection is never relayed to the service (which is only reachable via the IPv4 mapping). The client sends its HTTP/2 preface/SETTINGS and the Echo request, nothing comes back — no SETTINGS ack, no response headers, no first item — and the probe's 2 s deadline expires → `DEADLINE_EXCEEDED`, exit 2. The interceptor log confirms the request never reached the service. The address-only comparison (`127.0.0.1:50051` → `pong 1`, `pong 2`, exit 0, `invoked=true completed=true`) isolates the variable to the destination address; everything else was held constant.

The curl comparison is a red herring rather than a contradiction: it's a different port/listener (50080) and curl does its own connect-fallback, so it does not exercise the `[::1]:50051` path that gRPC-Ruby is stuck on.

**Smallest safe remediation**

Use the IPv4 loopback address explicitly for this target; no code, host-file, IPv6, or Docker config changes:

```powershell
ruby probes/stream.rb --target 127.0.0.1:50051 --timeout 2
```

(If a resolver-hint form is preferred, `--target ipv4:127.0.0.1:50051` is equivalent.) I would *not* disable IPv6, edit `hosts`, set `GRPC_DNS_RESOLVER`, or change the probe — those are broader than the problem. If you want a durable fix beyond this probe, the next-smallest change is publishing the port on IPv4 only (`127.0.0.1:50051:50051`) or making the service listen dual-stack, but that's a separate decision from unblocking this call.

**Confirmation**

1. Re-run the command above: expect exit 0, `pong 1` / `pong 2` on stdout, empty stderr, well under the 2 s deadline.
2. Check the service interceptor log shows a new entry for that call with `invoked=true completed=true`.
3. (Optional, to prove it's address-specific and not flakiness) re-run the original `--target localhost:50051` once more and confirm it still fails identically with exit 2 and no interceptor log entry — same server, same config, only the address differs.
