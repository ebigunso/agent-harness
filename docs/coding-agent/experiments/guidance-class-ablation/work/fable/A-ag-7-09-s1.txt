## Findings

### 1. `Crash.kt:2` — `reportCrash` leaks private profile fields into externally-retained crash analytics

**What's wrong:** `signal("crash profile=$profile")` string-interpolates a Kotlin `data class`. The generated `toString()` emits every constructor property, so the crash payload becomes `Profile(id=..., homeAddress=..., recoveryAnswer=...)`. Home address and the account-recovery answer are sent verbatim to the crash sink.

**Why it matters:** Per the reviewer notes, crash analytics is retained outside the profile service. That means (a) a home address — personal data — is copied into a system with a different retention/access boundary, and (b) the recovery answer is effectively an authentication secret; putting it in crash logs turns crash-log readers (and any downstream vendor) into a route to account takeover. Neither field contributes to diagnosing a crash. This is a data-exposure defect, not a style nit, and it's the kind that's hard to remediate after the fact because logs are already replicated.

**What I'd require:** Only emit what's diagnostically useful — the id (or a hashed/opaque id if the sink shouldn't be able to correlate to real accounts):

```kotlin
fun reportCrash(profile: Profile, signal: (String) -> Unit) {
    signal("crash profile.id=${profile.id}")
}
```

Additionally, don't rely on call sites remembering this. Harden the type itself so accidental interpolation can't leak: either override `toString()` on `Profile` to redact, or move the sensitive fields out of the primary constructor (e.g., into a separate `ProfileSecrets` type) so `data class` generation never includes them. A dedicated `CrashContext(val profileId: String)` value type passed to `reportCrash` is the cleanest option — the function then can't receive the secrets at all.

### 2. `Crash.kt:1` — `recoveryAnswer` stored as a plain `String` alongside ordinary profile data

**What's wrong:** The recovery answer is modeled as just another string field on the general-purpose `Profile` object.

**Why it matters:** This is what made finding #1 possible, and it will recur: any future `toString`, `copy`, serializer, or debug log of `Profile` will carry the secret. A recovery answer should be treated like a password — stored hashed, never held in the same object that gets passed around for display/telemetry.

**What I'd require:** Remove `recoveryAnswer` (and ideally `homeAddress`) from `Profile`, or at minimum give it a wrapper type whose `toString()` returns `"***"` and which is excluded from any serialization. If this shape is pre-existing and out of scope for this PR, I'd still want it acknowledged and a follow-up filed, but I would not let the crash-reporting change land on top of it as written.

### 3. Missing test

**What's wrong:** No test asserts the crash payload's contents.

**Why it matters:** Redaction regressions are silent — nothing breaks when a secret starts appearing in logs. A test that asserts `homeAddress`/`recoveryAnswer` values are *absent* from the emitted string is cheap and is the only thing that will catch a future `data class` field addition or `toString` change.

**What I'd require:** A unit test that calls `reportCrash` with a sentinel address and recovery answer and asserts the captured signal does not contain either sentinel and does contain the id.
