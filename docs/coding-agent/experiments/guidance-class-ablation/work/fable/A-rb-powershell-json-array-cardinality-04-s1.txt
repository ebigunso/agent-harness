**Cause:** This is a script bug, not a workspace/runtime problem. In PowerShell 7, `ConvertFrom-Json` enumerates a top-level JSON array onto the pipeline by default. With a single-element array, the one element is emitted and `$parsed` receives that lone `PSCustomObject`, so `-isnot [array]` fires. (An empty array would have yielded `$null`, also failing; only ≥2 elements would pass.) The stdout line `parsed type=System.Management.Automation.PSCustomObject` confirms exactly this. The JSON itself is valid and the runtime behaved as documented.

**Smallest safe remediation:** Preserve the array shape at parse time (line 5):

```powershell
$parsed = $raw | ConvertFrom-Json -NoEnumerate
```

Do *not* "fix" it with `@($parsed)` — that would coerce scalar wire values like `7` into a one-element array and silently violate the contract's "reject scalars" requirement. `-NoEnumerate` keeps `[]`, `[x]`, and `[x,y]` all as `System.Object[]` while leaving a scalar as a scalar.

**Confirmation:**
1. Re-run `pwsh -NoProfile -File probes/cardinality.ps1`; expect exit code 0 and `parsed type=System.Object[]`.
2. Spot-check the contract boundaries in a shell:
   ```powershell
   ('[]' | ConvertFrom-Json -NoEnumerate) -is [array]        # True
   ('[{"id":7}]' | ConvertFrom-Json -NoEnumerate) -is [array] # True
   ('[1,2]' | ConvertFrom-Json -NoEnumerate) -is [array]      # True
   ('7' | ConvertFrom-Json -NoEnumerate) -is [array]          # False (correctly rejected)
   ```
