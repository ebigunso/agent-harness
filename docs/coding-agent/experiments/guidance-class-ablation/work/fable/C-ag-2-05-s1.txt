**Verdict: Block.**

## Findings

### 1. `core.rs:1` — Inward dependency on `axum` from the core crate
**What's wrong:** `use axum::http::StatusCode;` pulls a web framework into the domain/core module. Per the reviewer notes, `axum` is a dependency of the *outer HTTP crate*; core has no business importing it.
**Why it matters:** This inverts the dependency direction. Core now depends on a volatile vendor detail (axum's version, its `http` re-export, its `StatusCode` type). Every consumer of core — including the CLI — must now transitively build and link axum. Framework upgrades (axum 0.8 → 0.9) become breaking changes to core. This is exactly the "no framework/vendor calls in domain" seam violation.
**Require instead:** No `axum` (or `http`) import in core. Core stays framework-free.

### 2. `core.rs:3` — `allow()` now returns `Result<(), StatusCode>` instead of the domain error
**What's wrong:** The public signature of `allow` changed from the domain-typed `RuleError` to an HTTP status. `RuleError::Rejected` is still declared but is now dead — nothing produces it. HTTP semantics ("403 Forbidden") are baked into the rule itself.
**Why it matters:**
- The CLI caller (an existing consumer of core) now receives an HTTP status code for a business-rule rejection, which is meaningless in that context and will require the CLI to interpret HTTP codes — or it simply breaks at compile time if it matched on `RuleError`.
- The mapping "rule rejected ⇒ 403" is a *presentation* decision. Deciding it in core means changing it later (e.g. to 422 or 409) requires editing domain code; and a second transport (gRPC, message bus) cannot reuse the rule without stripping HTTP meaning back out.
- Leaving `RuleError` in place while bypassing it makes the intended interface a lie — future readers will assume it's the error contract when it isn't.
**Require instead:** Restore `pub fn allow(active: bool) -> Result<(), RuleError>`. Keep `RuleError` as the sole error type core exposes.

### 3. Missing change — the actual task ("return rule rejection to HTTP caller") is not implemented at the correct seam
**What's wrong:** The diff touches only core. The place that should change is the HTTP handler in the outer crate, which is the only layer that knows about status codes. Nothing in the diff shows that adapter.
**Why it matters:** The task is legitimately about the HTTP boundary, but the author solved it by moving the boundary into core rather than mapping at the edge. That makes the change both incorrect (per #1/#2) and incomplete — the HTTP crate still has no explicit rejection → response mapping.
**Require instead:** Add the mapping in the HTTP crate, e.g.:

```rust
// http crate — the one that already depends on axum
impl axum::response::IntoResponse for RuleErrorResponse { /* ... */ }
// or a plain match:
match core::allow(active) {
    Ok(()) => StatusCode::OK.into_response(),
    Err(RuleError::Rejected) => StatusCode::FORBIDDEN.into_response(),
}
```

If the orphan rule prevents `impl IntoResponse for core::RuleError` directly, use a newtype wrapper in the HTTP crate (`struct HttpRuleError(RuleError)`) or a free `fn to_status(e: &RuleError) -> StatusCode`. Either way, core is untouched.

### 4. Cargo manifest — `axum` would have to be added as a core dependency (implied, not shown)
**What's wrong:** For this to compile, `core`'s `Cargo.toml` must gain `axum = "0.8"`. The diff doesn't show the manifest, so either it's missing (won't build) or it was added silently.
**Why it matters:** Either way it's a red flag: an undisclosed change to core's dependency graph is the kind of edge that needs to be visible in review, and the correct fix requires *no* manifest change.
**Require instead:** No `axum`/`http` entry in core's `Cargo.toml`. If one was added in a companion change, revert it.

- Implement the rejection → `403 FORBIDDEN` mapping in the HTTP adapter crate only.
- Confirm the CLI still compiles against the unchanged `RuleError` contract.
