**Verdict:** This is a workspace/local-configuration problem, not a server, image, or code defect.

## Cause

The local configuration profile was just switched from `127.0.0.1:50051` to `localhost:50051`. On this Windows host, `localhost` resolves to `::1` first, so the gRPC channel dials `[::1]:50051`. Docker Desktop's published-port proxy on the IPv6 loopback accepts the TCP connection (so the client sees a "connected" socket and never falls back) but does not complete the HTTP/2 (h2c) exchange — no response headers arrive, the request never reaches the container (no entry in the service interceptor log), and the probe's 2s deadline fires with `DEADLINE_EXCEEDED` / exit 2.

The evidence lines up:

- Same method, payload, deadline, server, container and config, differing only in target: `127.0.0.1:50051` → exit 0, `pong`, and the server logs `invoked=true completed=true`. So the service and port mapping are healthy; only the `::1` path is broken.
- The REST sibling on `localhost:50080` returns 200 in 12 ms, which shows the asymmetry is specific to HTTP/2 over the IPv6-loopback proxy, not to Docker networking generally (and curl's HTTP/1.1 path is unaffected).
- The probe does not override resolution or retry on another address, so it cannot self-heal.

## Smallest safe remediation

Revert the local configuration profile target from `localhost:50051` back to `127.0.0.1:50051`.

Do **not** touch server code, the image, port mappings, the hosts file, or system IPv6 settings — those are broader changes with wider blast radius, and the address-only comparison already shows the IPv4 target is sufficient.

## Confirmation

1. Run the original failing invocation against the reverted profile (equivalently `java -jar probes/kotlin-probe.jar --target 127.0.0.1:50051 --timeout 2`) and check: exit code 0, stdout `pong`, stderr empty.
2. Confirm the service interceptor log shows a new line `probe method="unary Echo" transport=h2c invoked=true completed=true` for that call.
3. Optionally re-run the `localhost:50051` variant once to confirm it still reproduces (exit 2, `DEADLINE_EXCEEDED`), proving the target address is the sole variable.
4. Record for the ticket: targets/port (`[::1]:50051` fail vs `127.0.0.1:50051` pass), the deadline output, the REST timing (`200`, 0.012s), and the IPv4 retry result.

If `localhost` is ever required in this profile, that becomes a separate item to test against a Docker Desktop version that forwards HTTP/2 on `::1` — not something to fix in this workspace now.
