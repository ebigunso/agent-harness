**Verdict: Block.**

## Findings

### 1. `Crash.kt` — `reportCrash` leaks `homeAddress` and `recoveryAnswer` into crash analytics

**What's wrong:** `signal("crash profile=$profile")` string-interpolates the `Profile` data class, which invokes the generated `toString()`. Kotlin data-class `toString()` emits every primary-constructor property, so the emitted line is literally:

```
crash profile=Profile(id=..., homeAddress=<street address>, recoveryAnswer=<security answer>)
```

**Why it matters:**
- `recoveryAnswer` is an authentication secret — equivalent to a password fallback. Writing it to a crash log is a credential leak, and it's going to a system (crash analytics) that is retained *outside* the profile service, with different access controls and retention. Anyone with crash-dashboard access can now perform account recovery for these users.
- `homeAddress` is PII under GDPR/CCPA-style regimes; exporting it to a third-party/external store without necessity creates a data-minimization violation and expands breach blast radius.
- Neither field has any diagnostic value. The task was "attach profile *context*," which for triage means "which profile was this" — i.e., the `id`.
- Because the leak is via `toString()`, it is invisible at the call site. Anyone adding a field to `Profile` later (SSN, phone, etc.) silently leaks it too. This is a structural hazard, not just a one-line bug.

**Required change:** Log only the identifier, explicitly:

```kotlin
fun reportCrash(profile: Profile, signal: (String) -> Unit) {
    signal("crash profileId=${profile.id}")
}
```

Additionally, to close the structural hole, prevent `Profile` from ever serializing its sensitive fields by accident — either override `toString()` to redact them, or (better) don't carry `recoveryAnswer` on the general-purpose profile object at all; a secret used only during recovery flow should not ride around on the entity handed to crash reporting. At minimum:

```kotlin
data class Profile(val id: String, val homeAddress: String, val recoveryAnswer: String) {
    override fun toString() = "Profile(id=$id)"
}
```

(Overriding `toString` on a data class is allowed and does not affect `equals`/`hashCode`/`copy`.)

### 2. `Crash.kt` — no test or guard against regression

**What's wrong:** Nothing asserts that the crash signal excludes the sensitive fields.

**Why it matters:** This is exactly the kind of defect that gets reintroduced by a well-meaning "add more context" change. Given the retention/exposure consequences, the constraint should be enforced, not just remembered.

**Required change:** A unit test that captures the emitted string and asserts it contains `profile.id` and does **not** contain `homeAddress` or `recoveryAnswer` values. Cheap, and it makes the requirement executable.

## Not flagged

- The `signal: (String) -> Unit` indirection and the message format are fine for the stated scope; I'm not going to require structured logging here.
- The commit message accurately describes the intent; the defect is in the implementation, not the framing.
