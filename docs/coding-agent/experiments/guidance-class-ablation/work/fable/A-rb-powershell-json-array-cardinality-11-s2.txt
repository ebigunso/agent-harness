**Cause — probe logic bug, not a workspace/runtime problem.**
Line 5, `$parsed = @($raw | ConvertFrom-Json)`, unconditionally wraps whatever comes out of the pipeline in a new array. `'7' | ConvertFrom-Json` correctly yields an `[Int64]` scalar, but `@(...)` turns it into a one-element `System.Object[]`, so `$parsed -is [array]` is true and line 10 throws by design. The probe can never observe a scalar, so this inverse test is structurally incapable of passing. Runtime, execution policy, cwd and the JSON itself are all fine (stdout shows the parse succeeded).

Note the second half of the same bug: without the wrap, plain `ConvertFrom-Json` in PowerShell 7 *enumerates* JSON arrays, so `'[7]'` would parse to a scalar `7` and `'[]'` to `$null` — the positive cases (empty/singleton arrays accepted) would then be misclassified. That is presumably why someone added `@()`. The correct fix is to preserve the wire shape at the parser rather than coerce it afterward.

**Smallest safe remediation** — change line 5 only:

```powershell
$parsed = $raw | ConvertFrom-Json -NoEnumerate
```

`-NoEnumerate` returns a JSON array as a single `Object[]` (length 0, 1 or n) and a JSON scalar as the scalar, so `-is [array]` now reflects the wire cardinality exactly. No other lines need to change; the `$null` guard on line 8 remains harmless.

**Confirmation**

1. Rerun `pwsh -NoProfile -File probes/cardinality.ps1` — expect exit 0, no stderr, and `parsed type=System.Int64`.
2. Verify the positive contract still holds with the same parsing form:
   ```powershell
   foreach ($j in '[]','[7]','[1,2]','7','"x"','null') {
     $p = $j | ConvertFrom-Json -NoEnumerate
     '{0,-6} -> array={1}' -f $j, ($p -is [array])
   }
   ```
   Expect `True` for the three arrays and `False` for `7`, `"x"`, and `null`. If that matrix matches, the probe (and any sibling probes that copied the `@()` pattern) is discriminating correctly.
