**Findings**

1. **`Money.cs`, `public Money(decimal amount)` constructor — validation is bypassable, so the "nonnegative debit magnitude" invariant does not actually hold.**
   - What's wrong: `Create` rejects negative amounts, but the constructor is `public` and does no checking. Per the reviewer notes, import and API adapters call the constructor directly, so `new Money(-50m)` is a legal construction and flows straight into `Ledger.Debit`.
   - Why it matters: `Debit(balance, new Money(-50m))` returns `balance + 50` — a debit silently becomes a credit. Because overdraft is permitted and balance bounds are deliberately separate from `Money`, there is no downstream check that would catch this; the type is the only place the sign invariant lives, and it isn't enforced. Anyone reading the `Create` guard will reasonably assume `Money.Amount >= 0` and write code (and tests) on that assumption.
   - Required instead: make the invariant unconditional. Either move the `amount < 0` check into the constructor (and have `Create` just call it), or make the constructor `private` so `Create` is the only entry point. Given external adapters already use the constructor, the first option is the lower-risk change: they keep compiling and now get the exception at the boundary where bad data enters. Add a test that constructing a negative `Money` throws, and one that `Debit` with a valid `Money` never increases the balance.

No other blocking issues. `decimal` subtraction in `Debit` throws `OverflowException` on overflow regardless of `checked` context, so there is no silent wraparound concern there, and treating `balance` as an unconstrained `decimal` is consistent with the stated overdraft policy.
