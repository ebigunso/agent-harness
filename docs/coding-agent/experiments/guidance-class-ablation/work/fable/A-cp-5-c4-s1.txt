**Verdict:** Small, mostly sound change. Nothing I'd block outright, but I'd require the first two items fixed before merge and would ask about the third.

1. **buffer_test.go, `TestConfig` — upper boundary not tested.**
   The invalid cases are `-1, 0, 8388609` and the only valid case is `1`. The maximum valid size `8388608` is never exercised, so an off-by-one in `size > 8*1024*1024` (e.g. someone changing it to `>=`) passes the suite. Since the whole point of this change is boundary validation, both edges need a passing case. Require: add `New(8*1024*1024)` succeeds and `Allocate()` returns that length.

2. **buffer.go / buffer_test.go — not gofmt'd.**
   `&Buffer{size:size}`, `make([]byte,b.size)`, `if _,err:=New(n); err==nil`, single-line struct/func bodies, etc. This will fail any standard `gofmt -l` / lint gate and creates noisy diffs for the next editor. Require: run `gofmt` (or `goimports`) on both files.

3. **buffer.go, `New` — validation error omits the offending value and duplicates the limit as a literal.**
   `"buffer size must be 1..8388608"` doesn't say what was actually configured, which is exactly what an operator needs when startup fails. The bound also appears twice (`8*1024*1024` in the check, `8388608` in the message), so they'll drift the first time someone changes one. Require: a named constant (e.g. `MaxSize`) and a message like `fmt.Errorf("buffer size %d out of range [1, %d]", size, MaxSize)`.

4. **Scope vs. task — nothing here runs at startup.**
   The task is "validate upload configuration at startup," but the diff only adds a constructor. Nothing shown calls `New` from config loading / `main`, so as submitted the validation is only as good as the caller remembering to use it. If the wiring exists elsewhere and was intentionally left out of this fixture, fine; otherwise the change is incomplete and I'd want the call site included (or a follow-up ticket referenced in the commit message).

Not raising: the zero-value `Buffer{}` returning an empty slice — the reviewer note explains it's intentional, the field is unexported so callers can't fabricate an invalid non-zero size, and it doesn't panic. Also not raising the `t.Fatal(n)` / `t.Fatal("valid")` messages; they're terse but the failing input is at least printed for the invalid loop.
