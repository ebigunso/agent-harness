## Review findings

**1. `Invoice.java` — the change is labeled "additive" but breaks the Java constructor contract.**
Adding a component to a record changes the canonical constructor from `Invoice(String)` to `Invoice(String, String)`. Every existing `new Invoice(id)` call site stops compiling, and any binary consumer breaks at link time. That is a breaking source/binary change, not additive optional metadata — the reviewer notes only assess the JSON side and miss this. Gate 4 requires the impact scope to be stated accurately and producers to be synchronized; the diff shows no call-site updates and no compatibility shim.
*Require:* either (a) keep the old shape compatible by adding a delegating constructor:
```java
record Invoice(String id, String label) {
    Invoice(String id) { this(id, null); }
}
```
or (b) relabel the change as breaking, update all constructors of `Invoice` in the same change, and note it in the commit message.

**2. `Invoice.java` — "optional" is not actually modeled; it is implied by an unannotated nullable `String`.**
Nothing in the type or the record states that `label` may be absent, what absence means, or whether `""` and `null` are equivalent. Callers will have to guess (call-site assumption), which is the exact anti-pattern the gate calls out. It also silently changes `equals`/`hashCode`: two invoices with the same `id` but different labels are now unequal, and `Invoice("a", null)` ≠ `Invoice("a", "")`.
*Require:* make optionality explicit — `@Nullable String label` (or `Optional<String>` if that's the codebase convention) plus a compact constructor that normalizes (e.g., blank → `null`), and a one-line comment stating the semantics. Confirm that changing record equality is acceptable for how `Invoice` is used.

**3. Serialization side of the contract is unaddressed.**
Deserialization of old JSON (no `label`) into `Invoice` yields `null` — fine. But serialization of `Invoice` now emits `"label": null` for every existing invoice. The notes only establish that *this repo's* `Reader` tolerates unknown fields; nothing verifies other consumers of `Invoice` JSON (other services, persisted schemas, strict validators) accept a new field or a `null` value.
*Require:* either `@JsonInclude(JsonInclude.Include.NON_NULL)` on `label` so the wire shape is unchanged when the label is absent, or an explicit statement in the change of which downstream consumers were checked.

**4. No test covers the new contract.**
There is no test that (a) a JSON payload without `label` round-trips, (b) a payload with `label` populates it, and (c) legacy construction (`Invoice(id)`) still works if the shim in #1 is adopted. Given this is a contract change, the compatibility claim should be executable, not asserted in reviewer notes.
*Require:* a small Jackson round-trip test for both shapes.

**Verdict:** Not acceptable as-is. Block on #1 (mislabeled breaking change / missing compatibility constructor); #2–#4 should be fixed in the same change since they are all part of making the "optional" contract explicit and verifiable.
