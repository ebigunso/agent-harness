## Cause

This is a script bug, not an environment problem.

`ConvertFrom-Json -NoEnumerate` correctly preserves `[7]` as a one‑element array **inside** `Parse`. The problem is the function's *output*: the last statement `$items` emits the value to the pipeline, and PowerShell's function/pipeline output **re‑enumerates** collections. A single‑element array gets unwrapped, so `$parsed` ends up as the lone `System.Int64` element rather than an array. That is exactly what stdout shows (`parsed type=System.Int64`), which makes `$parsed -isnot [array]` true and triggers the `throw`.

In short: `-NoEnumerate` stops the *conversion* from enumerating, but the *function return* enumerates again and defeats it.

## Smallest safe remediation

Suppress enumeration on the function's output with the unary comma (array‑wrap) operator. Change line 4:

```powershell
function Parse { $items = $raw | ConvertFrom-Json -NoEnumerate; ,$items }; $parsed = Parse
```

The leading `,` wraps the result in an outer array so the pipeline unwraps *that* wrapper and leaves the real array intact. (Equivalent alternative: `Write-Output -NoEnumerate $items`.) Nothing else in the script needs to change, and it still correctly rejects true scalar wire values.

Expect:
