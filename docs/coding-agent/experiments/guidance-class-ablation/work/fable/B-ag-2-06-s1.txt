**Findings**

1. **`Feature.cs`, `Feature.Status(SqlRepository repo, long id)` — feature bypasses the `IAccounts` seam and binds to `SqlRepository.InternalConnection`.**
   - What's wrong: The feature takes the concrete `SqlRepository`, reaches into an `internal` property, and issues its own SQL against the connection. The `IAccounts` abstraction exists precisely so callers don't do this; `Feature` ignores it.
   - Why it matters: This inverts the dependency direction (Gate 2). Feature/domain code now depends on `Microsoft.Data.Sqlite` and on the physical schema (`accounts.status`), not on a stable abstraction. Any change to storage (different provider, table rename, caching, connection pooling) now has two places to break instead of one, and `Feature` can no longer be tested with a fake `IAccounts`. It also breaks the repository's ownership of the connection lifecycle — the feature is now executing commands on a connection it doesn't own and whose disposal/threading it doesn't control.
   - Require instead:
     ```csharp
     public static class Feature {
       public static string? Status(IAccounts accounts, long id) => accounts.Status(id);
     }
     ```
     `Feature` should depend on `IAccounts` only and should not `using Microsoft.Data.Sqlite`.

2. **`Feature.cs`, `SqlRepository.InternalConnection` — leaks the connection as an `internal` property.**
   - What's wrong: Exposing the connection (even `internal`) is what enabled finding #1. Nothing in the task ("read account status") requires it; it exists solely to let `Feature` bypass the repository.
   - Why it matters: `internal` is not an abstraction boundary — every type in the assembly can now execute arbitrary SQL on the repository's connection, silently defeating the repository's encapsulation and lifecycle guarantees. Reviews of future changes will have no seam to enforce.
   - Require instead: make the connection a `private readonly` field. If some test genuinely needs access, use `InternalsVisibleTo` for the test assembly only, not a property consumed by production code.

3. **`Feature.cs` — duplicated query.**
   - What's wrong: `SELECT status FROM accounts WHERE id=$id` is copy-pasted verbatim into `SqlRepository.Status` and `Feature.Status`.
   - Why it matters: Two sources of truth for the same read; they will drift (e.g., adding `AND deleted = 0` in one place). This is a symptom of #1 and disappears once `Feature` delegates to `IAccounts`, but I'd flag it explicitly so it doesn't survive a partial fix.
   - Require instead: single implementation in `SqlRepository`; `Feature` delegates.

**Verdict:** Block. The change is not acceptable as-is. The minimal correct diff is `Feature` depending on `IAccounts` and calling `Status(id)`, with `InternalConnection` removed (or made private). The repository implementation itself (`SqlRepository.Status`) is fine — parameterized, disposes the command — and can stay.
