**Findings**

1. **`DiscountAdapter.cs`, `DiscountAdapter.Map` / `DiscountView` — presence is silently collapsed into an explicit zero.**
   - What's wrong: `discount.proto` declares `optional int32 cents`, so the wire contract has three-way semantics for the field: absent (unknown), present-and-zero, present-and-nonzero. The Java transport model (`hasCents`, `Discount.unknown()`) preserves that. The C# adapter maps `HasCents == false` to `new DiscountView(0)`, which is indistinguishable from a wire message that explicitly set `cents = 0`. `DiscountView(int Cents)` has no way to represent "unknown" at all.
   - Why it matters: this is exactly the implicit coercion the contract-fidelity guideline calls out. Downstream consumers of `DiscountView` will treat "no discount information was sent" and "the discount is zero" identically — e.g. rendering "$0.00 discount" or applying a zero discount when the server actually said nothing. The upstream schema and the client model no longer agree on semantics, and there is no way to recover the lost bit once it has passed through `Map`. The task was to map an *optional* discount, and the optionality is precisely the part that got dropped.
   - What I'd require: make the client model carry presence, e.g. `public record DiscountView(int? Cents);` with `Map` returning `new(wire.HasCents ? wire.Cents : null)` (or an explicit `Unknown` state / `Optional`-style wrapper if the codebase has a convention for it). Add unit tests covering all three cases — absent, explicit `0`, and nonzero — asserting that absent and explicit-zero produce distinguishable `DiscountView` values. If a default-to-zero behaviour is genuinely wanted at some *presentation* layer, that decision should live there and be named as such, not be baked into the transport adapter.

No other issues I would raise; the proto and the Java/C# wire records themselves are consistent with each other and with the proto3 presence API described in the notes. The change is **not acceptable as-is** because of finding 1.
