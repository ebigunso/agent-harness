**Verdict: not a workspace or Docker-networking problem.** The reference article's hypothesis (IPv6 `::1` loopback stall in Docker Desktop's port proxy) does not apply here, and the evidence already rules it out.

## Cause

The requests are reaching the service. The failure is a **server-side stall inside the handler**, not a transport hang:

- The reference's own step 1 — retry with `127.0.0.1` — was effectively already done, and it fails identically to `localhost` (exit 2, `DEADLINE_EXCEEDED` after 2s). No IPv4/IPv6 asymmetry exists.
- The interceptor records an invocation for both targets, and the handler trace shows `method=Echo invoked=true phase=db-query waiting_on=lock-42`. A transport-level HTTP/2 stall would never produce a handler invocation.
- `lock-42` is held by a **stalled migration transaction**. The `Echo` handler blocks on the DB lock longer than the 2s client deadline, so the client cancels and reports `DEADLINE_EXCEEDED`.
- The REST health endpoint on 50080 is fast because it doesn't touch that lock — it's a red herring for the "gRPC vs REST" framing.

Changing the connection string to `127.0.0.1` (the reference's remediation) would change nothing.

## Smallest safe remediation

Resolve the stalled migration transaction holding `lock-42` — do **not** touch the probe, the target address, or the port mapping:

1. Identify the migration process/session holding `lock-42` (e.g. `pg_stat_activity` / `pg_locks` for Postgres, or the equivalent for the DB in use) and determine whether it's genuinely stuck or just slow.
2. If it's stuck/orphaned, let it finish or roll it back / terminate that single session so the lock is released. Do not kill the gRPC service or restart the container first — that doesn't release a lock held in the DB and risks leaving the migration half-applied.
3. Only if the migration is legitimately long-running, raise the probe `--timeout` temporarily for diagnosis — but that's a workaround, not a fix.

## Confirmation

1. Verify the lock is gone: re-check the DB lock view and confirm no session holds `lock-42`, and the handler trace no longer shows `waiting_on=lock-42`.
2. Re-run the original command unchanged:
   `python probes/unary.py --target 127.0.0.1:50051 --timeout 2`
   Expect exit 0, the response value on stdout, and empty stderr.
3. Re-run with `localhost:50051` and expect the same result, confirming the address never mattered.
4. Optionally confirm the migration reached a consistent terminal state (applied or rolled back) so the stall doesn't recur on the next deploy.
