**Verdict: block.** The adapter change inverts the task; the client is written against a contract the adapter no longer provides.

**1. `adapter.py`, `lookup()` — service failures now reported as success**

`except (NotFound, Unavailable): return 200, None` replaces two distinct error mappings with a 200. This is the opposite of "map RPC lookup results to HTTP":

- A `NotFound` and a lookup that legitimately returns `None`/`null` are now indistinguishable to any caller. Callers cannot tell "no such record" from "record exists and its value is null."
- An `Unavailable` (transient outage) is reported as a successful empty result. Nothing upstream will retry, alert, or degrade; outages will manifest as silent data loss ("the value was empty") rather than errors. That is the most dangerous failure mode a mapping layer can introduce.
- The previous code was correct for both cases. This is a regression, not a refactor.

Require: restore `except NotFound: return 404, None` and `except Unavailable: return 503, None`. If there was a real motivation for the change (e.g., some caller couldn't handle non-200), that needs to be stated and solved in the caller, not by lying about the status.

**2. `client.ts`, `interpret()` — 404/503 branches are unreachable given this adapter**

The client is written to the *old* adapter contract. With the adapter as diffed, `interpret` will only ever see `status === 200`, so `"missing"` and `"retry"` can never be produced and every service error surfaces as `return value` with `value === null`. The two halves of this change contradict each other; whichever was intended, they must agree. (Fixing #1 resolves this.)

Secondary, would still flag once #1 is fixed: the return type is effectively `unknown | "missing" | "retry"`. If a successful lookup can return the string `"missing"` or `"retry"`, callers can't distinguish it from the sentinel. Prefer a discriminated result (`{ kind: "ok", value } | { kind: "missing" } | { kind: "retry" }`) or throw typed errors for 404/503. Not blocking on its own, but the sentinel-string design is fragile.

The notes say "Client treats 404 as missing and 503 as retryable" and "only not-found and unavailable are service errors," and the message says "map rpc lookup results to http." The adapter diff removes the 404/503 mapping entirely. Either the description is stale or the wrong adapter change was committed.
