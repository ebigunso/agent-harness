**Verdict: not acceptable as-is.** The change does not do what the task asks; it moves the fix to the wrong layer and leaves the actual defect in place.

**1. `src/Session.kt`, `Session.logout()` — the root cause is untouched**

`logout()` still only calls `credentials.clear()`. `tenantKeys` — the tenant session material the task is about — is never cleared. Since `Session` is service-owned and shared with background sync, the previous tenant's keys remain live in the service after logout and will be used by the next sync (and by the next tenant's session, if they log in on the same instance). This is exactly the "remove previous tenant session material" requirement, and nothing in the diff addresses it.

Required: clear the tenant material inside `Session.logout()` itself, e.g. `tenantKeys.clear()` alongside `credentials.clear()`, so every consumer of `Session` (screens *and* background sync) gets the invariant "logout ⇒ no tenant material" from the single owner of that state. The reviewer note confirms this runs on the serialized session executor, so a plain `clear()` here is sufficient; no additional synchronization is warranted.

**2. `src/Session.kt`, `LogoutScreen.confirm()` — `app.restart()` is a symptom patch that doesn't even cover the symptom**

Replacing `showSignedOut()` with `restart()` attempts to wipe state by tearing down the foreground process. But per the reviewer notes, `restart()` only restarts the foreground; the service that owns `Session` and its `tenantKeys` survives. So this is a heavy, user-visible workaround (full app restart on every logout) that still leaks the previous tenant's keys to background sync. It also couples a UI screen to a lifecycle hack to compensate for a missing cleanup in a model class — if any other logout path (background timeout, account switch, remote revoke) calls `session.logout()` without going through this screen, it gets no cleanup at all. That's the duplicated/compensating-logic pattern to avoid.

Required: revert to `app.showSignedOut()` (or whatever the intended post-logout UI transition is). Once `Session.logout()` clears its own state, there is no need for a restart. If a foreground restart is genuinely desired for an unrelated reason, that should be a separate change with its own justification — it should not be presented as the fix for tenant material cleanup, and the commit message ("restart the foreground app on logout") should not be the description of this task.

**3. (Minor, follow-up) `Session.tenantKeys` is a public mutable map**

Exposing `val tenantKeys = mutableMapOf(...)` lets any caller mutate or hold a reference to the map, which makes the "cleared on logout" invariant easy to violate from outside `Session`. Not blocking for this change, but I'd suggest exposing it read-only (`Map<String,String>`) with mutation going through `Session` methods, so the cleanup in `logout()` is the only place that needs to be correct.
