**Verdict: block.** The change does not do what the task and commit message claim.

## Findings

**1. `query.ts`, `handle()` — the caller's signal is never wired to the query.**

`callerSignal` is accepted as a parameter and then ignored. The query is given `new AbortController().signal`, a fresh controller that nothing ever aborts. Functionally this is identical to passing no signal at all: when the caller disconnects, `db.query` keeps running to completion, the scoped connection stays held for the full duration, and the result is produced for a caller that is gone. The one thing the task asked for — cancellation propagating from caller to query — does not happen. Because `Database.query` is stated to honor the signal and release its connection on abort, the cost of this bug is real: abandoned expensive queries continue to consume pool slots, so a burst of client disconnects (timeouts, retries, navigation away) leaves the DB doing unwanted work and can starve live callers.

Required instead: pass the caller's signal straight through.

```ts
export async function handle(db: Database, callerSignal: AbortSignal) {
  return await db.query(callerSignal);
}
```

If there is a reason to build a separate controller at this boundary (e.g. to also impose a server-side deadline), it must be linked to the caller signal, not detached:

```ts
export async function handle(db: Database, callerSignal: AbortSignal) {
  const signal = AbortSignal.any([callerSignal, AbortSignal.timeout(QUERY_DEADLINE_MS)]);
  return await db.query(signal);
}
```

Either form is acceptable; the current form is not.

**2. `query.ts`, `handle()` — already-aborted callers are not short-circuited.**

Related to (1): if `callerSignal.aborted` is already true when `handle` runs (caller left during queueing), the function should not start the query at all. Passing the caller signal through (fix for #1) covers this if `db.query` checks `signal.aborted` on entry; if that isn't guaranteed by the `Database` contract, add `callerSignal.throwIfAborted()` before the call. This is a minor point contingent on #1, but I'd want it confirmed rather than assumed.

**3. Commit message / task claim is inaccurate.**

"cancel expensive queries when callers leave" describes behavior the diff does not implement. A reviewer skimming the log would believe cancellation is in place. Fix the code so the message is true, rather than the reverse.

## Not flagged

- No test is included. For a four-line change I'd normally ask for one, but the bug here is visible by inspection; once #1 is fixed, a single test that aborts `callerSignal` and asserts `db.query` received an aborted signal would be sufficient and I'd expect it to accompany the fix.
- Error propagation on abort (the `AbortError` rejection surfacing to the caller) is the correct behavior and does not need special handling at this boundary — the caller is gone, so there is no one to degrade for.
