**Cause**

Stale working directory in the persistent shell. The prior `Set-Location -LiteralPath 'C:/work/scratch'` moved the shell's cwd to `C:\work\scratch` (contains only `notes.txt`), and that cwd persists across commands. Cargo resolves the workspace by walking up from the process cwd looking for `Cargo.toml`; from `C:\work\scratch` it finds none (the parent `C:\work` has no manifest either), so it exits 101 with "could not find `Cargo.toml`". The tool UI's remembered root (`C:/work/rust-service`) is not the shell's cwd — they diverged.

This is a workspace/cwd problem, not a code, toolchain, dependency, or permission problem: the project manifests exist and are readable, and the identical command succeeds once run from the correct directory.

**Smallest safe remediation**

Run the command from the intended base, either by navigating first:

```powershell
Set-Location -LiteralPath 'C:/work/rust-service'
cargo test -p api
```

or, without changing the shell's cwd, by pointing Cargo at the manifest explicitly:

```powershell
cargo test --manifest-path 'C:/work/rust-service/Cargo.toml' -p api
```

No file edits, no reinstalls, no config changes. If further commands in this shell are meant to target the service, the `Set-Location` form is preferable so subsequent relative-path commands don't hit the same problem.

**Confirmation**

1. `pwd` (or `Get-Location`) prints `C:\work\rust-service` (normalized `C:/work/rust-service`).
2. `cargo test -p api` exits 0 (`$LASTEXITCODE -eq 0`) with `test result: ok. 1 passed; 0 failed`, and stderr shows `Running unittests src/lib.rs` — matching the captured comparison run.
3. A trailing `pwd` still shows `C:/work/rust-service`, confirming the shell cwd now matches the workspace root the tool UI displays.
