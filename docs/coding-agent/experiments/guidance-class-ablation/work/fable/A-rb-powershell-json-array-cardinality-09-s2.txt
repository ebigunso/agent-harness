**Verdict:** Not an environment/workspace problem. `data.json` is valid, `ConvertFrom-Json` parsed it correctly, and the throw is the script's own assertion firing because of a bug on line 5.

**Cause**

```powershell
$parsed = $raw | ConvertFrom-Json | Write-Output
```

In Windows PowerShell 5.1, `ConvertFrom-Json` emits a JSON array as a single `Object[]` (it does not enumerate). But the extra `| Write-Output` stage *does* enumerate its input: it unrolls the one-element array and writes `$true` to the pipeline. The assignment therefore captures a scalar `System.Boolean` (exactly what stdout shows: `parsed type=System.Boolean`), and `$parsed -isnot [array]` is true → `throw`. The wire value was a singleton array, so the contract says it should pass; the checker collapsed it itself.

**Smallest safe fix**

Remove the enumerating stage on line 5:

```powershell
$raw = Get-Content -Raw data.json; $parsed = $raw | ConvertFrom-Json
```

(Equivalently `| Write-Output -NoEnumerate`, but simply dropping the pipe is smaller.)

Do **not** "fix" it with `$parsed = @(... | ConvertFrom-Json ...)` — that would wrap a scalar wire value like `true` into a one-element array and silently violate the "reject scalars" contract.

Note for portability: if this probe is ever run under PowerShell 7, `ConvertFrom-Json` there enumerates arrays by default, so you'd need `ConvertFrom-Json -NoEnumerate` (that switch doesn't exist in 5.1). The fix above is correct for the stated 5.1 runtime.

**Confirmation**

1. Re-run `powershell.exe -NoProfile -File probes/cardinality.ps1` with the current `data.json` (`  [true]  `). Expect exit code 0 and stdout containing `parsed type=System.Object[]`, no stderr.
2. Quick contract check without touching data.json (the checker writes no files, so vary input in a throwaway copy or inline):
   - `'[]' | ConvertFrom-Json` → `Object[]`, length 0 → should pass.
   - `'[1,2]' | ConvertFrom-Json` → `Object[]` → passes.
   - `'true' | ConvertFrom-Json` → `Boolean` → still throws `Expected JSON array` (exit 1), proving the scalar-rejection path is intact.

Incidental: lines 3–4 (`$raw = '  [true]  '`, `$wireCount = '1'`) are dead/hard-coded scaffolding — `$raw` is immediately overwritten and `$wireCount` isn't derived from the data. Harmless to this failure, but worth cleaning up separately so the "wire elements=" line reports something real.
