**Findings**

1. **`ClusterReducer.scala`, `run()` — transition logic has no callable seam (blocking).**
   The `(state, event) match { ... }` is the entire point of the change ("add paused event transition"), but it is inlined between a socket read and a `println`. The only way to exercise it is to boot the real cluster server on 5080, open a connection, and scrape stdout. That is exactly the "fragile setup" the guideline warns against: the test depends on a live network service, a fixed port, process stdout, and the harness happening to emit a `running`/`pause` pair. If the cluster server is down, the port is taken, or the harness emits a different first event, the check fails or passes for reasons unrelated to the transition table. It also can't cover the negative cases (`("paused","pause")` stays `paused`, unknown event is a no-op) without steering the harness.
   Require: extract a pure function, e.g. `def transition(state: String, event: String): String`, and have `run()` call it. Then add a plain unit test covering `running+pause → paused`, `paused+resume → running`, and the identity cases. The socket-driven `run()` can stay as the I/O shell.

2. **Validation evidence is disproportionate to the change surface (flag, follows from #1).**
   The change is a two-branch state table; the stated validation is "boot the cluster and grep stdout for `paused`." A substring search on stdout is not a check of the transition — `paused` appears in output for any input where state was already `paused`, so the check would pass even if the `("running","pause")` branch were deleted. Once the seam in #1 exists, the direct unit test is the right-sized evidence; keep the cluster boot (if at all) as a smoke test, not the proof that the transition is correct.

3. **`ClusterReducer.scala`, `readLine()` calls — no handling of a short/closed stream (minor).**
   If the peer closes before two lines arrive, `readLine` returns `null`; `(null, null)` falls into `case _ => state` and the program prints the literal `null`. The notes say the protocol is closed and guarantees both lines, so I wouldn't block on this, but with the seam from #1 in place it becomes trivial to have `run()` fail fast on `null` rather than silently emitting a bogus state. Worth doing while you're in there.

Not raised: hardcoded `127.0.0.1:5080` and the `var state` reassignment are consistent with the harness contract as described and don't affect correctness or testability once the pure function exists.
