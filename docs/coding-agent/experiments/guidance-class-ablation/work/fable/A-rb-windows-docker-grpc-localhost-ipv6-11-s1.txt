**Verdict:** This is a workspace/host-networking problem (address selection), not a defect in the probe, the gRPC library, or the service.

**Cause**

`localhost` resolves to `::1` first, and the Dart gRPC channel connects to `[::1]:50051` and stays there — it does not fall back to `127.0.0.1`. Docker Desktop's port proxy accepts the TCP connection on the IPv6 loopback, but the traffic never reaches the container (the published mapping is effectively IPv4-only on this host), so the h2c connection preface/`SETTINGS` never gets answered. The client sits on a half-open-in-practice connection until the 2 s deadline fires → `DEADLINE_EXCEEDED`, exit 2. That matches every observation:

- TCP connect succeeds but no HTTP/2 headers arrive.
- No invocation in the interceptor log — the request never left the host proxy.
- The identical call to `127.0.0.1:50051` succeeds (`pong 1`, `pong 2`, `invoked=true completed=true`).
- The curl sibling on 50080 succeeding is not a counterexample: curl uses Happy Eyeballs and quietly falls back from `::1` to `127.0.0.1`; the Dart channel does not.

TLS is ruled out (plaintext h2c, no cert check), and the server handler is fine.

**Smallest safe remediation**

Point the probe at the IPv4 loopback explicitly:

```powershell
dart run probes/bidi.dart --target 127.0.0.1:50051 --timeout 2
```

(and use `127.0.0.1:50051` in any config/script that currently says `localhost:50051`). This changes nothing on the host, in Docker, in the hosts file, or in IPv6 settings.

A slightly broader but still safe alternative, if you want `localhost` to work for everyone: bind the publish explicitly to IPv4 (`-p 127.0.0.1:50051:50051`) so `[::1]:50051` gets an immediate connection refused instead of a silent stall. I'd only do that if the target string can't be changed.

**Confirmation**

1. Rerun the command above — expect exit 0, stdout `pong 1` / `pong 2`, empty stderr, and a new `probe method="bidirectional Echo" transport=h2c invoked=true completed=true` line in the service log (this is exactly what the captured comparison already showed).
2. To confirm the diagnosis rather than just the fix, rerun with `--target localhost:50051` and see it still fail identically, and run `curl.exe -6 --max-time 2 http://localhost:50080/health` vs `curl.exe -4 ...` — the `-6` form should stall/time out while `-4` returns 200, proving the asymmetry is at the IPv6 loopback → container hop, not in the probe.
