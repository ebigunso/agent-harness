## Cause

This is not a failed check — every check passed. The process died while *printing* the result.

Because stdout is a pipe (not an interactive console), CPython 3.12 on Windows falls back to the locale ANSI code page for the stream: `sys.stdout.encoding = cp1252`, and UTF-8 mode is off (`utf8_mode = 0`). `check.py` line 15 does `print('PASS ' + symbol)` where `symbol` is U+2713 CHECK MARK, which has no mapping in cp1252. The `charmap` codec raises `UnicodeEncodeError`, the traceback goes to stderr, nothing reaches stdout, and the interpreter exits 1.

So the "failure" is an I/O-encoding mismatch between the script's output and the captured stream's encoding, layered on a script that assumes it can emit non-ASCII to any stdout. The exit code is misleading: the diagnostic itself succeeded.

## Smallest safe remediation

Run the script in UTF-8 mode without touching the code:

```powershell
python -X utf8 check.py
```

or equivalently, for the session/pipeline:

```powershell
$env:PYTHONUTF8 = 1
python check.py
```

Either forces `sys.stdout.encoding` to `utf-8` regardless of whether the stream is a console or a pipe. No source change, no global machine setting, fully reversible.

If you'd rather fix it in the script so it's robust for every caller, the minimal code change is at the top of `check.py`:

```python
import sys
sys.stdout.reconfigure(encoding="utf-8", errors="replace")
```

(`errors="replace"` alone would also stop the crash by printing `?`, but then the check mark is silently lost — prefer setting the encoding.)

One caveat for the consumer: PowerShell decodes native-process output using `[Console]::OutputEncoding`, which on Windows often still defaults to the OEM code page. If the ✓ shows up as mojibake in the pipeline after the fix, set `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8` in the session. That's a display issue, not a crash, and separate from what killed the process.

## Confirmation

1. Verify the mode took effect in the same captured-stream context:
   ```powershell
   python -X utf8 -c "import sys; print(sys.stdout.encoding, sys.flags.utf8_mode)" | Out-String
   ```
   Expect `utf-8 1`.
2. Rerun `python -X utf8 check.py` (or with `PYTHONUTF8=1`) through the same pipe. Expect exit code 0, stderr empty, and stdout containing `PASS ✓` (ASCII bytes `50 41 53 53 20` followed by `E2 96 93` when inspected raw).
3. `echo $LASTEXITCODE` → `0`.

## Is it a workspace problem?

Partly. The environment's default encoding for piped stdout is what triggered it, but the root fragility is in `check.py`: it emits non-ASCII output without controlling its stream encoding, so it will fail on any Windows host whose stdout is redirected and not in UTF-8 mode. The one-line `reconfigure` in the script is the durable fix; the `-X utf8` flag is the safe immediate unblock.
