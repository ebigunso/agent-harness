**Verdict: block.** The change does the opposite of the task — it makes export completion *less* trustworthy under disk-full, and it regresses the atomic-publish guarantee the old code had.

## Findings

### 1. `src/export.php`, `catch (DiskWriteError $error)` — failure is swallowed and reported as success
`writeFully` throwing is the exact "disk filled mid-write" signal the task is about. The handler logs it and falls through to `return ['status' => 'ready', 'path' => $destination]`. Consumers, per the notes, open the returned path when status is `ready`, so they will read a truncated/partial artifact and treat it as the complete report. A log line is not a substitute for a correct result; the caller has no way to learn the export failed. This is a silent-data-corruption path.

**Require:** do not catch `DiskWriteError` here at all (let it propagate to whoever owns the export boundary), or catch it, clean up, and return an explicit failed status / rethrow with context. Under no circumstances may `'status' => 'ready'` be returned after a write error.

### 2. `src/export.php`, `$writer->openForReplace($destination)` — writes in place, destroying the previous valid artifact before success is known
`openForReplace` truncates `$destination` immediately. The previous code (`replaceAtomically`) wrote beside the destination and published only on complete success, so a mid-write failure left the earlier valid file intact. Now the moment the export starts, the last-known-good artifact is gone; if the disk fills, what remains at `$destination` is a zero-length or partial file, regardless of what status is returned. Even with finding #1 fixed, this still loses the safe fallback state the system previously had.

**Require:** keep the write-to-temp-sibling / publish-on-success pattern. Either revert to `replaceAtomically`, or if streaming was the motivation, stream into a temp path adjacent to the destination, flush/fsync, and rename over `$destination` only after every chunk succeeds; on failure, delete the temp file and leave the destination untouched.

### 3. Commit message / task mismatch
"stream directly to the ready artifact" describes precisely the behaviour the task was meant to rule out. The diff is not an implementation of the stated task; it needs to be reworked rather than patched.
