**Verdict: the core requirement is met, but I would not approve as-is.** The sink receives only `LoginEvent` (eventId/requestId/accountId), and nothing from `Credentials` reaches it. Two findings:

1. **`Login.java` — `success(LoginEvent event, Credentials credentials, Consumer<LoginEvent> sink)`: `credentials` is an unused parameter.**
   The method never reads it. Passing a secret-bearing object into a telemetry method that has no use for it widens the blast radius for exactly the bug this change is meant to prevent: the next edit to this method has the password and bearer token sitting right there, one `event.toString() + credentials` away from the sink. It also makes the signature lie about what the method depends on, and every caller must now materialize a `Credentials` just to call it.
   **Require:** drop the parameter — `static void success(LoginEvent event, Consumer<LoginEvent> sink)`. If a future variant genuinely needs to make a decision based on credentials, add that then, with the decision visible in the body.

2. **`Login.java` — `record Credentials(String password, String bearerToken)` inherits the record default `toString()`, which prints both secrets in cleartext.**
   Any `log.info("...{}", credentials)`, string concatenation, exception message, `Objects.toString`, or debugger/`assert` output will emit `Credentials[password=..., bearerToken=...]`. The change is titled "log identifiers only" and then introduces a type whose default string form is the secret; that is a latent leak path independent of `success()`.
   **Require:** override `toString()` on `Credentials` to return a redacted form (e.g. `"Credentials[redacted]"`). Consider the same for any future secret-carrying records in this module.
