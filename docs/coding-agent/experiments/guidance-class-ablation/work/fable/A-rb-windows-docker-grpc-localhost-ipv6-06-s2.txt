**Verdict: workspace/environment problem — specifically loopback address-family asymmetry in the Docker Desktop port forward — not a probe bug, not a server bug, and not a deadline that's too short.**

## Cause

`localhost` resolves to `::1` first, so tonic dials `[::1]:50051`. The TCP connect succeeds (Docker Desktop's host proxy is listening on the IPv6 loopback), but the connection is never actually plumbed through to the container: the h2c preface/SETTINGS exchange gets no reply, no HTTP/2 headers ever arrive, and the service interceptor log shows no invocation. tonic sits on the half-open stream until the 2 s deadline and maps the result to `DEADLINE_EXCEEDED` / exit 2 per the probe contract.

Evidence that this is the address, not the service or the timeout:

- Identical call to `127.0.0.1:50051` succeeds in well under the deadline, prints `pong`, and produces `invoked=true completed=true` in the service log.
- HTTP/1.1 health on 50080 answers in 12 ms, so the container and Docker networking are healthy on the path that gets used; curl either lands on IPv4 or falls back, which the probe by contract does not do.
- The probe is stated to never rewrite `localhost` or retry on another address, so a first-family dial to a dead-end `::1` forward is terminal.

Raising `--timeout` would only make the failure slower.

## Smallest safe remediation

Point the probe at the IPv4 loopback explicitly:

```powershell
cargo run --manifest-path probes/Cargo.toml -- --target 127.0.0.1:50051 --timeout 2
```

That's a one-token change to the invocation, touches no system config, no hosts file, no IPv6 settings, and no container/service configuration. If you want the fix to be durable rather than per-invocation, the next-smallest step is to publish the port bound to IPv4 only (`-p 127.0.0.1:50051:50051`) so `::1` connects are refused outright instead of accepted-and-black-holed — but that's a service config change and isn't needed to unblock the probe.

## Confirmation

1. Re-run the command above: expect exit 0, stdout `pong`, stderr showing only the cargo `Finished`/`Running` lines.
2. Check the service interceptor log for a new `probe method="unary Echo" transport=h2c invoked=true completed=true` line correlating with that run.
3. To confirm the diagnosis rather than just the fix, re-run with `--target [::1]:50051` (should still time out with exit 2 and no log entry) and optionally `netstat -ano | findstr :50051` to see the `[::]:50051` listener owned by the Docker Desktop backend process rather than anything that reaches the container.
