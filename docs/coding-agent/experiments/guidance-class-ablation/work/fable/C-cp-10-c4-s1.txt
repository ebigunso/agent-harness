**Verdict: acceptable to merge as an incident mitigation.** The behaviour matches the stated contract (CRLF→LF, lone CR preserved, `strings.ReplaceAll` returns the input unchanged when there are no matches, so no extra allocation on already-clean feeds), the debt is bounded to a single boundary, and it carries owner/ticket/removal trigger. Nothing below is blocking; they're cheap clarity items I'd ask for in the same PR or an immediate follow-up.

1. **`feed.go` – not gofmt'd.** `text,"\r\n"`, `input,want:=range`, missing blank lines between `package`/`import`/func. Any `gofmt -l` / lint gate will fail this; even without one it's noise for the next reader and for the eventual revert diff. Run `gofmt` before merge — zero risk, zero cost.

2. **`feed.go` – the comment is an ownership note, not a doc comment.** The exported `Normalize` has no statement of its contract. The important invariants ("feed only contains LF/CRLF; lone CR is intentionally preserved") live only in the reviewer notes, which disappear. Require a doc comment such as:
   ```go
   // Normalize converts CRLF line endings to LF. Lone CR is preserved by design;
   // the legacy feed is known to emit only LF/CRLF.
   // Temporary adapter — Owner: Data Platform; FEED-41. Remove once vendor v4 emits LF.
   ```
   This is what makes the boundary legible and the removal safe.

3. **`feed_test.go` – `t.Fatalf` inside the table loop.** First failure aborts the loop, hiding whether the other cases pass; with a map, which case fails first is also nondeterministic. Use `t.Errorf` (or `t.Run` per case) so a regression shows the full picture. Minor, but it's a one-token change.

4. **Removal trigger has no signal (follow-up, not this PR).** The comment says "remove on vendor v4 LF rollout", but nothing tells you when the feed has actually stopped sending CRLF. Since this is the single feed boundary, a counter/log-once when a replacement actually occurs would give Data Platform concrete evidence to close FEED-41 rather than removing on a calendar and hoping. I wouldn't add a metrics dependency to this package under an urgent rollout; track it on the ticket.

Not raising: the `"\r\r\n"` interaction — `ReplaceAll` is single-pass, so it yields `"\r\n"` (preserved CR + LF), which is the correct outcome under the stated rules and is out of the declared input contract anyway.
