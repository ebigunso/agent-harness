**Findings**

1. **`domain.ts` line 1 — domain module imports the Prisma client (`PrismaClient`, `Invoice`) from `@prisma/client`.**
   This inverts the dependency direction (Gate 2). `domain.ts` previously depended on nothing but a primitive; it now depends on a vendor-generated client. The `Invoice` type is a generated artifact of `schema.prisma`, so any schema change (rename `cents`, add a column, change nullability) silently changes the domain's input contract. Core behavior now depends on storage details rather than the other way around. **Require:** define a domain-owned type (e.g. `export type Invoice = { cents: number }` or keep `total(cents: number)`) and have the persistence layer map Prisma rows into it. Domain must not import `@prisma/client`.

2. **`domain.ts` `loadTotal(db: PrismaClient, id)` — domain function makes a direct database call (`db.invoice.findUnique`).**
   The task is "calculate totals"; fetching is a storage concern. Placing the query in the domain module couples the pure calculation to Prisma's query API, makes the domain untestable without a Prisma client (or a mock of one), and means every consumer of `loadTotal` must construct/pass a `PrismaClient`. This is exactly the "domain logic directly calling vendor clients" anti-pattern. **Require:** either move `loadTotal` out of `domain.ts` into a repository/application layer (`invoiceRepository.ts` / `invoiceService.ts`), or if the domain needs a loading seam, depend on a narrow interface it owns (`interface InvoiceReader { findById(id: string): Promise<Invoice | null> }`) with the Prisma implementation living in an outer layer.

3. **`domain.ts` `total(invoice: Invoice)` — signature widened from `number` to the full generated `Invoice`.**
   `total` only reads `invoice.cents`, yet it now requires callers to supply a whole Prisma row (including `id`). Existing callers passing a number break, and new callers must construct full records to compute a total. Beyond the boundary issue in (1), this is an unnecessary API narrowing. **Require:** keep `total(cents: number)` (or accept a minimal domain-owned shape `{ cents: number }`), and let the loading layer extract `cents` from the row.

**Not flagged:** the `null` handling for a missing invoice is explicit and fine. The `schema.prisma` addition itself is fine as a storage-layer artifact; the problem is only that domain consumes its generated output directly.

**Verdict:** Block. The change is functionally plausible but violates Gate 2 on both counts the gate calls out (domain depends on a generated vendor type; domain directly invokes the vendor client). Required shape: `domain.ts` stays pure with a domain-owned input type; a separate persistence/application module holds the Prisma import and the `findUnique` call and maps into the domain type.
