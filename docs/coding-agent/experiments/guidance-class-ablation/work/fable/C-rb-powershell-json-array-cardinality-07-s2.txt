## Cause

This is a **workspace (script) bug**, not a runtime problem. The JSON is valid and PowerShell 7.4.6 behaves correctly.

The defect is the trailing re-pipe on line 5:

```powershell
$parsed = ($raw | ConvertFrom-Json -NoEnumerate) | Write-Output
```

`ConvertFrom-Json -NoEnumerate` does its job and emits the single-element array as one object. But piping that object into `| Write-Output` sends it through **another pipeline**, and PowerShell pipelines unroll arrays. The one-element array `["north"]` is enumerated down to its lone element, the string `"north"`. So `$parsed` ends up as `System.String`, `-isnot [array]` is true, and the `throw` fires.

The stdout confirms this exactly: `parsed type=System.String`. The `-NoEnumerate` guarantee was undone the moment the result was re-piped.

## Smallest safe remediation

Delete the redundant `| Write-Output` so the array is assigned directly from `ConvertFrom-Json`:

```powershell
$parsed = $raw | ConvertFrom-Json -NoEnumerate
```

Nothing else in the script needs to change. Assigning a single emitted object to a variable does not enumerate it, so the array framing survives.

## How to confirm

1. Re-run the exact command:
   ```
   pwsh -NoProfile -File probes/cardinality.ps1
   ```
2. Expect **exit code 0**, no stderr, and stdout showing:
   ```
   parsed type=System.Object[]
   ```
   (i.e. `-isnot [array]` is now false, so no throw).
3. Guard against a false pass on the singleton by also exercising the other contract cases with the same fix:
   - `'[]'` → `System.Object[]`, count 0, no throw (empty array preserved).
   - `'["a","b"]'` → `System.Object[]`, count 2, no throw.
   - A scalar like `'"north"'` → `System.String`, which should still (correctly) throw.

If you want extra assurance the acceptance rests on wire framing rather than parser mood — and to stay portable to Windows PowerShell 5.1, which lacks `-NoEnumerate` — additionally assert on the trimmed raw text: `$raw.Trim()` starts with `[` and ends with `]`. That is a framing check, not a JSON syntax validation, so keep it alongside (not in place of) the parse/type assertion.
