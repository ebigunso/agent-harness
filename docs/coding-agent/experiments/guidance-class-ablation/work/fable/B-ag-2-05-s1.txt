**Verdict: Block.** The change achieves the task by inverting the dependency direction, and it breaks an existing consumer.

## Findings

### 1. `core.rs:1` — Core now depends on the HTTP framework (`use axum::http::StatusCode`)

**What's wrong:** The domain/core module imports `axum`. This is the exact anti-pattern in Gate 2: domain logic reaching directly into a framework/transport client. The dependency arrow now points from the stable inner layer *outward* to a volatile delivery detail (axum 0.8 — a crate that has broken its public API across minor versions).

**Why it matters:**
- Core must now compile against axum, dragging hyper/tokio/http into every consumer of core, including ones that never serve HTTP.
- Any axum upgrade becomes a core change. The core crate's stability is now bounded by axum's.
- It establishes precedent: the next person will import `sqlx::Error` or `serde_json::Value` into core with this diff as justification.

**Require instead:** Core keeps returning its own error type. The HTTP crate owns the mapping. Either `impl IntoResponse for RuleError` (or a newtype wrapper if orphan rules bite) in the HTTP crate, or a `From<RuleError> for StatusCode` / explicit `match` at the handler boundary:

```rust
// in the HTTP crate, not core
fn map_rule_err(e: RuleError) -> StatusCode {
    match e { RuleError::Rejected => StatusCode::FORBIDDEN }
}
```

### 2. `core.rs:3` — `allow()` signature changed to `Result<(), StatusCode>`; breaks the CLI consumer

**What's wrong:** Per the reviewer notes, core is also used by the CLI. The CLI now receives an HTTP status code from a rule check. Either it fails to compile (if it matched on `RuleError::Rejected`) or it's now forced to interpret `403` in a non-HTTP context.

**Why it matters:** This is a public-API break for a consumer the author didn't touch or test, and it leaks transport semantics ("Forbidden") into a place where the correct rendering might be an exit code, a log line, or a user-facing message. The task was "return rule rejection to HTTP caller" — it says nothing about changing what non-HTTP callers get.

**Require instead:** Leave `allow` returning `Result<(), RuleError>`. The signature was already correct; only the HTTP handler needed to translate it.

### 3. `core.rs:2` — `RuleError` is now dead

**What's wrong:** The enum is kept but nothing in the diff returns it anymore. It's either orphaned (and will trip `dead_code` warnings/lints) or still used elsewhere in ways the diff no longer satisfies.

**Why it matters:** Minor on its own, but it's a signal the author didn't check who consumes `RuleError` — which is the same oversight as finding 2.

**Require instead:** Falls out of reverting finding 1/2. If `RuleError` is meant to grow (more variants), keep it as the single domain error and let the HTTP layer map each variant to a status.

### 4. Missing evidence — no HTTP-side change in the diff

**What's wrong:** The task is to surface the rejection to the HTTP caller, but the diff contains zero changes to the HTTP crate. There's no handler, no `IntoResponse` impl, no test asserting that a rejected rule yields a 403 response.

**Why it matters:** Gate 2's evidence expectation is that the review can verify the abstraction seam where the external system is involved. The seam here is the handler; it's not in the diff, so the actual user-visible behavior is unreviewable. The commit message claims an outcome the diff doesn't demonstrate.

**Require instead:** The diff should touch the HTTP crate (handler + error mapping) and include a test that calls the handler with an inactive rule and asserts `403`. Core should be untouched.

## Summary of what an acceptable change looks like

- `core.rs`: **no changes.**
- HTTP crate: add `impl IntoResponse for RuleError` (or a local newtype / mapping fn), use it in the handler, add a handler-level test for the 403 path.
- `Cargo.toml` for core: verify axum is **not** added as a dependency.
