**Verdict: block.** The change introduces a second write path that bypasses the only place the "quantity ≥ 0" invariant is enforced.

## Findings

### 1. `inventory.rb`, `admin_update` — invariant not enforced on the new write path (blocking)
`admin_update` does `item.update!(quantity: item.quantity + delta)` with no check. With a negative `delta` whose magnitude exceeds the current quantity, the row goes negative. Nothing stops it: no DB CHECK constraint, no model validation, and the guard lives only in `normal_update`. The reviewer notes say quantity must never be negative, and the task ("allow adjustments in admin") doesn't say admins may override that rule — so this is a straight violation of the stated invariant, not an intentional exemption.

Require: the same `value < 0` rejection in `admin_update` (or, better, one shared `adjust(item, delta)` that both paths call), so the two paths can't drift. If the product intent really is that admins may force negative stock, that contradicts the stated invariant and needs to be resolved explicitly in the task, not left implicit in a missing `if`.

### 2. `inventory.rb`, `Inventory` model / schema — invariant is enforced only in an optional caller path (blocking, independent of #1)
Even after fixing `admin_update`, the invariant is still protected by convention: any future `update`, `update_column`, `increment!`, console edit, or bulk import can drive `quantity` negative. This diff is itself the proof — the second caller that ever existed already skipped the guard.

Require enforcement at the authoritative boundaries:
- Database: `add_check_constraint :inventories, "quantity >= 0", name: "inventory_quantity_non_negative"` (Rails 7 supports this natively). This is the only enforcement point that survives every write path and concurrent writers.
- Model: `validates :quantity, numericality: { greater_than_or_equal_to: 0 }` so `update!` raises `RecordInvalid` with a readable error before hitting the DB.

The `with_lock` + explicit `value < 0` check in application code is still fine to keep for a clean error message, but it should be defense-in-depth, not the sole guard.

### 3. `inventory.rb` — duplicated adjustment logic with no ownership (flag)
Two top-level functions each implement "lock, compute, write" independently. Whoever next changes the rule (e.g., adds a max cap, audit log, or reservation semantics) has to remember both. Require one method (on the model or a service) that owns the transition; `normal_update`/`admin_update` should differ only in authorization/audit, not in how the invariant is checked.

## What's fine
- Both paths run under `with_lock`, which reloads the row after acquiring the lock, so the read-modify-write is not racy against concurrent adjusters.
- Raising inside the `with_lock` block rolls back the transaction correctly.
- Deltas are pre-parsed integers, so no type-coercion concerns here.
