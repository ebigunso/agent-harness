**Findings**

1. **charge.js, line 5 — fresh `Idempotency-Key` on every retry.** `randomUUID()` is evaluated inside the loop, so each retry sends a new key. The notes state a timeout can follow a committed charge; with a new key the server treats the retry as a distinct request and charges again. This is the defect the idempotency header exists to prevent, and the retry-on-timeout policy makes double (or N-fold) charging the expected outcome, not an edge case. Require: generate the key once before the loop and reuse it for every attempt of the same logical charge.

2. **charge.js, line 3 — `for (;;)` with no attempt cap or backoff.** If the payment host is slow (each attempt times out at 1 s), this loop retries forever with zero delay, sending a continuous stream of POSTs to a degraded dependency and never returning to the caller. That is both an unbounded wait for the caller and a load amplifier against the downstream. Require: a bounded attempt count (e.g., 3–5), backoff between attempts, and after exhaustion surface a distinct error (e.g., `ChargeTimeoutError` carrying the idempotency key) so the caller can reconcile the possibly-committed charge rather than assume failure.

3. **charge.js, line 8 — retry decision keyed on `error.name === "TimeoutError"` only, and it discards that the charge may have committed.** Minor relative to 1 and 2, but: once the loop is bounded, the final error must not be a bare timeout — the caller needs to know the charge is in an unknown state. Also, `AbortSignal.timeout` covers the request but the `response.text()` read on line 7 is outside the retried operation's success/failure semantics: a timeout there means the server did respond (charge committed) and the retry (with the same key, per finding 1) is safe and will return the stored result — acceptable, but only once finding 1 is fixed.

Not blocking on its own, but worth noting: with a fixed 1 s timeout and no jitter, the caller has no way to distinguish "payment service down" from "one slow request"; a cap plus a surfaced terminal error is sufficient to make degradation intentional here.

**Verdict:** Not acceptable as-is. Finding 1 is a correctness/financial defect (duplicate charges by design); finding 2 is an unbounded retry against an external dependency. Both must be fixed before merge.
