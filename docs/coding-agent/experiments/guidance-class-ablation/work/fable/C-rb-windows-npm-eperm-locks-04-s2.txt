**Cause**

`npm ci` wipes `node_modules` before reinstalling. The unlink of `node_modules\@parcel\watcher\build\Release\watcher.node` fails with `EPERM` (errno -4048) because a running process has that native addon mapped, and Windows won't let a loaded DLL/`.node` be deleted. This is not a permissions, lockfile, registry, or cache problem — the probe file beside the module writes and deletes fine, ACLs are clean, and the lockfile is in sync.

`tasklist /m watcher.node` identifies exactly one holder: `node.exe` PID 4104, which is this repo's own watch task (`scripts/watch.js`), left running detached from its original shell. So this is a workspace problem: a stale repo dev process is holding the file.

**Smallest safe remediation**

1. Stop the holder. Since it's detached from its shell there's no Ctrl+C to send, so ask it to close first, then force only if needed (the PID is confirmed as repo-owned, so the last-resort step is safe here):
   ```powershell
   taskkill /PID 4104          # graceful; console node processes usually refuse this
   taskkill /PID 4104 /F       # only if the line above reports it must be terminated forcefully
   ```
   Don't kill any other `node.exe` — only 4104 was shown holding the module.
2. Re-run the original command unchanged:
   ```powershell
   npm ci
   ```
3. Restart the watcher afterwards if it's still wanted (`node scripts/watch.js`), so it picks up the freshly installed binary rather than a stale mapping.

No changes to `package.json`, `package-lock.json`, npm config, or `node_modules` by hand are needed.

**Confirmation**

- Before the retry: `tasklist /m watcher.node` should print `INFO: No tasks are running which match the specified criteria.` If a holder still appears, the kill didn't take (or another process loaded it) — re-inspect before retrying.
- `npm ci` exits 0 with no `EPERM`/`unlink` lines, and `node_modules\@parcel\watcher\build\Release\watcher.node` exists after the run.
- Optional sanity check that the rebuilt addon loads: `node -e "require('@parcel/watcher')"` exits 0.
- If the retry still fails on the same path, run `tasklist | findstr node` and `tasklist /m watcher.node` again — the module is a source build, so also check that the rebuild in the retry didn't spawn/leave a new holder.
