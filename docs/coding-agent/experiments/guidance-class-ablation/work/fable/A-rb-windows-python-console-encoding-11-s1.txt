## Cause

This is a code defect in `export_report.py`, not a workspace/environment fault (the environment merely exposes it).

Line 25 opens the output file with no `encoding=` argument:

```python
open('report.txt','w').write(text)
```

On this machine the locale default is cp932 and UTF-8 mode is off (`utf8_mode = 0`), so the file handle is cp932. The report text contains U+2014 (EM DASH), which Python's cp932 codec cannot encode (cp932 maps 0x815C to U+2015, not U+2014), so the write raises `UnicodeEncodeError`.

Two things to note:

- **stdout is not involved.** `sys.stdout.encoding = cp932` is a red herring here; the failing handle is the file. `PYTHONIOENCODING` would not fix this.
- **Data loss already happened.** `'w'` truncates on open, before the write fails, which is why `report.txt` is now 0 bytes. The previous valid report is gone, but the inputs are intact so it can be regenerated.

## Smallest safe remediation

Make the output encoding explicit at line 25:

```python
with open('report.txt', 'w', encoding='utf-8') as f:
    f.write(text)
```

That is the whole fix: one argument, plus a context manager so the handle is closed/flushed deterministically. It is portable (works identically on non-Japanese locales and CI) and does not depend on process-wide switches.

I would **not** reach for `PYTHONUTF8=1` or `-X utf8` as the fix: it works, but it changes the default encoding for every open()/stdin/stdout in the process, and it has to be remembered on every machine and scheduler that runs the script. Explicit `encoding=` is smaller in blast radius and self-documenting.

Optional hardening (separate change, worth doing given the file was just wiped): write to a temp file in the same directory and `os.replace()` it over `report.txt` on success, so a future encode/IO error cannot leave a truncated report behind.

## Confirmation

1. Rerun `python export_report.py` in the same piped, cp932 environment → exit code 0, no traceback.
2. `report.txt` is non-zero size and round-trips: `python -c "print(open('report.txt', encoding='utf-8').read().count('\u2014'))"` returns ≥ 1 and does not raise.
3. Sanity-check that the content matches expectations against the (unchanged) input data — this regenerates the report that was truncated.
4. Verify downstream consumers of `report.txt` read it as UTF-8 (if something else was opening it with the locale default, it would now hit the mirror problem on the decode side, and needs the same `encoding='utf-8'` treatment).
