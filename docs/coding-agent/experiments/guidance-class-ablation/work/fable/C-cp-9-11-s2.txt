**Verdict: block.** The change replaces a fast, visible failure with an infinite busy-loop that wedges the exact thread the task says must not be wedged.

## Findings

### 1. `src/service.cpp`, `Service::process` — unbounded retry on a non-transient failure

**What's wrong:** `for (;;) { try … catch (bad_alloc) { continue; } }` retries the identical call forever. Per the notes, validated input can legitimately require more memory than the fixed worker limit, and identical retries cannot reduce the allocation. For such inputs the loop never exits.

**Why it matters:** This is a single-dispatch-thread service. An input that exceeds the limit now spins that thread at 100% CPU indefinitely, blocking all subsequent requests. That is precisely the "wedged service worker" outcome the task was meant to prevent — the patch makes the failure mode strictly worse (before: one request fails; after: the whole service hangs). It is also trivially triggerable by any caller who can submit a large input.

**Require:** No unbounded loop. Since retrying the same allocation cannot succeed for oversized inputs, either don't retry at all, or retry a small fixed number of times (with backoff) only if there is evidence of transient pressure — and then fail. Any loop must have a hard bound.

### 2. Same location — failure is swallowed with no context and no signal

**What's wrong:** The `catch` discards the exception, logs nothing, and returns nothing to the caller. There is no record that an allocation failed, how many times, or for which input.

**Why it matters:** Operators see a hung worker with no log line explaining why; callers see a request that never completes. The failure is hidden rather than handled. This violates the boundary-error guidance loaded for this review (handle with context; never hide or blur failures).

**Require:** Catch `std::bad_alloc` at this boundary and convert it into an explicit error `Result` carrying context (e.g. input identifier/size, the worker limit, retry count if any), and emit a log at error level. The caller must be able to distinguish "allocation failed" from a normal result.

### 3. Same location — busy-spin with no backoff

**What's wrong:** Even in the (hypothetical) transient case, `continue` with no sleep/backoff re-enters `allocate_and_run` immediately.

**Why it matters:** Hot-spins the only dispatch thread and starves anything else on the core; even a bounded version of this loop would be harmful without a delay.

**Require:** If any retry is kept, add a bounded backoff between attempts. Given the notes, the simpler and more correct fix is to drop retry entirely (see #1).

### 4. Commit message — misleading

**What's wrong:** "retry allocation until successful" asserts a success path that does not exist for inputs over the limit.

**Require:** Message should describe the actual behavior of the corrected change, e.g. "return error on allocation failure instead of propagating bad_alloc".

## What I'd accept instead (sketch)

```cpp
Result Service::process(const Input& input) {
    try {
        return engine_.allocate_and_run(input);
    } catch (const std::bad_alloc&) {
        LOG_ERROR("allocation failed processing input {} (size={}, worker_limit={})",
                  input.id(), input.size(), kWorkerMemoryLimit);
        return Result::error(ErrorCode::OutOfMemory,
                             "input exceeds worker memory limit");
    }
}
```

Optionally add a pre-flight size check against the known limit so oversized inputs are rejected before the allocation is attempted. If a bounded retry is genuinely justified by observed transient pressure, cap it (e.g. 2–3 attempts with backoff) and include the attempt count in the error/log — but the notes give no basis for that here.

Things that are fine and not findings: `<new>` is already included; `allocate_and_run` releases partial resources and has no pre-success side effects, so re-invoking it is safe in principle — the problem is solely that the retry is unbounded and silent.
