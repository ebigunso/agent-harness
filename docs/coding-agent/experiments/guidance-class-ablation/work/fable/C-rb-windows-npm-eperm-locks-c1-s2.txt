**Cause**

This is not a workspace/environment problem and not a file-lock problem. `npm ci` exited with `EUSAGE` because `package.json` (now `is-number@7.0.0`) and `package-lock.json` (still `is-number@6.0.0`) are out of sync. `npm ci` refuses by design to reconcile that; it only installs from a lockfile that already matches. The developer's intentional edit to `package.json` is the direct trigger.

The loaded reference about EPERM/EBUSY on `.node` files does not apply: the error code is `EUSAGE`, not `EPERM`/`EBUSY`, no native addon unlink occurred, paths are writable, the registry is reachable, and `tasklist /m better_sqlite3.node` shows no holders. There is nothing to stop or kill; a `taskkill` here would be both unnecessary and unsafe.

**Smallest safe remediation**

Regenerate the lockfile to match `package.json`, without touching `node_modules`:

```powershell
cd C:/work/npm-lock
npm install --package-lock-only
```

(If you'd rather also update `node_modules` in one step, plain `npm install` works too, but `--package-lock-only` is the minimal change.)

Then review the diff — it should show `is-number` moving from 6.0.0 to 7.0.0 in `package-lock.json` and little else — and commit it alongside the `package.json` change so CI and other developers stay in sync:

```powershell
git diff package-lock.json
git add package.json package-lock.json
git commit -m "Bump is-number to 7.0.0 and update lockfile"
```

**Confirmation**

Re-run the original command:

```powershell
npm ci
```

It should exit 0 with no `EUSAGE` message. Then verify the resolved version:

```powershell

```

Expected output includes `is-number@7.0.0`. Optionally run the project's test suite to confirm the major-version bump (6 → 7) didn't break callers.
