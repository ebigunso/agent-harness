**Verdict:** Not a workspace/code defect. The failure is a local Docker-Desktop-on-Windows networking asymmetry: `localhost` resolves to `::1` first, and the published-port proxy on `[::1]:50051` accepts the TCP connect but never completes the HTTP/2 (h2c) exchange, so the channel sits there until the 2s deadline fires.

**Cause (from the evidence)**

- Failed call: `--target localhost:50051` → channel used `[::1]:50051`, TCP connect succeeded, no HTTP/2 response headers before deadline → exit 2, `DEADLINE_EXCEEDED: deadline expired after 2s`. No entry in the service interceptor log, so the RPC never reached the server.
- Same host path over HTTP/1.1 (`http://localhost:50080/health`) returned 200 in 0.012s — so it is not a general "container unreachable" problem; the stall is specific to h2c through the `::1` proxy.
- Address-only comparison: `--target 127.0.0.1:50051` → exit 0, stdout `pong`, empty stderr, service log `invoked=true completed=true`. Same server, container, method, payload, deadline; only the address changed.

That isolates the cause to the IPv6 loopback path of Docker Desktop's published-port proxy, not the probe, the build, the service, the port mappings, or the deadline value.

**Smallest safe remediation**

Change the local target from `localhost:50051` to `127.0.0.1:50051` in the local probe/client config (or the invoking command). Nothing else: no server change, no Docker/WSL settings change, no system-wide IPv6 disable, no `-Djava.net.preferIPv4Stack=true` (broader than needed), no retry logic or longer deadline (a longer deadline would just hang longer). The health check on 50080 can stay on `localhost` — it works.

**Confirmation**

1. Rerun the exact failed command with only the target substituted:
   `java -jar probes/grpc-probe.jar --target 127.0.0.1:50051 --timeout 2`
   Expect: exit 0, stdout `pong`, stderr empty.
2. Check the service interceptor log for the new line: `probe method="unary Echo" transport=h2c invoked=true completed=true`.
3. (Optional, to document the asymmetry rather than a transient) rerun with `localhost:50051` once and confirm it still exits 2 with `DEADLINE_EXCEEDED`.

**Record for the incident note:** targets `localhost:50051` (→ `[::1]:50051`, fail) vs `127.0.0.1:50051` (pass), deadline 2s, deadline output `DEADLINE_EXCEEDED: deadline expired after 2s` / exit 2, REST `http_code=200 total_seconds=0.012000`, IPv4 retry exit 0 / `pong` with server-side `invoked=true completed=true`.

The fallback branch from the reference ("if both fail, inspect service, published ports, container health") does not apply here: the IPv4 retry succeeded and the mappings `50051->50051`, `50080->50080` are confirmed.
