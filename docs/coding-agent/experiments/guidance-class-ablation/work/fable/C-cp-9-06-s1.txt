**Verdict: block.** The fallback as written can grant access that the service would have denied, which is the one thing a fallback for authorization must never do.

**1. `Authorization.cs`, `catch (PolicyUnavailable)` — fallback can return `true` from stale cache**

- What's wrong: `cache.Get(user, resource)?.Allowed` is returned as the access decision. Per the notes, cache entries never expire, and a stale `Allowed = true` from last week persists after revocation. During an outage this method will answer "yes" for a user whose access has been revoked.
- Why it matters: the access contract says revocations take effect immediately and offline grants are not authorized. This change violates both. It converts a service outage into a privilege-escalation window, and does so silently from the caller's point of view (they just see `true`). Even bounding by `FetchedAt` with a TTL would not satisfy "immediately" — any cached grant is an offline grant.
- Required instead: fail closed. On `PolicyUnavailable`, never return `true`. Either return `false` outright, or (better, see #2) surface the outage explicitly. If a cache is to be consulted at all, it may only be used to *deny* faster, never to allow. Drop the "use cached access policy during outages" framing from the commit message; it describes behavior the contract forbids.

**2. `Authorization.cs`, `catch` block — outage is collapsed into an ordinary denial**

- What's wrong: on a miss the method returns `false`, and after fixing #1 it will always return `false` during an outage. Callers cannot distinguish "policy says no" from "policy service is down," and the only trace is a `Warning` log without user/resource identifiers.
- Why it matters: this hides a boundary failure behind a normal-looking result. Callers that want to show a retry/maintenance response, or ops looking at denial rates, will see a spike in denials with no signal that authorization itself is degraded. Warning level understates a security-relevant dependency failure.
- Required instead: propagate a distinct, bounded failure — e.g. rethrow as `AuthorizationUnavailableException` (wrapping `error`, carrying user/resource ids) or return a tri-state result — so callers deny *and* know why. Log at Error with the identifiers, and emit a metric/alert for the unavailable path. Keep the catch scoped to `PolicyUnavailable` as it is now; don't widen it.

No other issues: catching only `PolicyUnavailable` is appropriately narrow, and the `?? false` on cache miss is the correct direction.
