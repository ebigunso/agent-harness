## Verdict

This is a workspace problem, not an npm/registry/permissions problem: two repository-owned test workers still have the native addon mapped, and Windows refuses to unlink a mapped image.

## Cause

`npm ci` must remove the existing `node_modules` tree before reinstalling. On Windows, a `.node` addon is a DLL; once a process has loaded it, the file cannot be deleted until every process that mapped it exits. The evidence lines up exactly:

- Error is `EBUSY` on `syscall unlink` for `better_sqlite3.node` — not `EACCES`/`EPERM`, and the probe file beside it can be created/removed, so ACLs and disk writability are ruled out.
- Lockfile/manifest are in sync and the registry works, so this isn't a dependency-resolution failure.
- `tasklist /m better_sqlite3.node` shows PIDs 4111 and 4112 (`node.exe`), both launched from `C:/work/npm-lock/workers/test-worker.js`, both with that absolute addon path loaded and neither finished.

So the lock holders are this repo's own test workers, which is the expected case in the reference runbook.

## Smallest safe remediation

1. **Stop the workers gracefully first.** Whatever spawned `workers/test-worker.js` (a watch-mode test runner, a leftover terminal, an editor test integration) should be stopped from its own side — Ctrl+C the runner / stop the watcher. That lets the workers close their SQLite handles cleanly.
2. **Re-check for holders:**
   ```
   "C:\Program Files\PowerShell\7\pwsh.exe" -Command "tasklist /m better_sqlite3.node"
   ```
3. **Only if 4111/4112 are still listed**, kill them directly (they are confirmed repo-owned, so this is safe; do not blanket-kill all `node.exe`):
   ```
   taskkill /PID 4111 /F
   taskkill /PID 4112 /F
   ```
4. Re-run `npm ci`.

What *not* to do: don't delete `node_modules` by hand (it fails on the same file), don't use `--force`/`--no-bin-links` tricks (they don't address a mapped DLL), and a reboot is unnecessary overkill.

## Confirmation

- `tasklist /m better_sqlite3.node` returns `INFO: No tasks are running which match the specified criteria.`
- `tasklist | findstr node` shows no stray node processes for this repo (optional belt-and-braces).
- `npm ci` exits 0 with no `EBUSY`/`EPERM` in stderr.
- `C:\work\npm-lock\node_modules\better-sqlite3\build\Release\better_sqlite3.node` exists with a fresh timestamp, and `node -e "require('better-sqlite3')"` loads without an ABI error (Node 20.18.0 / better-sqlite3 9.6.0 is a supported pairing, so a prebuilt binary should be fetched rather than compiled).
- Restart the test runner afterward and confirm it works against the reinstalled module.
