## Findings

**1. `approval.rb:4-5` — two separate `update!` calls commit an invalid intermediate state (blocking).**
Without a caller transaction, each `update!` is its own transaction. After line 4 commits, the row is `status = "approved", approver_id = <nil or previous value>` and visible to any observer — exactly the state the invariant ("approved requires non-null approver") forbids. If the process dies or line 5 raises, the record stays there permanently. Require a single write: `update!(status: "approved", approver_id: approver)` — one `UPDATE`, one commit, no intermediate state. (Wrapping the two calls in `transaction` would also work but is strictly worse: it's still two statements and two validation passes for no benefit.)

**2. `approval.rb:4` — ordering makes the method fail or lie, given the existing validation (blocking).**
The notes say approver ID is already validated. Trace both possibilities:
- If it's `presence: true, if: approved?` (the correct form of this invariant), line 4 raises `RecordInvalid` on every call, because it tries to persist `approved` with no approver. The method never succeeds.
- If it's unconditional `presence: true`, line 4 only passes when `approver_id` is already set, i.e. the record was already attributed — so line 5 then overwrites a prior approver's identity.
Either way the two-step ordering is wrong. The single-update fix in (1) resolves this. Also add the DB-level guard so the invariant isn't enforced by model validation alone: `CHECK (status <> 'approved' OR approver_id IS NOT NULL)`.

**3. `approval.rb:3` — no transition guard; repeated/concurrent calls silently rewrite attribution (blocking).**
`approve!` accepts any current state. Calling it on an already-approved record (retry, double-click, two approvers racing) replaces `approver_id` with the last caller and leaves no trace. For an audit field this is data loss. Require an authoritative transition: only `pending → approved`, enforced at the row rather than in a read-then-write:
```ruby
def approve!(approver_id)
  rows = self.class.where(id: id, status: "pending")
             .update_all(status: "approved", approver_id: approver_id, updated_at: Time.current)
  raise InvalidTransition, "not pending" unless rows == 1
  reload
end
```
or equivalently `with_lock` + explicit state check + single `update!`. A model-level `if` check without locking is an optional guard and doesn't survive concurrency; a CHECK/optimistic-lock (`lock_version`) or conditional `UPDATE` does.

**4. `approval.rb:3,5` — parameter is named `approver` but assigned to `approver_id` (flag).**
Callers will reasonably pass a `User`; ActiveRecord will cast it to an integer via `to_i`/`nil`, producing a wrong or null id without error (and with the `if: approved?` validation, a confusing failure). Name it `approver_id`, or accept the record and write `approver_id: approver.id` / `approver: approver` via a `belongs_to`.

## Verdict
Not acceptable as-is. Minimum to merge: collapse to a single atomic write, guard the `pending → approved` transition at the row level, fix the parameter contract, and back the invariant with a DB CHECK constraint.
