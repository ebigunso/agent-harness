**Verdict: block.** The change does not fix the reported failure; it adds a compensating lock that cannot cover the actual race.

**Findings**

1. **`invoices/allocate.go` — `httpMu` is a process-local mutex, but the collision is cross-process.**
   Reviewer notes state the HTTP service and batch workers are *separate OS processes* sharing one SQLite file. A `sync.Mutex` only serializes goroutines inside one process; the batch process never sees it. The HTTP↔batch race the task describes is untouched. Even inside the HTTP process, `BatchCreate` is left unlocked, so any in-process batch caller still races `HTTPCreate`. The commit message ("serialize HTTP invoice creation") is honest about the narrower scope, but that scope doesn't satisfy the task.

2. **`invoices/allocate.go:allocate` — the defect's origin is the non-atomic read-then-write (`SELECT MAX(id)+1` → separate `INSERT`), and it is still there.**
   Two callers can both read the same `MAX(id)`, then both attempt the same primary key; the second fails. This is a classic TOCTOU on the database, and no application-side lock can make it correct across processes. Note also that `db.QueryRow` and `db.Exec` on a `*sql.DB` may run on different pooled connections, so even wrapping in a transaction would need care (`BEGIN IMMEDIATE` in SQLite).

   **Required instead:** let the database allocate the ID, which the notes say it already supports authoritatively. Replace the two statements with a single insert that omits `id` (e.g. `INSERT INTO invoices DEFAULT VALUES` against an `INTEGER PRIMARY KEY` / `AUTOINCREMENT` column) and return `res.LastInsertId()`. This is atomic under SQLite's own locking, works across processes, and eliminates the `SELECT` entirely. Once that's done, both `HTTPCreate` and `BatchCreate` are correct with no lock at all.

3. **`invoices/allocate.go` — the mutex is duplicated/compensating serialization and should be removed, not extended.**
   The DB already provides the invariant (unique, monotonically allocated IDs); the mutex re-implements a weaker version of it in one process. Beyond being incomplete, it serializes every HTTP invoice creation behind a round-trip to disk for no benefit once the insert is atomic. If someone later "fixes" the gap by adding a second mutex to `BatchCreate` or a file lock, that's more compensating machinery on top of a query that shouldn't exist. Do not ship the lock; fix the query.

4. **Minor — `import ("database/sql"; "sync")` is not gofmt-formatted.** Would be moot after the fix above since `sync` won't be needed, but if any import block remains, run gofmt.

**Summary of what I'd accept:** a diff that changes `allocate` to a single auto-ID insert returning `LastInsertId()`, removes the `MAX(id)+1` select, and adds no mutex. Both entry points can then remain as thin wrappers. Optionally add a test that spawns concurrent inserts (ideally across two `sql.Open` handles to mimic two processes) and asserts no unique-constraint errors.
