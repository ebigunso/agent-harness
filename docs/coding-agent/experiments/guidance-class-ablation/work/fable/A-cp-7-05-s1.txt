**Findings**

1. **`fee.py`, `test_average` — does not provide the required deterministic validation of the formula or threshold.**
   The only assertion is that the mean of `fee(100)` over 1000 draws lands in (13, 17). That check would pass for many wrong implementations: a function that always returns 15; one that returns 12/18 instead of 10/20; one whose threshold is `>= 99` or `>= 50` (the test never probes below 100); one that applies the discount at `cents < 100` and skips it above. It also never checks the two concrete outcomes (10 and 20) or the no-discount branch at all. The reviewer notes explicitly call for the exact formula and threshold to be validated deterministically; this test does neither.
   *Required:* deterministic tests asserting `fee(100) == 10` when selected, `fee(100) == 20` when not selected, `fee(99) == 20` regardless of selection, and `fee(0) == 20` (boundary + nonnegative floor). Keep the statistical test only as a supplementary check that selection actually occurs in production, if at all.

2. **`fee.py`, `fee()` — randomness is hard-wired to the global `random` module, which is what makes (1) impossible without monkeypatching.**
   `random.choice` is called on module-global state inside the function, so callers/tests cannot control selection. This also means `test_average` depends on global RNG state that any other test (e.g. one calling `random.seed`) can perturb.
   *Required:* make the selection injectable — either accept an `rng: random.Random` parameter (defaulting to a module-level instance) or split the pure computation out (`fee(cents, selected: bool)`) with a thin wrapper that draws `selected`. Test the pure part exhaustively; test the wrapper for "both outcomes occur" if desired.

3. **`fee.py` — test code is co-located in the production module and imports nothing from a test framework, so it is unclear it will be collected.**
   `test_average` is defined in `fee.py` rather than a `test_fee.py`; whether pytest picks it up depends on collection config. Minor, but it should live in a test module so it is actually run and so `random`-driven test helpers don't ship in production code.

Not raising: input validation for negative/non-integer cents (notes state inputs are nonnegative ints), and flakiness of the (13, 17) window — with σ≈0.16 on the mean it is not realistically flaky; the problem is that it is insufficient, not unstable.
