**Verdict: this is not a workspace or Docker address problem.** The playbook's IPv4-vs-`localhost` hypothesis is already ruled out by the evidence.

**Cause**

The `Echo` RPC reaches the server on both `127.0.0.1:50051` and `localhost:50051` (`invoked=true` in the interceptor for each). The handler then blocks in `phase=db-query` waiting on database lock `lock-42`, which is held by a stalled migration transaction. The probe's 2 s deadline expires while the handler is parked on that lock, so the probe reports `DEADLINE_EXCEEDED` and exits 2 as its contract specifies. The REST health endpoint on 50080 is fast because it doesn't touch the locked resource.

Why the reference playbook doesn't apply:
- The first command was *already* the IPv4 retry (`127.0.0.1:50051`) and it failed identically to `localhost:50051` — no asymmetry.
- The playbook's "if both fail, inspect service/ports/health" branch leads to the service evidence, which shows the connection and HTTP/2 path are fine; the stall is behind the handler, in the database.
- Port mapping is confirmed correct; no TLS/name-check is involved.

Nothing in `C:/work/grpc-local` (probe, config, dependencies, Docker publish config) is at fault.

**Smallest safe remediation**

Clear the stalled migration transaction holding `lock-42` on the database side — either let the migration finish if it is genuinely progressing, or roll back / terminate that specific transaction (e.g. `pg_terminate_backend(<pid>)` / `KILL <id>` for the identified session) after confirming it is the migration and is not making progress. Do not change the probe, the target address, the timeout, or the Docker port config; raising `--timeout` would only mask the lock.

If the migration must remain running, the alternative is to point the local probe at a database/service instance not undergoing migration — but that's a larger change than releasing one stuck transaction.
