**Cause**

Not a project/code defect and not a slow server. On this host, `localhost` resolves to `::1` before `127.0.0.1`, so the .NET channel dialed `[::1]:50051`. Docker Desktop's published-port proxy on the IPv6 loopback accepts the TCP connection but never completes the HTTP/2 (h2c) exchange — no response headers arrive, the 2 s deadline fires, and the probe reports `DEADLINE_EXCEEDED` (exit 2). The request never reached the service: the interceptor log has no entry for the failed call.

Supporting evidence:
- REST on 50080 via `localhost` is fine (`200`, 12 ms) — HTTP/1.1 through the same proxy path works, so the container, network, and port mappings are healthy.
- The identical RPC (same method, payload, deadline, container, config) to `127.0.0.1:50051` succeeded in-deadline (`pong`, exit 0), and the service log shows `invoked=true completed=true`.

So the only variable is the loopback address family: the IPv6 published-port path stalls HTTP/2. This is a host-environment (Docker Desktop on Windows) quirk, not a workspace problem.

**Smallest safe remediation**

Point the probe's local target at IPv4 explicitly: use `127.0.0.1:50051` instead of `localhost:50051` in the local config / launch args for this environment (e.g. the dev appsettings or the probe's default `--target`). Do not change the server, the deadline, the container, or the machine's hosts/IPv6 settings — those are broader than needed.

**Confirmation**

1. Run `dotnet run --project probes/GrpcProbe -- --target 127.0.0.1:50051 --timeout 2` → expect exit 0, stdout `pong`, empty stderr, well inside the 2 s deadline.
2. Check the service interceptor log shows a new `probe method="unary Echo" transport=h2c invoked=true completed=true` line for that call.
3. Optionally re-run with `--target localhost:50051` once more to confirm it still fails — proving the fix is address-specific, not timing luck.

Record for the ticket: targets (`localhost:50051` → `[::1]:50051` vs `127.0.0.1:50051`), the deadline output (exit 2, `DEADLINE_EXCEEDED: deadline expired after 2s`), the REST timing (`200`, 0.012 s), and the IPv4 retry result (exit 0, `pong`, server-side `invoked=true completed=true`).
