**Verdict: block.** The change introduces a second write path for `total` that contradicts the model's own invariant, and the task ("admin adjustments") is not actually represented in the data model.

## Findings

### 1. `order.php` — `adminTotal()` breaks the `total == sum(lines)` invariant with no ownership of the field
- **What's wrong:** `total` is defined as a derived value (`array_sum($lines)`), but `adminTotal` writes it directly while leaving `lines` untouched. After the call, `total` and `lines` disagree and nothing records why.
- **Why it matters:** Two writers with no ownership → order-dependent results, even serially:
  - `adminTotal(...)` then `setLines(...)`: the adjustment is silently discarded (recompute overwrites it).
  - `setLines(...)` then `adminTotal(...)`: order is now internally inconsistent; any consumer that recomputes from `lines` (refunds, tax, reporting, exports) produces a different number than the stored `total`.
  Neither outcome is detectable after the fact — the order looks well-formed.
- **Require:** Represent the adjustment *inside* the authoritative model rather than overriding the derived field. E.g. add an `adjustments` array of signed integer cents (with actor/reason), and make one function the sole owner of `total`:
  ```php
  function recomputeTotal(array &$order): void {
      $order["total"] = array_sum($order["lines"]) + array_sum($order["adjustments"] ?? []);
  }
  ```
  `setLines` and `addAdminAdjustment` both mutate their own field and call `recomputeTotal`. Remove `adminTotal` entirely — a free-form total setter should not exist.

### 2. `order.php` — no truth table / attribution for what an "adjustment" is
- **What's wrong:** The feature is a classification/attribution change (this total was adjusted, by whom, by how much, why), but the diff models it as an opaque overwrite. There is no way to answer "what was the original amount?", "how much was adjusted?", or "was this adjusted at all?".
- **Why it matters:** Refund limits, revenue reporting, and dispute handling all need the decomposition, and it's unrecoverable once overwritten. Gate 5 explicitly asks for the truth table before picking the data model; the states here are at least {unadjusted, adjusted up, adjusted down, adjusted after line change}, and the current model collapses them all into one integer.
- **Require:** Store adjustments as first-class entries (amount, actor, reason, timestamp). Derive, don't store, anything that can be computed from them.

### 3. `order.php` — no validation at the enforcement point
- **What's wrong:** `setLines` accepts any array (`array_sum` on floats/strings/nested arrays yields floats or warnings, violating "integer cents"); `adminTotal` accepts any `int` including negative or arbitrarily large values. Nothing checks bounds.
- **Why it matters:** These are the only write paths, so this is the reliable place to enforce the integer-cents and bounded-sum invariants. Leaving it to callers is the "enforced only in optional caller paths" anti-pattern.
- **Require:** Validate `is_int` and range for every line/adjustment amount and the resulting total; throw on violation rather than storing a bad state.

### 4. `order.php` — "admin" is only a name
- **What's wrong:** Nothing distinguishes `adminTotal` from a general setter; authorization is entirely the caller's responsibility and not recorded.
- **Why it matters:** Any code path with the order array can rewrite the total. Combined with #1 this is an unaudited money-altering primitive.
- **Require:** At minimum, the adjustment entry must carry the acting principal (see #2); ideally the function takes an actor/authorization context rather than trusting the name.

### 5. No tests
- **What's wrong:** No coverage for the sequencing cases in #1 (adjust-then-setLines, setLines-then-adjust) or for invalid inputs.
- **Require:** Tests asserting `total` equals the derived value after every write sequence, and that adjustments survive a subsequent `setLines`.
