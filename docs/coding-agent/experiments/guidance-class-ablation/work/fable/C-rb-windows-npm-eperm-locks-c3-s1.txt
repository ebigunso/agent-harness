**Cause**

This is not the `.node` unlink / process-holder problem the reference material describes. There is no unlink, no native module, and no holder was found, so `tasklist`/`taskkill` do not apply and should not be used.

The failing syscall is `mkdir C:\locked-cache`. npm's cache directory is configured to `C:\locked-cache` (`npm config get cache`), and the effective ACL explicitly denies this user create/write there. `npm ci` must be able to create/write its cache (`_cacache`) before it can install, so it fails before touching the repo at all. The repository path itself is writable, and package.json/lockfile are in sync — the workspace is fine.

Whether it's a "workspace problem" depends on where that config value comes from, which the observations don't show. Check:

```powershell
npm config list -l | Select-String cache
npm config get cache --location=project
npm config get cache --location=user
$env:NPM_CONFIG_CACHE
```

- If a project `.npmrc` in `C:\work\npm-lock` sets `cache=C:\locked-cache`, it's a repo config problem.
- If it comes from the user `.npmrc`, a global/`prefix` npmrc, or `NPM_CONFIG_CACHE`, it's a machine/user environment problem, not the workspace.

**Smallest safe remediation**

Don't modify the ACL on `C:\locked-cache` — an explicit deny is likely deliberate (or admin-owned), and changing it is a larger, privileged change than needed. Just point npm's cache at a user-writable location.

For a single run (no persistent change):

```powershell
npm ci --cache "$env:LOCALAPPDATA\npm-cache"
```

If the bad value is persisted in a config file you own, fix it at that scope so future runs work too, e.g. for user scope:

```powershell
npm config set cache "$env:LOCALAPPDATA\npm-cache" --location=user
```

(If it's in the project `.npmrc`, remove/correct the `cache=` line there instead. If it's set by `NPM_CONFIG_CACHE`, unset or correct the env var.)

**Confirmation**

1. `npm config get cache` → prints the new writable path.
2. `npm ci` → exit code 0, no `EPERM`, `node_modules` populated and matches `package-lock.json` (`npm ls --depth=0` reports no missing/invalid).
3. `Test-Path "$env:LOCALAPPDATA\npm-cache\_cacache"` → `True`, showing npm actually wrote its cache there.

Record: original command and error (`EPERM mkdir C:\locked-cache`), the config source of the cache path, the change made (cache relocation, scope), and the successful retry. No PIDs were killed and none should be.
