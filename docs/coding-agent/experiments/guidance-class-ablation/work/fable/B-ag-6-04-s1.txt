**Verdict: Block.** The change implements "retry" as an unbounded hot loop with no error classification, which violates Gate 6 on every axis (bounded retries, deliberate error propagation, containment).

## Findings

### 1. `partner.py:3-5` — Unbounded retry loop with no attempt cap or overall time budget
**What's wrong:** `while True` retries every non-200 response forever. There is no max-attempt count and no wall-clock deadline. The per-attempt `timeout=1` only bounds a single call; the loop itself is unbounded.
**Why it matters:** A partner that is down, misconfigured, or returning a permanent non-200 turns `read()` into a call that never returns. Any caller thread, worker, or request handler is pinned indefinitely — this is exactly the "cascading failure path without isolation boundary" anti-pattern. It also means the function has no failure signal at all: it can only succeed or hang.
**Require:** A fixed max attempt count (e.g. 3–5) and/or an overall deadline; on exhaustion, raise a specific exception (e.g. `PartnerUnavailable`) carrying the last status/body so the caller can degrade or fail fast.

### 2. `partner.py:5` — Retries permanent (4xx) failures that can never succeed
**What's wrong:** The loop treats every non-200 identically. Per the reviewer notes the request bytes are immutable, so a `400` (or `401`, `403`, `404`, `422`) will return the same result on every attempt. The loop will spin on it indefinitely.
**Why it matters:** Retrying non-retryable errors wastes the retry budget, hides the real root cause (a bad request) behind an apparent "partner unavailable" symptom, and hammers the partner with guaranteed-to-fail traffic. This is error suppression that obscures root causes.
**Require:** Classify responses: retry only on transient signals (`5xx`, `429`, connection errors, timeouts); raise immediately on `4xx` with the status and body surfaced. Also treat other `2xx`/`3xx` explicitly rather than lumping them with failures.

### 3. `partner.py:3-4` — No delay or backoff between attempts
**What's wrong:** On a fast non-200 (e.g. an immediate `503` or `400`), the loop re-issues the request with zero sleep — a tight loop hitting the partner as fast as the network allows.
**Why it matters:** This amplifies load on a partner that is already struggling, turning one client's failure into a contribution to the partner's outage (retry storm). Combined with finding 1, a single degraded partner endpoint can saturate your outbound capacity and the partner's inbound capacity indefinitely.
**Require:** Exponential backoff with jitter between attempts, capped at a sensible maximum; honor `Retry-After` on `429`/`503` if present.

### 4. `partner.py:4` — Transport exceptions escape without retry, so the "retry" doesn't cover the most common transient failures
**What's wrong:** `requests.get` raises `requests.Timeout` / `requests.ConnectionError` on the failures that are actually most worth retrying (the 1s timeout firing, connection reset, DNS blip). These propagate out of the loop immediately on the first occurrence.
**Why it matters:** The behavior is inverted from what the task asked for: permanent HTTP errors are retried forever, while transient transport errors are not retried at all. Fallback behavior is not deliberate — it is an accident of which failure path fires.
**Require:** Catch `requests.RequestException` (or the specific transient subclasses) inside the attempt and count it toward the same bounded retry budget as retryable status codes; re-raise on exhaustion with the underlying cause chained.

### 5. `partner.py` — No documented failure modes or containment notes
**What's wrong:** The commit message and diff contain no statement of which failures are expected, which are retried, which are surfaced, or how callers should degrade. There is no docstring, no named exception type, and no test.
**Why it matters:** Gate 6 asks that the plan list likely failure modes and that risky operations include containment strategy notes. Without them, a reviewer cannot verify the behavior is intentional, and the next maintainer cannot tell whether the loop's semantics are a bug or a decision.
**Require:** A short docstring or module comment stating retry policy (what's retried, how many times, backoff, what's raised on exhaustion), a dedicated exception type, and at least one test each for: success after transient failure, immediate raise on 4xx, raise after exhausting retries on persistent 5xx/timeout.

### 6. `partner.py:1-5` (minor) — Style/hygiene
Missing blank line after import, missing spaces around `=`/`==`, compressed `if ...: return` on one line, no type hints. Not blocking on its own, but the file should pass the project's formatter/linter before merge.
