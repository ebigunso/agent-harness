**Verdict: block.** The fallback is not safe under the stated access contract.

**1. `Authorization.cs`, `catch (PolicyUnavailable)` block — fallback grants access from stale, never-expiring cache entries.**
- What's wrong: On outage, `cache.Get(user, resource)?.Allowed` is returned as the decision. Entries never expire and `FetchedAt` is never consulted, so an `Allowed = true` entry from last week is honored even if the grant was revoked since. Cache misses deny (correct direction), but cache hits are an unbounded stale-grant path.
- Why it matters: The contract says revocations take effect immediately and offline grants are not authorized. This change converts a service outage into a window where revoked users regain access, for as long as the outage lasts and as long as the entry sits in the cache. That is the failure mode the task was supposed to make safe; instead it makes it silent and open. A "fallback" that can return `true` without a live policy decision is not a fallback, it's an alternate authorization source that contradicts the source of truth.
- Required instead: Fail closed. The catch block should return `false` (and log/metric the outage), which already matches the miss behavior. If product genuinely needs degraded-mode access, that requires a contract change first; only then would a bounded fallback (check `FetchedAt` against a short TTL, deny anything older, and make revocation write-through/invalidate the cache) be acceptable. As written, the commit message ("use cached access policy during outages") describes exactly the behavior the contract forbids.

**2. `Authorization.cs`, same block — outage-path decisions are not distinguishable or bounded.**
- What's wrong: The log line records that the cache was consulted but not the outcome, the user/resource, or the entry's age. Callers receive a plain `bool` and cannot tell a policy denial from an outage denial (or, currently, a stale grant). There is no counter/metric for "decision made without live policy."
- Why it matters: During an incident you can't answer "who was allowed in via cache, and how old was their entry?" and you can't alert on the rate of degraded decisions. Fallbacks need to be observable so the outage is fixed rather than quietly absorbed.
- Required instead: Emit a metric (e.g. `authz.policy_unavailable` with outcome tag) and include user/resource identifiers in the log at a level that pages. If a bounded fallback is ever adopted, log the entry's `FetchedAt` on every degraded grant.

Finding 1 alone is blocking; finding 2 should be addressed in the same change since the fail-closed version still needs to be visible.
