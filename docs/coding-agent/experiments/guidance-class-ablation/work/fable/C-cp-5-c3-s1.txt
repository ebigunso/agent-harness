**Verdict:** Core normalization is correct (shape gate → `-00:00` rejection → `fromisoformat` → `astimezone(utc)`, with `OverflowError` covered for the min/max-year edge). I would not block on correctness, but I would require one change before merge.

**1. `time_input.py`, `except ... raise ValueError("timestamp: explicit known ISO offset required")` — one message for every failure mode, and it's wrong for most of them.**
The two inner reasons ("timestamp shape", "unknown offset") and `fromisoformat`'s own errors (bad month/day/hour, leap second, year 0) and the `OverflowError` from `astimezone` are all rewritten into a message claiming the offset is missing. For `"bad"`, `None`, `"2026-13-01T00:00:00Z"`, or `"9999-12-31T23:59:59-01:00"` the caller is told to add an offset that is either irrelevant or already present. The chained `__cause__` is not what surfaces in logs/API responses. This violates "fail actionably."
Require: keep the field prefix but preserve the reason — e.g. `timestamp: malformed (expected YYYY-MM-DDTHH:MM:SS[.ffffff](Z|±HH:MM))`, `timestamp: -00:00 (unknown offset) not allowed`, `timestamp: out of range: <inner message>`. Simplest is to raise the specific messages directly in the two guards and only wrap the `fromisoformat`/`astimezone` block.

**2. Regex uses `\d`, which in Python `re` matches any Unicode decimal digit (`٢٠٢٦-…`, fullwidth `２０２６-…`).**
The shape check therefore does not enforce the wire contract by itself; it happens to work only because `fromisoformat` (ASCII-only parser) rejects those strings afterward. That is an accidental second gate, and the resulting error (per finding 1) would say "offset required." Make the invariant explicit: compile with `re.ASCII` or use `[0-9]`.

**3. `check()` — ad hoc assert-based test, insufficient coverage.**
Runs nothing under `-O`, isn't discoverable by a test runner, and doesn't exercise fractional seconds (1 and 6 digits, 7 digits rejected), a well-formed but out-of-range value (`2026-02-30T…Z`), or the `OverflowError` path at year 0001/9999 with a non-zero offset. Those are exactly the paths the notes claim are handled. Move to a real test module and add those cases, asserting on the specific messages from finding 1.

Nits (would not block): no blank lines between defs / missing docstring stating the accepted shape; the `-00:00` check is fine but a comment citing RFC 3339 §4.3 would explain why `+00:00` is accepted and `-00:00` is not.
