**Verdict: block.** The change does exactly what the task says, but the task itself violates Gate 6 (failure containment), and the implementation adds no bounds or degradation path to compensate.

## Findings

### 1. `pool.go` — `Enrich` and `Payment` share one 4-slot pool (no isolation boundary)

**What's wrong:** Both callers draw from the same `chan struct{}` with capacity 4. Enrichment is optional; payments are correctness-critical. Nothing prevents enrichment from consuming all four slots.

**Why it matters:** Per the reviewer notes, callbacks are external work and may stall. Four stalled (or merely slow) enrichment jobs mean `Payment` blocks indefinitely at `p <- struct{}{}`. This is a textbook cascading failure: a non-essential dependency's outage takes down a critical path. Gate 6 explicitly calls out "cascading failure paths without isolation boundaries."

**Required instead:** Separate pools per workload class (bulkhead pattern), e.g. `NewEnrichPool()` / `NewPaymentPool()`, or a pool that reserves capacity for the priority class (e.g. enrichment may use at most N-of-4, payments can always take the remainder). If the sharing is a hard product requirement, that requirement should be pushed back on with this failure mode as the justification.

### 2. `pool.go` — `Run` blocks unboundedly on slot acquisition

**What's wrong:** `p <- struct{}{}` has no timeout, no context, and no cancellation. A caller with a stalled pool hangs forever.

**Why it matters:** Even with separate pools, a critical-path caller (payment handler) has no way to degrade, time out, or return an error. This is "blocking operations in critical paths" from the anti-pattern list, and it makes the finding above strictly worse — there's no recovery once saturation happens.

**Required instead:** `Run(ctx context.Context, job func()) error` that does

```go
select {
case p <- struct{}{}:
case <-ctx.Done():
    return ctx.Err()
}
```

so callers can bound acquisition and choose their fallback (enrichment: skip; payment: fail fast and surface the error).

### 3. `pool.go` — no bound on job execution time

**What's wrong:** `job()` runs with no deadline. A stalled external call holds its slot indefinitely.

**Why it matters:** Slot occupancy is the resource being protected; without a per-job bound, a single upstream outage permanently exhausts the pool (this is the mechanism behind finding 1). `Run` also can't release the slot on timeout since `job` is a bare `func()` with no way to be interrupted.

**Required instead:** Pass `ctx` through to the job (`job func(ctx context.Context)`) and have callers derive a deadline-bearing context. Note that Go can't forcibly kill a goroutine, so the slot will still be held until the job respects cancellation — that's an argument for making the deadline part of the contract, not for omitting it.

### 4. `pool.go` — panic in `job()` is not contained (minor, but worth fixing while here)

**What's wrong:** `defer func(){<-p}()` correctly releases the slot on panic, but the panic propagates to the caller's goroutine. For a shared pool with untrusted/external callbacks, one misbehaving enrichment callback can crash the process.

**Why it matters:** Failure scope should be the job, not the process. Low severity relative to 1–3, and there's a reasonable argument that swallowing panics is itself an anti-pattern (Gate 6 warns against "broad suppression that obscures root causes"), so I'd flag rather than block on this one.

**Required instead:** Either document that panics propagate (and callers must recover), or recover, log with stack, and return an error — do not silently swallow.

## Not flagged

- Fixed capacity of 4 with no configuration — acceptable for a first cut if a constant/constructor param is added later; not a Gate 6 issue on its own.
- Missing tests — I'd normally require a test demonstrating that a saturated enrichment pool does *not* block payments, but that test can only be written once finding 1 is addressed.
