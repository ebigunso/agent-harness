**Cause**

`npm ci` deletes `node_modules` before reinstalling. On Windows a loaded DLL/native addon cannot be unlinked, and `better_sqlite3.node` is currently mapped into `node.exe` PID 4101 — the repo's own Express/TypeScript dev server (`src/server.ts`), which loaded the addon on startup. So `unlink` fails with `EPERM` (errno -4048, a sharing violation, not an ACL denial). The diagnostics rule out the other candidates: lockfile is in sync, project/cache/registry are fine, a probe file beside the module can be created and removed, and no permission denial is observed. This is a workspace problem (a stale file handle held by a process the repo owns), not a corrupted install or a permissions issue.

**Smallest safe remediation**

Stop the dev server, then rerun the install. Prefer a graceful stop in its original terminal (`Ctrl+C`) since it's your own process; if that terminal isn't reachable:

```powershell
Stop-Process -Id 4101
npm ci
```

Don't delete `node_modules` by hand, run as admin, disable antivirus, or use `--force` — none of those address the open handle, and the last three are broader than necessary.

**Confirmation**

1. `tasklist /m better_sqlite3.node` returns no `node.exe` row (or "No tasks are running which match the specified criteria").
2. `npm ci` exits 0 and `node_modules\better-sqlite3\build\Release\better_sqlite3.node` is present again.
3. Restart the dev server and verify it starts and the sqlite-backed routes respond — this confirms the rebuilt/reinstalled addon still loads against Node 20.18.0.

Going forward, stop the dev server before `npm ci` (or run installs from a script that does so) to avoid repeating this.
