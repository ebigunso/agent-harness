**Cause**

`npm ci` must delete `node_modules` before reinstalling, and the unlink of `@swc\core-win32-x64-msvc\swc.win32-x64-msvc.node` fails with EPERM (errno -4048). This is a file lock, not a permissions or workspace-config problem: the lockfile is in sync, the registry is reachable, and npm can create/remove a probe file in the same directory with no ACL denial. `tasklist /m swc.win32-x64-msvc.node` shows the binary is mapped into `node.exe` PID 4103, which is the Next dev server (`next dev`) launched from this repository. Windows will not let a loaded native module be unlinked while a process has it mapped, so the dev server is the blocker.

**Smallest safe remediation**

Stop the dev server rather than force-killing it, since it is a known, repo-owned process:

1. In the terminal (or editor task) running `next dev` for `C:\work\npm-lock`, press Ctrl+C.
2. Verify the lock is gone: `tasklist /m swc.win32-x64-msvc.node` should report no processes.
3. Re-run `npm ci`.

Only if step 1 isn't possible (orphaned terminal, unresponsive process) and the PID is confirmed to be 4103 for this repo: `taskkill /PID 4103 /F`, then repeat steps 2–3.

Do not delete `node_modules` by hand, run as Administrator, or disable antivirus — none of those address a mapped-module lock and they add risk.

**Confirmation**

- `tasklist /m swc.win32-x64-msvc.node` returns "INFO: No tasks are running which match the specified criteria."
- `tasklist | findstr node` shows no stray node processes tied to this project.
- `npm ci` exits 0 with the normal "added N packages" summary and no EPERM/EBUSY.
- Optional sanity check: `node -e "require('@swc/core')"` exits 0, then restart `next dev`.

If a retry fails on a *different* `.node` file, another process holds that one — repeat the `tasklist /m <file>` step with the new filename.

Note: all process/lock data here is from the synthetic scenario, not live inspection; re-run `tasklist /m` on the real machine before killing anything.
