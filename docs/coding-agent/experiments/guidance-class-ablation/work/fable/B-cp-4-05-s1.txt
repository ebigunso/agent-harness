**Findings**

1. **`Signup.java`, `validate(...)` body (blocking).** A method named `validate`, exposed to callers as a boolean validation API, now inserts a row into `signup` and appends to the mail outbox. That is a persistence and messaging workflow hidden behind a predicate. Callers cannot tell from the name, signature, or return type that calling it has effects; any caller that invokes it more than once per request (re-checking on a form round-trip, calling it in a precondition guard and again in the handler, retrying on a transient error) will create duplicate signup rows and duplicate welcome messages on an auto-commit connection with no way to undo. The `SQLException` in the throws clause was already there, but the method now actually throws for reasons unrelated to validity, so callers treating a `false`/exception as "input was bad" will misinterpret DB failures. This is exactly the hidden-coupling / surprising-side-effect problem the guidelines call out, and the task ("validate signup requests") did not ask for enrollment or notification. Require: keep `validate` pure (input in, boolean out, no `Connection`/outbox needed), and put the insert-and-notify sequence in a separately named operation (e.g. `register(email, db, outbox)`) that calls `validate` first and is invoked once from the request handler. If the author genuinely intends validate-then-register as one step, the name, return type, and commit message must say so and the change needs its own review against duplicate-submission behavior.

2. **`Signup.java`, the validity check itself (should fix under this task).** The only actual validation is unchanged: non-null and non-blank after trim. The stated contract is "one nonempty email token"; the current check accepts `"a b"` and `"@"`. Since the task is to validate signup requests, the change should at minimum enforce the single-token part of the contract (reject internal whitespace) and the check should be the thing this method is about. Require that the accepted shape be encoded explicitly (and, once the side effects are removed, that the method be trivially unit-testable for it).

3. **`Signup.java`, minor.** `rows == 1` is evaluated twice; bind it once (`boolean inserted = rows == 1;`) so the condition that gates the mail and the return value are visibly the same. Also `mail` as a parameter name reads as a single message; `outbox` would state the role. Not blocking on their own; they fall out naturally when the method is split per finding 1.

The change is not acceptable as-is because of finding 1.
