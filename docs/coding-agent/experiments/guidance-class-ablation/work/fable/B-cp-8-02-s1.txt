1. **`cli.py` — `PROVIDERS` / `discover()` / `importlib` registry replacing a direct import (blocking)**

   - **What's wrong:** A one-line static import (`from status import handle`) has been replaced with a string-keyed registry, a dynamic `importlib.import_module` + `getattr` resolver, and a dict lookup by string key at call time — all to reach the same single function.
   - **Why it matters:** Per your own reviewer notes, this is the sole locally invoked command with no extension consumers, so there is exactly one concrete use and nothing to justify the abstraction. The change strictly increases cognitive load and reduces maintainability with no measurable benefit:
     - Static tooling loses the reference: IDE go-to-definition, rename refactors, linters, and type checkers can no longer see that `cli.main` depends on `status.handle`. A typo in `"status"` or `"handle"` is now a runtime `ModuleNotFoundError`/`AttributeError`/`KeyError` instead of an import-time failure.
     - `discover()` re-imports and re-resolves every provider on each `main()` call, and the result is immediately indexed with the same hard-coded string that's already in `PROVIDERS` — the indirection is fully circular.
     - The dependency direction is now hidden in data rather than expressed in code, which is the opposite of "keep dependency direction intentional."
     - This is speculative generality: it's building a plugin mechanism in anticipation of consumers that the notes explicitly say don't exist.
   - **Require instead:** Revert `cli.py` to the direct import:
     ```python

     def main():
         return handle()
     ```
