**Verdict: not acceptable as-is. One blocking defect, one thing I'd flag.**

**1. `Authorization.cs`, `catch (PolicyUnavailable)` branch — fallback grants access from stale, never-expiring cache entries (BLOCK)**

- **What's wrong:** On outage the method returns `cache.Get(user, resource)?.Allowed`. Per the reviewer notes, cache entries carry `FetchedAt` but never expire, and nothing here checks it. An `Allowed = true` entry from last week will grant access even though the user's permission has since been revoked.
- **Why it matters:** The access contract says revocations take effect immediately and offline grants are not authorized. This change violates both: it is fail-open for any principal who was ever granted access, for an unbounded window, precisely when the authoritative check is unavailable. That is the one condition the task ("safe fallback") was meant to cover. The fallback is not bounded or correct.
- **What I'd require:** Fail closed for grants during an outage. The simplest correct implementation is to log the outage with context (user, resource, error) and `return false` — the cache may still be consulted for a cached *deny* if that's useful, but a cached *allow* must not be honored. If product/security explicitly decide that short-lived cached grants are acceptable (which would require amending the contract), then the grant must be gated on `FetchedAt` being within a small, configured TTL (minutes, not days), the TTL must be enforced in this method (or in `cache.Get`), and expired entries must be treated as misses. Either way, add a test: cached `Allowed = true` entry older than the window → `CanAccess` returns `false` while `policy.Check` throws `PolicyUnavailable`.

**2. `Authorization.cs`, same branch — degraded decisions are indistinguishable from authoritative ones (flag)**

- **What's wrong:** The method returns a bare `bool`, so callers, audit logs, and metrics cannot tell a cache-derived (or outage-forced) result from a real policy decision. The only signal is a per-call `log.Warning`, which will flood during an outage and is easy to lose.
- **Why it matters:** Operators need to see that authorization is running degraded, and audit trails need to record that a decision was made without the policy service. Hiding this behind a warning line blurs the failure.
- **What I'd require:** Emit a metric/counter for the fallback path (rate-limit the warning or log at outage transitions), and ensure whatever records access decisions can tag them as "policy unavailable / fallback". If the codebase has an authorization result type rather than `bool`, prefer returning it with a `Source`/`Degraded` indicator.

**Things that are fine:** Catching only `PolicyUnavailable` (other failures still propagate) and denying on cache miss are both correct. The commit message accurately describes the change, but the change itself needs the fix in #1 before merging.
