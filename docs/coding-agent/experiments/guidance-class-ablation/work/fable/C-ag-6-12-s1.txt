**Verdict: block.** The change does what the commit message says in the narrowest sense, but the fallback path is an unbounded, amplifying fan-out into the same failing domain, which is worse than no fallback under the stated conditions.

## Findings

**1. `Fallback.scala:4` — no deadline on the fallback path; result can never complete.**
`Future.firstCompletedOf` only completes when at least one input completes. The notes say gateway futures may never complete and there is no per-call or aggregate timeout, so during an outage every caller blocks indefinitely on this future, pinning threads/connections upstream of this code. Require: a per-mirror timeout and an aggregate budget for the whole fallback (e.g. race each call against a scheduler-backed timeout future that fails with `TimeoutException`, and race the composed result against an overall deadline). A fallback with no deadline isn't degradation; it's a hang.

**2. `Fallback.scala:4` — unconditional 3× fan-out into the outage domain on every request.**
`mirrors.map(call => call())` fires all three mirrors eagerly for every request while the circuit is open. The three mirrors share the upstream outage domain with the primary, so when the circuit opens (because that domain is unhealthy), this triples the load sent to it exactly when it can least absorb it, and the losing calls are never cancelled (Scala `Future`s can't be), so they keep consuming sockets/threads until they finish or never. That's a cascade amplifier. Require: sequential try-next-mirror (or hedged fan-out with a delay), gated by a concurrency limit / mirror-side breaker so the fallback path has its own ceiling and can itself degrade to a cached value or an explicit "unavailable" error.

**3. `Fallback.scala:4` — `firstCompletedOf` returns the first *completion*, including failures.**
A mirror that fails fast (connection refused, 503) wins the race and the whole read fails, even if another mirror would have succeeded a moment later. Fallback semantics should be "first success, else the last/aggregated failure". Require: fold over mirrors with `recoverWith` (sequential), or if you keep racing, race only successful outcomes and fail only once every mirror has failed or timed out.

**4. `Fallback.scala:4` — empty `mirrors` yields a future that never completes.**
In 2.13, `Future.firstCompletedOf(Vector.empty)` is a promise that is never completed. Misconfiguration (or a config that legitimately has zero mirrors) turns into an infinite wait instead of a fast, visible error. Require: if the circuit is open and there are no mirrors, fail immediately with an explicit exception (or return a documented degraded default).

**5. `Fallback.scala:4` — losing/failed mirror outcomes are silently dropped.**
After the race is decided, the other mirrors' results — including failures and timeouts — are discarded with no logging or metrics. That's broad suppression: you lose the signal you'd need to notice "all mirrors are also down" and to decide when to open a mirror-side breaker. Require: observe every mirror outcome (at minimum log/count failures and timeouts), and feed that into whatever health signal governs the fallback path.

**6. Missing tests.**
None of the above behaviours (timeout, first-success-not-first-completion, empty mirrors, bounded fan-out) are covered. Require tests with never-completing and fast-failing `Promise`s for each case before merge.

Minor, not blocking: `primary()` / `call()` throwing synchronously escapes as an exception rather than a failed `Future`; wrapping in `Future.fromTry`/`Future(...).flatten` or `Try` would keep the error channel consistent.
