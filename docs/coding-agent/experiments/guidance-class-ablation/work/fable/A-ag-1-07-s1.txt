1. **`order.rb`, `Order#summary` — serialization initiates fulfillment.**
   `summary` calls `fulfill!(outbox)` whenever `status == "paid"`, so every list/render of a paid order enqueues a fulfillment request. This is exactly what the reviewer notes forbid: serialization must not initiate fulfillment. Idempotency of the outbox key only prevents duplicate shipments; it does not make it acceptable for a read path to be the thing that *starts* fulfillment. Consequences: rendering an admin list, an API index, a background report, or a test fixture dump will kick off fulfillment for every paid order it touches, and the timing of fulfillment becomes coupled to whether/when something happens to display the order rather than to an explicit business event. It also makes `summary` untestable/unrenderable without an outbox.
   **Require:** remove the `fulfill!` call from `summary` entirely. `summary` should be a pure projection: `{ id: id, status: status }`. Fulfillment must be invoked from an explicit command path (e.g. the payment-confirmed handler or a `FulfillOrder` service), not from a serializer.

   Once (1) is fixed, the `outbox` parameter has no purpose in `summary`; keeping it would invite the same coupling back. **Require:** `def summary` with no arguments.
