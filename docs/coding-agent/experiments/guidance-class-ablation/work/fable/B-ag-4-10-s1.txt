**1. `repo.php`, `update()` return type — ambiguous failure signal collapses two distinct outcomes.**

- **What's wrong:** `update()` returns `false` both when the record is missing (`!array_key_exists`) and when the update is temporarily rejected (`$rejected`). The single consumer, `nextAction()`, maps `false` → `"create"` unconditionally. So a temporary rejection of an *existing* record routes to create, which is wrong per the stated requirement (missing → create, rejected → retry).
- **Why it matters:** This is the exact Gate 4 anti-pattern — returning an ambiguous success/failure signal and leaving the caller to guess. The consequence isn't just a wrong label: a "create" on a record that already exists will either fail downstream or produce a duplicate, and the transient rejection never gets retried. The contract as written cannot express the third outcome, so no consumer can be correct.
- **What I'd require:** Make the outcome explicit in the type. In PHP 8.1+, an enum is the natural fit:

  ```php
  enum UpdateResult { case Updated; case Missing; case Rejected; }

  function update(array &$records, string $id, string $value, bool $rejected): UpdateResult {
      if (!array_key_exists($id, $records)) return UpdateResult::Missing;
      if ($rejected) return UpdateResult::Rejected;
      $records[$id] = $value;
      return UpdateResult::Updated;
  }

  function nextAction(UpdateResult $r): string {
      return match ($r) {
          UpdateResult::Updated  => "done",
          UpdateResult::Missing  => "create",
          UpdateResult::Rejected => "retry",
      };
  }
  ```

  Using `match` without a default makes any future addition to the enum a hard error at the call site rather than a silently wrong action. If the codebase predates enums, a string/int constant set with the same three values is acceptable, but a `bool` is not. Both producer and consumer must change together in this commit — this is a breaking contract change and should be labeled as such.

One further note (not blocking, but I'd ask): the ordering of the two checks is a design decision that should be stated. As written, a missing-and-rejected call reports `Missing`. That's probably right — you can't retry an update on something that doesn't exist — but a one-line comment or test pinning that precedence would prevent someone "fixing" it later.
