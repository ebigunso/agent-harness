**Verdict: block.** The change does the opposite of both stated requirements: it accepts naive input, and it does not normalize offset-aware input to UTC. Both produce silently wrong scheduling times downstream.

### Findings

**1. `Ingress.java`, `parseBest(..., OffsetDateTime::from, LocalDateTime::from)` — naive input is accepted, not rejected.**
The `LocalDateTime::from` fallback exists precisely to make offset-less input succeed. `"2026-09-09T10:00:00"` parses to a `LocalDateTime`, `toString()` yields `"2026-09-09T10:00:00"`, and it is enqueued. Downstream then interprets that as UTC, so a caller in UTC+9 who meant 10:00 local gets scheduled nine hours late, with no error anywhere. The notes say naive input is ambiguous and must be rejected.
Require: drop the `LocalDateTime` fallback and either parse with `OffsetDateTime::from` only (`DateTimeParseException` → 400 via transport, per notes) or, better, parse and then explicitly reject when no offset was supplied with a clear validation error that transport maps to 400 (a bare `DateTimeParseException` message for this case is confusing to callers, since the syntax is valid). Note that `ISO_DATE_TIME` also accepts `"...T10:00:00[Europe/Paris]"` (zone but no offset); `OffsetDateTime::from` fails on that and currently falls through to the naive path. Decide whether zone-only input is accepted (`ZonedDateTime::from` gives an unambiguous instant) or rejected, and test it — don't leave it to fall into the naive branch.

**2. `Ingress.java`, `queue.add(parsed.toString())` — offset-aware input is not converted to UTC.**
`OffsetDateTime.toString()` preserves the original offset: `"2026-09-09T10:00:00+02:00"` is enqueued verbatim. Downstream "interprets each string as UTC", so it reads the wall-clock `10:00` as 10:00Z — two hours off from the instant the caller denoted. The requirement is that the queue stores ISO UTC instants and that offset input "denote the same instant".
Require: `odt.toInstant().toString()` (or `odt.withOffsetSameInstant(ZoneOffset.UTC)`), which yields `"2026-09-09T08:00:00Z"`. `Instant.toString()` is also a stable, seconds-always format; `OffsetDateTime.toString()` drops `:00` seconds and varies in fractional-second width, so even for `Z` input the stored strings would be inconsistent with what downstream presumably expects.

**3. No tests.**
This is a small, pure function with a precise contract and three obvious cases: `Z` input passes through as UTC, `+HH:MM` input is shifted to the same instant in UTC, naive input is rejected. Both bugs above would have been caught by any of these. Require unit tests for those three cases (plus the zone-only case from #1 once the decision is made) before merge.

### Minor / non-blocking
- `input == null` will NPE inside the formatter rather than surface as a 400; worth a `Objects.requireNonNull` or explicit validation depending on how transport handles NPEs, but this is secondary to the above.
