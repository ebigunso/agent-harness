## Cause

The gRPC probe is not failing because of the workspace, the build, or the service. It's failing at the transport layer on the IPv6 loopback path:

- `localhost` resolves to `::1` first, so the channel dials `[::1]:50051`.
- Docker Desktop's IPv6 port proxy completes the TCP handshake but never returns HTTP/2 response headers, so tonic sits waiting until the 2s deadline → `DEADLINE_EXCEEDED`, exit 2.
- The service interceptor log shows no invocation for that call, confirming the request never reached the container.
- The controlled comparison — identical method, payload, deadline, container, config, only the target changed to `127.0.0.1:50051` — succeeds (exit 0, stdout `pong`, service log `invoked=true completed=true`).
- The REST sibling on `localhost:50080` works because HTTP/1.1 doesn't hit the same stall in the IPv6 proxy.

So this is a Docker Desktop for Windows loopback/HTTP-2 asymmetry, not a defect in the Rust probe, tonic, the service, or the port publishing.

## Smallest safe remediation

Change the target in the client connection string from `localhost` to `127.0.0.1` for gRPC clients that talk to Docker Desktop published ports:

```powershell
cargo run --manifest-path probes/Cargo.toml -- --target 127.0.0.1:50051 --timeout 2
```

If the address is baked into a config file or a `Cargo` example/default, update that value to `127.0.0.1:50051`. Do not touch the service, the port mappings, the timeout, or the probe code — those are all already known-good.

(Optional hardening if you must keep the name `localhost`: have the client resolve and prefer IPv4, or connect explicitly by IP. But the literal `127.0.0.1` is the smallest change and is already proven to work here.)

## Confirmation

1. Rerun the probe against `127.0.0.1:50051` with the same `--timeout 2`:
   - expected exit code `0`
   - expected stdout `pong`
   - expected stderr only the cargo `Finished`/`Running` lines, no `DEADLINE_EXCEEDED`
2. Check the service interceptor log for a matching entry: `probe method="unary Echo" transport=h2c invoked=true completed=true`.
3. As a control, rerun once against `localhost:50051` and confirm it still hangs to exit 2 with no service log entry — that proves the fix is the address, not a transient.

All three already appear in the captured evidence, so the remediation is confirmed; the remaining step is just to make `127.0.0.1` the persistent default wherever the target is configured.
