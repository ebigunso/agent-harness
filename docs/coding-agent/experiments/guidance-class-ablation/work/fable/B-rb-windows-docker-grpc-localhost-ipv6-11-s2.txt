**Cause:** Not a service or project-workspace defect. `localhost` resolves to `::1` first on this host, so the Dart gRPC channel dials `[::1]:50051`. Docker Desktop's IPv6 port proxy accepts the TCP connect but never returns HTTP/2 frames, so the h2c channel stalls at the transport layer until the 2 s deadline fires (`DEADLINE_EXCEEDED`, exit 2). The evidence is consistent with this and rules out the service:

- REST on the sibling port (`localhost:50080`, HTTP/1.1) answers in 12 ms — the proxy handles HTTP/1.1 fine, only HTTP/2 stalls.
- The service interceptor log shows no invocation for the failed call — the request never reached the handler, so it isn't a handler/deadline/payload issue.
- The identical call to `127.0.0.1:50051` (only the target differs) succeeds: exit 0, `pong 1` / `pong 2`, and the service logs `invoked=true completed=true`.
- No TLS/cert-name check exists, so hostname-vs-IP isn't a certificate concern.

**Smallest safe remediation:** Change the local gRPC target from `localhost:50051` to `127.0.0.1:50051` (in the probe invocation and any local config/connection string that feeds it). Don't touch the service, port publishing, or container config — they're healthy. Leave the REST port alone; it works on either address.

**Confirmation:**
1. `dart run probes/bidi.dart --target 127.0.0.1:50051 --timeout 2` → exit 0, stdout `pong 1` / `pong 2`, empty stderr (already observed).
