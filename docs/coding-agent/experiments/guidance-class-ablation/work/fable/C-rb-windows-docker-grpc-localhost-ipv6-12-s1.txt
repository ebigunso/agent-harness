**Verdict:** This is a workspace/local-configuration problem, not a server or code defect.

**Cause**

`localhost` on this host resolves to `::1` first, so the Kotlin probe dials `[::1]:50051`. Docker Desktop's published-port proxy on the IPv6 loopback accepts the TCP connection but never returns HTTP/2 (h2c) response headers, so the channel sits in the connect/handshake phase until the 2 s deadline fires. The evidence lines up:

- The service interceptor log shows **no invocation** for the failed call — the request never reached the container.
- The identical RPC against `127.0.0.1:50051` succeeded (`pong`, exit 0, `invoked=true completed=true`).
- Only the local config target changed (`127.0.0.1` → `localhost`) immediately before the failure; server code and image are unchanged.
- The REST check on 50080 is a weaker control (different port, HTTP/1.1, and curl will happily use whichever address family answers), so its speed doesn't contradict the gRPC stall.

The probe's `DEADLINE_EXCEEDED` / exit 2 is its normalized mapping of the deadline expiry — it's a symptom, not a separate bug.

**Smallest safe remediation**

Revert the local configuration profile's target from `localhost:50051` back to `127.0.0.1:50051`. That's the one change that introduced the failure and it's local-only. Do **not** modify the hosts file, disable IPv6, rebuild the image, or change server ports/handlers.

**Confirmation**

1. Run the probe exactly as it failed, but via the corrected profile (or explicitly): `java -jar probes/kotlin-probe.jar --target 127.0.0.1:50051 --timeout 2` → expect exit 0, stdout `pong`, empty stderr.
2. Check the service log shows a new `probe method="unary Echo" transport=h2c invoked=true completed=true` entry for that call.
3. Optionally rerun with `localhost:50051` once to confirm it still fails the same way, proving the address family (not timing) is the variable.
4. Record for the ticket: target/port (`[::1]:50051` vs `127.0.0.1:50051`), the deadline output (`DEADLINE_EXCEEDED: deadline expired after 2s`, exit 2), the REST timing (`http_code=200 total_seconds=0.012`), and the IPv4 retry result.

If both addresses had failed, the next step would be `docker ps`/port mappings and container health — but here the IPv4 success already isolates it to the Docker IPv6 loopback proxy.
