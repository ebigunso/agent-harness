**Cause**

This is a workspace/local-config problem, not a service bug.

On this host `localhost` resolves to `::1` first, so the probe opens `[::1]:50051`. Docker Desktop's published-port proxy on the IPv6 loopback accepts the TCP connection (so there is no `UNAVAILABLE`), but the h2c stream never gets a response — no HTTP/2 headers arrive, the tonic client waits until the 2 s deadline, and the probe maps that to exit 2 / `DEADLINE_EXCEEDED`. The service interceptor log shows no invocation for that call, confirming the request never reached the server.

The evidence isolates the address as the only variable:

- REST on `localhost:50080` is fine (12 ms, 200) — HTTP/1.1 through the same proxy path works, so this is specific to HTTP/2 over the `::1` proxy, not a dead container or bad port mapping.
- Same binary, method, payload, deadline, server and container against `127.0.0.1:50051` returns `pong` (exit 0) and the service logs `invoked=true completed=true`.
- Service is up, port mappings are correct, no TLS/name checks involved.

**Smallest safe remediation**

Point the local probe/client config at the IPv4 loopback instead of the hostname:

```powershell
cargo run --manifest-path probes/Cargo.toml -- --target 127.0.0.1:50051 --timeout 2
```

and persist `127.0.0.1:50051` (not `localhost:50051`) wherever the local gRPC target is configured (probe defaults, `.env`, dev config). Do not change the service, the container, the port publishing, or the probe's exit-code mapping. Avoid host-wide changes like editing the `hosts` file or disabling IPv6 — those are broader than needed and affect unrelated tooling.

**Confirmation**

1. Re-run the probe against `127.0.0.1:50051` with the same 2 s timeout: expect exit 0, stdout `pong`, no `DEADLINE_EXCEEDED` on stderr.
2. Check the service interceptor log shows a new `probe method="unary Echo" transport=h2c invoked=true completed=true` entry for that call.
3. Optionally run the `localhost:50051` variant once more to show it still times out — confirming the target address, not timing or flakiness, is the difference.
4. Leave the sibling health check as-is (`curl` to `localhost:50080` still 200) as a control that nothing else changed.

Record for the ticket: targets/port (`localhost:50051` → `[::1]:50051` failed; `127.0.0.1:50051` succeeded), deadline output (`DEADLINE_EXCEEDED: deadline expired after 2s`, exit 2), REST timing (`200`, 0.012 s), and the IPv4 retry result (`pong`, exit 0, server-side invocation logged).
