**Cause**

Not a service problem and not a code/dependency problem in the workspace. It's the Docker Desktop for Windows IPv6 loopback path: `localhost` resolves to `::1` first, the Dart gRPC channel connects to `[::1]:50051`, Docker Desktop's IPv6 port proxy accepts the TCP handshake but stalls the HTTP/2 (h2c) stream, so the bidi Echo never reaches the server handler and the probe's 2s deadline fires (`DEADLINE_EXCEEDED`, exit 2). The evidence is consistent and complete:

- Same probe, same payload, same deadline, same container — only the target changed to `127.0.0.1:50051` — succeeds (`pong 1`, `pong 2`, exit 0) and shows `invoked=true completed=true` in the interceptor log.
- The failed call has no interceptor-log entry at all, i.e. it died at the transport, not in the handler.
- The HTTP/1.1 sibling on 50080 answers in 12 ms via `localhost`, which matches the known asymmetry: the IPv6 proxy passes HTTP/1.1 but breaks HTTP/2.
- No TLS/SNI involved (plaintext h2c), so certificate-name or ALPN issues are ruled out.

**Smallest safe remediation**

Change the gRPC target from `localhost:50051` to `127.0.0.1:50051` wherever the bidi probe (and any other local gRPC client in this workspace) builds its connection string — e.g. the default/`--target` value used for local runs. Do not touch the service, port publishing, the Dart/grpc versions, or Docker settings; the address-only comparison already proves those are healthy. Disabling IPv6 on the host or hacking the `hosts` file is broader than necessary and not needed.

**Confirmation**

1. Rerun the original command with the corrected address:
   `dart run probes/bidi.dart --target 127.0.0.1:50051 --timeout 2`
   Expect exit 0, stdout `pong 1` / `pong 2`, empty stderr.
2. Check the service interceptor log for `probe method="bidirectional Echo" transport=h2c invoked=true completed=true` for that run.
3. Optionally rerun with `--target localhost:50051` once more to confirm it still fails identically (exit 2, `DEADLINE_EXCEEDED`, no log entry) — this reconfirms the cause is address resolution rather than something transient.
4. Sanity-check that the REST sibling still returns 200 on both `localhost:50080` and `127.0.0.1:50080`, so nothing else changed.

If step 1 also fails on `127.0.0.1` (it did not in the captured run), only then move on to investigating the service, port mappings, and container health.
