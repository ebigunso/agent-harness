**Cause**

This is not the native-module lock case the reference describes, and it is not a workspace problem. The `EPERM` is on `syscall mkdir` for `C:\locked-cache`, which is npm's configured cache directory (`npm config get cache` → `C:\locked-cache`). The effective ACL on that path denies this user directory creation/write, so npm cannot create/populate its cache before installing. The repo at `C:/work/npm-lock` is writable, the lockfile is in sync, and no `<module>.node` unlink or lock holder is involved — so the tasklist/taskkill steps do not apply and should not be run.

**Smallest safe remediation**

Point npm at a writable cache without touching ACLs or killing anything:

1. Verify where the bad value comes from so the fix is targeted:
   ```
   npm config list -l | findstr /i cache
   ```
   (Look for `cache = "C:\locked-cache"` and whether it's user, global, project `.npmrc`, or an `npm_config_cache` env var.)

2. Override for this run:
   ```
   npm ci --cache "$env:LOCALAPPDATA\npm-cache"
   ```

3. If it succeeds, make it persistent at the scope where the bad value was set — e.g. for user config:
   ```
   npm config set cache "$env:LOCALAPPDATA\npm-cache"
   ```
   or delete the offending line from the relevant `.npmrc` / unset `npm_config_cache` so npm falls back to its default.

Do not try to fix `C:\locked-cache` permissions (that's an admin/policy decision) and do not run `taskkill`.

**Confirmation**

- `npm config get cache` returns the writable path (not `C:\locked-cache`).
- Plain `npm ci` (no override flag) exits 0 with no `EPERM`/`mkdir` errors, and `node_modules` is populated (`npm ls --depth=0` shows no missing deps).
- Optional: `npm cache verify` runs cleanly against the new path.

Evidence to keep: original error, `npm config list -l` output showing the cache source, the retry command and its exit code.
