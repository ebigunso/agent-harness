**Cause:** This is a workspace problem, not a permissions/registry/lockfile issue. `npm install` failed with `EBUSY` on `unlink` of `node_modules\bcrypt\lib\binding\napi-v3\bcrypt_lib.node` because a running process has the native addon mapped. `tasklist /m bcrypt_lib.node` identifies exactly one holder: `node.exe` PID 4105, a Jest integration-test worker running `jest.js --watch` from this repository, idle in watch mode after the last run. Windows won't let npm replace a loaded `.node` DLL, so the install aborts. The other observations (probe file create/delete works, no ACL denial, lockfile in sync, registry OK, cache writable) rule out the alternative causes.

**Smallest safe remediation (in order):**

1. Stop the Jest watcher gracefully — go to the terminal/editor session running `jest --watch` for `C:/work/npm-lock` and quit it (`q` in the watch UI or Ctrl+C). It's owned by this repo and idle, so nothing is lost.
2. Only if it can't be stopped that way, kill it as a last resort:
   ```
   taskkill /PID 4105 /F
   ```
3. Retry:
   ```
   npm install
   ```

Don't delete `node_modules` or touch permissions; that isn't the cause and won't help while the DLL is mapped.

**Confirmation:**

- Before retrying: `tasklist /m bcrypt_lib.node` should report "No tasks are running which match the specified criteria" (and `tasklist | findstr node` shows no leftover workers for this repo).
- `npm install` exits 0 with no `EBUSY`/`EPERM` output.
- Sanity check the addon still loads on Node 20.18.0: `node -e "require('bcrypt'); console.log('ok')"`.
- If a retry fails with a different `.node` filename, repeat step 2's `tasklist /m <that file>` for the new module.

**Prevention:** run `npm install` only after stopping watchers/dev servers, or run Jest without `--watch` in sessions where you expect to update dependencies.
