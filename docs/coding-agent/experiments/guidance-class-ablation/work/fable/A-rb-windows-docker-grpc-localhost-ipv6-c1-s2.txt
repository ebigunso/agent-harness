## Verdict

This is **not a workspace problem**. The Docker/port/address theory is ruled out by the evidence itself, and the failure is a **server-side application/database stall**.

## Cause

- Both `127.0.0.1:50051` and `localhost:50051` produce the identical `DEADLINE_EXCEEDED` after exactly 2s. If this were a Docker Desktop IPv4/IPv6 or port-mapping asymmetry, one address would fail differently (typically `UNAVAILABLE` / connection refused immediately, not a full-deadline wait) — and the service trace confirms the connection succeeded.
- The trace shows `method=Echo invoked=true phase=db-query waiting_on=lock-42`: the request reached the server, the interceptor logged it, the handler ran, and it is blocked on database lock `lock-42` held by a stalled migration transaction. The probe's deadline simply expires while the handler waits.
- The HTTP health endpoint on 50080 returns 200 in 12ms because it is a shallow liveness check that does not touch the database. It tells you the process is up, not that the data path works — which is exactly why it disagrees with the gRPC probe.
- The probe, Python/grpcio versions, plaintext h2c, and absence of TLS are all irrelevant here; the client behaved correctly and the exit code 2 is the probe's defined mapping for a deadline.

## Smallest safe remediation

Fix the lock holder, not the client:

1. On the database, identify the session holding `lock-42` (e.g. Postgres: `pg_locks` joined to `pg_stat_activity`; MySQL: `performance_schema.data_locks` / `SHOW ENGINE INNODB STATUS`). Confirm it is the migration transaction and that it is genuinely stalled (idle-in-transaction / no progress), not just slow.
2. Let the migration finish if it's actually progressing. If it is stalled, roll back / terminate that single session (`pg_terminate_backend(pid)` or `KILL <id>`) — coordinating with whoever owns the migration so it can be re-run cleanly afterward.

Do **not**:
- Raise `--timeout` — that only hides the stall and will hang the probe longer.
- Restart the gRPC service or Docker Desktop — the service is healthy; a restart won't release a lock held in the database and may leave the migration half-applied.
- Change Docker port mappings or localhost resolution — there is no asymmetry to fix.

## Confirmation

1. Re-run the failing command:
   ```powershell
   python probes/unary.py --target 127.0.0.1:50051 --timeout 2
   ```
   Expect exit code 0, the echoed response on stdout, empty stderr, and a wall time of milliseconds rather than ~2s. Run the `localhost:50051` variant too to show both still agree.
2. Re-check the handler trace: it should show the call completing (no `waiting_on=lock-42`).
3. Query the DB lock view again to confirm no session holds or waits on `lock-42`.
4. Optionally, follow up by giving the health endpoint (or a separate readiness check) a DB-touching dependency so 50080 stops reporting 200 during this class of failure.
