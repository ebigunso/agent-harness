**Cause**

This is a workspace problem, not an npm/registry/permissions issue. `npm install` needs to replace `node_modules\bcrypt\lib\binding\napi-v3\bcrypt_lib.node`, but Windows refuses to unlink a loaded native module (EBUSY, errno -4082). `tasklist /m bcrypt_lib.node` shows the holder is `node.exe` PID 4105 — the repo's own Jest integration-test worker sitting in `--watch` mode after its last run, with `bcrypt_lib.node` still mapped. Everything else checks out (lockfile in sync, registry OK, probe file beside the module writable, no ACL denial), so the only thing in the way is that process.

**Smallest safe remediation**

1. Stop the watcher gracefully: go to the terminal running `jest --watch` and press `q` (or Ctrl+C). That's the whole fix — no `node_modules` deletion, no `--force`, no admin shell, no cache clean.
2. Only if it won't exit on its own (hung/detached terminal), and after re-confirming the PID is still the same repo-owned Jest worker:
   `taskkill /PID 4105 /F`
3. Re-run the original command: `npm install`

**Confirmation**

- `tasklist /m bcrypt_lib.node` → should report no tasks (no `node.exe` row).
- `npm install` → exit code 0, no EBUSY in stderr.
- Sanity-check the addon still loads on this runtime: `node -e "require('bcrypt'); console.log('ok')"` (and/or `npm ls bcrypt` shows 5.1.1 without errors).
- Then restart the Jest watcher if you want it back.

If the retry fails again, run `tasklist | findstr node` and `tasklist /m bcrypt_lib.node` once more to see whether a new holder appeared (e.g. a dev server or editor language service), and note the original command/error, the module path, the tasklist output, any PIDs killed, and the retry result.
