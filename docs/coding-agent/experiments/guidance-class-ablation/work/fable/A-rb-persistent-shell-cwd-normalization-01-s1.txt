**Cause:** Stale working directory, not a project problem. The persistent shell had already been moved into `C:/work/shop/web` by the earlier `Set-Location`. The failing command assumed the cwd was still the workspace root (`C:/work/shop`, which is what the tool UI still displayed) and ran `cd web` again, so PowerShell tried to enter `C:\work\shop\web\web`, which doesn't exist. `Set-Location` failed, `&&` short-circuited, and `npm run build` never ran — the exit status 1 is from the failed `cd`, not from npm/tsc. The comparison run proves this: same command, only the starting directory differs, and it builds cleanly.

**Smallest safe remediation:** Don't repeat the relative `cd`. Either run the build from where the shell already is:

```powershell
npm run build
```

or, to be robust against whatever the shell's cwd happens to be, anchor the navigation absolutely:

```powershell
Set-Location -LiteralPath 'C:/work/shop/web'; npm run build
```

No code, config, dependency, PATH, or permission changes are needed — nothing about the workspace is broken.

**Prevention going forward:** In a persistent shell, treat the tool UI's "workspace root" as unreliable for cwd and use absolute paths (`Set-Location -LiteralPath ...`) or `pwd` checks before relative `cd` commands.
