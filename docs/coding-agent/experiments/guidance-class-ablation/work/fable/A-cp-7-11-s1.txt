**Findings**

1. **`schedule.cpp`, `test_due`, `assert(!due(deadline));` — flaky by construction (would block).**
   The deadline is `now() + 20ms`, and the assertion assumes fewer than 20ms elapse between that line and the call to `due`. Under CI load, a preempted or paused process (exactly the scenario the notes call out) can easily lose 20ms there, at which point `due` returns `true` and the test fails with no code defect. No sleep/yield margin fixes this — any "before" assertion against a real clock is a race against the scheduler, and widening to 200ms or 2s only lowers the probability. The "after" half is fine (steady clock is monotonic), but the "before" half is what actually proves the threshold direction, so the test doesn't reliably prove what it's intended to.
   **Require:** make time injectable so the boundary can be tested deterministically — e.g. `bool due(Clock::time_point now, Clock::time_point deadline) { return now >= deadline; }` (with a convenience overload that passes `Clock::now()`), or template `due` on the clock type and test with a fake clock. Then assert `due(t, t+1ms) == false`, `due(t, t) == true`, `due(t+1ms, t) == true` with no real-time dependence. This also lets you cover the `==` boundary, which the current test never exercises even in the best case.

2. **`schedule.cpp`, `test_due` — not wired up, and `assert`-based (would flag).**
   Nothing calls `test_due`; there's no `main` and no test-framework registration, so as landed this verifies nothing. Separately, using `assert` means a release/`NDEBUG` build silently turns the test into a 20ms busy-wait that always "passes." **Require:** hook it into whatever test runner the project uses (or add a `main`), and use the runner's check macros rather than `assert` — or at minimum `#undef NDEBUG` at the top of the test TU.

3. **`schedule.cpp`, busy-wait loop (minor, goes away with #1).**
   `while (now < deadline) yield()` spins a core for the whole window. Acceptable for a 20ms unit test, but if you keep a real-clock "after" check at all, `std::this_thread::sleep_until(deadline)` is cheaper and clearer. With the injected-clock fix this loop disappears entirely.

The `due` function itself (`now >= deadline`, inclusive at the boundary) is correct and the right semantics for a dispatch threshold; the problems are all in how it's tested.
