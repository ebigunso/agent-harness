**Findings**

1. **`Invoice.java` — `Invoice.total` reads a hidden mutable global (`Rates.current`).**
   The rate is an input to the calculation but is not an explicit parameter; it's a package-visible static that any code (including any test class in the same suite) can mutate. That makes the core behavior untestable in isolation and violates the "prefer deterministic seams over hidden global state" guideline. The reviewer note that a rate snapshot must be stable during a calculation also argues for capturing the rate as a value at the call boundary rather than reading a live static.
   *Require:* pass the rate explicitly — e.g. `static double total(double base, double rate)` — or inject a `RateSource`/`Rates` instance into `Invoice`. If a process-wide default must exist, keep it behind an accessor and make `total` take the snapshot as an argument.

2. **`InvoiceTest.java` — tests are order-dependent and leak state.**
   `euros` sets `Rates.current = 0.9` and never restores it; `dollars` asserts against `1.0` but never sets it. JUnit 5 does not run methods in declaration order by default, so if `euros` runs first, `dollars` fails (`10 * 0.9 = 9.0`). Per the reviewer notes, other test classes also mutate `Rates.current` before this class runs, so `dollars` can fail even if it runs first. As written the suite is flaky and neither test proves the conversion independently.
   *Require:* each test must establish the state it depends on and not leave residue. With fix (1), this is simply `assertEquals(9.0, Invoice.total(10, 0.9))` and `assertEquals(10.0, Invoice.total(10, 1.0))`. If the global is retained, add `@BeforeEach` that sets `Rates.current = 1.0` and `@AfterEach` that restores the prior value, and have `dollars` set its rate explicitly rather than assuming the default.

Not raised: `double` for money and thread-safety of the static — the notes state amounts are toy exact doubles and the suite is single-threaded, so neither is a defect in this context.
