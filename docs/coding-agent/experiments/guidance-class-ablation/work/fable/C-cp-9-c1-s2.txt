1. **`catalog/fetch.go`, `FetchFailure.Error()` — the message discards the cause and the timeout distinction.**
   `Error()` returns only `"fetch catalog failed"`. Anything that logs or reports the error as a string (`%v`, `%s`, `err.Error()`, most structured loggers) will show that and nothing else — no underlying reason, no indication it was a timeout. The information exists in `Cause`/`Timeout`, but only for callers that know to `errors.As` into `*FetchFailure`; everyone else sees a blurred failure. The reviewer note that store errors are already sanitized at source removes the only reason to omit the cause from the string.
   **Require:** include the cause in the message (`e.Operation + " failed: " + e.Cause.Error()`, with a nil guard on `Cause`), and reflect the timeout in the wording (e.g. `"fetch catalog timed out: ..."` when `Timeout` is set). Keep the public HTTP mapping as-is; this is about what the error says internally.

2. **`catalog/fetch.go`, `Timeout: errors.Is(err, context.DeadlineExceeded)` — timeout detection depends on the store propagating the context error in its chain.**
   If `Store.Fetch` (or the driver under it) returns its own error for a deadline hit without wrapping `context.DeadlineExceeded` — common with `os.ErrDeadlineExceeded` from net I/O or driver-specific timeout errors — `Timeout` will be `false` even though the request timed out, which is exactly the context the task says to preserve.
   **Require:** either confirm the `Store` contract guarantees wrapping of the context error, or make the check robust: also consult `ctx.Err() == context.DeadlineExceeded` and `errors.Is(err, os.ErrDeadlineExceeded)` (and a `net.Error` with `Timeout()` if network stores are in play).
