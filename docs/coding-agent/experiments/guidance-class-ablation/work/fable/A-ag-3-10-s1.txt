## Findings

### 1. `templates/page-01.html` … `templates/page-80.html` — unrelated whitespace churn (block)

**What's wrong:** All 80 template files are changed from `<p>Ready</p>` to `<p> Ready </p>`. This has nothing to do with the task ("include locale in cache key"), isn't mentioned in the commit message, and as the reviewer notes confirm, has no rendering effect — it's purely a whitespace preference.

**Why it matters:**
- The commit is mislabeled: `git log`/`git blame` will attribute 80 template edits to "include locale in cache key". Anyone bisecting or auditing template history later gets misdirected.
- It buries the one meaningful line in 160 lines of noise, making the actual change harder to review and increasing the chance a real defect slips through.
- If anything downstream does compare template text byte-for-byte (snapshot tests, content hashes, CDN etags), this will trip it for no benefit.
- Even if the whitespace style is desired, it should be its own commit so it can be reverted or reasoned about independently.

**Require instead:** Drop the template changes from this patch. If the whitespace style is wanted, land it as a separate, clearly-labeled commit (ideally driven by a formatter so it's mechanical and reproducible).

### 2. `cache.php` — key format change silently orphans every existing cache entry (flag, not block)

**What's wrong:** Keys change from `$id` to `$id:$locale`. Every entry written under the old scheme becomes unreachable but stays resident until TTL/eviction.

**Why it matters:** On deploy you get a full cold-cache miss storm (every request recomputes), plus double memory occupancy until old entries age out. That's expected and usually acceptable for this kind of fix, but it should be a conscious decision.

**Require instead:** Either note the one-time cache-bust in the commit message/PR description, or flush the cache as part of deploy if the backing store makes that cheap. No code change needed.

### 3. `cache.php` — no test for the new behavior (flag)

**What's wrong:** The whole point of the change is that `keyFor('x', 'en') !== keyFor('x', 'fr')`, and nothing in the patch asserts that.

**Require instead:** Add a small unit test covering (a) different locales produce different keys for the same id, and (b) the same id+locale is stable. This is the regression that motivated the change; it should be pinned.

---

The `cache.php` change itself is correct: `"$id:$locale"` is fine given the stated validation (no colons in ids/locales), so there's no delimiter-collision risk. The blocking issue is solely the 80 unrelated files.
