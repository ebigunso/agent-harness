**Cause**

Not a bug in the checks — they all passed. The crash is at the final `print`: `sys.stdout` is `cp1252` and U+2713 (✓) has no mapping in that code page, so `codecs.charmap_encode` raises before the result line is emitted.

One nuance vs. the reference note: this isn't the interactive-console path (where Python 3.6+ writes UTF-16 to the console API and would have printed ✓ fine). Because stdout is a **pipe**, Python falls back to the process's ANSI code page (cp1252 here, not CP932), and `utf8_mode = 0` means nothing overrides it. Same mechanism and same fix; just don't expect to reproduce it by running the script in a bare terminal.

**Smallest safe remediation**

Rerun with the encoding override (PowerShell 7.4):

```powershell
$env:PYTHONIOENCODING = 'utf-8'; python check.py
```

(`$env:PYTHONUTF8 = 1` is an equivalent, slightly broader switch.) No cleanup is needed first: the checks were read-only and the failure happened at print time, so there are no partial side effects to undo.

For the durable fix, since `check.py` is your script, make the output site explicit rather than locale-dependent — add near the top:

```python
import sys
sys.stdout.reconfigure(encoding="utf-8")
```

(or, if the symbol is purely cosmetic, use ASCII `PASS` / `OK` and remove the dependency entirely).

**Confirmation**

- Rerun exits 0 and stdout contains `PASS ✓` (no traceback on stderr).
- `python -c "import sys; print(sys.stdout.encoding)"` under the same pipe reports `utf-8` when the override is set.
