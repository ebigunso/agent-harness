**Verdict: not a workspace problem.** The project, descriptors, build, reflection, container and service are all healthy; the failure is a local host-networking asymmetry in how `localhost` reaches Docker Desktop's published port.

## Cause

- On this Windows host, `localhost` resolves to `::1` first. grpcurl dialed `[::1]:50051`.
- Docker Desktop's published-port proxy on the IPv6 loopback accepts the TCP connection but never completes the HTTP/2 (h2c) handshake — no SETTINGS/response headers arrive — so grpcurl blocks in dial until `-max-time 2` expires: `Failed to dial target host "localhost:50051": context deadline exceeded`.
- The server never received the request (no interceptor log entry), which rules out the service, the RPC, and reflection.
- The HTTP/1.1 health check on 50080 succeeds in 12 ms because that path either works over the `::1` proxy or falls back to IPv4; either way it doesn't exercise the stalled h2c path.
- The controlled comparison — same command with only the target changed to `127.0.0.1:50051` — exits 0, returns `{"value":"pong"}`, and logs `invoked=true completed=true`. That isolates the variable to the address family of the target.

Raising `-max-time` would not help; nothing arrives from the `::1` proxy, it isn't slow.

## Smallest safe remediation

Point the local gRPC target at the IPv4 loopback explicitly: use `127.0.0.1:50051` instead of `localhost:50051` in the local config/scripts that set the demo.Probe target (e.g. the `.env`/config value or the grpcurl wrapper in `C:/work/grpc-local`).

Do **not** disable IPv6, edit the `hosts` file, change Docker port mappings, or reconfigure the service — those are broader, affect other tools, and address symptoms that aren't the actual variable here.

## Confirmation

1. Re-run the original call with the new target:
   `grpcurl -plaintext -max-time 2 -d '{}' 127.0.0.1:50051 demo.Probe/Ping`
   Expect exit 0 and `{"value": "pong"}`.
2. Check the service interceptor log shows the matching line: `probe method="unary demo.Probe/Ping" transport=h2c invoked=true completed=true`.
3. Optionally confirm reflection on the same path: `grpcurl -plaintext 127.0.0.1:50051 list` should list `demo.Probe`.
4. Re-run the REST check to confirm nothing regressed (`http_code=200`, sub-second `time_total`).

Record for the ticket: targets/port (`localhost` → `[::1]:50051` fails, `127.0.0.1:50051` works), the deadline-exceeded stderr, the REST timing (0.012 s), and the IPv4 retry result. If the `localhost`/`::1` path must eventually work (e.g. for tooling you can't configure), that's a Docker Desktop proxy issue to report/track separately — not something to fix in this workspace.
