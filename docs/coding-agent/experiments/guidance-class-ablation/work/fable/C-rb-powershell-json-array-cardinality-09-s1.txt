## Cause

Not a workspace problem. `data.json` is valid and *does* satisfy the contract — it is a one‑element JSON array (`[true]`, valid empty/singleton/multiple all accepted).

The failure is a bug in the probe. The array is parsed correctly, but it flows through a **pipeline**:

```powershell
$parsed = $raw | ConvertFrom-Json | Write-Output
```

PowerShell pipelines *unroll* collections, so the single‑element array `[true]` is enumerated down to its lone member. `$parsed` therefore ends up as the scalar `System.Boolean` (`$true`), which is exactly what stdout reports (`parsed type=System.Boolean`). The post‑pipeline `-isnot [array]` test then fires and throws.

In other words, `-is [array]` after a pipeline cannot prove wire framing — the enumeration has already destroyed the array‑ness. On Windows PowerShell 5.1 there is no `ConvertFrom-Json -NoEnumerate` to preserve it, so the type‑based assertion is fundamentally unreliable here.

## Smallest safe remediation

Assert on the **raw wire framing** instead of the post‑pipeline object type. Replace only the assertion line (line 10):

```powershell
$t = $raw.Trim()
if (-not ($t.StartsWith('[') -and $t.EndsWith(']'))) { throw 'Expected JSON array' }
```

Notes on why this is the minimal/safe choice:

- It is a framing check, **not** a JSON syntax validator — which is all the contract needs (accept `[]`, `[x]`, `[x,y,…]`; reject scalar wire values like `true`, `42`, `"s"`).
- Do **not** "fix" it with `$parsed = @($raw | ConvertFrom-Json)`. That would wrap a genuine scalar wire value (`true`) into a one‑element array and wrongly *accept* it, breaking the reject‑scalars part of the contract.
- The stray `| Write-Output` on line 6 is harmless once framing is checked from `$raw`, but it can be dropped since it does nothing but re‑enumerate.
