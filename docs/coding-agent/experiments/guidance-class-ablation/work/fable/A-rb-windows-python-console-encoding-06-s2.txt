**Cause**

Not a bug in the diff logic — the comparison completed and `diff` is `'before \u2014 after\n'`. The failure is at the output boundary. Because stdout is a pipe (not an interactive console), CPython on Windows falls back to the locale ANSI code page for `sys.stdout`, here `cp932`, and UTF-8 mode is off (`sys.flags.utf8_mode = 0`). `cp932` cannot encode U+2014 EM DASH (Python's cp932 table maps the JIS dash 0x815C to U+2015, not U+2014), so `sys.stdout.write` raises `UnicodeEncodeError`. Under an interactive console this would have worked, which is why it can look intermittent.

This is an environment/encoding configuration problem, not a workspace or data problem.

**Smallest safe remediation**

Run the script with UTF-8 mode for that invocation only, no code or environment changes:

```powershell
python -X utf8 tree_diff.py
```

Equivalent: `$env:PYTHONUTF8 = '1'; python tree_diff.py` (session-scoped) or `$env:PYTHONIOENCODING = 'utf-8'` if you want to touch only the stdio encoding.

If the output is consumed by PowerShell itself (captured into a variable or piped to another cmdlet), also make PowerShell decode the pipe as UTF-8 so the em dash doesn't get mojibaked on the way in:

```powershell
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()
```

If you want the script to stop depending on the caller's environment, the durable fix is one line near the top of `tree_diff.py`:

```python
sys.stdout.reconfigure(encoding="utf-8")
```

(Or `errors="replace"` if lossy output is acceptable; I wouldn't default to that for a diff.) I'd still make the invocation change first since it's zero-risk and reversible.

**Confirmation**

1. `python -X utf8 -c "import sys; print(sys.stdout.encoding, sys.flags.utf8_mode)"` in the same piped context → `utf-8 1`.
2. `python -X utf8 tree_diff.py; $LASTEXITCODE` → exit code `0`, no traceback, stdout is `before — after`.
3. If bytes matter downstream: `python -X utf8 tree_diff.py | Format-Hex` (with `[Console]::OutputEncoding` set to UTF-8) shows `E2 80 94` for the dash, not `3F` (`?`) or a substitute.
4. Rerun without the flag once to confirm the original failure still reproduces, so you know the flag is what fixed it and not a transient difference in how stdout was attached.
