**Verdict:** Not a workspace or service problem. The failure is at the loopback/transport layer between the PHP gRPC client and Docker Desktop's IPv6 port proxy.

**Cause**

`localhost` resolves to `::1` first on this host. The PHP grpc probe connects to `[::1]:50051`; the TCP handshake completes (Docker Desktop's proxy accepts it), but no HTTP/2 response frames come back, so the channel sits idle until the 2s deadline fires and the probe maps that to exit 2 / `DEADLINE_EXCEEDED`. The evidence lines up exactly with the IPv6-proxy-stalls-h2 pattern:

- Same probe, same everything, target `127.0.0.1:50051` → exit 0, `pong`, and the service interceptor logs `invoked=true completed=true`.
- The `localhost` call never appears in the service log — the request never reached the service, so it can't be a handler, auth, or method-name issue (which would have surfaced as 3 anyway).
- Sibling port 50080 over `localhost` responds in 12 ms — plain HTTP/1.1 is unaffected by the h2 stall, which is why REST "works" while gRPC hangs.
- No TLS in play, so hostname/cert mismatch is ruled out.

**Smallest safe remediation**

Change the gRPC target from `localhost:50051` to `127.0.0.1:50051` wherever the PHP client (and any other local gRPC clients hitting Docker Desktop published ports) builds its address. Nothing in the container, port mapping, or service needs to change. Don't touch the hosts file or disable IPv6 system-wide — that's broader than necessary and affects other tooling.

**Confirmation**

1. Rerun the original command with the IPv4 target:
   `php probes/unary.php --target 127.0.0.1:50051 --timeout 2`
   Expect exit 0, `pong` on stdout, empty stderr (already observed once; repeat after the config change to confirm the change is what's in effect).
2. Check the service interceptor log shows a new `probe method="unary Echo" transport=h2c invoked=true completed=true` entry for that call.
3. Optionally rerun with `localhost:50051` once more to confirm it still hangs — that keeps the diagnosis honest by showing the only variable is the address, not a transient service state.

If step 1 ever fails with the IPv4 target, then and only then look at the service, the port publish, or container health.
