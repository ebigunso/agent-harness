**Verdict: block.** The change does not meet the stated contract ("one failing user must not cancel siblings").

## Findings

### 1. `Sync.kt` line 5 — a single failing `sync` cancels the whole batch
**What's wrong:** `async` inside `coroutineScope` is a regular (non-supervisor) child. When `sync(user)` throws, that `Deferred` fails, the failure propagates to the parent scope, and `coroutineScope` cancels every sibling still in flight and rethrows. `awaitAll()` also fails fast on the first failed deferred, so even if siblings were somehow protected the caller never learns which users succeeded.

**Why it matters:** The task explicitly requires isolation between users. With this code, one bad record aborts the tenant batch mid-flight, leaving an unknown subset of users unsynced (or partially synced, depending on where cancellation lands inside `sync`). That's the exact failure the task is meant to prevent.

**Required instead:** Isolate failures per user *inside* each coroutine, then aggregate after all have completed. Note that `supervisorScope` alone is not enough — `awaitAll()` still throws on the first failure, and that exception escaping the `supervisorScope` block cancels the remaining children. Something along these lines:

```kotlin
suspend fun syncUsers(
    users: List<String>,
    sync: suspend (String) -> Unit,
): Map<String, Throwable> = coroutineScope {
    users.map { user ->
        async {
            try {
                sync(user); null
            } catch (e: CancellationException) {
                throw e                      // do not swallow cancellation
            } catch (e: Exception) {
                user to e
            }
        }
    }.awaitAll().filterNotNull().toMap()
}
```

Then the caller either inspects the failure map or the function throws an aggregate exception *after* all users have finished. The key points I'd check in the revision: (a) exceptions are caught per user, not at the scope, (b) `CancellationException` is rethrown so external cancellation still works, (c) results are reported, not dropped.

### 2. `Sync.kt` line 4 — return type gives the caller no way to see outcomes
**What's wrong:** The function returns `List<Unit>` (the result of `awaitAll()` on `Deferred<Unit>`), which is meaningless, and once failures are isolated per #1 there is no channel to surface them.

**Why it matters:** Silently swallowing failures is worse than the current fail-fast behaviour. A batch sync that returns "ok" while some users failed is a data-integrity problem.

**Required instead:** Return per-user results (as above) or throw an aggregate after completion. This is really part of the fix for #1 rather than a separate change, but I'd want the signature settled explicitly rather than falling out of `awaitAll()`.

### 3. `Sync.kt` line 5 — unbounded fan-out (flag, not block)
**What's wrong:** One coroutine per user with no concurrency limit. For a large tenant this fires every `sync` at once.

**Why it matters:** Depending on what `sync` does (HTTP calls, DB writes), this can trip rate limits or exhaust a connection pool, which then manifests as a wave of failures unrelated to any individual user's correctness.

**Required instead:** Either a `Semaphore(n)` around `sync(user)`, or a comment/justification that the caller already bounds batch size. I'd accept either; I mainly want it to be a deliberate decision.
