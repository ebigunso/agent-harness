**Verdict: block.**

**1. `src/service.cpp`, `Service::process` — unbounded retry loop turns a recoverable failure into a permanent hang.**

The reviewer notes establish that validated input can legitimately require more memory than the fixed worker limit, and that identical retries cannot reduce the allocation. For such an input, `allocate_and_run` throws `bad_alloc` deterministically every time, so `for (;;) { try … catch { continue; } }` never exits. Because this service has a single dispatch thread, that thread now spins at 100% CPU forever on one request and every subsequent request is starved. This is precisely the "wedged service worker" the task was meant to eliminate — the change makes the failure mode strictly worse (a crash or propagated exception at least surfaced the problem; this silently pins the process).

Even for a hypothetical transient failure, there is no bound, no backoff, and no yield, so the loop is a busy-wait rather than a retry policy.

Required instead: treat `bad_alloc` from `allocate_and_run` as a per-request failure, not a condition to wait out. Catch it once, and return an error `Result` (e.g. resource-exhausted / request-too-large) so the caller can reject that input and the dispatch thread immediately moves on to the next request. Since the notes confirm the engine releases partial resources on throw and has no external side effects before success, this is safe with no cleanup work. If there is a real, documented transient allocation-failure case, it needs a small fixed retry count with a sleep/backoff — but the over-limit case must still terminate with an error, never a retry.

**2. Same location — the failure is swallowed with no observability.**

The catch block discards the exception without logging or a metric. Combined with (1), an operator sees a worker at 100% CPU serving nothing and has no log line explaining why. Require: log (rate-limited) and/or count the rejection when returning the error result.

**3. Commit message — "retry allocation until successful" is factually wrong.**

For over-limit inputs there is no "successful"; the message documents behavior the change cannot deliver. Reword to describe the actual behavior once fixed (e.g. "reject request on allocation failure instead of propagating").
