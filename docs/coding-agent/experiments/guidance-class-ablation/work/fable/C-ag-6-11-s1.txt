**Findings**

1. **`state.cpp`, `update()` — exporter is called while `state_mutex` is held.**
   `export_metrics(count)` runs inside the `lock_guard` scope. The reviewer notes say the exporter is an optional network integration that may block. Any stall in the exporter (slow endpoint, TCP connect timeout, retry loop inside the callback) holds `state_mutex` for the duration, so every other writer that takes the same mutex blocks behind it. A failure in an optional side channel becomes a stall of the core state path — the opposite of containment. It also creates a reentrancy/deadlock hazard: if the exporter (or anything it calls) ever touches state that acquires `state_mutex`, it deadlocks on a non-recursive mutex.
   **Require:** copy the value under the lock, release the lock, then export:
   ```cpp
   void update(const std::function<void(unsigned)>& export_metrics) {
       unsigned snapshot;
       {
           std::lock_guard<std::mutex> guard(state_mutex);
           snapshot = ++count;
       }
       export_metrics(snapshot);
   }
   ```
   This matches the stated rule "Lock must protect state, not wait for optional external work." Whether the exporter should additionally be bounded (timeout / async hand-off / queue with drop policy) is the exporter's responsibility, but it must not be given the state lock to block on.

2. **`state.cpp`, `update()` — exporter exceptions are not contained.**
   Since the exporter is optional, an exception thrown from `export_metrics` propagates out of `update()`. With the current ordering, the increment has already happened, so callers see a failure for an update that actually succeeded, and the caller now has to know about the exporter's failure modes. The task is "export metrics when state updates", not "fail state updates when export fails".
   **Require:** decide explicitly and document it. For an optional integration the reasonable contract is that export failures do not fail the state update — wrap the (post-lock) call in a `try`/`catch` that logs/counts the failure and continues, rather than letting it escape. If the team instead wants failures surfaced, that should be a deliberate, documented choice, not the accidental result of the current code.

3. **`state.cpp`, `update()` — no guard for an empty `std::function`.**
   "Exporter is optional" suggests the callback may be unset. Invoking an empty `std::function` throws `std::bad_function_call`. Combined with (2), an unconfigured exporter turns every `update()` into a throw after the state has already been mutated.
   **Require:** `if (export_metrics) export_metrics(snapshot);` (or make the API non-optional and document that). Minor if the call sites guarantee a valid callable, but the notes say it is optional, so it should be handled here.

**Not flagged:** unsigned wraparound is stated to be out of scope; the mutex correctly protects the increment itself; the `std::function` by-const-ref signature is fine.

**Verdict:** block on (1); (2) and (3) should be resolved in the same change since they are all about the same contract — the exporter is optional external work and must not be able to stall, deadlock, or fail the state update.
