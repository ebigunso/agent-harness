**Cause — script bug, not a workspace/environment problem.**

`ConvertFrom-Json` in PowerShell 7 unrolls a top‑level JSON array onto the pipeline by default. For `'[]'` that produces zero objects, so `$parsed` is assigned `$null` (exactly what stdout shows: `parsed type=<null>`), and the `-isnot [array]` guard throws. The same defect would also misfire on a singleton: `'[1]'` would assign the scalar `1`, not a one‑element array. The JSON is valid, the runtime is fine, and execution policy is irrelevant here — line 10 is doing what it was told with a value the parser call mangled.

**Smallest safe remediation**

Tell the cmdlet to preserve the array shape:

```powershell
$parsed = $raw | ConvertFrom-Json -NoEnumerate
```

(One flag, no other logic changes. `-NoEnumerate` exists in PS 7.x; it returns `[]` as an empty `System.Object[]`, `[1]` as a one‑element `Object[]`, and still returns scalars for scalar wire values, so the existing `-isnot [array]` check now matches the stated contract.)

**Confirmation**

1. Re‑run `pwsh -NoProfile -File probes/cardinality.ps1` — expect exit code 0 and `parsed type=System.Object[]` with nothing on stderr.
2. Quick contract sweep in the same shell to make sure the fix generalizes and didn't over‑accept:
   ```powershell
   '[]','[1]','[1,2]' | % { ($_ | ConvertFrom-Json -NoEnumerate) -is [array] }   # True True True
   '5','"x"','{"a":1}' | % { ($_ | ConvertFrom-Json -NoEnumerate) -is [array] }  # False False False
   ```
   Empty/singleton/multi arrays pass; scalars (and, incidentally, objects) are rejected, which is the behavior the checker is meant to enforce.
