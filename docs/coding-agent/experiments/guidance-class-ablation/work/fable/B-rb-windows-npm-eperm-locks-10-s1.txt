**Cause**

Not a workspace/config problem. `package.json`/lockfile are in sync, the registry is reachable, and the probe file next to the module proves there's no ACL issue. The `EPERM … unlink better_sqlite3.node` (errno -4048) is a Windows file-in-use lock: `Code.exe` PID 4110 — the editor's extension/test host — has `C:\work\npm-lock\node_modules\better-sqlite3\build\Release\better_sqlite3.node` mapped as a loaded module (`tasklist /m` shows it, and the test-host log names the same PID and path). Windows won't let npm delete a mapped native image, so `npm ci`'s node_modules teardown fails on the first locked file.

**Smallest safe remediation (in order; stop as soon as the lock is gone)**

1. Release the handle from inside the editor rather than killing it: stop the editor-integrated test run / test runner, then restart the extension host (in VS Code: `Developer: Reload Window`, or `Developer: Restart Extension Host`). That unloads the addon without losing the editor session.
2. Only if the module is still listed afterward, kill the specific host process:
   `taskkill /PID 4110 /F`
   (This is `Code.exe`, so expect the editor window/extension host to go down — that's why it's the fallback, not the first move.)
3. Re-run `npm ci`.

Don't chmod, delete node_modules by hand while the process is alive, or run as admin — none of those address a mapped-image lock and the last two can leave a half-torn-down tree.

**Confirmation**

- `tasklist /m better_sqlite3.node` → `INFO: No tasks are running which match the specified criteria.` (and `tasklist | findstr node` shows nothing stray for this repo).
- `npm ci` exits 0 with no `EPERM`/`EBUSY` lines.
- `node -e "require('better-sqlite3'); console.log('ok')"` prints `ok` from the CLI Node 20.18.0.

**One follow-up caveat**

The previous binary was an *editor-runtime source build* (compiled against the extension host's Electron ABI). `npm ci` will replace it with one built/prebuilt for Node 20.18.0. The CLI will be happy, but the editor test integration will likely fail to load the addon again (ABI mismatch) until it's rebuilt for Electron (e.g. `@electron/rebuild` or the extension's own rebuild step). That's expected after this fix, not a regression of it — but keep the two builds separate (e.g. a distinct install for the extension host) or you'll be back in this loop every time the test host is running during `npm ci`.
