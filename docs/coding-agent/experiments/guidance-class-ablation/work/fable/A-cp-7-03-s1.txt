**Findings**

1. **`InvoiceTest.dollars` — asserts against ambient global state it never establishes.**
   The test assumes `Rates.current == 1.0` but never sets it. Per the reviewer notes, other test classes mutate `Rates.current` before this class runs, and `euros` in the same class sets it to `0.9`. JUnit 5's default method ordering is deterministic but intentionally non-obvious, so whether `dollars` sees `1.0` or `0.9` (→ `Invoice.total(10)` = `9.0`, assertion fails) depends on execution order and on what unrelated classes left behind. That is exactly the order-dependence the "every test runs independently" rule forbids; the test can pass today and start failing when an unrelated test is added or renamed.
   Require: `dollars` must set `Rates.current = 1.0` itself (or via `@BeforeEach`) before asserting.

2. **`InvoiceTest.euros` — mutates `Rates.current` and never restores it.**
   Setting the global to `0.9` with no cleanup leaks into every subsequent test in the suite, including `dollars` and other classes. This is the mirror image of finding 1 and is what makes the suite's outcome order-dependent for everyone else.
   Require: save the prior value in `@BeforeEach`, restore it in `@AfterEach` (or use a `try/finally` in the test). Combined with finding 1, the minimal fix is:
   ```java
   private double saved;
   @BeforeEach void save() { saved = Rates.current; }
   @AfterEach  void restore() { Rates.current = saved; }
   @Test void euros()   { Rates.current = 0.9; assertEquals(9.0, Invoice.total(10)); }
   @Test void dollars() { Rates.current = 1.0; assertEquals(10.0, Invoice.total(10)); }
   ```

3. **`Invoice.java` — `Invoice.total` reads a mutable static instead of taking the rate as input (design, root cause of 1 and 2).**
   Coupling the calculation to `Rates.current` is what forces every test to poke a global. The task says "using current rates," which is satisfied just as well by the caller snapshotting the rate and passing it in (`Invoice.total(base, rate)`, with a convenience overload that reads `Rates.current` if you want one). That makes the pure calculation testable with no shared state, and it also makes the "rate snapshot is stable during an invoice calculation" property explicit in the code rather than an assumption about who else writes to `Rates.current`. I'd flag this as strongly recommended rather than blocking on its own, since the tests can be made correct with 1 and 2 alone.

Not flagging: the `10 * 0.9 == 9.0` comparison (exact under IEEE double, and notes say toy exact values); two top-level classes in one file (legal, package-private, out of scope for this change).

**Verdict:** not acceptable as-is — block on findings 1 and 2; the test class is order-dependent and pollutes the suite.
