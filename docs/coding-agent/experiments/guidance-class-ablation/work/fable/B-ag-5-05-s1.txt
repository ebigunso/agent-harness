**Verdict: block.** The change introduces two write paths to the same field with different conversion rules, which is exactly the "conflicting write paths without ownership clarity" anti-pattern.

## Findings

### 1. `balance.ts:2–3` — Two write paths, two rounding rules for the same stored value
`api` uses `Math.round`, `imported` uses `Math.trunc`. For the reviewer's own example, `1.239` becomes `124` via the API and `123` via import. The same customer, same real-world balance, lands on different integer cents depending on which door it came through. That makes `balanceCents` unreconcilable: reports, refunds, and audits can't tell whether a 1-cent discrepancy is a real transaction or an artifact of entry path.

**Require:** a single authoritative `dollarsToCents(dollars: number): number` that owns the conversion policy, and have both `api` and `imported` call it. Pick one rule (nearest, with a documented tie-breaking behavior) and record it in the function's doc comment. Nothing else in the codebase should compute `dollars*100`.

### 2. `balance.ts:2–3` — `dollars*100` is not a reliable cents conversion under either rule
Float multiplication drifts: `0.29*100` is `28.999999999999996`, `1.005*100` is `100.49999999999999`. With `Math.trunc` this silently drops a cent (`0.29` → `28`); with `Math.round` it gets ties wrong (`1.005` → `100`). Since inputs like `1.239` are explicitly allowed, sub-cent precision is in scope and this will produce wrong balances, not just inconsistent ones. Truncation is the worse offender because it amplifies every negative float error into a lost cent.

**Require:** the shared conversion from #1 must be robust to this — e.g. `Math.round(dollars * 100 + Number.EPSILON * Math.sign(dollars))`, or parse the decimal string representation and shift the decimal point, whichever the team prefers. Add unit tests for `0.29`, `1.005`, `1.239`, `0`, `1000`, and verify both entry points produce identical output for the same input.

### 3. `balance.ts:2–3` — Input invariants are enforced only in caller paths
The notes say dollars are validated finite, nonnegative, `<= 1000` — but not here. Both functions accept any `number`, so `NaN`, `Infinity`, or a negative value from an unvalidated future caller writes directly into `balanceCents` with no check. This is the "invariants enforced only in optional caller paths" anti-pattern.

**Require:** the shared conversion (or a `setBalance` that wraps it) should assert the invariant at this boundary — `Number.isFinite`, `>= 0`, `<= 1000` — and throw. Cheap, and it guarantees the stored integer is always well-formed regardless of who calls in.

## Not raised
- Concurrency: per notes, single-process serialized writes; nothing to add.
- In-place mutation of `customer`: acceptable for this scope; not blocking.
