**Verdict: block.** The change replaces a behavioral test with an implementation-coupled test and drops all output assertions. Net effect is a maintainability regression and a real loss of protection.

## Findings

### 1. `test_calc.py` — `test_total` no longer verifies the result of `calculate`
**What's wrong:** The two output assertions (`calculate(100) == 110`, `calculate(0) == 0`) were deleted and replaced solely with a check on `tracker.mock_calls`. The return value of `calc.calculate(100)` is discarded.

**Why it matters:** `calculate` is the public, pure API; its only contract is the number it returns. With this test, `return _base(cents) - _tax(cents)`, `return _base(cents)` (after calling `_tax` for side effects), or `_base(cents) + _tax(cents) + 1` all pass green, because the same helper calls still occur. The test name is `test_total` and it asserts nothing about the total. This is worse than having no test, because it creates false confidence.

**Required instead:** Restore the value assertions on the public function:
```python
def test_total():
    assert calc.calculate(100) == 110
    assert calc.calculate(0) == 0
```
Keep the pre-existing cases at minimum; the `0` edge case in particular was silently dropped.

### 2. `test_calc.py` — asserting private helper call order over-specifies the implementation
**What's wrong:** The test pins that `_base` is called before `_tax`, each exactly once, with `100`, via `patch.object` on underscore-prefixed internals.

**Why it matters:** `_base` and `_tax` are independent computations; their relative order is not part of any contract. Legitimate refactors — inlining the helpers, evaluating `_tax` first, caching, computing both in a single helper — would all break this test while leaving behavior identical. That is the definition of debt amplification: every future touch to `calculate` now requires editing the test, and the test's failures carry no signal about correctness. Reaching into `_`-prefixed names from a test also erases the boundary the underscore was meant to establish. Per the "Leave the System Easier to Change" check, this is a clear degradation.

**Required instead:** Test through the public interface only. If the extraction genuinely warrants coverage of the helpers, test their *outputs* directly (`assert calc._tax(100) == 10`, `assert calc._tax(9) == 0`) rather than their invocation sequence — and even that is optional given how trivial they are. Remove the `Mock`/`patch`/`call` machinery entirely; it adds ~6 lines of setup to test a two-line pure function.

### 3. Commit message / task framing does not match the change
**What's wrong:** "Update calculation tests after helper extraction" implies a mechanical adjustment. The actual change alters *what* is tested (interaction instead of result) and reduces coverage (drops the `0` case). Nothing in the extraction required any test change at all — the original two assertions would still pass unchanged against the new `calc.py`.

**Why it matters:** A reviewer skimming by message would approve a coverage regression. If the author intended a deliberate shift to interaction testing, that decision needs to be stated and justified; here it isn't, and it wouldn't be justifiable for a pure function.

**Required instead:** Either leave `test_calc.py` untouched (the correct outcome here), or, if adding helper tests, describe that explicitly in the message.

## Summary of required changes
- Reinstate `assert calculate(100) == 110` and `assert calculate(0) == 0`.
- Delete the `patch.object`/`Mock`/`call` sequence assertion.
- Do not assert on private helper invocation order; if helpers need tests, assert their return values.
