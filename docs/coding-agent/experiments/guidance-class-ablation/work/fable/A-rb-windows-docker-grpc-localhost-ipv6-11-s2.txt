**Cause**

This is an address-selection/forwarding problem on the host, not a bug in the probe or the service.

- `localhost` resolves to `::1` first, and the Dart gRPC channel uses the first address: `[::1]:50051`.
- On that endpoint the TCP handshake completes (Docker Desktop's host port proxy is listening on IPv6), but nothing is actually relayed to the h2c service — no HTTP/2 SETTINGS/response headers ever come back, so the client sits until the 2 s deadline and the probe maps it to exit 2 / `DEADLINE_EXCEEDED`. The service interceptor log confirms the request never reached the handler.
- The controlled comparison (only the target changed to `127.0.0.1:50051`) succeeds immediately with `pong 1 / pong 2` and `invoked=true completed=true`. Same server, container, payload, deadline — so the service, the bidi handler, and the probe are fine; the IPv6 loopback path through Docker's port publishing is a black hole (accepts, doesn't forward — typical when the container-side process is bound to IPv4 only / the WSL2 forwarding isn't wired for `::1`).
- The `curl` success on `localhost:50080` doesn't contradict this: curl tries addresses in sequence and falls back, whereas the grpc-dart channel has no fallback and the probe explicitly does not retry with another address.

**Smallest safe remediation**

Use the IPv4 literal instead of the name for this target:

```powershell
dart run probes/bidi.dart --target 127.0.0.1:50051 --timeout 2
```

That's a one-argument change with no effect on the service, container, or probe code. Don't "fix" it by raising `--timeout` (the call would never complete) or by changing the service's port publishing under a diagnosis you haven't confirmed.

If you want the name `localhost` to work later, the proper follow-up is to make the service inside the container bind dual-stack (`::`/`[::]:50051`) or otherwise get Docker Desktop's IPv6 proxy forwarding to the container — but that's a separate change, not the minimal remediation.

**Confirmation**

1. Re-run the command above. Expect exit code 0, stdout `pong 1` / `pong 2`, empty stderr.
2. Check the service interceptor log for a new line `probe method="bidirectional Echo" transport=h2c invoked=true completed=true` correlating with that run.
3. (Optional, to prove the asymmetry rather than assume it) run the same probe once with `--target [::1]:50051 --timeout 2` — expect the original exit 2 / `DEADLINE_EXCEEDED` with no interceptor log entry — and, if you have it, `grpcurl -plaintext 127.0.0.1:50051 list` vs `grpcurl -plaintext [::1]:50051 list` should show the same success/hang split.

**Is it a workspace problem?**

Partly. Nothing in `C:/work/grpc-local` is broken — files, deps, build, and the service all check out. The failure comes from the host networking layer (IPv6 loopback → Docker Desktop port forwarding) combined with the probe deliberately taking the first resolved address with no fallback. Treat it as an environment/target-address issue, not a code defect.
