**Verdict: block.** The change does not correctly implement "record approval audit events" — as written it records approvals that may never happen, and it puts the policy in the wrong layer.

## Findings

### 1. `ApprovalDao.update` — audit event emitted before commit (correctness, blocking)
**Location:** `ApprovalDao.scala`, line `if (changed == 1 && status == "approved") audit(s"Approved:$id")`

**What's wrong:** The notes state the caller owns the transaction (`autoCommit=false`) and may roll back after this call, and that an `Approved` event means *committed* business approval. The DAO fires `audit(...)` immediately after `executeUpdate()`, i.e. while the row change is still uncommitted. `audit` is an independent sink, so it cannot participate in the rollback.

**Why it matters:** Any rollback after `update` returns leaves a durable `Approved:<id>` audit record for an order that is *not* approved in the database. That is a false audit trail — the worst failure mode for an audit feature. It is also non-obvious to the caller, since nothing in the signature says "side effect escapes the transaction."

**Required instead:** Do not emit the event from inside the transaction. The component that owns the commit must emit it after `commit()` succeeds (or use a transactional outbox / post-commit hook if the codebase has one). The DAO should not receive an `audit` callback at all.

### 2. `ApprovalDao.update` — business policy in the data-access layer (placement, blocking)
**Location:** `ApprovalDao.scala`, the `status == "approved"` check, the `audit: String => Unit` parameter, and the `s"Approved:$id"` event format.

**What's wrong:** Three pieces of business/application policy live in a DAO:
- the rule "a status transition to `approved` is an auditable business approval";
- the decision to publish an event and where it goes (`audit` sink injected into data access);
- the wire format of the audit event (`"Approved:$id"` string).

This is exactly the "policy in data access" the guidance prohibits. The DAO's job is to execute the UPDATE and report what happened; deciding what that *means* and who needs to know is the application/domain layer's job. The change also adds no service/app-layer counterpart and gives no explanation of why placement here is correct.

**Why it matters:** Beyond the layering rule, this is what *causes* finding 1 — the DAO has no way to know whether the transaction will commit, so it is structurally the wrong place for the event. It also makes the rule untestable without JDBC and forces every DAO caller to thread an audit sink through.

**Required instead:**
- `ApprovalDao.update(db, id, status)` does only the UPDATE and returns the affected row count (or `Boolean`).
- An application-layer approval service (the transaction owner) calls the DAO, commits, and *then* records the audit event, deciding based on its own domain knowledge (e.g. a typed status/event rather than the `"approved"` magic string) that an approval occurred.
- The plan/commit message should name the service-layer owner receiving the moved logic and state why the DAO does not emit events.

### 3. `ApprovalDao.update` — result of the update is discarded (minor, would flag)
**Location:** return type `Unit`; `changed == 1` used only to gate the audit.

**What's wrong:** If `executeUpdate()` returns 0 (no such `id`) or >1 (unexpected), the method silently does nothing and the caller has no signal. Once the audit callback is removed per findings 1–2, the DAO has no reason to swallow this.

**Required instead:** Return `changed` (or `changed == 1`) so the app layer can distinguish "approved," "not found," and "unexpected multi-row update," and decide whether to commit and audit.

---

Findings 1 and 2 are the same root problem: the audit decision is placed somewhere that cannot know whether the approval is real. Fixing placement fixes the bug.
