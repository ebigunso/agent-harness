**Findings**

1. **`charge.js` line 5 — `Idempotency-Key: randomUUID()` is evaluated inside the retry loop.**
   Every retry sends a *new* key. The reviewer notes state explicitly that a timeout can follow a committed charge. With a fresh key per attempt, the server sees each retry as a distinct charge, so a timeout on a committed request produces a duplicate 100-cent charge (and a triple charge on two timeouts, etc.). This defeats the entire purpose of the idempotency key and is a money-losing bug for the customer. **Block.**
   Required: generate the key once per `charge()` invocation, before the loop, and reuse it on every attempt:
   ```js
   export async function charge() {
     const idempotencyKey = randomUUID();
     for (;;) {
       ...headers: {"Idempotency-Key": idempotencyKey}...
   ```
   A test that simulates a timeout followed by success and asserts the same key was sent on both attempts should accompany the fix.

2. **`charge.js` line 3 — `for (;;)` with no attempt cap or backoff.**
   If the payments host is degraded such that every request exceeds 1s, this loop retries forever with zero delay: the caller never returns or fails, and the client hammers an already-struggling payment service at ~1 req/s per pending charge. Retrying timeouts is the goal, but "retry" needs a bound. **Flag (would require before merge).**
   Required: a maximum attempt count (e.g. 3–5) after which the last `TimeoutError` is rethrown so the caller learns the outcome is unknown, ideally with a short backoff between attempts.

No other issues: the `error.name !== "TimeoutError"` check is correct for Node 24's `fetch` + `AbortSignal.timeout` (the rejection reason is a `DOMException` named `TimeoutError`), non-OK statuses correctly surface without retry, and the fixed body/amount is per the task framing.
