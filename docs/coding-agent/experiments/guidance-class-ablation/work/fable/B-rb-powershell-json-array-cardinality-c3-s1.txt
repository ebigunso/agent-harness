**Cause**

This is not a workspace, environment, or pipeline-unrolling problem. The script itself feeds `ConvertFrom-Json` invalid JSON: the hard-coded literal `'[1,'` is truncated — it has a trailing comma and no closing `]` (and no second value). `ConvertFrom-Json` correctly rejects it at the syntax stage (`Invalid array passed in, extra trailing ','`), `$ErrorActionPreference = 'Stop'` turns that into a terminating error, and the script exits 1 on line 5.

The loaded reference note (one-element arrays looking scalar after `ConvertFrom-Json`) does not apply here: that issue only arises *after* a successful parse, and this parse never succeeds. Nothing in Windows PowerShell 5.1, the cwd, or the file system is at fault, and no files were modified.

**Smallest safe remediation**

Fix the payload so it is well-formed JSON. If `[1]` was the intended one-element test case, change line 3 to:

```powershell
$raw = '[1]'
```

If `$raw` was meant to represent data from an upstream source (file, HTTP response, etc.), then the truncation happened there and the fix belongs at the source — the script should not be changed to "tolerate" a cut-off payload. Do not add `-NoEnumerate` or any array-type workaround; that's a different problem and `-NoEnumerate` isn't available in 5.1 anyway.

**Confirmation**

Re-run the same command:

```
powershell.exe -NoProfile -File probes/parse.ps1
```

Expected: exit code 0, stdout shows `raw=[1]`, and stderr is empty. To make the probe self-checking, append a line like `Write-Output ('count=' + @($parsed).Count)` and expect `count=1`.

One caveat for the follow-on work: once this parses, `$parsed -is [array]` will report `$false` for `[1]` because of pipeline unrolling — that is the behaviour described in the reference note and is expected, not a failure. If the probe needs to assert array framing under 5.1, check the raw string (`$raw.Trim().StartsWith('[') -and $raw.Trim().EndsWith(']')`) rather than the parsed object's type.
