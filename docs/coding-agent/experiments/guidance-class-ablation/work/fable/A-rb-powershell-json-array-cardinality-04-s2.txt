**Cause — script defect, not a workspace/environment problem.**

`$parsed = $raw | ConvertFrom-Json` loses the array. In PowerShell 7, `ConvertFrom-Json` enumerates a top-level JSON array onto the pipeline by default; a one-element array `[{"id":7}]` therefore emits a single `PSCustomObject`, and assigning a single pipeline item to a variable yields that scalar, not an `Object[]`. The stdout line `parsed type=System.Management.Automation.PSCustomObject` confirms exactly that. The same bug would turn `[]` into `$null` (also wrongly rejected), while 2+ element arrays would happen to pass — so the probe violates the stated contract (empty and singleton arrays must be accepted). Runtime, execution policy, cwd, and the JSON itself are all fine.

**Smallest safe remediation** — keep the array intact at the parse site (line 5):

```powershell
$parsed = $raw | ConvertFrom-Json -NoEnumerate
```

`-NoEnumerate` makes the cmdlet emit the whole array as one object, so `$parsed` is `System.Object[]` for empty, singleton, and multi-element input, while a scalar wire value (`7`, `"x"`, `null`) still parses to a non-array and correctly hits the `throw`. Nothing else in the script needs to change; don't weaken the `-isnot [array]` assertion or wrap with `@(...)`, since `@()` would also mask scalars as arrays and break the reject-scalar requirement.

**Confirmation**

2. Spot-check the contract edges in the same shell:

