**Cause: expired/invalid registry credentials, not a workspace problem.**

The error is `E401` — the configured private registry answered `401 Unauthorized` with `WWW-Authenticate: Bearer`. That means npm reached the right registry (scope/URL in `.npmrc` is correct) and the server rejected the bearer token. Everything in the workspace itself checks out: package.json and lockfile agree, cwd and cache are writable, and no native-addon unlink was attempted (`tasklist /m sharp-win32-x64.node` finds nothing). The EPERM/EBUSY lock runbook above does not apply here — do **not** kill any processes; that would be treating a symptom that isn't present.

**Smallest safe remediation**

Re-authenticate against the scoped registry (not the public one):

```powershell
npm login --scope=@<your-scope> --registry=https://<private-registry>/
```

or, if your org issues tokens out-of-band, refresh the `//<private-registry>/:_authToken=` entry in the user-level `~/.npmrc` (never commit it to the project `.npmrc`). If this is CI, rotate/re-inject the `NPM_TOKEN` secret — a 401 from a freshly-minted token usually means it was issued for the wrong scope/registry or lacks read permission.

**Confirmation**

1. `npm whoami --registry=https://<private-registry>/` returns your username instead of E401.
2. Re-run `npm install` — expect exit code 0 and no `E401` in stderr.
3. Optionally, `npm view @<scope>/<some-package> version` succeeds, proving scoped reads work.

If `npm whoami` still 401s after a fresh login, the problem is on the registry/identity side (token revoked, account deprovisioned, wrong tenant), and you'll need the registry admin — nothing further to fix in `C:/work/npm-lock`.
