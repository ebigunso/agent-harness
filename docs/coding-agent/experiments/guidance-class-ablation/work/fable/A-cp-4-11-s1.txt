**Findings**

1. **`preview.cpp`, `format_preview` — preview mutates the shared ID counter.**
   - *What's wrong:* `format_preview` now executes `next_id++`, the same increment `allocate_id` performs. Every call to render a preview consumes an ID from the allocator's sequence.
   - *Why it matters:* The reviewer notes state previews are expected to be observational. This change makes rendering a preview a side-effecting operation: (a) it is no longer idempotent — calling `format_preview("x")` twice yields `x:1` then `x:2` with no allocation in between; (b) it silently changes the result of the next `allocate_id()`, so any code that previews before allocating will get a different ID than it would have without the preview (and the "hint" shown in the preview will not match the ID actually allocated afterward — the preview shows `N` but the subsequent allocation returns `N+1`); (c) previews rendered in loops, re-rendered UI, logging, etc. will burn through the sequence for no reason. Uniqueness is preserved, so this won't show up as a duplicate-ID bug — it will show up as confusing, hard-to-trace ID gaps and mismatched hints, which is worse in practice.
   - *Require instead:* Read the counter without modifying it: `return name + ":" + std::to_string(next_id);`. This makes the hint accurately reflect the ID that *will* be allocated next and keeps `format_preview` pure. If the intent was genuinely to reserve an ID at preview time, that should be a separate explicit API (e.g., preview takes an already-allocated `id` parameter) and the commit message/notes should say so — a function named `format_preview` taking a `const std::string&` gives no indication that it allocates.

No other issues: overflow and thread safety are out of scope per the notes, and the string concatenation itself is fine.
