**Verdict: block.**

1. **`parser.cpp` — `last_output = &output;` in `parse`, dereferenced in `preview()`: dangling pointer / undefined behavior.**
   The stated contract is that the caller owns `output` and may destroy it immediately after `parse` returns. Storing its address and reading through it later means `preview()` reads freed or reused memory as soon as any caller does the obvious thing (e.g. `std::string s; parse(in, s);` inside a function that then returns). This isn't a corner case — it's the *default* usage pattern the contract permits. It also silently breaks if the caller `std::move`s or reassigns the string. The commit turns a borrowed reference into an ownership assumption without adding any borrowing/lifetime contract, and none should be added since it would be a breaking change to every existing caller.
   **Require:** cache by value: `static std::string last_output;` (or `std::optional<std::string>`), assigned `last_output = output;` (or `= input` — same thing here) inside `parse`, and `preview()` returns a copy. The extra copy is the correct price for a stable boundary.

2. **`parser.cpp` — `preview()` has an ambiguous "nothing parsed yet" signal.**
   Returning `std::string{}` when `last_output == nullptr` is indistinguishable from the case where the last successfully parsed token was the empty string. The interface now has two states collapsed into one value, so a consumer cannot tell "no prior parse" from "prior parse yielded empty". This is exactly an implicit/ambiguous success contract.
   **Require:** either return `std::optional<std::string>` (`std::nullopt` when nothing has been parsed), or document explicitly that empty is the sentinel and that empty tokens are never distinguishable — and only choose the latter if empty input is genuinely impossible by the parser's contract. Prefer the optional.

3. **`parser.cpp` — cache update is unconditional on the success path and unspecified on the failure path.**
   `parse` returns `bool`, so a failing parse is part of the interface even though the current body always succeeds. The diff writes `last_output` before returning, with no statement of what `preview()` should show after a failed parse (stale previous value? cleared? untouched?). Any future `return false;` path added to `parse` will leave `preview()` with an unspecified relationship to the last call.
   **Require:** decide and encode it: update the cache only on the success return (`if (ok) last_output = output;`), and state in the declaration comment that `preview()` reflects the most recent *successful* parse.

4. **`parser.cpp` — new mutable global with no declaration exposure for the new public function.**
   `last_output` is a non-`static`, externally-linked global (name collision risk in a larger link, and not thread-safe: concurrent `parse` calls or `parse`/`preview` races are a data race). `preview()` is a new public entry point but the diff doesn't touch the header, so consumers either can't see it or must forward-declare it themselves.
   **Require:** make the cache `static` (internal linkage) or wrap `parse`/`preview` in a class/namespace so the coupling is explicit; declare `preview()` in `parser.h` alongside `parse` with its contract (returns last successful parse, no thread-safety guarantee — or add a mutex if callers are concurrent). Impact classification for the header change: **additive**, no migration required.

Findings 1 and 2 are blocking; 3 and 4 I'd flag and expect fixed in the same change since they're cheap and the interface is being introduced now.
