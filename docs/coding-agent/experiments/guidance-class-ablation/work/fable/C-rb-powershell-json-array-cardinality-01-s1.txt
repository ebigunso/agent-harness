## Cause

This is a **script bug, not a workspace problem**. The raw JSON `[7]` is valid, the file system is untouched, and the runtime behaves correctly.

The failure is in line 5:

```powershell
$parsed = $raw | ConvertFrom-Json
```

Piping through `ConvertFrom-Json` makes PowerShell's pipeline **unroll** the result. A single-element array `[7]` is enumerated down to its one member, so `$parsed` is the scalar `System.Int64` `7` (exactly what stdout shows: `parsed type=System.Int64`). The assertion `$parsed -isnot [array]` is therefore true and throws.

Critically, `-is [array]` on a post-pipeline value **cannot prove wire framing** anyway: the pipeline has already destroyed the array-ness of any 0- or 1-element array, so this check will wrongly reject the legitimate empty (`[]`) and singleton (`[7]`) cases the contract is supposed to accept.

## Smallest safe remediation

You are on PowerShell 7.4.6, so `-NoEnumerate` is available. Stop piping and stop the unroll by using call syntax:

```powershell
$parsed = ConvertFrom-Json -InputObject $raw -NoEnumerate
```

Leave the rest untouched — the downstream `$parsed -isnot [array]` never re-pipes `$parsed`, so the preserved array survives to the assertion.

(If this had to run on Windows PowerShell 5.1, which lacks `-NoEnumerate`, the correct fallback is to assert on the **raw** string instead: trimmed `$raw` starts with `[` and ends with `]`. That is a framing check, not a JSON syntax validator, which matches the contract.)

## How I'd confirm

   - `[7]` → array, accepted (the previously broken singleton case)

If all four match the contract (accept 0/1/many-element arrays, reject scalars), the fix is verified.
