## Cause

This is a workspace (script) problem, not a runtime/environment fault. The JSON is valid; the bug is a PowerShell semantics issue.

`ConvertFrom-Json` **enumerates** a top-level JSON array onto the pipeline element-by-element. When the result is captured with `$parsed = $raw | ConvertFrom-Json`:

- `[7]` → a single element `7` is emitted, so `$parsed` becomes a scalar `System.Int64` (exactly what stdout shows: `parsed type=System.Int64`).
- `[7,8]` → two elements are emitted, so `$parsed` collects back into an `Object[]`.

So the `-isnot [array]` check passes for multi-element arrays but **fails for the singleton `[7]`**, throwing "Expected JSON array". The contract (accept empty/singleton/multiple arrays, reject scalars) is not met because single-element arrays get unwrapped to scalars.

## Smallest safe remediation

Stop the enumeration by adding `-NoEnumerate` (PowerShell 6+, available on your 7.4.6). Change line 5:

```powershell
$parsed = $raw | ConvertFrom-Json -NoEnumerate
```

This preserves the JSON array as an array object regardless of element count. No other logic changes; the checker still writes no files.

## How to confirm

1. Re-run the command:
   ```
   pwsh -NoProfile -File probes/cardinality.ps1
   ```
   Expect exit code `0` and `parsed type=System.Object[]` (no thrown error).

2. Verify the full contract with quick one-liners:
   ```powershell
   ('[]'    | ConvertFrom-Json -NoEnumerate) -is [array]   # True  (empty accepted)
   ('[7]'   | ConvertFrom-Json -NoEnumerate) -is [array]   # True  (singleton accepted)
   ('[7,8]' | ConvertFrom-Json -NoEnumerate) -is [array]   # True  (multiple accepted)
   ('7'     | ConvertFrom-Json -NoEnumerate) -is [array]   # False (scalar rejected)
   ```
   A scalar `7` stays `Int64` and still trips the `throw`, which is the desired rejection.

Confirm exit code explicitly with `$LASTEXITCODE` after the script run to ensure `0`.
