**Findings**

1. **`lib/customers.rb`, `find_customer` — `rescue DatabaseUnavailable; nil` collapses an outage into "not found".**
   The contract (per the reviewer notes and `find_by_email`'s behavior) reserves `nil` for a genuinely absent row. After this change, a caller cannot distinguish "the customer doesn't exist" from "we couldn't check." That is exactly the ambiguous state the guideline warns against: the failure is not made explicit at the boundary, it is erased at the boundary.
   *Concrete consequence:* `get_or_create(email)` does `customer || database.create_customer(email)`. During a replica outage the read fails, `find_customer` returns `nil`, and the write primary — which is still up — happily inserts a **duplicate customer** for an email that already exists. The change converts a transient, loud infrastructure error into a silent data-integrity bug that persists after the outage ends. (This is not the create race the notes exclude; it happens with fully serialized calls.)
   *Required instead:* do not map `DatabaseUnavailable` to `nil`. Either let it propagate, or rescue-and-reraise as a domain error that carries context (e.g. `raise CustomerLookupUnavailable, "customer lookup failed for #{email}"` with `cause` preserved). `get_or_create` must not fall through to `create_customer` unless the lookup positively returned "not found". If a degraded read path is genuinely wanted, it needs a distinct signal (a result object / `:unavailable`), never the same value as "absent".

2. **Same location — the failure is swallowed with no observability.**
   Nothing is logged, counted, or annotated when the rescue fires. An operator seeing a spike in duplicate accounts (or in "not found" results) would have no signal tying it to the replica outage. Fallbacks are supposed to be observable and bounded; this one is invisible and unbounded (it will silently create records for the entire duration of the outage).
   *Required instead:* if any rescue remains at this boundary, it must at minimum log/emit a metric with the email (or a hash of it) and the underlying error before re-raising or returning a distinct unavailable signal.

3. **Commit message / task mismatch.** The task was to handle the outage *explicitly*; the commit does the opposite (makes it implicit). Flagging so the author re-scopes rather than just patching the rescue clause.

**Verdict:** Block. The change trades a diagnosable exception for silent duplicate-customer creation. Remove the `nil` fallback and surface the outage as a distinct, contextual error; ensure `get_or_create` only creates on a confirmed not-found.
