**Findings**

1. **`Sessions.scala`, `expire` — expiring an owner does not revoke that owner's capabilities.**
   `expire` removes the owner from `owners` but leaves every `Capability(owner, active = true)` in `capabilities` untouched. Since the stated invariant is "capability is valid only while its owner session exists," this is a correctness/security bug: after `expire("alice")`, `valid(token)` still returns `true` for all of alice's tokens. The task was "expire owner sessions," and the capability side of a session is precisely what a caller can still use after expiry, so the change does not actually accomplish the task.
   Require: on expire, deactivate (or remove) every capability whose `owner == owner` — e.g. `capabilities.filterInPlace((_, c) => c.owner != owner)` or replace with `c.copy(active = false)`.

2. **`Sessions.scala`, `valid` — verifier does not consult owner liveness.**
   Even with (1) fixed, `valid` checks only the capability record. Any other path that removes an owner (or a capability inserted for an owner that was never/no longer in `owners`) would again yield a valid token with no session. The invariant should be enforced at the check, not only at cleanup, so the two can't drift.
   Require: `capabilities.get(token).exists(c => c.active && owners.contains(c.owner))`. Doing both (1) and (2) is cheap and makes the invariant hold structurally rather than relying on every cleanup path remembering to sweep.

3. **`Sessions.scala` — no test covering the expire → valid path.**
   The defect in (1) is exactly the kind of thing a two-line test would catch: add owner, add capability, expire owner, assert `valid(token) == false`. Require a test with this change (the reviewer note's "single-threaded" framing means no concurrency test is needed, but the sequencing test is).

Minor / non-blocking: `owners` and `capabilities` are exposed as public mutable collections, so external code can bypass `expire` entirely; consider `private` with explicit `addOwner`/`grant` methods. Not required for this change, but it undermines whatever invariant (1)/(2) establish.

**Verdict:** Not acceptable as-is. Block on (1) and (2); (3) should accompany the fix.
