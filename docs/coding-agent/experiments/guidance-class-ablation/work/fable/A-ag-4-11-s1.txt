**Findings**

1. **`parser.cpp:2-3` — `last_output` stores a pointer to caller-owned storage (dangling pointer / use-after-free).**
   `last_output = &output;` borrows the caller's `output` reference. The stated contract is that the caller owns `output` and may destroy it immediately after `parse` returns. Any subsequent `preview()` then dereferences a dangling pointer — undefined behavior, typically a crash or garbage output, and it will be intermittent (works when the string happens to still be alive or the freed memory hasn't been reused). This is a blocking defect, not a style nit.
   Required: cache by value, not by address. `static std::string last_output;` (or a `std::optional<std::string>`) and `last_output = output;` in `parse`. `preview()` then returns a copy of the cached value. If a copy is deemed too expensive, the alternative is to add an explicit borrowing/lifetime contract to the public API — but the reviewer notes say no such contract was added, so the copy is the only correct option for this change.

2. **`parser.cpp:2` — global state introduced without any thread-safety or documentation.**
   `last_output` is a mutable global written by `parse` and read by `preview`. Concurrent `parse`/`preview` calls race on it. Even single-threaded, "last parsed" is now process-wide hidden state with no declaration of that in the header or commit message.
   Required: at minimum, document that `preview()` returns the most recent `parse` result and is not thread-safe; if the codebase already has a parser object/context, attach the cache to that instead of a file-scope global. Mark it `static` (internal linkage) rather than an exported non-const global with external linkage — as written, `last_output` is a symbol any TU can clobber.

3. **`parser.cpp:3` — cache is updated even though only the success path is meaningful, and `preview()` cannot distinguish "never parsed" from "parsed empty".**
   `parse` always returns `true` today, so this is latent, but the pattern is wrong: `last_output` is assigned unconditionally, so a future failing `parse` would still publish a partially-written `output`. Separately, `preview()` collapses "no parse yet" and "last parse yielded `""`" into the same empty string, which callers cannot tell apart.
   Required: only update the cache on the success path (`if (ok) last_output = output;`), and consider `std::optional<std::string>` / a `has_preview()` accessor so the "nothing cached" state is representable. The second point is a flag, not a block, if the team is fine with the ambiguity.

4. **No test for the new behavior, and specifically none that exercises the destroy-after-parse case.**
   A test that calls `parse` on a local `std::string`, lets it go out of scope, then calls `preview()` would have caught defect #1 (under ASan it fails deterministically).
   Required: add that test alongside the fix.

**Verdict:** Not acceptable as-is. Finding #1 is a hard block — the change directly violates the documented ownership contract and produces UB in the normal usage pattern.
