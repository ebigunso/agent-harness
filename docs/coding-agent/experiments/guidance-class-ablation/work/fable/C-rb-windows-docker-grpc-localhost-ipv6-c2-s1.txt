**Cause:** The command targeted the wrong port. `50052` has no listener and no Docker port mapping — only `50051/tcp` (gRPC h2c) and `50080/tcp` (health) are published. The server never saw the call, and both `localhost:50052` and `127.0.0.1:50052` fail identically with an immediate `UNAVAILABLE: connection refused`.

This is **not** the Windows/Docker `localhost → ::1` HTTP/2 stall described in the reference material. That pattern presents as a *hang* ending in `DEADLINE_EXCEEDED` (TCP accepted, HTTP/2 never progresses) with the IPv4 retry succeeding. Here the failure is instant, refused, and address-independent — the address-only comparison rules the IPv6 proxy theory out. It's also not a workspace, dependency, or environment problem: the probe, Docker Desktop, the service, and correctly targeted 50051 probes are all healthy. It's a typo/misconfiguration in the invocation (50052 vs 50051).

**Smallest safe remediation:** Correct the target port; nothing else needs to change.

```powershell
node probes/unary.mjs --target localhost:50051 --timeout 2
```

If this were coming from a config file or script rather than a hand-typed command, fix the port value at its source so it doesn't recur. No Docker, firewall, or IPv4/IPv6 changes are warranted.

**Confirmation:**
1. The corrected command exits `0` with response values printed to stdout and empty stderr (per the probe contract, stdout is only written after a successful call).
2. The call appears in the server invocation log (the refused attempts were absent, so its presence proves the request reached the service).
3. Optionally, sanity-check the mapping directly: `docker port <container>` shows `50051/tcp -> 0.0.0.0:50051` and nothing for 50052; `Test-NetConnection localhost -Port 50051` succeeds while port 50052 is refused — matching the observed asymmetry.
