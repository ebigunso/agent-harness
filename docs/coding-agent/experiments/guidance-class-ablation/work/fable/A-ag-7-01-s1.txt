**Findings**

1. **`Login.java`, `Login.success` — secrets written to telemetry (blocking).**
   `"login_success " + credentials` invokes the record's auto-generated `toString()`, which emits every component: `Credentials[accountId=..., password=..., bearerToken=...]`. The plaintext password and a live bearer token land in a long-retained log accessible to people outside the auth operator group. That is a credential leak on every successful login — anyone with log read access can replay the session token or reuse the password. The task only calls for account/event/request identifiers.
   Require: log an explicit, allow-listed set of fields, never the DTO. E.g. `log.accept("login_success accountId=" + credentials.accountId())` (plus a request/correlation id if available). Do not rely on string concatenation of a record that carries secrets.

2. **`Login.java`, `Credentials` record — secret-bearing type with a leaky default `toString()` (should fix alongside #1).**
   Fixing the one call site leaves the same footgun for the next caller, exception message, or debugger dump. A DTO that carries a password and bearer token should not have a `toString()` that prints them.
   Require: override `toString()` on `Credentials` to redact secrets (e.g. `Credentials[accountId=..., password=***, bearerToken=***]`), or better, don't carry secrets in a general-purpose record that flows past the auth boundary — pass a separate `LoginContext(accountId, requestId)` to logging code so secrets can't reach it by construction.

3. **`Login.java` — `Credentials` is only needed for authentication, yet is passed to a post-auth logging helper.**
   The reviewer notes say login is already authenticated at this point. Passing the full credential object into `success(...)` widens the blast radius for no benefit and invites exactly the bug in #1.
   Require: change the signature to accept only the identifiers needed (`success(String accountId, String requestId, Consumer<String> log)` or a dedicated context type), so the method cannot leak what it never receives.

**Verdict:** Not acceptable as-is. Finding #1 alone is a blocking security defect; #2 and #3 are the structural fixes that prevent recurrence.
