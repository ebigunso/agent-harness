## Cause

Print-time encoding failure, not a data or database problem. The DB driver returned a proper Unicode string (`"Launch 🚀"`); the crash happens when `print()` encodes it to `sys.stdout`, whose encoding is `cp932`. CP932 has no representation for U+1F680 (🚀), so the codec raises.

One correction to the reference material's mechanism for this specific case: stdout here is a **pipe**, not an interactive console, so Python isn't using the console code page. When stdout is redirected on Windows and UTF-8 mode is off (`sys.flags.utf8_mode = 0`), Python falls back to the locale's ANSI code page (`locale.getpreferredencoding()`), which is CP932 on a Japanese-locale system. Same symptom, same fix, but it means changing `chcp` in the console would *not* have helped — the environment/script-level override is what matters.

This is not a workspace problem (no bad file, no bad checkout). It's the process's default stdout encoding under this locale. The reference's example characters (em-dashes, smart quotes) are just illustrative; an emoji is a stronger version of the same failure, since it fails under every legacy code page.

## Smallest safe remediation

For this run, in PowerShell 7.4:

```powershell
$env:PYTHONIOENCODING = 'utf-8'; python db_report.py
```

Equivalent alternatives: `$env:PYTHONUTF8 = '1'` or `python -X utf8 db_report.py` (enables full UTF-8 mode, which also covers `open()` defaults — slightly broader, but fine if the script has no legacy-encoded file I/O).

Side effects check: the diagnostic states the database read committed no writes, and the traceback is at `print` on line 34 after the read, so there's nothing to roll back or clean up. If `db_report.py` also writes files elsewhere, confirm none were left half-written; nothing in the transcript suggests it does.

For a durable fix in the script you own, add near the top of `db_report.py`:

```python
import sys
sys.stdout.reconfigure(encoding="utf-8")
```

(and `encoding="utf-8"` on any file handles). That removes the dependency on the caller's environment.

## Confirmation

1. Rerun with the override. Expect exit code 0, no traceback on stderr, and stdout containing the description rows including `Launch 🚀`.
2. Optionally verify the stream encoding in the same invocation: `python -c "import sys; print(sys.stdout.encoding)"` with the env var set should print `utf-8`.
3. One caveat for reading the piped output in PowerShell: Python will now emit correct UTF-8 bytes, but if PowerShell decodes the pipe with a non-UTF-8 `[Console]::OutputEncoding`, the rocket may render as mojibake. That's a display issue on the consumer side, not a failure; set `[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()` if you need it to look right, or redirect to a file and inspect it with a UTF-8 aware viewer.
