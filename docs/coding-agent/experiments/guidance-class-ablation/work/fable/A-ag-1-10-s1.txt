## Findings

### 1. `Invoice.java` — `Billing.due()` still returns 30 days; the domain rule was not changed
- **What's wrong:** The task is "change invoice due period to 45 days," but `Billing.due(issued)` — the single source of the due-date rule — is untouched and still does `plusDays(30)`.
- **Why it matters:** Every caller of `Billing.due()` (including `batchDue` here, and anything outside this file) continues to compute a 30-day due date. The task is only partially delivered, and the commit message claims a scope ("change invoice due period") that the diff does not fulfill.
- **Require instead:** Change `Billing.due` to `issued.plusDays(45)` (ideally via a named constant, e.g. `DUE_PERIOD_DAYS = 45`). That is the one-line change the task actually calls for.

### 2. `Invoice.jsonDue` — bypasses `Billing.due` and hardcodes `plusDays(45)` inline
- **What's wrong:** Instead of updating the shared rule, the diff duplicates it into the JSON response mapper with a literal `45`, no longer delegating to `Billing`.
- **Why it matters:** This creates two independent definitions of "due period" that now disagree (45 in the JSON response, 30 in the batch export and in `Billing`). Consumers of the API response and consumers of the batch export will see different due dates for the same invoice — a correctness bug, not just a style issue. It also means any future policy change must be made in multiple places, which is exactly the drift that just occurred. No rationale is given for moving the rule out of the billing domain.
- **Require instead:** Revert `jsonDue` to `return Billing.due(issued).toString();` so both mappers remain thin wrappers over the domain rule.

### 3. `Invoice.batchDue` — still emits a 30-day due date
- **What's wrong:** Per the reviewer notes, the batch exporter is explicitly in scope, but it's unchanged and still routes through the un-updated `Billing.due`.
- **Why it matters:** Batch exports will carry the wrong (old) due date after this ships; downstream systems ingesting the batch file will disagree with the API.
- **Require instead:** Nothing needs to change in `batchDue` itself once Finding 1 is fixed — that is the point: fixing `Billing.due` corrects both call sites at once.

### 4. No test coverage for the policy change
- **What's wrong:** No test asserts the new 45-day value, and no test would have caught that `jsonDue` and `batchDue` now diverge.
- **Why it matters:** The divergence in this very diff is precisely the kind of regression a simple test (`due(2026-01-01) == 2026-02-15`, and `jsonDue == batchDue`) would flag.
- **Require instead:** Add a unit test for `Billing.due` with the new period, and one asserting `jsonDue` and `batchDue` produce the same value for the same input.
