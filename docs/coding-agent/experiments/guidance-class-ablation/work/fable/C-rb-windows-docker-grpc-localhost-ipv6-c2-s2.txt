**Cause: wrong port in the command, not the workspace.**

The probe targeted `localhost:50052`, but Docker publishes only `50051/tcp` (gRPC) and `50080/tcp` (health). Nothing listens on 50052, so the OS refuses the TCP connect and grpc-js reports `UNAVAILABLE: connection refused` (probe-normalized, exit 2).

The loaded reference note (localhost → `::1`, Docker proxy accepts TCP but stalls HTTP/2) does **not** apply here, and the evidence rules it out:

- The failure is an immediate `connection refused`, not `DEADLINE_EXCEEDED` after 2s. A stalled-but-accepted connection would hang to the deadline; a refused one fails at connect.
- The address-only retry at `127.0.0.1:50052` fails identically. IPv4 vs IPv6 makes no difference because there's no listener on either.
- The REST check on 50080 succeeding only proves the container is up and the host→container path works; it says nothing about 50052.
- Correctly targeted 50051 probes are healthy and there's no 50052 mapping in `docker port` / service config.

So the service, port publishing, container health, and the probe tooling are all fine. The command's `--target` argument is the defect.

**Smallest safe remediation**

Rerun with the published gRPC port:

```powershell
node probes/unary.mjs --target localhost:50051 --timeout 2
```

No config, Docker, or code changes. Don't publish 50052 or change the compose file to "fix" this — the service isn't supposed to be on 50052.

**Confirmation**

1. Exit code `0`, stderr empty, response values printed to stdout.
2. The call appears in the server invocation log (the two refused attempts were absent, so a new entry is the positive signal).
3. Optionally, `docker port <container>` still shows `50051/tcp` and `50080/tcp` only — confirming nothing was changed.

If the 50051 call *does* hang to the 2s deadline with `localhost` but succeeds with `127.0.0.1:50051`, that's when the IPv6/proxy note becomes relevant and pinning IPv4 in local config is the right follow-up. Nothing in the current evidence suggests that.

One thing worth checking upstream: where `50052` came from (a stale env var, a copy-pasted script, or a config default). If it's in a shared script or `.env`, correct it there so the mistake isn't repeated.
