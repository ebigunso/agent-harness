**Verdict: Block.** The change introduces a second writer to `Inventory#quantity` that does not enforce the stated invariant, and nothing downstream (model or DB) catches it.

Classification of inputs (both paths, `delta` is an integer, `quantity` is current row value under lock):

| Case | `normal_update` | `admin_update` |
|---|---|---|
| `delta >= 0` | writes `q + delta` | writes `q + delta` |
| `delta < 0`, `q + delta >= 0` | writes `q + delta` | writes `q + delta` |
| `delta < 0`, `q + delta < 0` | raises, no write | **writes negative quantity** |

Third row is the defect; everything else is equivalent.

---

**1. `inventory.rb`, `admin_update` — invariant violation persisted to the database**

- What: `admin_update` computes `item.quantity + delta` and writes it with no floor check. With `quantity = 3` and `delta = -5`, the row is saved with `quantity = -2`.
- Why: The reviewer note states "quantity must never become negative." That is a domain invariant, not a normal-user policy. Per the notes, the DB has no `CHECK` constraint and the model has no numericality validator, so this path is the only thing standing between the input and a corrupted row. Once one row is negative, every downstream reader (availability, reservations, reporting) is operating on an impossible state, and `normal_update` will then also happily accept it as a starting value.
- Require: `admin_update` must enforce the same floor. If admin genuinely needs a different capability (e.g. corrections), that capability must be expressed explicitly — set an absolute non-negative quantity, or record a stock-count adjustment with a reason — not by silently dropping the guard on the delta path.

**2. `inventory.rb` (model / schema) — invariant is caller-enforced only; there is no authoritative owner**

- What: The only enforcement of `quantity >= 0` is an `if` in one of two call paths. This diff demonstrates the failure mode of that design: the second writer simply omitted it.
- Why: An invariant enforced only by "remember to check in each caller" is an optional guard. Any future writer — another service, a console fix-up, `update_column`, raw SQL, a data migration — bypasses it. The commit itself is the proof.
- Require:
  - Migration adding `CHECK (quantity >= 0)` on `inventories.quantity` (authoritative; covers all writers including non-AR ones). Note that adding this constraint is a good time to verify no existing rows already violate it.
  - `validates :quantity, numericality: { greater_than_or_equal_to: 0 }` on `Inventory` so `update!` raises `ActiveRecord::RecordInvalid` before hitting the DB.
  - Keep the explicit check inside the `with_lock` block as the fast, clear-message path, but it is no longer load-bearing.

**3. `inventory.rb` — two divergent implementations of the same operation (conflicting writers)**

- What: `normal_update` and `admin_update` are the same operation (lock → add delta → save) differing only in whether the guard runs. Duplicating the body invites exactly this kind of drift.
- Why: Any future fix to one (e.g. adding audit logging, changing lock strategy, handling `RecordInvalid`) will be missed in the other. Authorization ("is this caller an admin?") is a separate concern from the arithmetic and invariant, and should not be encoded as a second copy of the write path.
- Require: One primitive, e.g. `Inventory#adjust!(delta)` that does `with_lock`, computes, raises on negative, saves. Both the normal and admin controllers call it. If admin has extra privileges, they're a different operation (see #1), not a weakened copy of this one.

**4. Non-idempotent delta writes, unaddressed retry behaviour (flag, not block on its own)**

- What: Both functions apply a relative delta. A retried request (client retry, job retry, double submit) applies it twice. `with_lock` guarantees serialisation but not deduplication.
- Why: Pre-existing for `normal_update`, but this diff makes it worse: on the admin path a retried negative delta with no floor can drive the value further negative with each replay, compounding #1. Once #1/#2 are fixed, the replay just fails loudly on the second application, which is acceptable — but it should be a deliberate decision.
- Require: At minimum, state in the commit/PR how admin adjustments are expected to be retried. If admin adjustments are meant to be corrections, an absolute-set operation is naturally idempotent and would resolve this along with #1.

**5. No tests**

- What: The diff adds two write paths with a safety invariant and no tests.
- Why: The specific bug in #1 is a one-line test (`quantity: 3`, `delta: -5`, expect raise, expect row unchanged). Its absence is how the regression shipped.
- Require: Tests for each row of the truth table above on the shared primitive; a test that the DB constraint rejects a negative value written via `update_column` (proves the authoritative layer, not just the AR layer); and a concurrent test (two threads, two connections) showing the lock serialises and the floor holds.

**Minor (would not block):** `ArgumentError` is a programmer-error type; a domain failure like "insufficient stock" is better modelled as a specific error class so controllers can map it to a 422 rather than a 500. Fold into the refactor in #3 if convenient.
