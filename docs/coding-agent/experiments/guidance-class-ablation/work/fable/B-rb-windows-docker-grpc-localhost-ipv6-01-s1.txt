**Cause**

This is not a service or workspace-content problem. `localhost` resolves to `::1` first on this host, so the gRPC channel connects to `[::1]:50051`. Docker Desktop's IPv6 port proxy accepts the TCP connect but never forwards the HTTP/2 (h2c) traffic, so the client sits at transport setup until the 2s deadline fires (`DEADLINE_EXCEEDED`, exit 2). The evidence lines up:

- The service interceptor log shows no invocation for the failed call — the request never reached the server.
- The identical probe against `127.0.0.1:50051` succeeds (`pong`, exit 0) and the service logs `invoked=true completed=true`.
- The HTTP/1.1 sibling on `localhost:50080` works because the IPv6 proxy path only stalls HTTP/2, not HTTP/1.1.

The only variable between the failing and passing runs is the target address, so the asymmetry is loopback resolution, not the probe, the container, port publishing, or the service.

**Smallest safe remediation**

Change the gRPC target from `localhost:50051` to `127.0.0.1:50051` (in the command line and in any local connection string/config the probe or clients read). Nothing else needs to change: no service restart, no port remap, no Docker reconfiguration, no probe code edits, no hosts-file changes.

```powershell
python probes/unary.py --target 127.0.0.1:50051 --timeout 2
```

Do not "fix" this by disabling IPv6 system-wide or editing `hosts` — those are broader than needed and affect other software.

**Confirmation**

1. Run the probe with `--target 127.0.0.1:50051 --timeout 2`: expect exit 0, stdout `pong`, empty stderr.
2. Check the service interceptor log for a new line `probe method="unary Echo" transport=h2c invoked=true completed=true` correlated to that run.
3. (Optional negative control) Re-run with `--target localhost:50051` once to confirm it still hangs to deadline — this proves the address, not timing or a transient state, is the discriminator.
4. If any other local gRPC clients or config files in `C:/work/grpc-local` reference `localhost:50051`, update them the same way and re-run their smoke checks.

If step 1 ever fails against `127.0.0.1` too, only then move on to investigating the service, port publishing, and container health.
