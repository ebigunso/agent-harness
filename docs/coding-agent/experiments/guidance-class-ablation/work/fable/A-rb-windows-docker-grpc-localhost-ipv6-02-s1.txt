**Cause**

This is an address/transport asymmetry in the workspace, not a bug in the probe or the service.

- `localhost` resolves to `::1` first, and `@grpc/grpc-js` uses that. The TCP handshake to `[::1]:50051` succeeds (Docker Desktop's host-side proxy listens on the IPv6 loopback), but the connection is never forwarded to the container's h2c listener — no HTTP/2 SETTINGS/response headers ever come back, and the service interceptor log shows no invocation. grpc-js does not fall back to the next address once a TCP connect has succeeded, so the call just sits until the 2 s deadline and the probe normalizes it to exit 2 / `DEADLINE_EXCEEDED`.
- The identical call to `127.0.0.1:50051` returns `pong` with `invoked=true completed=true`, which isolates the variable to the destination address.
- The HTTP/1.1 sibling on 50080 succeeding via `localhost` doesn't contradict this: curl does its own IPv4/IPv6 fallback (and the port may be forwarded differently), so it isn't evidence that `[::1]:50051` works.

Raising `--timeout` would not help — the request never reaches the server.

**Smallest safe remediation**

Target the IPv4 loopback explicitly:

```powershell
node probes/unary.mjs --target 127.0.0.1:50051 --timeout 2
```

If you want `localhost` to keep working for everyone, the next-smallest fix is on the Docker side: publish the port bound to IPv4 only (`-p 127.0.0.1:50051:50051` / `"127.0.0.1:50051:50051"` in compose) so that `[::1]:50051` refuses instead of half-accepting, or otherwise fix the IPv6 forwarding for that port. Don't change resolver order machine-wide or edit the hosts file — that's broader than the problem.

**Confirmation**

1. Rerun the probe against `127.0.0.1:50051`: expect exit 0, stdout `pong`, empty stderr, and a matching `invoked=true completed=true` line in the service log.
2. Rerun against `localhost:50051` (unchanged): expect it to still fail with exit 2 and no interceptor entry — this proves the address, not timing or the service, is the discriminator.
3. Optional corroboration: `Test-NetConnection -ComputerName ::1 -Port 50051` shows TCP open, while a bare h2c request to `[::1]:50051` (e.g. `curl.exe --http2-prior-knowledge --max-time 2 http://[::1]:50051/`) hangs to the timeout, whereas the same against `127.0.0.1:50051` gets an HTTP/2 response (even if it's a gRPC error status). If you apply the Docker binding fix, the `::1` connect should then be refused immediately rather than time out.
