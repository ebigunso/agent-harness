## Diagnosis

**This is not a code/workspace problem; it is a host networking asymmetry.** The probe, its dependencies, and the service are all fine — the comparison run against `127.0.0.1:50051` returns `pong`, exit 0, and the interceptor logs `invoked=true completed=true`.

**Cause:** `localhost` resolves to `::1` first, and grpc-go uses that first address. Docker Desktop's port-forwarding on the WSL2 backend accepts the TCP connection on `[::1]:50051` (so you get no `UNAVAILABLE` / connection refused), but nothing is forwarded to the container over that path — the h2c preface/SETTINGS exchange never completes, no HTTP/2 headers arrive, and the service interceptor log shows no invocation. The client sits on an open-but-dead socket until the 2 s deadline, and the probe maps that to `DEADLINE_EXCEEDED` / exit 2. Unlike curl, which uses Happy Eyeballs and quietly succeeds via `127.0.0.1`, the probe does not fall back to a second address once a TCP connect succeeds.

Ruling out alternatives: it isn't TLS (plaintext h2c, no cert check), not a wrong method (that would be `UNIMPLEMENTED` → exit 3), and not a stopped service (TCP connect succeeded and the IPv4 call works). The `exit code 1` / `exit status 2` pair is just `go run` reporting the probe's exit 2 — not a separate fault.

## Smallest safe remediation

Address the service by IPv4 loopback instead of the `localhost` name:

```powershell
go run ./cmd/probe --target 127.0.0.1:50051 --timeout 2s
```

(Equivalently `--target ipv4:127.0.0.1:50051` if you want to be explicit about the resolver.) This changes nothing in the code, container, or Docker/IPv6 configuration. If the host-side mapping must work over `::1` long-term, that is a separate Docker Desktop port-publishing fix (e.g. publishing explicitly as `127.0.0.1:50051:50051` or resolving the IPv6 forwarding issue), but it is not required to unblock this call.

## Confirmation

1. The IPv4 command exits 0, prints `pong` to stdout, stderr is empty.
2. The service log shows a new `probe method="unary Echo" transport=h2c invoked=true completed=true` line for that run.
3. (Optional, to prove causation rather than coincidence) re-run the original `--target localhost:50051` once more and confirm it still fails with `DEADLINE_EXCEEDED` and no interceptor entry — same server, same config, only the address differs.
