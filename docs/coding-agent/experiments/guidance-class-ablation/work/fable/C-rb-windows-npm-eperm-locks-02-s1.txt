**Cause**

This is a workspace-state problem, not an npm/registry/permissions issue. npm needed to replace `node_modules\sharp\build\Release\sharp-win32-x64.node` (errno -4082 = EBUSY on `unlink`). On Windows a native addon that is mapped into a running process cannot be unlinked. `tasklist /m sharp-win32-x64.node` shows exactly one holder: `node.exe` PID 4102, which is this repo's image worker (`workers/images.js`) — it outlived the terminal that launched it. The probe-file test, writable cache, synced lockfile and successful registry requests rule out ACLs, lockfile drift and network.

**Smallest safe remediation**

1. Stop the holder, gracefully first. PID 4102 is repo-owned and orphaned, so nothing else depends on it staying up. If `workers/images.js` has a shutdown hook (IPC/queue drain), use it; otherwise, since a console node process ignores `taskkill` without `/F`:
   ```powershell
   taskkill /PID 4102 /F
   ```
   Only that PID — don't kill all `node.exe`.
2. Re-run the original command unchanged:
   ```powershell
   npm install
   ```
   No cache clean, no `rm -rf node_modules`, no `--force` needed.

**Confirmation**

- `tasklist /m sharp-win32-x64.node` returns no rows (nothing holds the module).
- `npm install` exits 0 with no EBUSY line.
- `node -e "require('sharp'); console.log('ok')"` prints `ok` (new binary loads on Node 20.18.0).
- Restart the worker deliberately (`node workers/images.js`) so it picks up the fresh addon.

If the retry fails again, check `tasklist | findstr node` for another holder (e.g. an editor/test runner) and inspect the newly written module before escalating.

**Record for the log:** original command `npm install` → `EBUSY unlink …\sharp\build\Release\sharp-win32-x64.node` (errno -4082); module `sharp-win32-x64.node` (sharp 0.32.6); `tasklist /m` output showing node.exe 4102; killed PID 4102 (repo image worker, `workers/images.js`); retry result of `npm install`.
