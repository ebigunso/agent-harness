## Cause

This is a **script logic bug, not a workspace problem**. The raw JSON `[7]` is valid, the runtime (pwsh 7.4.6) supports `-NoEnumerate`, and nothing needs writing.

The defect is in how the parsed value reaches `$parsed`:

- `ConvertFrom-Json -NoEnumerate` *does* return a real array for `[7]`.
- But that array is emitted as the output of the `Parse` function. **A single-element array returned through the function/pipeline gets unrolled**, so `$parsed` is assigned the lone element — `System.Int64` — exactly as stdout shows (`parsed type=System.Int64`).
- Therefore `$parsed -isnot [array]` is true and the script throws.

This matches the known trap: `-NoEnumerate` preserves arrays *unless re-piped*, and a post-pipeline `-is [array]` test cannot prove wire framing. A one-element array collapses to a scalar, and (conversely) a genuinely scalar wire value could be re-wrapped into an array — so the type check does not reflect the contract.

## Smallest safe remediation

Assert on the **trimmed raw JSON framing**, not on the post-pipeline object type. Replace the final assertion:

```powershell
$trimmed = $raw.Trim()
if (-not ($trimmed.StartsWith('[') -and $trimmed.EndsWith(']'))) { throw 'Expected JSON array' }
```

This correctly accepts empty `[]`, singleton `[7]`, and multi-element `[7,8]` arrays, and rejects scalar wire values (`7`, `"x"`, `true`), independent of pipeline unrolling. It is a framing check, not a full syntax validator — which is appropriate to the stated contract.

(Do **not** "fix" it by wrapping the function output with `,$items`. That would make the singleton pass, but it would also wrap a scalar `7` into an array and make it pass too — silently violating the "reject scalars" contract.)

The originally failing case (`[7]`) should now print `parsed type=System.Int64` yet exit 0, and the scalar cases should be the only ones that throw.
