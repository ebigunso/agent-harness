**Cause:** Not a permissions/ACL or npm state problem — lockfile is in sync, registry works, and a probe file can be created/removed next to the module. The `EPERM unlink` on `node_modules\lmdb\build\Release\lmdb.node` is a Windows file lock: a native addon that is loaded into a running process is memory‑mapped and cannot be unlinked. `tasklist /m lmdb.node` shows exactly one holder, `node.exe` PID 4106, which is this repo's own Gatsby cache/build watcher (`scripts/gatsby-watch.js`). `npm ci` removes `node_modules` first, hits the mapped file, and aborts. So this is a workspace problem (a dev process left running), not a toolchain or npm defect.

**Smallest safe remediation:**

1. Stop the watcher gracefully — Ctrl+C in the terminal running `gatsby-watch.js`, or stop whatever npm script/task launched it. Don't touch any other `node.exe`.
2. Confirm the handle is released:
   ```powershell
   tasklist /m lmdb.node
   ```
   Expected: "No tasks are running which match the specified criteria."
3. Re-run the original command:
   ```powershell
   npm ci
   ```
4. Only if the watcher doesn't exit on its own (hung), and after re-confirming PID 4106 is still the `gatsby-watch.js` process:
   ```powershell
   taskkill /PID 4106 /F
   ```
   then repeat steps 2–3.

**Confirmation it worked:**

- `npm ci` exits 0 with no EPERM/EBUSY output.
- `node_modules\lmdb\build\Release\lmdb.node` exists with a fresh timestamp (rebuilt from source, since lmdb 2.9.4 is a source build here), and `node -e "require('lmdb')"` loads without error.
- Restart the Gatsby watcher afterwards; it should load the new binary. If a second `npm ci` ever fails the same way, re-run `tasklist /m lmdb.node` and `tasklist | findstr node` to find the new holder.

**Record for the log:** command `npm ci`, error `EPERM unlink …\lmdb\build\Release\lmdb.node` (errno -4048), module lmdb 2.9.4, `tasklist /m` output showing node.exe 4106 (gatsby-watch.js), whether a graceful stop sufficed or PID 4106 was force-killed, and the retry result.
