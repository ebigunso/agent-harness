**Findings**

1. **Next.tsx, onClick handler — blocking.** `load(String(Number.parseInt(nextCursor, 10) + 1))` treats the cursor as an integer page index. Per the contract the cursor is an opaque token (e.g. `k:af31`), so `parseInt` returns `NaN`, `NaN + 1` is `NaN`, and `load` is called with the string `"NaN"`. The button will never advance; every click sends a garbage cursor to the loader, and even a token that happens to start with digits would be silently mutated. This is exactly the coercion/shape-drift the contract forbids: the client is re-interpreting a value it is supposed to pass through verbatim. Require `onClick={() => { if (nextCursor !== null) load(nextCursor); }}` — no parsing, no arithmetic. (The `disabled={nextCursor === null}` gating is fine and can stay.)

2. **Page.java — flag, non-blocking.** `record Page(String nextCursor)` carries the end-of-list `null` case only by convention; nothing in the type or a compact constructor states that the field is nullable, nor that a non-null value must be nonempty. The TS side hard-codes `string | null`, so the two sides agree only tacitly, and a serializer configured to omit nulls would deliver `undefined` to the TS component (which would then enable the button with an `undefined` cursor). Require at minimum a `@Nullable` annotation / Javadoc on `nextCursor` stating "null = no further page", and ideally a compact constructor rejecting empty strings so the "nonempty or null" invariant is enforced at the boundary rather than assumed. Also confirm the serializer emits an explicit `null` rather than dropping the key, or widen the TS prop and check accordingly.

Not acceptable as-is; item 1 must be fixed before merge.
