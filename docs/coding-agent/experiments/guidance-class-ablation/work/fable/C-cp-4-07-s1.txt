**Findings**

1. **`Orders.cs`, `ProcessOrder` — business flow now depends on a side effect inside a "log" call.**
   `events.Add("reserve")` and `events.Add("charge")` only execute if `Log` synchronously invokes its callback exactly once each time. That's the correctness contract of a logging helper, which the reviewer notes explicitly say is "normally observational." If `Log` is later changed to no-op when logging is disabled, to buffer/defer, or to invoke the callback more than once, orders silently stop being reserved or charged. This is hidden coupling in its purest form: the reader of `ProcessOrder` cannot tell it works without reading `Log`.
   *Require:* Sequential, unconditional appends. Never route control flow through a log/observability hook.

2. **`Orders.cs`, `ProcessOrder` — the change doesn't record phases.**
   The task is "record order processing phases." `Log` discards `message`, so `"start"` and `"reserved"` go nowhere; `phase` is a local that's thrown away; `events` receives exactly what it did before. Net effect: zero new information recorded, plus new failure modes. The commit message describes something the diff doesn't do.
   *Require:* Actually record the phases — e.g. append explicit phase markers to `events` (or a dedicated phase list), or make `Log` write its message somewhere. Whatever "record" means here, it should be visible in the output/state, not in a discarded counter.

3. **`Orders.cs`, `ProcessOrder` — failed phase checks fail silently.**
   `if (phase == 1) ...` / `if (phase == 2) ...` skip the step with no signal when the guard is false. An order that isn't reserved or charged would be indistinguishable from one that was, except by absence. If the intent was to enforce phase ordering, wrong state should throw, not fall through.
   *Require:* If phase validation is wanted, model it explicitly (an enum state, an assertion/exception on unexpected transitions). Don't use `if` to quietly drop work.

4. **`Orders.cs`, `ProcessOrder` — intent is not locally readable; two abstraction levels interleaved.**
   A reader sees a counter mutated via closure, a helper named `Log` that takes an `Action`, and guards keyed on magic numbers 1 and 2. Nothing on the page says why.    *Require:* Keep the workflow at one level: the sequence of steps. If phase tracking is genuinely needed, name it (`Phase.Reserved`, etc.) and keep it adjacent to and independent of the step it describes.
