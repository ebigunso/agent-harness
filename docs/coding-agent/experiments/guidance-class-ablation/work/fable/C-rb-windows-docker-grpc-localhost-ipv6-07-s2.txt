**Verdict:** This is a local host-networking/config issue, not a defect in the service, the proto, or the grpcurl command. The server never saw the call.

**Cause**

On this Windows host, `localhost` resolves to `::1` before `127.0.0.1`. grpcurl dialed `[::1]:50051`. Docker Desktop's published-port proxy on the IPv6 loopback accepts the TCP connection but never completes the HTTP/2 (h2c) exchange, so the channel sits with no response headers until the 2 s `-max-time` expires → `Failed to dial target host ... context deadline exceeded`. Because the dial never finishes, neither reflection nor `demo.Probe/Ping` runs, which is why the interceptor log has no entry for the failed attempt. The HTTP/1.1 health check on 50080 isn't affected (curl completes in 12 ms), which rules out "container down" or "port not published."

The address-only comparison confirms it: identical command against `127.0.0.1:50051` returns `{"value":"pong"}` in-deadline, and the service log shows `invoked=true completed=true`.

**Smallest safe remediation**

Use the IPv4 loopback in the local gRPC target instead of `localhost`:

```
grpcurl -plaintext -max-time 2 -d '{}' 127.0.0.1:50051 demo.Probe/Ping
```

and change any local config/scripts/env vars in `C:/work/grpc-local` that set the gRPC target from `localhost:50051` to `127.0.0.1:50051`. Do not touch the server, the Dockerfile/compose port mappings, or system IPv6 settings — none of those are at fault, and disabling IPv6 host-wide is a larger change than needed.

**Confirmation**

1. Re-run the exact failed command with the IPv4 target (above): expect exit 0 and `{"value": "pong"}` well under 2 s.
2. Check the service interceptor log for a new line `probe method="unary demo.Probe/Ping" transport=h2c invoked=true completed=true`.
3. Optionally `grpcurl -plaintext 127.0.0.1:50051 list` to confirm reflection works on the same path (the original command depends on it).
4. Record for the incident note: target/port (`[::1]:50051` vs `127.0.0.1:50051`), the deadline error text, the REST timing (`200`, 0.012 s), and the successful IPv4 retry.

If the IPv4 retry had *also* failed, the next step would be to inspect `docker ps` / published ports and container health rather than the address — but here that branch is already excluded by the captured comparison.
