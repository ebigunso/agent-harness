**Cause**

This is a workspace/connection-string problem, not a service defect. `localhost` resolves to `::1` first on this host, so the Kotlin gRPC channel connected to `[::1]:50051`. Docker Desktop's IPv6 port proxy accepts the TCP connect but never completes the HTTP/2 (h2c) handshake, so the unary Echo sat at the transport layer until the 2 s deadline and the probe mapped that to exit 2 / `DEADLINE_EXCEEDED`. Corroborating evidence: the service interceptor log shows no invocation for the failed call (the request never reached the server), the HTTP/1.1 sibling on `localhost:50080` answered in 12 ms (IPv6 proxy is fine for HTTP/1.1, broken for HTTP/2), and the identical call against `127.0.0.1:50051` returned `pong` with `invoked=true completed=true`. The only thing that changed before the failure was the profile target flipping from `127.0.0.1:50051` to `localhost:50051`; server code and image are unchanged. TLS/SNI is not a factor (plaintext h2c, no name check).

**Smallest safe remediation**

Revert the local configuration profile target from `localhost:50051` back to `127.0.0.1:50051` (the last known-good value). Do not touch the service, port mappings, container, or the probe. If other local gRPC targets in this profile use `localhost`, switch them to `127.0.0.1` as well; leave the REST/health target alone since it works either way.

**Confirmation**

1. Re-run the failing command with the corrected profile / explicit address:
   `java -jar probes/kotlin-probe.jar --target 127.0.0.1:50051 --timeout 2`
   Expect exit 0, stdout `pong`, empty stderr.
2. Check the service interceptor log shows a new line for that call with `invoked=true completed=true`.
3. Optionally re-run once with `--target localhost:50051` to confirm it still reproduces the deadline (proving the address, not timing, is the variable), then leave the profile on `127.0.0.1`.

If the IPv4 call ever fails too, that would point at the service or port publishing instead — but nothing in the captured evidence suggests that.
