**Verdict: acceptable as-is.** The core logic is correct and I'd approve it.

Why it holds up:

- `apply` does check → mutate → record under a single `Lock`, so the check-then-act is atomic. No TOCTOU window between `ident not in self._seen` and `self._seen.add(ident)`.
- The return value is read inside the lock, so the `[1]*32` expectation is sound: the first delivery makes the value 1 and returns it; every duplicate (whether racing or serialized) sees `_value == 1` and returns 1. There's no ordering where a caller could observe 0 or 2.
- `value()` also takes the lock, so the final read is consistent.
- Given the stated contract (single-process, in-memory, immutable delta per ID, no persistence), the objections I'd normally raise — restart losing `_seen`, same ID with a different delta, multi-process coordination — are explicitly out of scope, and the code doesn't pretend otherwise.

Non-blocking notes (I'd mention, not require):

1. **`counter.py` — `check()` is defined but never invoked, and lives in the production module.** It's only useful if something runs it. I'd move it into a `test_counter.py` (or at minimum add `if __name__ == "__main__": check()`) so the 32-delivery concurrency check actually executes somewhere in CI. As written it's dead code with an `assert` that also vanishes under `python -O`.

2. **`_seen` grows without bound.** That's inherent to a "remember every ID forever" dedupe with no TTL/window in the contract, so it's not a defect against this task — but if this store outlives short bursts it'll want an eviction policy, and that decision should be made deliberately rather than discovered as memory growth.

3. Style only: the semicolon-joined statements (`self._lock=Lock(); self._seen=set(); ...`, `with self._lock: return self._value`) are legal but read poorly and would fail most formatters. Not worth blocking on.
