**Cause**

`npm ci` never got as far as touching the project. npm's `cache` setting resolves to `C:\locked-cache` (confirmed by `npm config get cache`), and the effective ACL on that directory explicitly denies this user create/write. `npm ci` always writes to the cache (it fetches tarballs into the cacache store before extracting to `node_modules`, even when everything is already resolved in the lockfile), so the first `mkdir` under the cache root fails with `EPERM` (errno -4048) and npm aborts before doing anything else.

This is not a dependency, lockfile, or file-lock problem: the lockfile is in sync, there is no native binary unlink, no process holds `node_modules`, and the repo path is writable. It's an npm configuration / permissions problem in the environment.

**Smallest safe remediation**

Point npm at a cache you can write to, without touching the ACL on `C:\locked-cache` (that deny is probably intentional, and changing it would need elevation).

1. Immediate unblock — per-invocation override, no persistent change:
   ```powershell
   npm ci --cache "$env:LOCALAPPDATA\npm-cache"
   ```
   (`%LOCALAPPDATA%\npm-cache` is npm's own default on Windows.)

2. Then fix the source so it doesn't recur. Find where `cache` is being set:
   ```powershell
   npm config list -l | Select-String cache
   npm config get cache --location=project
   npm config get cache --location=user
   $env:NPM_CONFIG_CACHE; $env:npm_config_cache
   ```
   - If it comes from a project `.npmrc` in `C:\work\npm-lock`, remove that `cache=` line (a machine-specific absolute path shouldn't be committed).
   - If it comes from the user/global `.npmrc` or an environment variable, delete the entry or set it to a writable path:
     ```powershell
     npm config delete cache --location=user
     ```

Do **not** run npm elevated, and don't `icacls /grant` on `C:\locked-cache` — either would bypass a deliberate restriction and widen the blast radius of a one-line config fix.

**Confirmation**

```powershell
npm config get cache          # should print a writable path, e.g. C:\Users\<you>\AppData\Local\npm-cache
npm ci                        # exit code 0, no EPERM
$LASTEXITCODE                 # 0
Test-Path .\node_modules      # True
npm ls --depth=0              # no missing/invalid entries
```

If step 1 succeeds but a plain `npm ci` still fails, the persistent config source (step 2) hasn't been cleared yet — re-run `npm config list -l | Select-String cache` to see which file is still supplying `C:\locked-cache`.
