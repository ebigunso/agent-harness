**Finding 1 — `shipment.rb`, `rescue StandardError` swallowing the booking failure**

- **What's wrong:** The vendor call either books or raises; per the reviewer notes, an exception means the shipment was *not* booked. The rescue catches every `StandardError`, discards it, and execution falls through to `{ booked: true }`. So on failure the function returns success.
- **Why it matters:** This is the core of the task ("book required shipment before completion") and the change inverts it. Callers will mark orders complete with no shipment booked, and nothing is logged, so the failures are silent and undiscoverable. The comment ("retries will be investigated later") does not justify suppressing the error now — it's a deferred TODO masquerading as error handling.
- **Require instead:** Do not swallow the exception. Either let it propagate:
  ```ruby
  def complete(order_id, vendor)
    vendor.call(order_id)
    { order_id: order_id, booked: true }
  end
  ```
  or, if a non-raising contract is wanted, return the true state and surface the failure:
  ```ruby
  def complete(order_id, vendor)
    vendor.call(order_id)
    { order_id: order_id, booked: true }
  rescue StandardError => e
    logger.error("shipment booking failed for order #{order_id}: #{e.class}: #{e.message}")
    { order_id: order_id, booked: false, error: e }
  end
  ```
  Either way, `booked: true` must only be reachable when `vendor.call` returned normally. Also drop the placeholder comment or turn it into a tracked TODO with an issue reference; retry logic, if added later, belongs in a bounded retry loop, not a bare rescue.

**Finding 2 — no tests for the failure path**

- **What's wrong:** The diff adds a new module with no tests, and the only interesting behavior (vendor raises) is exactly the one that's broken.
- **Why it matters:** A test asserting `booked: false` / raise when the vendor throws would have caught Finding 1 and will prevent regression when retries are later added.
- **Require instead:** Add specs for both paths: vendor succeeds → `booked: true`; vendor raises → exception propagates (or `booked: false`, per the chosen contract), and confirm `booked: true` is never returned after a raise.
