**Cause:** Not a workspace/environment problem. The payload itself is malformed: `$raw = '[1,'` is a truncated array — one element, a trailing comma, no closing `]`. `ConvertFrom-Json` correctly rejects it (`Invalid array passed in, extra trailing ','`), and with `$ErrorActionPreference = 'Stop'` that terminates the script with exit 1. The failure occurs at syntax level, before any question of array shape or pipeline unrolling arises. Nothing in Windows PowerShell 5.1, the execution policy, or the cwd is at fault.

**Smallest safe remediation:** Fix the data, not the parser. In the probe that means correcting the literal to a complete array (`'[1]'`, or `'[1,2]'` if a second element was intended). If the literal is a stand-in for a real source (file/API), fix the truncation upstream — don't "repair" JSON in the script by appending `]`. Optionally, add a cheap framing guard before parsing so truncation is reported explicitly:

```powershell
$t = $raw.Trim()
if (-not ($t.StartsWith('[') -and $t.EndsWith(']'))) {
    throw "raw JSON is not framed as an array: $raw"
}
$parsed = ConvertFrom-Json -InputObject $raw
```

This is a framing check only, not a syntax validator; `ConvertFrom-Json` remains the syntax authority. On 5.1 there is no `-NoEnumerate`, so the raw framing check is the right way to prove wire-level array framing — don't rely on `-is [array]` after a pipeline.

1. Re-run `powershell.exe -NoProfile -File probes/parse.ps1`; expect exit code 0 and no stderr.
2. Record: raw JSON (`[1]`), framing result (starts `[`, ends `]`), element count (`@($parsed).Count` → 1), and the exact parse call used.
3. Negative check: temporarily feed `'[1,'` again and confirm the framing guard fires (or, without the guard, the same `ArgumentException` reappears) — proving the fix was the data and the parser behavior is unchanged.
