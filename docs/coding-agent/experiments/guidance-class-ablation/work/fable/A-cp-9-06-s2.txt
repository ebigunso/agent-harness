**1. `Authorization.cs`, `catch (PolicyUnavailable)` branch — fallback grants access from stale cache entries, violating the access contract.**

- **What's wrong:** On outage, `cache.Get(user, resource)?.Allowed` is returned as the authorization decision. Per the reviewer notes, cache entries never expire and `FetchedAt` is never consulted, so an entry written last week that said `Allowed = true` will still grant access today even if the user's access was revoked in the meantime. The contract states revocations take effect immediately and offline grants are not authorized. This branch is therefore a fail-open path for revoked principals whenever the policy service is down (or can be made to look down).
- **Why it matters:** This is an authorization bypass, not a degraded-mode inconvenience. An attacker who can induce or wait for a `PolicyUnavailable` (network partition, DoS on the policy service, deliberate outage) retains access after revocation. The commit message ("use cached access policy during outages") describes exactly the behaviour the contract forbids. Denying on cache miss is correct but does not mitigate the stale-hit case.
- **What I'd require:** Fail closed. Replace the cache lookup with `return false` (keep the warning log, ideally plus a metric so outages are visible). If product genuinely wants a bounded-staleness fallback, that has to be a contract change first; only then would a cache read be acceptable, and it would need to check `FetchedAt` against an explicitly agreed maximum age and deny anything older. As written, the unused `FetchedAt` field is a signal that this check was anticipated and simply not done.

No other issues: the catch is correctly scoped to `PolicyUnavailable` rather than a blanket `Exception`, and the logging is appropriate.
