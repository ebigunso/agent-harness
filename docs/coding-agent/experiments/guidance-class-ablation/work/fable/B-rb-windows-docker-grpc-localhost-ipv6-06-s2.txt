**Verdict:** This is not a workspace/project problem. The probe, its dependencies, the build, and the service are all fine. The failure is a host-networking/address-selection issue between the client and Docker Desktop's published port.

**Cause**

`localhost` resolves to `::1` before `127.0.0.1` on this host, so the gRPC channel targets `[::1]:50051`. Docker Desktop for Windows' IPv6 port proxy accepts the TCP connect but does not pass HTTP/2 through, so the h2c channel never receives response headers and the 2s deadline fires (`DEADLINE_EXCEEDED`, exit 2). The service never sees the request. The evidence lines up:

- Same call to `127.0.0.1:50051` → exit 0, `pong`, service log `invoked=true completed=true`.
- Failed call → no entry in the service interceptor log (the request never reached the container).
- Sibling HTTP/1.1 port `localhost:50080` works in 12 ms — HTTP/1.1 is unaffected by the IPv6 proxy stall, which is why REST "looks fine" while gRPC hangs.
- TCP connect to `[::1]:50051` succeeds, so this isn't a closed/unpublished port; the stall is at the HTTP/2 layer.

Raising `--timeout` would not help; the request is not queued, it's stuck.

**Smallest safe remediation**

Change only the target address in the local connection string from `localhost` to `127.0.0.1`:

```
cargo run --manifest-path probes/Cargo.toml -- --target 127.0.0.1:50051 --timeout 2
```

If the address is stored in a local config/env var rather than passed on the command line, change it there. Do not touch the service, port mappings, container, tonic version, or probe code. Keep the change scoped to local Windows + Docker Desktop connection strings; this is not a reason to force IPv4 in shared or production configs.

**Confirmation**

1. Rerun the probe against `127.0.0.1:50051` with the same method/payload/timeout: expect exit 0 and `pong` on stdout (already observed in the captured comparison).
2. Check the service interceptor log for the matching `probe method="unary Echo" transport=h2c invoked=true completed=true` line (already observed).
3. Optionally rerun against `localhost:50051` once more to reconfirm the asymmetry is address-only; it should still return exit 2 / `DEADLINE_EXCEEDED`. If it instead succeeds, the resolution order changed and the diagnosis should be revisited.

If the `127.0.0.1` call ever starts failing too, that is the point to investigate the service, port publishing, and container health.
