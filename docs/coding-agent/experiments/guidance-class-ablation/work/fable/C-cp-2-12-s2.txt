**Verdict: not acceptable as-is. The change does not do what the task asks; it replaces a UI transition with a foreground restart while leaving the tenant material in place.**

## Findings

### 1. `src/Session.kt` — `Session.logout()` never clears `tenantKeys` (blocking)

`logout()` still only calls `credentials.clear()`. `tenantKeys` — the previous tenant's session material that the task is explicitly about — survives logout untouched. Because `Session` is a service-owned cache shared with background sync, the service keeps the old tenant's keys and background sync will keep using them after the user has logged out, and after a subsequent login they can be mixed with the new tenant's state.

This is the root cause, and the diff doesn't touch it.

**Require:** clear the tenant material in `logout()` itself, so the invariant "after `logout()` returns, the `Session` holds no credential or tenant material" is owned by `Session` and holds for every caller (screens *and* background sync), not just the one that happens to restart the app:

```kotlin
fun logout() {
    credentials.clear()
    tenantKeys.clear()
}
```

Since login and sync already run on the same serialized session executor, this clear should run through that executor too (or be invoked from it), so ordering relative to an in-flight sync is by construction rather than by luck.

### 2. `src/Session.kt` — `LogoutScreen.confirm()`: `app.restart()` is compensating logic that doesn't reach the state it's meant to clean (blocking)

Per the reviewer notes, `App.restart()` restarts only the foreground process. The service that owns the `Session`/`tenantKeys` is unaffected. So this change:

- does nothing for the background-sync half of the task,
- only "works" for the foreground by throwing the whole process away instead of clearing the specific state, which masks the fact that `logout()` is incomplete, and
- silently changes user-visible behavior (a restart instead of the signed-out screen) for reasons unrelated to the stated task, with a commit message that describes the mechanism rather than the requirement.

If any other code path calls `session.logout()` without going through `LogoutScreen`, it gets no cleanup at all — the "fix" is bound to one caller.

**Require:** revert this line to `app.showSignedOut()` (or whatever the intended post-logout UX is) and rely on `Session.logout()` being correct per finding 1. If there is a separate, genuine reason to restart the foreground on logout, that should be its own change with its own justification; it must not be the mechanism by which session material gets dropped.

### 3. `src/Session.kt` — `tenantKeys` is a public mutable map (non-blocking, worth doing while here)

`val tenantKeys = mutableMapOf<String, String>()` lets any holder of a `Session` add, remove, or retain entries independently of `logout()`, which is how this bug is able to exist without anyone noticing. Tightening this makes the invariant from finding 1 harder to break:

```kotlin
private val tenantKeys = mutableMapOf<String, String>()
fun tenantKey(id: String): String? = tenantKeys[id]
fun putTenantKey(id: String, key: String) { tenantKeys[id] = key }
```

Not required to land the fix, but I'd ask for it or a follow-up ticket.

## Summary of what I'd expect to see instead

- `Session.logout()` clears both `credentials` and `tenantKeys` (run on the session executor).
- `LogoutScreen.confirm()` keeps calling `session.logout()` then `app.showSignedOut()`.
- Ideally a test that, after `logout()`, a background-sync read of tenant material returns nothing.
