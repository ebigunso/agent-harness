## Cause

This is a workspace/environment problem, not a bug in the computation.

`print(summary)` writes to `stdout`, which in this captured-pipe environment is bound to the legacy **cp932** codec (`sys.stdout.encoding = cp932`, `utf8_mode = 0`). The em dash `\u2014` in `'Summary — complete'` has no cp932 representation, so encoding raises `UnicodeEncodeError` at write time. The summary itself computed fine — the failure is purely on output encoding.

Because stdout is a redirected pipe (not an interactive console), Python defaults to the ANSI/OEM code page rather than UTF-8, which is why you hit cp932 here.

## Partial-effect check (before rerun)

Safe to rerun as-is:
- The summary is a **read-only** computation.
- **No files were written** (confirmed in observations).
- stdout produced nothing (empty), so no partial/corrupt output landed anywhere.

Nothing to clean up.

## Smallest safe remediation

Set the encoding for just this invocation via a **command-scoped** environment variable, then rerun — no code change:

PowerShell 7.4:
```powershell
$env:PYTHONIOENCODING='utf-8'; python report.py
```

This makes CPython encode stdout as UTF-8 for this process only, leaving the shell session and the script unchanged.

(If you owned the script and wanted a durable fix instead, the equivalent one-liner is `sys.stdout.reconfigure(encoding="utf-8")` near the top, and any file writes should use `open(..., encoding="utf-8")`. But for the smallest safe step, prefer the env var.)

3. **No new error:** stderr is empty.
