**Findings**

1. **lib.rs, `route` — destructuring order contradicts the tuple contract (blocking).**
   `policy::flags` is documented and implemented as `(retry, reject, quarantine)`, but `route` binds it as `(retry, quarantine, reject)`. The middle and last positions are swapped, so code 2 (reject) yields `"quarantine"` and code 3 (quarantine) yields `"reject"`. Every non-retry rejection is misrouted; the notes say the parser guarantees the range, so nothing upstream will catch this. Require the binding to match the declared order: `let (retry, reject, quarantine) = policy::flags(code);`. If the actual intent of "route rejected uploads for inspection" is that code 2 should land in the quarantine/inspection path, that must be expressed explicitly (e.g. map code 2 → `"quarantine"` deliberately, with a comment and the notes updated), not achieved by accident through a mislabeled destructure that also breaks code 3.

2. **policy.rs — `(bool, bool, bool)` is an unsafe interface for exactly this reason.**
   Three unlabeled, mutually exclusive booleans whose meaning lives only in a comment in another module is what produced defect #1, and it will produce it again the next time someone touches either side. Nothing in the type system distinguishes positions, and the "exactly one is true" invariant is unenforced. Require an enum (`Status::{Accept, Retry, Reject, Quarantine}`) with a `from_code` and a `match` in `route`; at minimum a struct with named fields. Also, since `mod policy` is private and `flags` is only consumed by `route`, the "documented only in the policy module" caveat is a maintenance hazard that an enum eliminates.

3. **No tests for the new mapping.**
   A four-line table (0/1/2/3 → accept/retry/reject/quarantine) would have caught #1 immediately. Require unit tests covering each code before merge.

Not acceptable as-is: #1 is a functional regression for the exact behavior the change is meant to add.
