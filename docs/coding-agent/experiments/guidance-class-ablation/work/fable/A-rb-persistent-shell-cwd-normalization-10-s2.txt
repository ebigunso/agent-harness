**Cause**

This is a working-directory drift in the persistent shell, not a workspace or repository problem. The earlier `Set-Location -LiteralPath 'C:/work/notes'` moved the shell's cwd to `C:/work/notes`, which contains only `today.txt` and has no `.git` in it or any parent. `git status --porcelain` therefore correctly reported `fatal: not a git repository` with exit 128. The tool UI's remembered root (`C:/work/repo`) is separate from the shell's actual cwd, which is why the two disagreed. The repo itself is intact (`C:/work/repo/.git` and `README.md` are present and readable); nothing about code, branch, PATH, config, or permissions changed.

**Smallest safe remediation**

Return the shell to the intended base before running git, or make the command cwd-independent:

```powershell
Set-Location -LiteralPath 'C:/work/repo'
git status --porcelain
```

or, without changing the shell state:

```powershell
git -C 'C:/work/repo' status --porcelain
```

No repair to the repository, no `git init`, no re-clone, and no environment change is needed. To prevent recurrence in a long-lived shell, either avoid leaving `Set-Location` side effects (use `Push-Location`/`Pop-Location`) or always pass `-C <path>` to git.

**Confirmation**

1. `pwd` (or `(Get-Location).Path`) prints `C:/work/repo`.
2. `git rev-parse --show-toplevel` prints `C:/work/repo`.
3. `git status --porcelain` exits 0 with empty stderr; empty stdout means the tree is clean.

The captured comparison already shows exactly this: after `Set-Location -LiteralPath 'C:/work/repo'`, the identical command exited 0 with no output on either stream, and the final `pwd` is `C:/work/repo`. Since only the navigation differed between attempts, that confirms the cause and the fix.
