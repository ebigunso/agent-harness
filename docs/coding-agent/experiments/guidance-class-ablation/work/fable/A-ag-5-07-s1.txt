1. **`approval.rb`, `approve!` — two separate `update!` calls with no transaction.**
   Each `update!` commits on its own (no caller transaction, per notes). After the first commit the row is `status: "approved", approver_id: NULL`, which is exactly the state the invariant forbids, and observers can read it. If the second `update!` fails (validation, DB error, process dies), the record is left permanently in that invalid state. Worse: if the "required approver ID" validation is conditional on approved status, the first `update!` raises `RecordInvalid` every time and the method never succeeds at all; if it's unconditional, the sequencing is merely racy rather than broken. Either way the split is wrong.

No transaction wrapper needed once it's one statement; if there's a reason to keep two writes, wrap them in `transaction do ... end`, but there isn't one here.

   The argument is named `approver` (implies a model object) but is assigned to `approver_id`. If callers pass a `User`, AR will cast the object to an integer (Rails 7 raises or coerces to garbage depending on the type); if callers pass an id, the name is misleading.
