**Cause**

Not a service, build, or workspace-file problem. `localhost` resolves to `::1` first, so the gRPC channel targets `[::1]:50051`. Docker Desktop's IPv6 port proxy accepts the TCP connect but never returns HTTP/2 response headers, so the client sits at the transport layer until the 2s deadline (exit 2, `DEADLINE_EXCEEDED`). The evidence lines up:

- The identical call to `127.0.0.1:50051` returns `pong`, exit 0, and the interceptor log shows `invoked=true completed=true`.
- The failed call never appears in the interceptor log — the request never reached the service.
- The HTTP/1.1 sibling on `localhost:50080` works because only HTTP/2 stalls on the IPv6 proxy path.

The only variable between success and failure is the address family of the target. The service and port mappings are fine.

**Smallest safe remediation**

Change the gRPC target from `localhost:50051` to `127.0.0.1:50051` (in the probe invocation and wherever the local connection string is configured). If you want to make the intent explicit and immune to resolver ordering, gRPC C++ also accepts `ipv4:127.0.0.1:50051`.

Do **not** reach for broader changes (disabling IPv6 on the host, editing `hosts` to drop `::1`, changing Docker networking, or altering probe/deadline settings). Those affect more than this one client and aren't needed. Scope the change to local Docker Desktop connection strings — don't hardcode `127.0.0.1` into shared or non-local configs.

**Confirmation**

1. `probes/grpc_probe.exe --target 127.0.0.1:50051 --timeout 2` → exit 0, stdout `pong`, empty stderr. (Already demonstrated in the captured comparison.)
2. Interceptor log shows a new entry `method="unary Echo" transport=h2c invoked=true completed=true` for that call.
3. Optional control: re-run with `--target localhost:50051` once more and confirm it still fails with exit 2 — proves the fix is the address, not a transient state.
4. Confirm the REST sibling still returns `200` in ~10ms so nothing else moved.

Note: this scenario is synthetic, but the asymmetry shown is exactly the known Docker Desktop-on-Windows IPv6/h2c behavior; the same diagnostic (IPv4 retry vs `localhost`) is the right first step in a live case.
