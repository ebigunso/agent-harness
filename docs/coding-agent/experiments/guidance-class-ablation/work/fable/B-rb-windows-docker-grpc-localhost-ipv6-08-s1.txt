**Cause**

This is not a fault in the service, the probe, or the project build. It is a loopback-address asymmetry on the host.

- `localhost` resolves to `::1` first; the failing channel used `[::1]:50051`.
- Docker Desktop's IPv6 port proxy accepts the TCP connect but never delivers HTTP/2 response headers, so the gRPC channel sits at the transport layer until the 2s deadline → probe exit 2, `DEADLINE_EXCEEDED`.
- The service interceptor log shows no invocation for the failed call, confirming the request never reached the container.
- The sibling REST port works over the same `localhost` name because HTTP/1.1 is not affected by the proxy's HTTP/2 stall.
- The controlled comparison (only the target changed to `127.0.0.1:50051`) succeeded in-deadline with `pong`, and the service logged `invoked=true completed=true`. Everything else — container, port mappings, method, payload, deadline, config — was identical.

So the service is healthy; the `localhost` → `::1` path through Docker Desktop's IPv6 proxy is what hangs.

**Smallest safe remediation**

Change the gRPC target from `localhost:50051` to `127.0.0.1:50051` in the connection string used for local Docker Desktop testing (the probe invocation and any local config/script that sets the target). Do not touch the service, port publishing, timeouts, or the probe's resolution logic. No TLS/SNI concern applies since this is plaintext h2c with no certificate-name check.

If the target lives in a config file or environment variable, changing only that value is preferable to editing code.

**Confirmation**

1. Re-run the original command with the corrected target:
   `probes/grpc_probe.exe --target 127.0.0.1:50051 --timeout 2`
   Expect exit 0, stdout `pong`, empty stderr, and a service log line `probe method="unary Echo" transport=h2c invoked=true completed=true`.
2. Optionally re-run with `localhost:50051` once more to confirm the failure is reproducible and address-specific (exit 2, `DEADLINE_EXCEEDED`, no interceptor log entry). That two-point contrast is the evidence that the fix addresses the actual cause rather than coinciding with a transient recovery.
3. Confirm the REST sibling still returns `200` on port 50080 to show nothing else changed.

If the `127.0.0.1` call were to also fail, then — and only then — investigate the service, port publishing, and container health. The captured comparison already shows it does not, so no further workspace investigation is warranted.
