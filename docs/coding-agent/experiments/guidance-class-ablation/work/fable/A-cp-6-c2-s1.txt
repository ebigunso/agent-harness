**Verdict:** the mapping itself is correct for the stated scope (three required fields, camelCase view keys, zero tax round-trips), but I would not approve as-is because the verification that the commit message and notes lean on doesn't actually run. Findings:

1. **`invoice.py` – `check()` is never invoked and is not a test.**
   It's a plain function with bare `assert`s: nothing calls it, no test runner will discover it (no `test_` prefix, not in a test module), and under `python -O` the asserts are stripped anyway. The reviewer notes claim "round-trip check exercises every required field," but as landed it exercises nothing. Require: move it to `tests/test_invoice.py` as `test_round_trip` (parametrized over the two cases), or at minimum call it from an existing test entry point. Also add the reverse direction (`to_view(to_proto(view)) == view`) since "lossless" is a two-way claim.

2. **`to_proto` constructs `InvoiceProto` positionally.**
   `InvoiceProto(view["id"], view["amount"], view["taxAmount"])` silently mis-maps if the dataclass field order ever changes; `amount` and `tax_amount` are both `int`, so nothing type-level would catch it. Require keyword construction: `InvoiceProto(id=view["id"], amount=view["amount"], tax_amount=view["taxAmount"])`.

3. **`to_proto` does no validation of required fields or types.**
   A missing key surfaces as a raw `KeyError('taxAmount')` from deep inside the mapper, and wrong types (`"100"`, `100.0`, `True`) are accepted and stored in the frozen dataclass without complaint — the round-trip check won't catch these because equality still holds. For a function whose contract is "required fields, lossless," I'd want at least an explicit check that all three keys are present with a clear error, and that `amount`/`tax_amount` are `int` (and not `bool`). If the team's convention is "trust the view," say so in a docstring; right now the function's behaviour on bad input is undefined-by-accident.

4. **Flag (needs an answer, not necessarily a change): integer width of `amount`/`tax_amount`.**
   If the upstream proto fields are `int64` and this "view" is serialized to JSON for a JS client, values above 2^53 lose precision — which is why protobuf's own JSON mapping emits int64 as strings. If the fields are `int32`/`sint32` or the view never leaves Python, this is a non-issue. Please confirm the field type in the schema and, if int64, either emit strings or document the bound.

5. **Nit:** no blank lines between top-level definitions and no type hints on `to_view`/`to_proto`. Wouldn't block on it, but run the formatter and annotate (`-> dict[str, Any]`, `view: Mapping[str, Any] -> InvoiceProto`) so the contract is visible.

Items 1 and 2 I'd require before merge; 3 and 4 I'd want addressed or explicitly answered; 5 is cosmetic.
