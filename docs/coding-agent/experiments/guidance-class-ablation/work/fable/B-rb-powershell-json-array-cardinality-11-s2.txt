**Cause:** not a workspace/environment problem — it's a logic bug in the probe. Line 5 wraps the parsed value in `@(...)`:

```powershell
$parsed = @($raw | ConvertFrom-Json)
```

`@()` unconditionally produces an `Object[]`, so `$parsed -is [array]` is true for *any* input, including the scalar wire value `7`. The assertion on line 10 therefore fires exactly as written; the failure is the script's own guard, not the runtime (7.4.6 parses `7` correctly as `Int64`; the stdout `parsed type=System.Object[]` is the `@()` wrapper, not the JSON). Per the reference, a post-parse `-is [array]` check reflects PowerShell collection handling (here, forced wrapping; in other cases pipeline unrolling), never wire framing.

**Smallest safe remediation:** test framing on the raw serialized string instead of on the parsed object. Replace lines 5 and 10:

```powershell
$parsed = ConvertFrom-Json -InputObject $raw
...
$t = $raw.Trim()
$isWireArray = $t.StartsWith('[') -and $t.EndsWith(']')
if ($isWireArray) { throw 'Scalar wire JSON accepted as array' }
```

(Alternative on pwsh 7+: drop the `@()` and use `$parsed = ConvertFrom-Json -InputObject $raw -NoEnumerate`, then keep `-is [array]`. That works on 7.4.6 but not Windows PowerShell 5.1; the raw-framing check works on both, so it's the safer minimal change.)

The one-element case `'[7]'` is the important one — the raw check keeps it an array regardless of whether the parsed value is later unrolled.
