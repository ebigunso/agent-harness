**Findings**

1. **`order.php`, `adminTotal()` — breaks the authoritative model.**
   The reviewer notes define `total` as *the sum of line amounts*. `adminTotal` writes `total` directly, so after it runs, `$order["total"] !== array_sum($order["lines"])`. There is now no single source of truth: anything that reads `lines` (reports, refunds, invoices, re-validation) disagrees with `total`, and there is no way to tell from the data whether an admin adjustment happened or the record is corrupt.
   *Require:* represent the adjustment inside the model rather than bypassing it — either append an adjustment line (e.g. `$order["lines"][] = $delta` / a keyed `"admin_adjustment" => $delta` entry) or add an explicit `$order["adjustment"]` field, and have one function derive `total = array_sum(lines) + adjustment`. `adminTotal` should never assign `total` itself.

2. **`order.php`, interaction between `setLines()` and `adminTotal()` — the two writers clobber each other, even serially.**
   Order A: `adminTotal($o, 900)` then `setLines($o, [...])` → `setLines` recomputes `total` and the admin adjustment is silently lost. Order B: `setLines` then `adminTotal` → lines and total diverge (finding 1). Since the note says both writers run in sequence, this is not a race; it is a design conflict that will occur in normal use. Last-writer-wins with no record of the admin's intent is not acceptable for money.
   *Require:* both paths update the same model (lines and/or adjustment field) and both go through the same recompute step, so the result is order-independent and the adjustment survives a later line edit.

3. **`order.php`, `adminTotal()` — no bound on the override.**
   Notes say "integer cents, bounded sums." `setLines` inherits bounds from the lines; `adminTotal` accepts any `int`, including negative or absurdly large values, with no check. Once the adjustment is modelled as a delta (finding 1), it should be validated against the same bounds as line amounts.
   *Require:* validate the adjustment (and resulting total) against the existing bounds; reject rather than store out-of-range values.

Minor/style, would not block on its own: the one-line `adminTotal` and the two statements on one line in `setLines` should be formatted like the rest of the codebase, and `setLines` should assert each line is an `int` before `array_sum` (floats/strings would silently produce non-cent totals).

**Verdict:** not acceptable as-is. The change needs to be restructured so the admin adjustment is data inside the order model and `total` is always derived, never assigned.
