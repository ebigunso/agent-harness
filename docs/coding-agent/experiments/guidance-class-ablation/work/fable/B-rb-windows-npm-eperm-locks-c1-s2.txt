**Cause**

`npm ci` refused to run because `package.json` and `package-lock.json` disagree: `package.json` now asks for `is-number@7.0.0` (an intentional edit), but the lockfile still pins `is-number@6.0.0`. `npm ci` is strict by design — it installs exactly what the lockfile says and errors (`EUSAGE`) if the manifest doesn't match. The dependency resolution for the bump was never completed, so the lockfile is stale.

This is a repository-state problem (lockfile drift), **not** a workspace/environment problem. Nothing is locked, permissions are fine, the registry is reachable, and no native addon was involved. The loaded EPERM/EBUSY reference material does not apply here: the `tasklist /m better_sqlite3.node` result ("No tasks…") is consistent with that, and no process should be killed.

**Smallest safe remediation**

Regenerate the lockfile to match the intended manifest, then re-run `npm ci`:

```powershell
cd C:\work\npm-lock
npm install          # resolves is-number@7.0.0 and rewrites package-lock.json
npm ci               # now succeeds against the updated lockfile
```

Notes:
- `npm install` is the tool npm itself recommends in the error; it only needs to touch the `is-number` entry (and anything that transitively depends on it).
- If you'd rather not touch `node_modules` at all during the lockfile refresh, `npm install --package-lock-only` updates just `package-lock.json`, then `npm ci` does the real install.
- Commit the updated `package-lock.json` alongside the `package.json` change so CI and other developers don't hit the same error.

**Confirmation**

1. `npm ci` exits 0 with no `EUSAGE` message.
2. `npm ls is-number` reports `is-number@7.0.0`.
3. `Select-String '"node_modules/is-number"' -Context 0,2 package-lock.json` (or a quick look at the file) shows `"version": "7.0.0"`; `git diff package-lock.json` should show only the is-number-related change, not unexpected churn.
