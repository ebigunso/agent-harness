2. **`plugins.cpp`, `registry` initializer — exception thrown during dynamic initialization of a namespace-scope object.**
   `resolve` throws `std::runtime_error` from inside the initializer of a global. An exception escaping static initialization cannot be caught by anyone; it calls `std::terminate` before `main` runs. The "missing plugin: …" message is not reliably surfaced (typically just `terminate called after throwing…` plus an abort). So the claimed error handling is not usable: it converts a link-time error into a pre-`main` abort. Even if the dlsym approach were kept, the lookup would need to be lazy and the failure reportable from a context that can handle it.

3. **`plugins.cpp`, `resolve()` — correctness now depends on build/link flags and a non-standard extension.**
   `dlsym(RTLD_DEFAULT, …)` finding symbols in the executable requires `-rdynamic` (or equivalent export), and `RTLD_DEFAULT` is a glibc/BSD extension gated on `_GNU_SOURCE`, not POSIX. Dropping `-rdynamic`, adding `-fvisibility=hidden`, or building with a different toolchain/libc silently turns a working binary into one that aborts at startup (see #2). The `reinterpret_cast<Handler>(void*)` is also only conditionally supported by the standard. None of this cost buys anything here: both handlers are defined in this same translation unit.

4. **`plugins.cpp`, `resolve()` — implicit naming contract with no enforcement.**
   The `"handle_" + label` concatenation only works because the handlers are `extern "C"`. A future handler written without `extern "C"` (or in a namespace) will compile, link, and then fail lookup at runtime. The old form had no such hidden contract. If a name-based scheme were ever genuinely needed (loading handlers from external `.so` files), it should be explicit about that boundary and separate from the in-process typed registry, not replace it.
