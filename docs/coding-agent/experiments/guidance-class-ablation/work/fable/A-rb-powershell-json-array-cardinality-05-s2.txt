**Cause — a script bug, not a workspace/runtime problem.**

`ConvertFrom-Json` in Windows PowerShell 5.1 does return the JSON array as a single `Object[]`, but the script then pushes it through `| Write-Output`. That pipeline stage enumerates the array, so the single element is emitted on its own and `$parsed` receives a bare `PSCustomObject` (stdout confirms: `parsed type=System.Management.Automation.PSCustomObject`). The `-isnot [array]` check then correctly throws. The raw JSON, the environment, and the runtime are all fine; the cardinality was destroyed by the script's own pipeline. (The same construction would also turn `[]` into `$null` and `[[1,2]]` into an inner array, so it's not just a singleton problem.)

**Smallest safe remediation**

Drop the redundant `| Write-Output` on line 5:

```powershell
$parsed = $raw | ConvertFrom-Json
```

On 5.1 this preserves the contract exactly: `[]` → `Object[]` (length 0), `[{"id":8}]` → `Object[]` (length 1), multi-element → `Object[]`, and a scalar wire value such as `8` → `Int32`, which still fails the `-isnot [array]` check as required. Do **not** "fix" it with `@(...)`, since that would wrap scalars into arrays and silently break the scalar-rejection rule.

Portability note: if this probe is ever run under PowerShell 7, `ConvertFrom-Json` enumerates arrays by default there, and you'd need `ConvertFrom-Json -NoEnumerate` (that switch does not exist in 5.1, so don't add it now).

**Confirmation**

1. Rerun `powershell.exe -NoProfile -File probes/cardinality.ps1`; expect exit code 0, no stderr, and stdout ending in `parsed type=System.Object[]`.
2. Spot-check the contract edges in the same shell:
   ```powershell
   ('[]' | ConvertFrom-Json) -is [array]          # True
   ('[{"id":8}]' | ConvertFrom-Json).Count        # 1
   ('[1,2]' | ConvertFrom-Json).Count             # 2
   ('8' | ConvertFrom-Json) -is [array]           # False (scalar still rejected)
   ```
