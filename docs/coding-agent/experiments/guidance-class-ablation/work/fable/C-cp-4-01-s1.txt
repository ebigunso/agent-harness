1. **`Pricing.java`, `isEligible` (blocking)** — A boolean query now has a hidden side effect: it writes the static `discount` that `price` silently reads. The correctness of `price(cents)` now depends on whether, and when, some *other* method was called on the class. Per the notes, only the UI calls `isEligible` first; every other caller of `price` gets either `0` (never set this session) or whatever value the last `isEligible` call left behind — including a member discount leaking into a non-member's price, or a non-member call clearing a member's discount, within the same session. The name `isEligible` gives no hint of this; a reader of `price` sees no input that explains the result. That is exactly the hidden coupling / non-local reasoning this review is meant to catch, and the "session reset per order" note doesn't rescue it because the ordering problem is intra-order.

   Require instead: make the dependency explicit in the signature and drop the mutable static. E.g. `static int price(int cents, boolean member) { return cents - discountFor(member); }` with `private static int discountFor(boolean member) { return member ? 10 : 0; }`. `isEligible` stays a pure predicate (or is removed if it's now just an identity). Callers that "use `price` directly" must then pass the membership flag, which is the point — they can't get a wrong answer by accident.
