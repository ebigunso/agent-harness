**Verdict: not acceptable as-is.** The change is labeled "additive" but it is a source-breaking change to the Java API, and "optional" is asserted rather than modeled.

## Findings

### 1. `Invoice.java` — record signature change breaks every existing constructor call site
`record Invoice(String id)` → `record Invoice(String id, String label)` replaces the canonical constructor. There is no `Invoice(String)` anymore, so every `new Invoice(id)` in the codebase (and any pattern match `Invoice(var id)`) fails to compile. Records have no default parameter values, so nothing about this is additive for Java callers — only the JSON wire shape is additive (and only for readers that tolerate unknown fields, which is what the reviewer notes actually verified).

The commit message and notes claim "additive optional metadata"; the impact statement is wrong for the in-process producer/consumer boundary.

**Require:** either state the impact as *breaking* and update all call sites in the same change, or make it genuinely additive by adding a compatibility constructor:
```java
record Invoice(String id, String label) {
    Invoice(String id) { this(id, null); }
}
```

### 2. `Invoice.java` — "optional" is not expressed in the type or contract
`String label` with no annotation, no `Optional`, no compact-constructor normalization, and no documentation of the absent value. A caller cannot tell whether absence is `null`, `""`, or forbidden, and equality/hashing of records will treat `null` and `""` as distinct invoices. This is exactly the ambiguous input/output contract the review criteria call out.

**Require:** pick one representation and make it explicit — e.g. `@Nullable String label` with a comment "null = no label", or a compact constructor that normalizes `""`/blank to `null` (or the reverse). If there are constraints (max length, trimming), enforce them in the compact constructor so invalid labels fail at construction, not downstream.

### 3. Commit/notes — the compatibility claim is scoped to the wrong boundary
The notes justify safety via `@JsonIgnoreProperties(ignoreUnknown=true)` on `Reader`. That covers one JSON consumer. It says nothing about: other JSON consumers of `Invoice` that don't set `ignoreUnknown`, or the Java callers above. A reviewer reading "additive" would merge this expecting zero consumer changes.

**Require:** an accurate impact statement — "JSON: additive (new nullable field); Java API: breaking unless (1) is applied" — and confirmation that all `Invoice` deserializers tolerate the new field (or a note that `Invoice` is producer-only).
