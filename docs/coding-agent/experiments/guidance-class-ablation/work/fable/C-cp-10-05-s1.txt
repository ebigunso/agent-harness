**Verdict: block.** The change achieves the visible goal (a `label` field on `Record`) by dismantling the mechanism that is supposed to produce it.

## Findings

**1. `build.rs` — the entire generator was deleted and replaced with `fn main() {}`.**
This is far outside the stated task ("add label to protocol record") and is not mentioned in the commit message. After this lands, `schema.fields` is dead input, `generated.rs` is a hand-maintained file that still claims to be generated, and the `rerun-if-changed` hook is gone. Anyone who later restores or re-runs the generator (the notes say a regeneration is planned) will overwrite the hand edit. Also, an empty `build.rs` still forces a build-script compile and run on every clean build for zero benefit — if it were genuinely unneeded, the file should be removed, not stubbed.
*Require:* restore `build.rs` unchanged. If there is a real reason to retire the generator, that is a separate, explicitly justified PR that also renames/re-homes `generated.rs` and removes `schema.fields`.

**2. `schema.fields` does not contain `label`; `generated.rs` was edited by hand.**
The schema file ends up with only `id:u32`, while `generated.rs` has `id` and `label`. The source of truth and the artifact now disagree, and the artifact is the one that got the change. This is exactly the drift a generator exists to prevent, and it is silent: nothing will fail until the next regeneration drops `label` and downstream code stops compiling (or worse, a wire layout changes without anyone touching the schema).
*Require:* add `label:String` to `schema.fields`, run the existing generator, and commit the regenerated `generated.rs`. The diff to `generated.rs` should be byte-identical to generator output, not a manual edit.

**3. `generated.rs` — `String` needs to be confirmed against the schema's allowed type set.**
The notes say this private schema has a fixed set of allowed field types. The generator does not enforce that set, so a hand edit trivially bypasses it. `String` also changes the character of `Record` (heap-owning, not `Copy`, variable-length) in a way a "protocol record" type may not be expected to have, even if there are no external serialization consumers yet.
*Require:* state which allowed type `label` maps to. If `String` is permitted, fine; if the intended type is something else (bounded/fixed-width, `&'static str`, an interned id), use that. Independently, the generator would benefit from rejecting unknown types so this can't be bypassed — but that is a follow-up, not a condition of this PR.

**4. Commit message omits the scope change.**
"add label to protocol record" describes one line of the diff; the removal of the build pipeline is the material change and is undisclosed. Reviewers and `git blame` readers need to see it.
*Require:* commit message that reflects what the change actually does (after fixing #1 it should again be accurate as written).

## Non-blocking note

`src/lib.rs`'s `include!("../generated.rs")` plus a build script that writes into the source tree is pre-existing and works, but it is a known Cargo anti-pattern (breaks `cargo package --verify`, read-only checkouts, and parallel builds). Not introduced here; worth a ticket. Likewise, a cheap diagnostic improvement for later would be to have `build.rs` fail with a clear message when the checked-in `generated.rs` differs from fresh generator output instead of silently rewriting it — that would have caught this exact PR.
