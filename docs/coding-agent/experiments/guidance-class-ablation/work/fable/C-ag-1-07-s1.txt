**Findings**

1. **`order.rb`, `Order#summary` — read path triggers a write command.**
   `summary` is a serializer (task: "serialize paid order summaries"), but it calls `fulfill!(outbox)` whenever the order is paid. That means listing, rendering, logging, or debugging an order enqueues a fulfillment request as a side effect. The reviewer notes are explicit: "listing/serialization must not initiate fulfillment." Idempotency of the outbox insert only prevents duplicate shipments; it does not make it correct for a query to initiate a business command. It also breaks the layering guidance: a serialization method is presentation/data-shaping, and a state-changing domain command has no business being invoked from it.
   **Require:** `summary` must be pure — return the hash and nothing else. Fulfillment should be initiated by an explicit application-level command (e.g. a `FulfillOrder` service / use case, or a controller action that calls `order.fulfill!(outbox)` deliberately), not as a hidden consequence of reading. If the author's actual intent was "fulfill paid orders and then summarize them," that should be two calls at the call site, not one method that does both.

2. **`order.rb`, `Order#summary(outbox)` — serializer signature leaks infrastructure.**
   A summary method taking an `outbox` parameter exists only to support finding #1. Once the side effect is removed, the parameter is dead and should go; leaving it invites callers to keep threading infrastructure into a read-only method.
   **Require:** `def summary` with no arguments.

3. **`order.rb`, `fulfill!` — `outbox[id] ||= :requested` is a placeholder, not an outbox insert.**
   The notes say fulfillment is "an outbox insert keyed by order ID," but the implementation writes into an arbitrary hash-like object passed in. That's fine as a test seam, but as the sole implementation of a domain command it means the model's correctness depends on whatever the caller happens to pass. This is a lower-priority flag than #1; I'd want the outbox to be a real collaborator with a defined interface (e.g. `outbox.enqueue(order_id: id)`), or at minimum a note that this is intentionally a stub.
   **Require:** either wire to the actual outbox abstraction or document the stub; do not leave the domain command's behavior defined by an untyped hash.

4. **Commit message doesn't describe the behavior shipped.**
   "serialize paid order summaries" describes a read; the diff introduces a write triggered by that read. Anyone bisecting a "why did fulfillment fire when I opened the orders page" bug won't find it from the log.
   **Require:** once #1 is fixed the message is accurate; if the author disagrees with #1, the message must state that serialization initiates fulfillment so the behavior is discoverable.

**Verdict:** Block. Finding #1 is a correctness/placement defect that directly contradicts the stated requirement; the rest follow from it. Minimal acceptable version:

```ruby
class Order < ActiveRecord::Base
  def fulfill!(outbox)
    outbox[id] ||= :requested
  end

  def summary
    { id: id, status: self[:status] }
  end
end
```

with fulfillment invoked explicitly from the application layer.
