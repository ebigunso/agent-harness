**Cause:** The failure is a cwd drift problem, not a workspace/code problem. The persistent PowerShell session had already been moved into `C:/work/shop/web` by the earlier `Set-Location`. The tool UI still showed `C:/work/shop` as the root, so `cd web` was written relative to the wrong assumption and tried to enter `C:\work\shop\web\web`, which doesn't exist. `Set-Location` failed (status 1) and `&&` short‑circuited, so `npm run build` never ran. Nothing is wrong with the project, dependencies, PATH, or permissions — the comparison run from `C:/work/shop` succeeded with `tsc` and empty stderr.

**Smallest safe remediation:** Don't rely on the remembered/displayed root in a persistent shell. Either run the build from where the shell already is:

```powershell
npm run build
```

or, better, make the command independent of prior cwd by anchoring it to the absolute path:

```powershell
Set-Location -LiteralPath 'C:/work/shop/web'; npm run build
```

(or `npm --prefix C:/work/shop/web run build`). No file, config, or environment changes are needed.

**Confirmation:**
1. `pwd` before running shows `C:/work/shop/web` (or the absolute `Set-Location` returns status 0 with no stderr).

3. Optionally `Get-ChildItem -Name` afterwards shows the tsc output (e.g. `dist` or emitted `.js` next to `src/index.ts`, per `tsconfig`).

Going forward, treat the shell's own `pwd` as the source of truth rather than the tool UI's displayed root, and prefer absolute `-LiteralPath` navigation in persistent sessions.
