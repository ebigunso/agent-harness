**Cause**

This is a workspace/local-environment problem, not a service bug. On the Windows host, `localhost` resolves to `::1` first, so the .NET probe dials `[::1]:50051`. Docker Desktop's published-port proxy on the IPv6 loopback accepts the TCP connection but never returns HTTP/2 (h2c) frames, so the client's 2s deadline fires with `DEADLINE_EXCEEDED` (exit 2). The evidence lines up:

- TCP connect to `[::1]:50051` succeeds, but no HTTP/2 response headers arrive.
- The interceptor log shows no invocation for the failed call — the request never reached the service.
- The sibling HTTP/1.1 health check on `localhost:50080` returns 200 in 12 ms, so the container is up and the mapping/proxy works for HTTP/1.1; the stall is specific to h2c over the IPv6 proxy path.
- The address-only comparison at `127.0.0.1:50051` (same method, payload, deadline, server, config) succeeds with `pong`, and the service logs `invoked=true completed=true`.

The port mappings (`50051->50051`, `50080->50080`) are correct, the service is healthy, and the probe itself behaves per its contract, so nothing needs to change in the container or the probe code.

**Smallest safe remediation**

Use the IPv4 loopback for the local gRPC target instead of `localhost`. Concretely, set the local-only target to `127.0.0.1:50051` — in the local config/launch settings or the environment variable the probe reads for `--target` — and leave everything else (Docker Compose, published ports, probe source, timeouts) untouched. Do not change global hosts-file resolution or disable IPv6; that's broader than needed.
