**Verdict: this is a workspace/environment problem (host networking + address selection), not a probe, gRPC, MSVC, or service-code defect.**

## Cause

- `localhost` resolves to `::1` first, then `127.0.0.1`. gRPC C++'s pick-first policy tries `[::1]:50051`. The TCP connect *succeeds* (Docker Desktop's port-publishing proxy listens on the IPv6 loopback), so the channel commits to that subchannel and never tries `127.0.0.1` — fallback only happens on connect *failure*, not on "connected but no HTTP/2 SETTINGS/response".
- Behind that IPv6 listener, nothing reaches the service: the interceptor log shows no invocation, and the same call to `127.0.0.1:50051` completes (`pong`, `invoked=true completed=true`). So the `::1` path is accept-and-blackhole (consistent with the container process binding only IPv4, or the WSL2 forwarding path not carrying the v6-accepted connection), and the 2 s deadline expires → the probe's normalized exit 2 / `DEADLINE_EXCEEDED`.
- The `curl` sibling test does **not** contradict this: curl uses Happy Eyeballs/parallel connects and will complete on whichever address answers, and it hits a different port/proxy path anyway. It proves the container is up, not that `::1` works for gRPC.

## Smallest safe remediation

Point the probe at the IPv4 loopback explicitly instead of `localhost`:

```powershell
probes/grpc_probe.exe --target 127.0.0.1:50051 --timeout 2
```

(`ipv4:127.0.0.1:50051` is equivalent and forces the scheme.) No code change, no hosts-file edit, no system-wide IPv6 disable.

If you want `localhost` itself to work, the next-smallest fix is at the publish boundary, not in the probe: publish with an explicit IPv4 bind (`-p 127.0.0.1:50051:50051` / `"127.0.0.1:50051:50051"` in compose). With no `::1` listener, the connect to `::1` fails fast and gRPC falls through to `127.0.0.1`.

## Confirmation

1. Rerun with `127.0.0.1:50051` → expect exit 0, stdout `pong`, empty stderr, and a new `invoked=true completed=true` line in the interceptor log.
2. Rerun the original `localhost:50051` command unchanged → still exit 2 with `DEADLINE_EXCEEDED`. Same binary, same server, only the address differs — confirms the isolation.
3. Optionally corroborate the mechanism: `netstat -ano | findstr :50051` on the host shows a listener on `[::1]`/`[::]`, while inside the container the service listens on `0.0.0.0:50051` only. If you applied the publish-binding fix, `docker port <container>` should show only `127.0.0.1:50051`, and then the `localhost:50051` invocation should succeed via fallback.

Caveat: the scenario is synthetic, so the Docker address asymmetry is the constructed premise rather than a live reproduction; the diagnosis follows from the stated observations.
