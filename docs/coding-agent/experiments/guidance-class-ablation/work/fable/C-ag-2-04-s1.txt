Findings (I would block on 1 and 2; 3 is a required follow-through of the fix):

1. **`domain.ts` — domain now imports and calls the Prisma client directly.**
   `loadTotal(db: PrismaClient, ...)` puts a vendor/framework call (`db.invoice.findUnique`) inside the core module. The dependency arrow now points from the domain outward to `@prisma/client`, which is the volatile detail; any change to Prisma's API, query shape, or the generated client forces a change in core. It also makes `total`/`loadTotal` untestable without a database (or a Prisma mock). Require: keep the query in an outer/adapter layer (e.g. a repository or the caller), and have the domain expose only `total(...)` on plain values. If the domain needs an abstraction, define an inner-owned interface such as `InvoiceRepository { findById(id): Promise<Invoice | null> }` and have the Prisma adapter implement it; the domain must not name `PrismaClient` at all.

2. **`domain.ts` — `total` now takes the generated `Invoice` type instead of stable values.**
   `total(cents: number)` was a stable seam; it now takes `type Invoice` from `@prisma/client`, so the schema generator (`schema.prisma`) controls the domain's input type. Adding, renaming, or retyping a column in the schema silently changes the domain's contract, and callers that previously had a number now need a full Prisma row. This is the same inversion as (1) at the type level. Require: revert to `total(cents: number)` (or a domain-owned `Invoice` type/interface declared in `domain.ts`), and map from the Prisma row to that type at the boundary.

3. **Missing boundary/edge documentation and a public-API change without justification.**
   The task was "calculate totals from stored invoices", but the change also alters the existing exported signature of `total` (breaking existing callers) and introduces a new persistence seam with no note on where the Prisma boundary is supposed to live. Once (1)/(2) are fixed, require a short comment or module note marking the adapter as the only place that touches `@prisma/client`, and keep `total`'s original signature so existing consumers are unaffected.

Not flagged: the explicit `null` handling in `loadTotal` is fine and should be preserved wherever that lookup ends up living; the schema addition itself is reasonable for the adapter layer.
