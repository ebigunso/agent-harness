**1. `importer/load.py`, `return {"status": "complete"}` — reports success unconditionally, hiding skipped rows.**
After this change, a run with one invalid row among valid rows silently drops that row and still returns `{"status": "complete"}`. Per the reviewer notes, this summary is the *only* thing the operator sees and there is no external log of failures, so the skipped row is unrecoverable information: the operator has no way to know data was lost, which row, or why. This is worse than the pre-change behaviour (a crash at least signalled a problem). **2. `importer/load.py`, `except Exception: continue` — catches far more than "bad row".**
The intent is to skip an invalid row, but `Exception` also swallows connection loss, permission errors, a misconfigured `store`, and plain bugs in `insert`. Broad catch-and-continue turns systemic failures into invisible ones.

Require: catch the specific exception type(s) the store raises for a row-level validation/insert rejection (e.g. `ValidationError` / whatever `store.insert` documents), and let everything else propagate. If the store's error hierarchy doesn't distinguish these, that's a gap to fix or at least document, not a reason to catch `Exception`.
