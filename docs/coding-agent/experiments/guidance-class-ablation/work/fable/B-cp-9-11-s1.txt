**Verdict: Block.** The change inverts the task — it converts a crash/exception into a permanent wedge of the only dispatch thread.

**1. `src/service.cpp`, `Service::process` — unbounded retry on a deterministic failure**
`for (;;)` with `continue` on `std::bad_alloc` has no attempt limit, no backoff, and no exit. The reviewer notes state that validated input can legitimately exceed the fixed worker limit and that identical retries cannot reduce the allocation. For such an input the loop is guaranteed to spin forever: `allocate_and_run` throws, we `continue`, it throws again, indefinitely. Because there is one dispatch thread, that single request blocks every subsequent request. This is exactly the "wedged service worker" the task asked to prevent, except now it's a 100%-CPU busy loop instead of a crash, and it's harder to detect from the outside because the process looks alive. Retrying is not a valid strategy here; the failure must be surfaced. Require: catch `std::bad_alloc` and return a failed `Result` (e.g. a resource-exhausted / rejected error) so the worker moves on to the next request. If there is evidence of genuinely transient allocation failures worth retrying, that would need a small fixed attempt cap (e.g. 2–3) with backoff, and still fall through to a returned error — never an unbounded loop.

**2. Same location — failure is swallowed with no diagnostics**
The catch block discards the exception and records nothing. There is no log line, metric, or context (input identity/size, attempt count) that would let an operator see that allocations are failing or that a request was dropped for being too large. When this loop spins, the only symptom is a stuck service with pegged CPU and no explanation. Require: on the failure path, log at warning/error level with enough context to identify the input and the reason, and increment a counter/metric so allocation failures are visible in monitoring.

**3. Commit message / intent mismatch (minor, but fix alongside)**
"retry allocation until successful" describes the bug, not a fix. The notes confirm `allocate_and_run` is exception-safe (releases partial resources, no side effects before success), so the correct behavior is straightforward: fail the request, stay alive, keep serving. The commit message should describe that.

**What I'd expect instead (sketch):**
```cpp
Result Service::process(const Input& input) {
    try {
        return engine_.allocate_and_run(input);
    } catch (const std::bad_alloc& e) {
        log_error("allocation failed processing input {}: {}", input.id(), e.what());
        metrics_.increment("service.alloc_failure");
        return Result::error(ErrorCode::ResourceExhausted);
    }
}
```
Adapt to the actual `Result`/logging APIs, but the shape is: bounded, observable, and returns control to the dispatch loop.
