**Findings**

1. **`app/imports.py`, `report()` — symptom patch, not a fix.**
   The dedupe is applied at read time, but the duplicates are created at write time in `import_rows()` (unconditional `store.append(row)`). After this change the store still accumulates a duplicate record every time an import is rerun; `report()` just stops showing them. Anything else that reads `store.rows()` (other reports, exports, counts, downstream jobs) still sees duplicates, and the data problem grows silently. The commit message ("hide repeated IDs") states this outright.

If the store can be changed, the stronger fix is an ID uniqueness invariant in the store itself so no writer can violate it; `import_rows` then just calls it.

2. **`app/imports.py`, `cli_import()` / `scheduled_import()` — task not addressed.**

3. **`app/imports.py`, `report()` — compensating logic with silent last-wins semantics.**

If two stored rows share an ID but differ in content, the report now silently picks one and masks a real data-integrity problem. It also means `report()` no longer reflects what is in the store, so a divergence between the two is invisible.
