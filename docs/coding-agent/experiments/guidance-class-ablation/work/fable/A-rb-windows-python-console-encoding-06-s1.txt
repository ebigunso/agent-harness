**Cause**

Not a workspace/code-logic problem — it's an output-encoding mismatch. The script did its work (both trees read and compared, `diff == 'before — after\n'`). It failed only on the final write because:

- stdout is a pipe, not an interactive console, so Python doesn't use the console's UTF-16 path; it falls back to the locale ANSI code page.
- On this machine that's **cp932** (Shift-JIS), and `sys.flags.utf8_mode == 0`, so nothing overrode it.
- U+2014 (EM DASH, the `—` in `before — after`) has no cp932 mapping → `UnicodeEncodeError`, exit 1.

**Smallest safe remediation**

Don't touch `tree_diff.py`. Run it in UTF-8 mode for this invocation only:

```powershell
$env:PYTHONUTF8 = 1
python tree_diff.py
```

(equivalently `python -X utf8 tree_diff.py`). This sets `sys.stdout.encoding` to `utf-8` regardless of the pipe/locale. It is read-only and has no side effects beyond the process.

If whatever is on the other end of the pipe is PowerShell itself (e.g. `python tree_diff.py | Out-File` or capture into a variable), also make PowerShell decode the bytes as UTF-8, or the `—` will come through as mojibake:

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
```

If this needs to be permanent, the least invasive code change is `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` at the top of the script — but I wouldn't make that change until the env-var fix is confirmed.

**Confirmation**

1. `python -c "import sys; print(sys.stdout.encoding, sys.flags.utf8_mode)" | Out-String` → expect `utf-8 1` in the same captured-stream context.
2. Rerun `python tree_diff.py` the same way; `$LASTEXITCODE` should be `0`, stderr empty, stdout `before — after` with the dash intact (check the bytes if in doubt: `E2 80 94`).

__ABLATION_DONE__ exit=0
