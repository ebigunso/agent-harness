**Cause**

This is a local Docker-networking (workspace) problem, not a server or probe defect.

- `localhost` resolves to `::1` first, so the gRPC channel dials `[::1]:50051`.
- Docker Desktop's published-port proxy on `::1` accepts the TCP connection but never returns HTTP/2 frames for the h2c stream, so the probe sits until its 2 s deadline → exit 2, `DEADLINE_EXCEEDED`.
- The server never saw the request (no interceptor log entry), which rules out slow handlers, auth, or method mismatch.
- The REST sibling on 50080 is fast because HTTP/1.1 through the same proxy path doesn't stall — the asymmetry is protocol-specific, not "the container is down."
- The controlled comparison proves it: identical call to `127.0.0.1:50051` returns `pong`, exit 0, and the service logs `invoked=true completed=true`. The only variable that changed was the address family.

**Smallest safe remediation**

Pin the local gRPC target to IPv4:

```
--target 127.0.0.1:50051
```

and make the same change in the local config / launch script that currently uses `localhost:50051`. Do not raise the timeout (it only delays the same hang), do not touch the server, container, or published-port mappings — they are correct (`50051→50051`, `50080→50080`, container healthy).

**Confirmation**

1. Re-run the exact failed command with the IPv4 target:
   `java -jar probes/grpc-probe.jar --target 127.0.0.1:50051 --timeout 2`
   Expect exit code 0, stdout `pong`, empty stderr.
2. Check the service interceptor log shows a new `method="unary Echo" transport=h2c invoked=true completed=true` line for that call.
3. Optionally re-run once with `localhost:50051` to confirm it still fails identically — this isolates the address, not timing, as the cause.
4. Record for the ticket: targets (`[::1]:50051` fail / `127.0.0.1:50051` pass), deadline output (`DEADLINE_EXCEEDED: deadline expired after 2s`, exit 2), REST timing (`200`, 0.012 s), and the IPv4 retry result.

If the IPv4 retry had *also* failed, the next step would have been inspecting the service, published ports, and container health — but the captured data shows that isn't needed here.
