**Verdict: this is a workspace/environment problem, not a logic bug.** The computation finished; only the final write failed.

## Cause

`tree_diff.py` runs to line 63 with `diff == 'before \u2014 after\n'`, then `sys.stdout.write(diff)` raises. Because stdout is a pipe (not a console) on Windows, Python 3.12 with `utf8_mode = 0` picks the ANSI code page for `sys.stdout` — here `cp932` (Japanese locale). cp932 has no mapping for U+2014 EM DASH (its 0x815C maps to U+2015), so the encoder fails on the first non-encodable character at position 7. Nothing else is wrong: trees were read and compared fine.

**Partial effects:** none to clean up. stdout is empty (the failure was on the first write), the command is read-only, and no files are produced.

## Smallest safe remediation

Rerun with the override scoped to this one command. Either form works; `-X utf8` is the most tightly scoped in PowerShell (no env var leaks into the session):

```powershell
python -X utf8 tree_diff.py
```

or, per the standard playbook:

```powershell
$env:PYTHONIOENCODING = 'utf-8'; python tree_diff.py; Remove-Item Env:\PYTHONIOENCODING
```

If `tree_diff.py` is owned code and this should never recur, the durable fix is one line before the first write (also covers any future non-cp932 characters):

```python
sys.stdout.reconfigure(encoding="utf-8")
```

(Any file outputs added later should use `open(..., encoding="utf-8")` for the same reason.)

## Confirmation

1. Rerun: exit code is `0` and stderr is empty.
2. Output contains the expected line `before — after` (one line, em dash intact). Quick check of the bytes rather than trusting the terminal rendering:
   ```powershell
   python -X utf8 tree_diff.py | Format-Hex
   ```
   You should see `E2 94 80`... no — you should see `E2 80 94` for U+2014 at bytes 7–9.
3. Optional sanity check that the override is actually in effect in the same pipe setup:
   ```powershell
   python -X utf8 -c "import sys; print(sys.stdout.encoding)"   # -> utf-8
   ```

One caveat for the consuming side: if PowerShell itself is capturing the output as a string, its `[Console]::OutputEncoding` may also be cp932, which would show mojibake for the em dash even though Python now succeeds. That's a downstream decode setting (`[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()`), separate from this failure.
