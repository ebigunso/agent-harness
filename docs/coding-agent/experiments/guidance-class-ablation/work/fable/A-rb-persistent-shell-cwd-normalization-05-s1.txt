**Cause:** Working-directory drift in the persistent shell. The earlier `Set-Location -LiteralPath 'C:/work/inventory/src'` left the shell's cwd at `C:/work/inventory/src`, while the relative path `Tests/Tests.csproj` was written against the intended base `C:/work/inventory`. From `src`, that resolves to `C:/work/inventory/src/Tests/Tests.csproj`, which does not exist — hence MSB1009. The tool UI's remembered root (`C:/work/inventory`) is not the shell's cwd. This is not a code, dependency, SDK, PATH, or permission problem; the exit-0 retry with identical command text after returning to the base confirms that only the cwd differed.

**Smallest safe remediation:** Don't rely on the shell's cwd. Either:

- Use an absolute project path so the command is cwd-independent:
  ```powershell
  dotnet test 'C:/work/inventory/Tests/Tests.csproj'
  ```
- Or, if you want to keep the relative form, run it from the intended base without permanently changing shell state:
  ```powershell
  Push-Location -LiteralPath 'C:/work/inventory'; try { dotnet test Tests/Tests.csproj } finally { Pop-Location }
  ```

Both are read-only with respect to repo contents and require no environment changes. The absolute-path form is preferable for anything scripted, since later `Set-Location` calls in the same persistent shell can shift cwd again.

**Confirmation:**
1. `pwd` beforehand (or not needed if using the absolute path) — verify it prints the expected base if using the relative form.
2. Run the command; expect exit code 0 and output like `Passed! - Failed: 0, Passed: 1, Skipped: 0, Total: 1 ... Tests.dll (net8.0)`, with no MSB1009.
3. Check `$LASTEXITCODE -eq 0`.
4. If using `Push-Location`/`Pop-Location`, `pwd` afterward should show the cwd restored to whatever it was before, proving no lingering state change.
