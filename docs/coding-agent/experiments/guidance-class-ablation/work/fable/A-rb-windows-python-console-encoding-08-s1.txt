**Cause — environment/workspace configuration, not a code or data bug.**
`row.description` is a correct `str` (`"Launch 🚀"`). The failure happens only at `print`: because stdout is a pipe (not an interactive console), CPython on Windows falls back to the locale ANSI code page for `sys.stdout`, which here is `cp932` (`sys.stdout.encoding = cp932`, `utf8_mode = 0`). cp932 has no encoding for U+1F680, so the write raises `UnicodeEncodeError` under the default `strict` error handler. The DB read is fine and nothing was written, so the run is cleanly retryable.

**Smallest safe remediation — enable Python's UTF‑8 mode for this invocation, no code change:**

```powershell
python -X utf8 db_report.py
```

(equivalently `$env:PYTHONUTF8 = 1; python db_report.py`). This makes `sys.stdout` UTF‑8 regardless of the console code page. Don't reach for `errors='replace'`/`'ignore'` or stripping the character — that silently alters report data. `sys.stdout.reconfigure(encoding='utf-8')` in the script would also work, but it's a code change and unnecessary for this fix.

One dependency to check: whatever is reading the pipe must decode it as UTF‑8. If the consumer is PowerShell itself (e.g. `| Out-File`, `| Select-String`, capture into a variable), PS 7 on Windows decodes native-command output with `[Console]::OutputEncoding`, which will still be cp932 → mojibake instead of a crash. In that case also set, in the same session:

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
```

1. Sanity-check the flag takes effect in the same piped context:
   `python -X utf8 -c "import sys; print(sys.stdout.encoding, sys.flags.utf8_mode)" | Out-String` → `utf-8 1`.
2. Rerun `python -X utf8 db_report.py`: exit code 0, no traceback, and the output line reads `Launch 🚀` (bytes `F0 9F 9A 80` for the emoji if you inspect the raw stream, e.g. `python -X utf8 db_report.py | Format-Hex` after setting `[Console]::OutputEncoding` — or redirect to a file and open as UTF‑8).
3. If you want this permanent for the workspace, set `PYTHONUTF8=1` in the launcher/task definition and re-verify step 1 from there rather than relying on a per-shell variable.
