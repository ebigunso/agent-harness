**Verdict: workspace/configuration problem, not a server or code defect.**

**Cause**

The profile change from `127.0.0.1:50051` to `localhost:50051` is the only delta between the passing and failing calls. On this host `localhost` resolves to `::1` first, and grpc-java's pick-first resolver takes that address. Docker Desktop's port proxy accepts the TCP connection on `[::1]:50051` (so connect "succeeds"), but nothing is forwarded to the container — the service never sees an HTTP/2 preface/SETTINGS exchange, which is why no invocation appears in the interceptor log and the client sits on the pending stream until the 2s deadline fires. grpc-java does not fall back to `127.0.0.1` once a TCP connection is established, so the call dies as `DEADLINE_EXCEEDED` rather than `UNAVAILABLE`. The curl check on 50080 doesn't contradict this: it's a different port mapping and HTTP/1.1 client, and it only proves the container is up — which the `127.0.0.1` gRPC comparison already proved. The server, image, and probe are fine.

**Smallest safe remediation**

Revert the local configuration profile's target to `127.0.0.1:50051` (or, equivalently, `ipv4:127.0.0.1:50051` if you want to keep the name-based form pinned to v4). Do not touch server code, the image, Docker Desktop settings, or system-wide IPv6 — the failure is scoped to one config value.

**Confirmation**

1. Re-run the exact failed command with the reverted target:
   `java -jar probes/kotlin-probe.jar --target 127.0.0.1:50051 --timeout 2`
   Expect exit 0, stdout `pong`, empty stderr.
2. Check the service interceptor log for a new line: `probe method="unary Echo" transport=h2c invoked=true completed=true`.
3. Optionally, as a negative control, run once more with `--target localhost:50051` and confirm it still exits 2 with `DEADLINE_EXCEEDED` — that isolates the address as the sole cause. If you want a note for the future, `netstat -ano | findstr :50051` will show whether Docker's proxy is listening on `[::]` as well as `0.0.0.0`, which is the source of the asymmetry.
