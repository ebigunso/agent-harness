## Cause

This is a file lock, not a permissions, cache, or lockfile problem. `EBUSY` (errno -4082, libuv's EBUSY) on `unlink` of `sharp-win32-x64.node` means npm tried to replace the sharp native addon while another process had it mapped. Windows won't let you unlink a DLL/`.node` that's loaded into a live process.

The evidence pins the holder down:

- `tasklist /m sharp-win32-x64.node` → `node.exe` PID 4102 has the module loaded.
- Process inspection confirms it's the image worker from `C:/work/npm-lock/workers/images.js`, loading the exact path npm is trying to unlink.
- The worker outlived its launch terminal, so it's an orphaned repo-owned process — nothing else is going to stop it.

Everything else checks out (lockfile in sync, registry reachable, probe file creates/deletes fine next to the module, no ACL denial), so `npm cache clean`, deleting `node_modules`, or reinstalling sharp would be wasted or harmful effort. Note the runbook's step 1 (stop dev servers/close terminals) doesn't apply here — the terminal is already gone.

## Smallest safe remediation

Kill only that one PID, then rerun the same command. You're already in PowerShell 7, so no need for the `pwsh.exe -Command` wrapper.

```powershell
taskkill /PID 4102 /F
npm install
```

`/F` is warranted: it's a headless worker with no console or window to deliver a graceful close to, and you've confirmed ownership, so there's no risk of killing something unrelated. Don't use `taskkill /IM node.exe` — that would take out every Node process on the machine.

After the install succeeds, restart the worker (e.g. `node workers/images.js`) if it's supposed to be running; it will pick up the reinstalled binary.

## Confirmation

1. `taskkill` reports `SUCCESS: The process with PID 4102 has been terminated.`
2. `tasklist /m sharp-win32-x64.node` returns no rows (or `INFO: No tasks are running which match the specified criteria.`).
3. `npm install` exits 0 with no `EBUSY`/`EPERM` lines.
4. Sanity-check the addon actually loads under the current runtime:
   ```powershell
   node -e "require('sharp'); console.log('sharp ok')"
   ```
   Should print `sharp ok`.

If the retry fails on a *different* `.node` file, repeat the `tasklist /m <that file>` → `taskkill` cycle for that module; if it fails on the *same* file, run `tasklist | findstr node` — something respawned the worker (a supervisor, task scheduler, or the editor) and needs to be stopped at the source before retrying.
