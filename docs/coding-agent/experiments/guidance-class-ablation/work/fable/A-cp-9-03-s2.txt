1. **`src/PaymentClient.java`, `charge()` — the `catch (GatewayTimeout)` branch marks the order paid and returns `PAID`. Blocking.**

   - **What's wrong:** A gateway timeout is an *indeterminate* outcome. Per the notes, the timeout can fire before or after the remote capture, so at this point the client does not know whether money moved. The new branch treats "we didn't hear back" as "the charge succeeded," which is exactly the misreporting the task asked to eliminate. The timeout path and the success path are now byte-for-byte identical (`store.markPaid(...)`; `return PAID`), so the `try/catch` adds no state distinction at all — it just swallows the exception. Net effect versus the original code: before, a timeout propagated and the order was left un-marked (recoverable); after, a timeout silently produces a confirmed-paid order that may never have been charged. That's a regression, not a fix — orders will ship/fulfill with no capture, and there's no signal for reconciliation to pick up because the record looks settled.

   - **What I'd require instead:** On `GatewayTimeout`, do not assert success. Either:
     - record the ambiguous state and let the existing reconciliation flow resolve it — `store.markPending(order.id()); return ChargeStatus.PENDING;` — or
     - since `paymentKey` is stable and the gateway is idempotent, retry `gateway.charge(...)` a bounded number of times to obtain a definitive answer, and only if it still times out fall back to `PENDING` + reconciliation.

     In no case should the timeout path call `markPaid` or return `PAID`. Add a unit test that stubs `gateway.charge` to throw `GatewayTimeout` and asserts the store is *not* marked paid and the returned status is `PENDING` (or that a retry was issued and its result is what's reported).

   - **Also:** the commit message ("complete checkout on gateway timeout") accurately describes the behavior, which is the problem — it should be reworded to reflect the pending/reconcile semantics once the code is corrected.
