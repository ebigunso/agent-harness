**Cause**

The failure is host loopback resolution, not the service and not the probe code. On this Windows/Docker Desktop host, `localhost` resolves to `::1` first, so the gRPC channel dials `[::1]:50051`. Docker Desktop's IPv6 port proxy accepts the TCP connect but never returns HTTP/2 (h2c) response headers, so the channel stalls at the transport layer until the 2s deadline → `DEADLINE_EXCEEDED`, probe exit 2 (`go run` then reports "exit status 2" and itself exits 1 — that's normal `go run` behavior, not a second problem).

Evidence that it's the address path, not the service:
- The address-only comparison `--target 127.0.0.1:50051` succeeds (exit 0, `pong`) and the interceptor log shows `invoked=true completed=true`.
- The failed `localhost` call never appears in the service interceptor log — the request never reached the server.
- The HTTP/1.1 sibling on `localhost:50080` works (12 ms) because the proxy only stalls HTTP/2, not HTTP/1.1.

**Smallest safe remediation**

Change the gRPC target from `localhost:50051` to `127.0.0.1:50051` wherever the local connection string is defined (the probe invocation / local config). Do not touch the service, the container, port publishing, the hosts file, or Docker's IPv6 settings.

```powershell
go run ./cmd/probe --target 127.0.0.1:50051 --timeout 2s
```

**Confirmation**

1. Re-run the previously failing invocation with the IPv4 target: expect exit 0, stdout `pong`, empty stderr.
2. Check the service interceptor log for a matching `probe method="unary Echo" transport=h2c invoked=true completed=true` entry.
3. Optionally re-run once with `localhost:50051` to confirm the asymmetry persists (deadline again, no log entry) — this proves the fix targeted the actual cause rather than a transient.

If `127.0.0.1:50051` had also failed, only then would investigating the service, port mappings, or container health be warranted; here it did not, so no further workspace changes are needed.
