**Cause**

Not a workspace problem — the raw JSON is valid and the environment is fine. The script's assertion is measuring the wrong thing. `$raw | ConvertFrom-Json | Write-Output` sends the parsed result through the pipeline, and PowerShell unrolls collections as they pass through. A one-element array arrives as its single element, so `$parsed` is a `PSCustomObject` (exactly what stdout shows), and `-isnot [array]` throws. The same script would pass for `[{"id":8},{"id":9}]` and fail for any singleton — a cardinality-dependent false negative, not a data problem.

Note the pwsh fix (`ConvertFrom-Json -NoEnumerate`) is not available here: this is Windows PowerShell 5.1, where that parameter doesn't exist and would itself produce a parameter-binding error.

**Smallest safe remediation**

Assert framing on the raw serialized value instead of on the post-pipeline object. Replace line 10:

```powershell
$trimmed = $raw.Trim()
if (-not ($trimmed.StartsWith('[') -and $trimmed.EndsWith(']'))) { throw 'Expected JSON array' }
```

Optionally drop the pointless `| Write-Output` on line 5, but it isn't required for correctness once the check no longer depends on `$parsed`'s shape. Do **not** "fix" this with `@($parsed)` or `-is [array] -or ...` — that would also make a scalar wire value (`{"id":8}`) pass, which the contract forbids.

**Confirmation**

1. Rerun `powershell.exe -NoProfile -File probes/cardinality.ps1` — expect exit code 0 and the same three stdout lines with no stderr.
2. Check the contract across cardinalities by substituting `$raw`:
   - `'[]'` → passes (empty array accepted)
   - `'[{"id":8}]'` → passes (singleton, the original failure)
   - `'[{"id":8},{"id":9}]'` → passes
   - `'{"id":8}'` → throws `Expected JSON array`, exit 1 (scalar rejected)
3. Capture as evidence: the first/last characters of `$raw`, the element count, and the exact assertion expression — so a future reader doesn't reintroduce the `-is [array]` check.
