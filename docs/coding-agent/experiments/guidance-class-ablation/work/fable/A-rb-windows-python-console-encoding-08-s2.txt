**Cause**

This is not a data or database problem — the driver already produced a correct `str` ("Launch 🚀"). The failure is in `print`: because stdout is a pipe (not a console), CPython on Windows with `utf8_mode = 0` encodes stdout using the locale ANSI code page, here cp932. U+1F680 has no cp932 representation, so the codec raises `UnicodeEncodeError` on the first row containing it. (Interactively it would likely work, because the Windows console path bypasses cp932 — which is why this only shows up under capture.)

So it is an environment/runtime-configuration issue with the process's stdout encoding, not a workspace bug in the script's logic or the data.

**Smallest safe remediation**

Enable UTF-8 mode for that invocation only; no code change, no global setting:

```powershell
$env:PYTHONUTF8 = '1'
python db_report.py
```

(Equivalently `python -X utf8 db_report.py`, or `PYTHONIOENCODING=utf-8` if you want to touch only the I/O streams.)

If a code-side fix is preferred instead, the minimal one is at the top of `db_report.py`:

```python
import sys
sys.stdout.reconfigure(encoding="utf-8")
```

One caveat: whatever consumes the pipe must decode UTF-8. If PowerShell itself is reading the native output (e.g. `python db_report.py | Out-File`), also set `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8` in that session; otherwise you avoid the crash but may see mojibake. If the pipe goes straight to a file/another UTF-8-aware tool, nothing more is needed.

**Confirmation**

1. In the same shell/env, `python -c "import sys; print(sys.stdout.encoding, sys.flags.utf8_mode)"` should report `utf-8 1` (or `utf-8` for `PYTHONIOENCODING`).
2. Re-run `python db_report.py` under the same capture: exit code 0, no traceback, and the captured stdout contains `Launch 🚀`.
3. To verify bytes rather than rendering: `python db_report.py > out.txt` and inspect with `Format-Hex out.txt` — the rocket should appear as `F0 9F 9A 80`.
