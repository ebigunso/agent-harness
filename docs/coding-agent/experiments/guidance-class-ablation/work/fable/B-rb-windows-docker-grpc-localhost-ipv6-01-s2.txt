**Cause**

Not a service or workspace problem. `localhost` resolved to `::1` first, and the failing channel connected to `[::1]:50051`. Docker Desktop's IPv6 port proxy on Windows accepted the TCP connect but never delivered HTTP/2 response headers, so the gRPC channel stalled at the transport layer until the 2s deadline (probe exit 2, `DEADLINE_EXCEEDED`). Evidence that the service is healthy and the fault is address-specific:

- Same call to `127.0.0.1:50051` succeeded (`pong`, exit 0) with an interceptor log entry `invoked=true completed=true`.
- The failed `localhost` call produced *no* interceptor log entry — the request never reached the server.
- REST on sibling port 50080 via `localhost` was fine (HTTP/1.1 isn't affected by the h2 stall), which is the expected asymmetry.

**Smallest safe remediation**

Change the local gRPC connection string from `localhost:50051` to `127.0.0.1:50051`:

```
python probes/unary.py --target 127.0.0.1:50051 --timeout 2
```

For the project, set the configured default/env target (whatever the probes and clients read) to `127.0.0.1:50051` for the Docker Desktop/Windows dev environment. Do not touch the service, port mappings, container, or the hosts file; do not add retries or address-fallback logic to the probe.
