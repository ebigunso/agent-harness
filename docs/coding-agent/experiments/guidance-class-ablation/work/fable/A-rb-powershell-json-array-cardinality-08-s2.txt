**Cause — script bug, not a workspace/runtime problem.**

`ConvertFrom-Json -NoEnumerate` does return the one‑element `Object[]`, but line 5 immediately pipes it through `ForEach-Object { $_ }`. `ForEach-Object` receives the array as one item and emits `$_`, and anything a script block writes to the pipeline is enumerated on output. The singleton array is therefore unrolled into its only element, so `$parsed` ends up as the `PSCustomObject` (the `{"id":9}` object), and `-isnot [array]` correctly fires. `-NoEnumerate` only protects the cmdlet's own output; the trailing `ForEach-Object` re‑introduces exactly the unwrapping it was meant to prevent. (Same thing would turn `[]` into `$null` and would still "work" by accident for 2+ elements, which is why only singleton/empty cases break.)

**Smallest safe remediation**

Drop the pass‑through stage so the array is assigned directly:

```powershell
$parsed = $raw | ConvertFrom-Json -NoEnumerate
```

Do **not** "fix" it with `@(...)` around the expression — that would coerce a scalar wire value (`9`, `"x"`, `{"id":9}`) into a 1‑element array and silently defeat the contract's scalar rejection. If you must keep a `ForEach-Object` for some reason, emit with the unary comma (`ForEach-Object { ,$_ }`), but simply removing it is the cleaner change.

**Confirmation**

1. Re‑run `pwsh -NoProfile -File probes/cardinality.ps1` → exit code 0, stdout shows `parsed type=System.Object[]`, no stderr.
2. Spot‑check the contract boundaries in the same runtime:
   - `'[]' | ConvertFrom-Json -NoEnumerate` → `Object[]`, `.Count` = 0 (empty array accepted, not `$null`).
   - `'[{"id":1},{"id":2}]'` → `Object[]`, `.Count` = 2.
   - `'{"id":9}'` and `'9'` → `PSCustomObject` / `Int64`, so `-isnot [array]` throws as intended.
3. `echo $LASTEXITCODE` after the script run to confirm 0.
