### 1. `migration.sql` — unrelated schema change bundled into a logging rename (block)

**What's wrong:** The diff adds `CREATE INDEX account_name_idx ON accounts(name);`. Per the reviewer notes, this has no dependency on the logging change; it was included because the author's local test DB was reset. Nothing in the task ("rename log request key consistently") or the commit message mentions a database index.

**Why it matters:** This is exactly the Gate 3 anti-pattern — incidental work riding along with weak coupling to the objective, and a hidden behavior change inside a nominally mechanical diff. Concretely:
- A schema migration is a production-affecting operation (lock/IO on `accounts`, deploy ordering, rollback story). Someone reading `git log` for "rename log request key consistently" will never expect it to have created an index.
- If the logging rename needs to be reverted, the revert silently drops a migration — and vice versa.
- "My test DB was reset" is a local environment problem, not a reason to change the repo. If the index is genuinely missing from `migration.sql`, that's a separate defect with its own justification (which table/query needs it, why non-unique, whether `CONCURRENTLY`/`IF NOT EXISTS` is needed for the target DB).

**Require instead:** Drop `migration.sql` from this change. If the index is actually needed, open a separate PR that states the query it supports and how the file got out of sync with the test DB. The logging commit should touch `logs.py` only.

### 2. `logs.py` — "consistently" is asserted but not evidenced (flag / needs confirmation)

**What's wrong:** The task is to rename the key *consistently*, but the diff touches a single emitter. Nothing shows that other producers of the `"request"` key (other loggers, tests, fixtures) or consumers of it (log parsers, dashboard/alert queries, structured-log schemas) were checked.

**Why it matters:** Renaming a structured-log field is an observability contract change. If any dashboard, alert, or downstream pipeline filters on `request`, it silently goes blind after deploy — a real behavior change hidden inside a one-line "rename." If other code still emits `"request"`, the change makes things *less* consistent, not more.

**Require instead:** Author states (in the PR description) the search performed for the old key across code, tests, and log-query definitions, and either confirms this is the only occurrence or includes the remaining updates. If external consumers depend on the old key, note the cutover plan (or emit both keys for a deprecation window).

The `logs.py` line change itself is correct and matches the stated intent; with item 1 removed and item 2 answered, this is mergeable.
