**Cause — script bug, not the workspace.** The producer, transport, and JSON are all fine (stdout confirms the exact body `[{"state":"ok"}]`). The problem is line 5:

```powershell
$parsed = $raw | ConvertFrom-Json
```

In PowerShell 7, `ConvertFrom-Json` **enumerates** a top-level JSON array into the pipeline by default (that's why the `-NoEnumerate` switch exists). A one-element array is therefore emitted as its single element, and `$parsed` receives a lone `PSCustomObject` — exactly what stdout shows (`parsed type=System.Management.Automation.PSCustomObject`). The `-isnot [array]` assertion then correctly fires. The check is only accidentally passing for multi-element arrays (the pipeline re-collects ≥2 items into `Object[]`) and would also misfire on `[]` (collapses to `$null`). So the cardinality probe is sensitive to element count, which is the opposite of what it's meant to test.

**Smallest safe remediation** — keep the array shape intact:

```powershell
$parsed = $raw | ConvertFrom-Json -NoEnumerate
```

(or `ConvertFrom-Json -InputObject $raw -NoEnumerate`). With `-NoEnumerate`, a JSON array of any length (0, 1, n) comes back as `System.Object[]`, while a scalar wire value (`1`, `"x"`, `true`) still comes back as a scalar, so the existing `-isnot [array]` check continues to reject scalars as the contract requires. Don't "fix" it with `@(...)` — that would coerce scalars into arrays and silently break the rejection case.

(The dead `$raw = '[...]'` / `$wireCount = '1'` literals at the top are harmless; leave them or clean up separately.)
