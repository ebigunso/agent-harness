**Verdict: block.** The change does not fix the reported problem; it adds a compensating lock that cannot address the cause.

**1. `invoices/allocate.go` — `allocate` still has the read-then-write race that is the actual origin of the collisions.**
`SELECT MAX(id)+1` followed by a separate `INSERT` is not atomic. Two writers that interleave between the SELECT and the INSERT compute the same id, and the second INSERT fails on the primary key. That is the defect. The diff leaves this code untouched and instead tries to prevent interleaving from outside, which only works if *every* caller in *every* process goes through the same lock — and per the notes they don't (see 2). The invariant "each allocated id is unique" should be enforced by the database, not by callers agreeing to serialize.

*Require:* let the database allocate the id. The notes say the schema already supports authoritative auto-generated integer IDs, so `allocate` should become `res, err := db.Exec("INSERT INTO invoices DEFAULT VALUES")` (or an explicit column list without `id`) and return `res.LastInsertId()`. This makes the collision impossible regardless of how many processes or goroutines call it, and deletes the `MAX(id)+1` logic entirely. If for some reason the schema really can't be relied on, the fallback is a single atomic statement / `BEGIN IMMEDIATE` transaction in the DB — still never an in-process mutex.

**2. `invoices/allocate.go` — `httpMu` is a process-local `sync.Mutex`, but the collisions are between separate OS processes.**
The reviewer notes state the HTTP service and batch workers are distinct processes sharing one SQLite file. A Go mutex lives in one process's memory; it has no effect on the other process. So the exact failure the task describes (HTTP vs. batch racing) is unchanged. All this lock achieves is serializing HTTP goroutines against each other inside one process — a narrower case that wasn't even named as the problem — while paying for it by holding a global lock across two DB round-trips on every HTTP invoice creation.

*Require:* remove `httpMu`. Once the DB generates the id (finding 1), no application-level serialization is needed.

**3. `BatchCreate` is not locked, and `HTTPCreate`/`BatchCreate` now have divergent concurrency semantics for the same operation.**
Even taking the mutex approach on its own terms, it's applied to one of two entry points. That's compensating logic bolted onto one caller of a shared helper — the next person who adds a third entry point (or calls `allocate` from a test or migration) reintroduces the bug. The asymmetry, plus the commit message "serialize HTTP invoice creation", shows the change targets a symptom observed in one path rather than the task ("remove duplicate invoice-ID allocation failures across HTTP and batch workers").

*Require:* the fix must live in `allocate` (or below it), so both `HTTPCreate` and `BatchCreate` — and any future caller — are correct by construction with no per-caller guard.

**4. Minor: `import ("database/sql"; "sync")` is not gofmt'd.**
Would be moot after removing `sync`, but as written it wouldn't pass `gofmt` in CI.

**What I'd accept instead (sketch):**
```go
func allocate(db *sql.DB) (int64, error) {
    res, err := db.Exec("INSERT INTO invoices DEFAULT VALUES")
    if err != nil {
        return 0, err
    }
    return res.LastInsertId()
}
```
with `HTTPCreate` and `BatchCreate` unchanged from the original, no mutex, and a test that runs concurrent allocations (ideally from two `*sql.DB` handles to mimic two processes) and asserts no PK errors and no duplicate ids.
