## Findings

### 1. `rpc.go` — `Fetch` collapses "service unavailable" and "no work" into the same value (`nil`)

**What's wrong:** `Fetch` returns `nil` for three distinct outcomes: `call()` returned an error, `call()` returned an empty slice, and `call()` returned a nil slice. The error is swallowed (`if err != nil { return nil }`) and never surfaced.

**Why it matters:** The task and reviewer notes are explicit: the consumer must distinguish legitimate empty success from an unavailable service, and unavailability must be surfaced so the caller can retry. With this adapter a caller sees `nil` and cannot tell whether the queue is genuinely drained (stop polling / idle) or the RPC failed (retry / back off / alert). An outage becomes indistinguishable from "all work done", which is a silent-failure mode in a job consumer — the worst kind, because nothing errors and work just stops being processed.

**Required instead:** Propagate the error. The adapter should return `([]string, error)` (or a small result type carrying both). Empty success should be representable distinctly from failure; the conventional Go shape is:

```go
func Fetch(call func() ([]string, error)) ([]string, error) {
    rows, err := call()
    if err != nil {
        return nil, err // unavailable: caller retries
    }
    return rows, nil // may be empty: legitimate "no work"
}
```

If the intent is to normalize empty vs nil, normalizing to a non-nil empty slice (`[]string{}`) on success is fine, but the error path must remain separate.

### 2. `rpc.go` — `HasWork` inherits the ambiguity and returns `false` on failure

**What's wrong:** `HasWork` returns `false` whenever `Fetch` returns `nil`, including on RPC error.

**Why it matters:** A caller polling `HasWork` will interpret an outage as "nothing to do" and go idle indefinitely. There is no path by which an error ever reaches the caller.

**Required instead:** Either `HasWork` returns `(bool, error)` and propagates the error, or it is removed — a boolean that throws away the data it just fetched (forcing a second RPC to actually get the rows) is also wasteful. Prefer having callers use `Fetch` directly and check `len(rows) == 0` themselves.

### 3. `rpc.go` — No tests

**What's wrong:** A new package with behavior that hinges on distinguishing three cases ships with zero tests.

**Why it matters:** The exact bug above (error and empty conflated) would have been caught by the most obvious table test: `{err: errors.New("down")}` vs `{rows: nil}` vs `{rows: []string{}}` vs `{rows: []string{"a"}}`. This is precisely the sort of logic where a test is the specification.

**Required instead:** Add a table-driven test covering: error → error returned, rows nil → empty success (no error), rows empty → empty success (no error), rows non-empty → rows returned.

### 4. `rpc.go` — Formatting / style (minor, but would flag)

**What's wrong:** Multiple statements per line joined by `;`, no spaces around operators, no doc comments, no blank line after `package`. This is not `gofmt`-compliant.

**Why it matters:** `gofmt` is the baseline expectation in Go codebases and CI will typically reject this; the dense one-liner also made the logic error above harder to spot in review.

**Required instead:** Run `gofmt`; add doc comments on the exported `Fetch`/`HasWork` explaining the semantics of empty vs error.

## Summary

Findings 1 and 2 are blocking: the commit message says "represent empty work from rpc" but the code makes empty work *unrepresentable* as distinct from failure. Return the error, keep empty-success as a non-error empty slice, and add the table test that proves the three cases are distinguishable.
