## Cause

This is a **bug in the probe, not a workspace problem**. `data.json` is valid and correctly framed — the trimmed raw content is `[true]`, which starts with `[` and ends with `]`, exactly the single-element array the contract is supposed to accept.

The failure comes from line 5:

```powershell
$raw = Get-Content -Raw data.json; $parsed = $raw | ConvertFrom-Json | Write-Output
```

`ConvertFrom-Json` parses `[true]` into a one-element array, but that array is then **sent through the pipeline** (both the `ConvertFrom-Json` output and the redundant `| Write-Output`). PowerShell pipelines unroll collections, so the single element `$true` is emitted and `$parsed` receives a bare `System.Boolean` — confirmed by the stdout line `parsed type=System.Boolean`. `-isnot [array]` is therefore true and the probe throws a **false negative**.

Crucially, on Windows PowerShell 5.1 there is no `-NoEnumerate` to prevent this, and as the reference notes, a post-pipeline `-is [array]` test **cannot prove wire framing** anyway. The assertion is testing the wrong thing on the wrong runtime.

## Smallest safe remediation

Don't infer wire cardinality from the post-pipeline object type on 5.1. Assert on the **trimmed raw JSON framing** instead. Replace the final assertion (line 10) with:

```powershell
$trimmed = $raw.Trim()
if (-not ($trimmed.StartsWith('[') -and $trimmed.EndsWith(']'))) { throw 'Expected JSON array' }
```

This accepts `[]`, `[true]`, and `[1,2]`, and rejects scalar wire values (`true`, `42`, `"x"`), matching the stated contract. It is a framing check, not a syntax validator, which is exactly the intent. (The redundant `| Write-Output` can also be dropped, but it is not the root cause and leaving it is harmless.)
