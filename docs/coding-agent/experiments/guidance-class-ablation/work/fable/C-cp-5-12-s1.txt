**Findings (would block on 1–3):**

1. **`Jobs.parse` / `Jobs.exhausted` — negative limits produce an unbounded retry loop, and nothing prevents them.**
   The operator contract is `0..10`, but `parse` returns any `Int`. For `limit < 0`, `exhausted` is always `false`, so `run` spins forever if the job keeps failing. The reviewer note "negative limits never exhaust" describes this as a property, but it is the failure mode: a stray `-` in config turns a bounded retry into an infinite loop with no log, no error, no way to tell it's misconfigured. The CLI boundary only catches `NumberFormatException`, so `-1` sails through. Required: enforce the stated invariant at entry — `parse` rejects anything outside `0..10` with a message naming the setting, the value received, and the allowed range. If "infinite retry" is a real requirement, model it explicitly (e.g. `Option[Int]` / a documented sentinel with its own check in `exhausted`) rather than letting it fall out of a comparison.

2. **`Jobs.run` — `limit = 0` never runs the job at all.**
   `attempt` starts at 0 and the loop condition is `attempt >= limit`, so `run(0, job)` exits immediately without calling `attemptJob`. `0` is inside the operator contract, and a *retry* limit of 0 almost certainly means "run once, don't retry", not "don't run". More generally the code treats `limit` as a total-attempt count while the config is named a retry limit, so every value is off by one relative to what an operator would expect. Required: decide and document whether `limit` is retries or attempts, and make the loop match (for retries: attempt once, then retry up to `limit` more times — `attempt <= limit`, or equivalent). Add a test for `limit = 0` and `limit = 1`.

3. **`Jobs.run` — exhaustion is silent.**
   `run` returns `Unit` whether the job succeeded or all attempts failed. Callers cannot distinguish the two, so a job that exhausts its retries looks identical to a job that succeeded. Required: return a result (`Boolean` / `Either` / throw on exhaustion) so the caller can fail actionably, and log or report the attempt count on exhaustion.

4. **`Jobs.parse` — failure is not actionable.**
   `raw.toInt` throws `NumberFormatException("For input string: \"abc\"")` with no indication of which setting was malformed, and does not trim whitespace (`" 5"` fails). Even if the CLI boundary catches it, the operator gets a message that doesn't say what to fix. Required: wrap the parse (`raw.trim.toIntOption`) and raise a single error that names the setting, the raw value, and the valid range — the same place where the range check from (1) lives.

5. **`Jobs.run` — exceptions from `attemptJob` abort without retry (clarify).**
   The loop only retries on `false`; a thrown exception escapes on the first attempt. If jobs signal transient failure by throwing, the retry limit doesn't apply to them. Not necessarily wrong, but the contract should be stated (and tested) so callers know whether to catch inside the thunk.

The Long counter note is fine; overflow is moot once (1) bounds the loop.
