## 1. `lib.rs:1-2` — business policy embedded in the decoder (blocking)

**What's wrong:** `decode` returns `(u8, bool)` where the `bool` is `*score >= 80`. That threshold is the domain's "flag for review" rule, but it lives inside the protobuf frame decoder — the transport/data-access layer.

**Why it matters:** The reference material is explicit: business rules belong in domain/app, not in data access. The reviewer notes even state the intended split ("Transport owns framing, domain owns score >= 80 review policy"), and this diff violates it. Consequences: the threshold can't be changed or tested without touching wire-parsing code; every caller gets the policy whether it wants it or not; the anonymous tuple `(u8, bool)` leaks meaning (what is the `bool`?) instead of naming it; and any future policy variant (per-tenant thresholds, multiple bands) would have to be threaded through the decoder.

**Required instead:**
- `decode(bytes: &[u8]) -> Result<u8, &'static str>` (or a `Score` newtype) — framing and range validation only.
- A separate domain function, e.g. `pub fn needs_review(score: u8) -> bool { score >= 80 }`, in the domain module, with the `80` named as a constant.
- Callers compose the two. Commit message / plan should state which owner each piece lands under and why (the guidance asks for placement to be verified and moves explained; the commit message "decode fraud score messages" doesn't).

The framing part itself is correct for the stated contract: field 1, wire type 0 → tag byte `8`; values 0..100 are single-byte varints; `<= 100` enforces the range; anything else is rejected. No issue there.

## 2. `lib.rs:2` — score `0` rejected if the sender is a standard proto3 encoder (flag / confirm)

**What's wrong:** A proto3 encoder omits fields at their default value, so `score = 0` is normally serialized as an *empty* message, not `[8, 0]`. This decoder rejects `[]` as `"invalid score frame"`.

**Why it matters:** If the producer uses a stock protobuf library, legitimate zero scores will fail to decode. The reviewer notes assert the contract is "exactly tag 8 plus one byte" with other frames rejected — if the producer is a hand-rolled encoder that always emits the field, this is fine, but that assumption should be made explicit.

**Required instead:** Either confirm and document in a comment that the producer always emits field 1 (including zero) so the empty frame is intentionally invalid, or accept `[]` as `Ok(0)`. Add a test for whichever is chosen.

No other findings; the error type and pattern-match structure are appropriate for a minimal decoder.
