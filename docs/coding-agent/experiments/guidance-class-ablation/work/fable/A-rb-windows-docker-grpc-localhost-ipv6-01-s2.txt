**Cause**

This is an environment (host networking) problem, not a probe or service bug.

`localhost` resolves to `::1` first, so the gRPC channel dials `[::1]:50051`. The TCP handshake succeeds — Docker Desktop's host-side port proxy is listening on the IPv6 loopback — but nothing is forwarded to the container on that path: no HTTP/2 SETTINGS/response headers ever arrive, and the service's interceptor log shows no invocation. gRPC does not fall back to the next address once a TCP connect has succeeded, so the RPC sits on a black-holed connection until the 2 s deadline fires. The exact same call to `127.0.0.1:50051` completes (`pong`, `invoked=true completed=true`), which isolates the difference to the address family on port 50051. The HTTP/1.1 sibling on 50080 succeeding doesn't contradict this; it only shows the 50080 mapping (or curl's address choice) doesn't hit the same v6 black hole.

Raising `--timeout` will not help — no bytes are coming back on that path.

**Smallest safe remediation**

Pin the probe target to the IPv4 loopback instead of the `localhost` name:

```powershell
python probes/unary.py --target 127.0.0.1:50051 --timeout 2
```

(If the target is in a config or script, change it there; `ipv4:127.0.0.1:50051` is the equivalent explicit gRPC target form.) Do not disable IPv6, edit the hosts file, change Docker's port bindings, or add retry/fallback logic to the probe — those are broader changes than the problem warrants and touch shared state.

**Confirmation**

1. The pinned command exits 0, prints `pong` on stdout, stderr is empty.
2. The service interceptor log shows a new `probe method="unary Echo" transport=h2c invoked=true completed=true` entry for that run.
3. Optional, to prove the address-family asymmetry independent of the probe: `curl.exe --http2-prior-knowledge --max-time 2 http://[::1]:50051/` stalls to timeout while the same against `http://127.0.0.1:50051/` returns an HTTP/2 response (even if it's a gRPC error body), and `netstat -ano | findstr :50051` shows both a `0.0.0.0` and a `[::]` listener owned by the Docker proxy.

If you want the root cause fixed rather than sidestepped, that's a Docker Desktop IPv6 port-forwarding issue for the 50051 mapping (worth a Docker Desktop restart/upgrade check), but that's a separate, larger change from the remediation above.
