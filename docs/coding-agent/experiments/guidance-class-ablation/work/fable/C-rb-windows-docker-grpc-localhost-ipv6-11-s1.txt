**Diagnosis**

This is not a project/workspace defect (probe code, dependencies, build, or the gRPC service are all fine). It is a local host-networking issue with Docker Desktop's published-port proxy on Windows:

- `localhost` resolves to `::1` first, so the Dart channel connects to `[::1]:50051`.
- The IPv6 published-port proxy accepts the TCP connect but never forwards/answers the HTTP/2 (h2c) traffic, so no SETTINGS/response headers arrive, the RPC never reaches the handler (confirmed: no interceptor log entry), and the probe's 2s deadline fires → `DEADLINE_EXCEEDED`, exit 2.
- The REST sibling on `localhost:50080` succeeds in 12 ms because HTTP/1.1 is handled fine by that path; the stall is specific to HTTP/2 over the `::1` mapping.
- The controlled comparison isolates the variable: identical call against `127.0.0.1:50051` succeeds (exit 0, `pong 1`/`pong 2`, server log `invoked=true completed=true`).

Not a TLS/cert issue (plaintext h2c), not a permissions/method issue (would be exit 3), not a container health issue (service is up and serves IPv4 correctly).

**Smallest safe remediation**

Use the IPv4 literal for the gRPC target in local configuration: `--target 127.0.0.1:50051` (or the equivalent host setting in the probe's local config/env). Do not change the service, the container, the port mappings, or the probe's code, and don't disable IPv6 system-wide — that's larger than necessary and affects other tooling.

**Confirmation**

1. Re-run `dart run probes/bidi.dart --target 127.0.0.1:50051 --timeout 2` → expect exit 0, stdout `pong 1` / `pong 2`, empty stderr.
2. Check the service interceptor log shows `probe method="bidirectional Echo" transport=h2c invoked=true completed=true` for that run.
3. Optionally re-run once with `--target localhost:50051` to confirm it still fails identically (exit 2, deadline message) — demonstrating the address is the only variable.
4. Record for the ticket: targets/port (`localhost` → `[::1]:50051` fail vs `127.0.0.1:50051` pass), deadline output (`DEADLINE_EXCEEDED: deadline expired after 2s`, exit 2), REST timing (`http_code=200 total_seconds=0.012`), and the IPv4 retry result (exit 0, `pong 1`/`pong 2`).

If a future retry at `127.0.0.1` also fails, that would point elsewhere — inspect the service, published mappings (`docker ps`, `docker port <container>`), and container health rather than the address.
