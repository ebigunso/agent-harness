**Verdict: workspace/environment problem, not a probe or service defect.** It's an IPv6-loopback address asymmetry in the Docker Desktop port publish for 50051.

## Cause

- `localhost` resolves to `::1` first, and grpc-js picks the first address. The channel connects to `[::1]:50051`.
- TCP connect to `[::1]:50051` succeeds (Docker Desktop's host-side proxy accepts on the v6 loopback), but nothing is forwarded to the container: no HTTP/2 SETTINGS/headers ever come back, and the service interceptor log has no entry for the call. The RPC just sits until the 2 s deadline → probe-normalized `DEADLINE_EXCEEDED`, exit 2.
- The identical call to `127.0.0.1:50051` completes in the same environment (`pong`, exit 0, `invoked=true completed=true`), which isolates the variable to the destination address, not the method, payload, deadline, server, or auth.
- Ruled out: deadline too short (working path is ~ms, deadline is 2 s); TLS/cert-name (plaintext h2c, no cert check); auth/method mismatch (would exit 3 as `PERMISSION_DENIED`/`UNIMPLEMENTED`, and the server would log an invocation).
- The curl success on `localhost:50080` is not a valid control: different port/mapping, and curl's own connection handling differs from grpc-js's single-address pick. It shows the daemon and HTTP sibling are up, nothing more.

## Smallest safe remediation

Target the IPv4 loopback explicitly for the gRPC probe instead of relying on `localhost`:

```powershell
node probes/unary.mjs --target 127.0.0.1:50051 --timeout 2
```

If you need to keep `localhost` in the command (e.g. scripted callers), the next-smallest change is process-scoped, not system-scoped:

```powershell
node --dns-result-order=ipv4first probes/unary.mjs --target localhost:50051 --timeout 2
```

Do **not** disable IPv6 on the host, edit the hosts file, or change Docker Desktop's global networking to fix a single port — those are wider blast radius than the problem warrants. The proper follow-up (separate from unblocking) is to make the 50051 publish behave the same on v4 and v6 as 50080 does, e.g. check how the service binds inside the container and the published mapping (`docker port <container>`), and fix at that level.

## Confirmation

1. Re-run `node probes/unary.mjs --target 127.0.0.1:50051 --timeout 2` (fresh, not the captured comparison): expect exit 0, stdout `pong`, empty stderr.
2. Check the service interceptor log for a new line `probe method="unary application health" transport=h2c invoked=true completed=true` correlated with that run — confirms the request actually reached the service, not just that the client returned.
3. Negative re-check to confirm the diagnosis rather than a flake: re-run the original `--target localhost:50051` once more and confirm it still yields exit 2 / `DEADLINE_EXCEEDED` with no interceptor entry. Same server, same moment, only the address differs → asymmetry confirmed.
