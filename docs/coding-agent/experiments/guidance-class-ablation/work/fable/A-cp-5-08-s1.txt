**1. `hook.ts` L3–4 — unknown event types crash instead of being handled**

`event.type as keyof typeof handlers` is a compile-time assertion with no runtime check. The reviewer notes say the remote service can send future event types, so `event.type` will at some point be something other than `"paid"` / `"cancelled"`. When that happens `handlers[type]` is `undefined` and the call throws `TypeError: handlers[type] is not a function` — the webhook endpoint fails on every new event the provider adds, which is exactly the case the task ("dispatch webhook event types") needs to survive. The cast is also silencing the very thing TypeScript would otherwise have caught: `handlers[event.type]` with `type: string` is an error under `noImplicitAny`/strict indexing.

Required: replace the cast with a real membership check and an explicit unsupported path. Whether that path is "acknowledge and ignore" or "raise a typed `UnsupportedEventError`" is a product decision, but it must be deliberate, not an incidental TypeError. Something like:

```ts
export function webhook(event: { type: string }) {
  if (!Object.hasOwn(handlers, event.type)) {
    return "ignored"; // or throw new UnsupportedEventError(event.type)
  }
  return handlers[event.type as keyof typeof handlers]();
}
```

Add a test for an unknown type (e.g. `"refunded"`) asserting the chosen behavior.

**2. `hook.ts` L1/L4 — plain object lookup keyed by remote-controlled string**

Related to (1) but worth calling out because a naive fix (`if (type in handlers)`) would still get it wrong: `handlers` has `Object.prototype` in its chain, so `event.type === "toString"` or `"constructor"` passes an `in` check and `handlers[type]()` executes `Object.prototype.toString` / `Object` — returning `"[object Object]"` or `{}` as if it were a handler acknowledgement. Since `type` comes straight from the network, the lookup must be own-property only (`Object.hasOwn`, as above), or use a `Map`/null-prototype object. Include `"toString"` / `"__proto__"` in the unknown-type test.
