**Cause**

This is not a service, descriptor, or project-file problem — it's a host networking asymmetry on the IPv6 loopback path.

- `localhost` resolves to `::1` first. Docker Desktop's port-forwarding proxy on Windows accepts the TCP connection on `[::1]:50051`, but nothing is forwarded to the container on that path (the container-side listener is only reached via the IPv4 mapping). The TCP handshake succeeds, so grpc-go considers the address "connected" and waits for the HTTP/2 server preface/SETTINGS, which never arrives. It does not fall back to `127.0.0.1` because the failure is a stall, not a refusal. After 2 s you get `Failed to dial target ... context deadline exceeded`, and — consistent with this — no invocation ever reaches the interceptor log.
- The HTTP/1.1 sibling on 50080 succeeds because curl uses Happy Eyeballs: it races `::1` and `127.0.0.1` and takes whichever answers, masking the same asymmetry.
- The address-only comparison confirms it: identical call to `127.0.0.1:50051` completes in one round trip with `invoked=true completed=true`.

**Smallest safe remediation**

Target the IPv4 loopback explicitly instead of `localhost`:

```powershell
grpcurl -plaintext -max-time 2 -d '{}' 127.0.0.1:50051 demo.Probe/Ping
```

If you want `localhost` to keep working for everyone (scripts, teammates), the next-smallest durable fix is to publish the port bound to IPv4 only, e.g. in compose `"127.0.0.1:50051:50051"` (or `-p 127.0.0.1:50051:50051`). With no `::1` listener, the `::1` attempt is refused instantly and grpc-go falls through to `127.0.0.1`. Do **not** disable IPv6 system-wide or edit the hosts file — both are broader than the problem.

**Confirmation**

1. Rerun the 127.0.0.1 command: exit code 0, `{"value": "pong"}`, and a new `invoked=true completed=true` line in the service log.
2. `grpcurl -plaintext 127.0.0.1:50051 list` returns `demo.Probe` — proves reflection (which the original command depends on) is reachable on that path.
3. If you applied the IPv4-only publish: rerun the *original* `localhost:50051` command and expect success well under the 2 s deadline (tens of ms), plus the log entry. Optionally `Test-NetConnection -ComputerName ::1 -Port 50051` should now report refused/false rather than succeeding.
