**Verdict:** This is a local host-networking issue (Windows Docker Desktop published-port proxy on IPv6 loopback), not a defect in the workspace code, dependencies, or the service. The evidence is a clean address-only A/B.

**Cause**

`localhost` resolves to `::1` before `127.0.0.1`, so the probe's channel targets `[::1]:50051`. Docker Desktop's published-port proxy on `::1` accepts the TCP connect but never completes the h2c HTTP/2 exchange, so the client sits until its 2s deadline and reports `DEADLINE_EXCEEDED`. The server never sees the RPC — the interceptor log has no entry for the failed call — which rules out server-side slowness, auth, or method problems. The identical call at `127.0.0.1:50051` succeeds (`pong`, exit 0, interceptor shows `invoked=true completed=true`), confirming the only variable is the address family. The HTTP/1.1 health probe on 50080 returning in 12 ms shows the container and host mapping are healthy; the stall is specific to HTTP/2 through the `::1` proxy path.

Side note on exit codes: the probe exited 2 (its documented deadline mapping — see `exit status 2` on stderr); the observed exit code 1 is `go run` wrapping the child's non-zero status. Any script gating on the probe's own codes should run the built binary (`go build ./cmd/probe`), not `go run`.

**Smallest safe remediation**

Point the local dev target at IPv4: `--target 127.0.0.1:50051` (and set the same in the local config/env that feeds the probe). Do not change the probe's resolver, do not disable IPv6 on the host, and do not touch the server or container mappings — they are working.

**Confirmation**

1. `go run ./cmd/probe --target 127.0.0.1:50051 --timeout 2s` → exit 0, stdout `pong`, empty stderr (already captured).
2. Service interceptor log shows a new `invoked=true completed=true` entry for that call.
3. Optionally re-run against `localhost:50051` once to confirm the failure is still address-specific and reproducible (so the fix is attributable, not timing).
4. Health check `curl.exe --max-time 2 http://localhost:50080/health` still returns 200 in ~10 ms, confirming nothing else moved.

If the `127.0.0.1` retry had also failed, the next step would be `docker compose ps` / `docker port <container>` and container health, but that is not needed here.

**Record for the ticket:** targets `localhost:50051` (→`[::1]:50051`, TCP ok, no HTTP/2 headers) vs `127.0.0.1:50051` (ok); deadline output `DEADLINE_EXCEEDED: deadline expired after 2s`, probe exit 2 / `go run` exit 1; REST `http_code=200 total_seconds=0.012000`; IPv4 retry exit 0 `pong` with server log `invoked=true completed=true`.
