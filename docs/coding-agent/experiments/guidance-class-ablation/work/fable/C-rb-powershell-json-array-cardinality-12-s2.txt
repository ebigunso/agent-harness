## Cause

This is a **bug in the probe's assertion logic**, not a workspace, runtime, or environment problem. The JSON is valid, script execution is permitted, and 7.4.6 is fine.

`[null]` is a legal one-element array. But `$raw | ConvertFrom-Json` sends the cmdlet's output through the pipeline, which **unrolls** the one-element array into its single element. That element is JSON `null`, so `$parsed` becomes `$null` — not an array. Your own guard confirms this (`parsed type=<null>`).

The assertion `$parsed -isnot [array]` is therefore testing the *unrolled* value, not the wire framing. Per the loaded guidance, a post-pipeline `-is [array]` check cannot prove how the JSON was framed on the wire — the pipeline has already destroyed the framing evidence before the test runs. So the probe rejects a value the contract says it must accept.

## Smallest safe remediation

Assert on the **raw wire framing**, which is the actual contract (accept `[...]`, reject scalars), instead of on the collapsed parsed object. Replace line 10:

```powershell
$t = $raw.Trim()
if (-not ($t.StartsWith('[') -and $t.EndsWith(']'))) { throw 'Expected JSON array' }
```

This is a syntactic framing check (not a full validator), which is exactly what distinguishes `[null]` / `[]` / `[1,2]` from scalar `null` or `5`, and it is immune to pipeline unrolling.

If you specifically need the *parsed* object to remain an array (e.g., to count elements), the minimal alternative on 7.4.6 is to stop enumerating:

```powershell
$parsed = ConvertFrom-Json -InputObject $raw -NoEnumerate
```

Then `$parsed -is [array]` holds and `$parsed.Count` is `1`. Caveat: `-NoEnumerate` only helps until the value is re-piped, and it does not exist on Windows PowerShell 5.1 — which is why the raw-framing check is the more portable primary fix.
