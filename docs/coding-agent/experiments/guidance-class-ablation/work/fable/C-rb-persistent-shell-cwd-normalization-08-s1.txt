**Cause**

This is a workspace (cwd) problem, not a build problem. The persistent shell's cwd was `C:/work/native/build` (left there by the prior `Set-Location`), but `cmake --build build` resolves its argument relative to the shell's cwd, so it looked for `C:/work/native/build/build`, which doesn't exist. The tool UI's remembered root (`C:/work/native`) and the shell's actual cwd had diverged. Nothing about the code, cache, generator, PATH, or permissions was wrong — the `Get-ChildItem` listing shows a valid configured build tree (`CMakeCache.txt`, `build.ninja`) one level above where the command was looking.

**Smallest safe remediation**

Navigate once, explicitly, to the intended base and rerun the original command unchanged:

```powershell
Set-Location -LiteralPath 'C:/work/native'
cmake --build build
```

No `cd ..` chains, no editing the command, no reconfigure.

**Confirmation**

- Before: `pwd` → `C:/work/native/build`; `cmake --build build` → exit 1, `Error: C:/work/native/build/build is not a directory`.
- After normalization: `pwd` → `C:/work/native`; `cmake --build build` → exit 0, stdout `[1/1] Linking CXX executable native.exe`, stderr empty.
- Final `pwd` → `C:/work/native`.

Status: resolved. The identical command succeeded with only the cwd changed, which confirms the diagnosis.

**Follow-up note (optional hardening, not required)**

If future commands in this persistent shell must be cwd-independent, invoke with an absolute build directory (`cmake --build C:/work/native/build`) or reset the shell to `C:/work/native` before each build step. Either is fine; the point is to avoid relying on whatever cwd a previous `Set-Location` left behind.
