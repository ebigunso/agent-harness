**Findings**

1. **charge.js, `catch` classification (`error instanceof Timeout`) — blocking.**
   The retry predicate only matches the locally defined `Timeout` class, but the mechanism the function actually uses to enforce the 1s bound is `AbortSignal.timeout(1000)`. When that signal fires, an adapter that "honors its AbortSignal" rejects with `signal.reason`, which is a `DOMException` with `name === "TimeoutError"` — not an instance of `Timeout`. So in the real path, the first genuine timeout is rethrown immediately and no retry ever happens; the retry branch is only reachable if the adapter separately throws this module's `Timeout` class (an implicit contract nothing in the diff establishes, and one that is fragile to duplicate module instances anyway). Require: classify on the signal's reason (`signal.aborted && signal.reason` / `error.name === "TimeoutError"`) and/or have the adapter contract defined explicitly; if `Timeout` is kept as the public error, `charge` should wrap the abort reason into it rather than expect callers to throw it.

2. **charge.js `check()` — test does not exercise the timeout mechanism at all.**
   Both fakes ignore the second argument and throw `new Timeout()` synchronously. The test therefore cannot detect finding #1, and the reviewer note "exactly three attempts bound total adapter wait to 3s" is asserted, not verified. Require a case where the fake actually waits on the signal (e.g. `new Promise((_, rej) => signal.addEventListener("abort", () => rej(signal.reason)))`) and confirm it retries, plus an assertion that each attempt receives a fresh, unaborted `AbortSignal`.

3. **charge.js retry loop — no backoff/jitter between attempts (non-blocking, would flag).**
   Three back-to-back attempts against a provider that is already timing out is straight load amplification during the exact condition where it's most harmful. The idempotency key prevents double-charge but not the cascade. Given the stated 3s budget, a short fixed/jittered delay that still fits the budget (or an explicit note that the caller is expected to rate-limit) would be appropriate.

4. **charge.js — final failure doesn't distinguish "uncertain" from "failed" (minor).**
   After the third timeout the caller gets a bare `Timeout`. The whole point of the task framing is that the charge may have succeeded; if a caller treats that as a failure and re-issues with a new key, the dedupe protection is defeated. At minimum the thrown error should carry the key (and ideally a distinct "outcome unknown, reconcile with this key" type) so the caller has what it needs to reconcile instead of re-charging.

Everything else (stable key across attempts, fresh signal per attempt, bounded attempt count, rethrow of non-timeout errors) is correct as written.
