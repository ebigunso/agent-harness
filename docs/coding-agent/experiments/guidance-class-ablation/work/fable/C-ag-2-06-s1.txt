**Verdict: block.** The change delivers the task ("read account status in feature") by bypassing the seam that exists for exactly this purpose.

## Findings

### 1. `Feature.cs` — `Feature.Status` bypasses `IAccounts` and binds to `SqlRepository.InternalConnection`
**What's wrong:** `Feature.Status(SqlRepository repo, long id)` takes the concrete repository, reaches into `repo.InternalConnection`, and runs its own SQL. `IAccounts.Status(long)` already provides this exact operation on the public seam.

**Why it matters:** The feature is now coupled to SQLite, to the `accounts` table schema, and to the repository's internal connection object. Any change to storage (different DB, caching, schema rename, connection pooling) now requires touching the feature. It also makes `Feature` untestable without a real `SqliteConnection`, and it defeats the only reason `IAccounts` exists. This is the interface bypass the guidance explicitly forbids.

**Require:** `Feature.Status(IAccounts accounts, long id) => accounts.Status(id);` — depend on the interface, not the concrete type, and delegate rather than re-implement.

### 2. `Feature.cs` — vendor dependency (`Microsoft.Data.Sqlite`) leaks into the feature/domain layer
**What's wrong:** `using Microsoft.Data.Sqlite;` is needed only because `Feature` calls `CreateCommand()` / `AddWithValue` directly. The domain-facing `Feature` should have no knowledge of a vendor driver.

**Why it matters:** Volatile outer detail (driver API, parameter naming conventions like `$id`) is now a compile-time dependency of the core. Dependency direction is inverted: the stable inner code points at the unstable outer vendor.

**Require:** Once Finding 1 is fixed, `Feature` needs no `Microsoft.Data.Sqlite` import. Keep the vendor `using` confined to `SqlRepository` (ideally in its own file so the boundary is visible in the import list).

### 3. `Feature.cs` — duplicated query logic
**What's wrong:** The SQL text, parameter binding, and result cast are copied verbatim from `SqlRepository.Status` into `Feature.Status`.

**Why it matters:** Two sources of truth for one query. A fix in one (e.g. handling `DBNull`, changing the column) will silently miss the other. The duplication is a direct symptom of the bypass.

**Require:** Delete the copy; delegate to `IAccounts.Status`.

### 4. `Feature.cs` — `InternalConnection` exposed as `internal` property invites further bypass
**What's wrong:** The connection is exposed on the repository purely so `Feature` can misuse it. The reviewer note says the repository owns the connection lifecycle, yet a second party now issues commands on it.

**Why it matters:** Shared mutable resource without a single owner; the `internal` modifier does nothing to stop same-assembly callers from repeating this pattern. Every future feature in the assembly has a ready-made escape hatch around the interface.

**Require:** Make the connection `private readonly` (or at minimum remove the property once `Feature` no longer uses it). If genuine internal access is ever needed, justify it explicitly rather than leaving it open by default.

## Acceptable form of the change

```csharp
// Feature.cs — no vendor imports
public static class Feature {
    public static string? Status(IAccounts accounts, long id) => accounts.Status(id);
}

// SqlRepository.cs — only place Microsoft.Data.Sqlite appears
using Microsoft.Data.Sqlite;
public sealed class SqlRepository : IAccounts {
    private readonly SqliteConnection _connection;
    public SqlRepository(SqliteConnection connection) { _connection = connection; }
    public string? Status(long id) { /* existing query */ }
}
```

Not flagged: the parameterized query itself (correct, no injection), `using var` disposal of the command, and `ExecuteScalar() as string` handling of a missing row — those are fine.
