**Cause**

This is a shell working-directory drift, not a workspace/build problem. A prior command in the same persistent shell did `Set-Location 'C:/work/native/build'`, so the shell's cwd was `C:/work/native/build`, while the tool UI still showed `C:/work/native` as the remembered root. `cmake --build build` resolves the relative `build` argument against the shell's actual cwd, producing `C:/work/native/build/build`, which doesn't exist — hence "is not a directory". The build directory itself is fine (`CMakeCache.txt` and `build.ninja` are present), and nothing in code, config, PATH, or permissions changed.

**Smallest safe remediation**

Don't chase the error message by creating a nested `build/build` or reconfiguring. Either:

- Run the command from the intended base:
  `Set-Location -LiteralPath 'C:/work/native'; cmake --build build`
- Or, more robustly and independent of cwd, use an absolute path:
  `cmake --build 'C:/work/native/build'`

The second form is preferable in a persistent shell where cwd can drift between steps, since it removes the dependency on prior `Set-Location` calls entirely.

**Confirmation**

1. `pwd` prints `C:/work/native` (if using the relative form).
2. `cmake --build build` (or the absolute-path form) exits 0 with build output — already observed in the captured comparison: `[1/1] Linking CXX executable native.exe`, empty stderr.
3. `Test-Path 'C:/work/native/build/native.exe'` returns `True`, and no stray `C:/work/native/build/build` directory was created.

**Prevention note**

Treat the UI's "workspace root" and the shell's cwd as separate state. Avoid persistent `Set-Location` in shared shells, or use `Push-Location`/`Pop-Location` around directory-scoped steps, and prefer absolute paths for tool arguments.
