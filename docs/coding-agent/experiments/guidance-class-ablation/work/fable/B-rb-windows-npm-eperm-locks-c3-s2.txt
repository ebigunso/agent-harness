**Cause**

This is not the native-module lock described in the reference material, and it is not a repository problem. `npm ci` failed before touching `node_modules` at all: `syscall mkdir`, `path C:\locked-cache`, errno -4048 (EPERM). npm's cache directory is configured as `C:\locked-cache` (`npm config get cache` confirms it), and the effective ACL on that path explicitly denies this user create/write access. npm needs a writable cache to fetch/extract packages, so it aborts immediately. Nothing in the failure references a `.node` binary, no unlink is involved, no process holds a lock, and the lockfile is in sync — so steps like `tasklist /m` or `taskkill` are irrelevant here and should not be run.

**Smallest safe remediation**

Don't modify ACLs on `C:\locked-cache` (that path was presumably locked down on purpose, and it may not be yours to change). Instead, redirect npm's cache to a location you own.

1. Find where the bad setting comes from so you fix the right layer:
   ```
   npm config get cache
   npm config list -l | findstr cache
   ```
   Also check the environment for `NPM_CONFIG_CACHE` and the repo for a `.npmrc` containing `cache=`.

2. Apply the narrowest fix that matches the source:
   - If it's set in the user or project `.npmrc`: remove the override so npm falls back to its default (`%LocalAppData%\npm-cache`):
     ```
     npm config delete cache            # user-level
     ```
     or delete the `cache=` line from the project `.npmrc`.
   - If it's an environment variable or a global/enterprise config you can't touch, override just for this invocation without changing persistent config:
     ```
     npm ci --cache "$env:LOCALAPPDATA\npm-cache"
     ```

**Confirmation**

- `npm config get cache` now prints a path under your profile (e.g. `C:\Users\<you>\AppData\Local\npm-cache`), or you are passing `--cache` explicitly.
- Re-run `npm ci`; expect exit code 0, no EPERM, and `node_modules` populated (`Test-Path node_modules\.package-lock.json` → True).
- Optionally `npm cache verify` to show the cache is writable and in use.

If the retry still fails, capture the new error verbatim — a different path or syscall would indicate a different problem (only then would the native-module lock playbook apply).
