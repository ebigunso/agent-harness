**Verdict:** Workspace problem — a repo-owned process is holding the native binary. Not a permissions, registry, cache, or lockfile issue.

**Cause**
`npm ci` removes `node_modules` before reinstalling. It failed on `unlink` of `node_modules\sharp\build\Release\sharp-win32-x64.node` with EPERM (errno -4048). On Windows a loaded DLL/`.node` addon cannot be unlinked while a process has it mapped. `tasklist /m sharp-win32-x64.node` shows exactly one holder: `node.exe` PID 4114, which is the thumbnail watcher started from `C:/work/npm-lock/workers/thumbnails.js` — i.e. this repository's own worker. Everything else checks out (package.json/lock in sync, a probe file beside the module can be created/deleted, no ACL denial, registry reachable), so this is purely a file-in-use lock. This is the second worker in a row (previous run: `better_sqlite3.node`, PID 4113, now gone), so the repo evidently has several long-running workers that each pin a native addon.

**Smallest safe remediation**
1. Stop the thumbnail watcher by its normal mechanism first (Ctrl-C in its terminal / the repo's stop script / editor task), since it's your own process. Only if it doesn't exit:
   `taskkill /PID 4114 /F`
2. Before retrying, check for any *other* repo workers so you don't hit a third module on the next pass:
   `tasklist | findstr node`
   and stop any that are launched from `C:/work/npm-lock/workers/` (leave unrelated node processes alone).
3. Retry: `npm ci`

No `sharp` rebuild, cache clean, or `node_modules` deletion by hand is needed — `npm ci` will recreate the tree once nothing holds the file.
