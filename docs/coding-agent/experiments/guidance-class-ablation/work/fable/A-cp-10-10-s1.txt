**Finding 1 — `Status.java`, `wire()`: wire codes now derived from `ordinal()`**

What's wrong: The explicit mapping (`OPEN→10, PAID→11, CLOSED→12`) has been replaced with `ordinal() + 10`. This ties an externally published, stable wire protocol value to the declaration order of the enum constants.

Why it matters: The reviewer notes state a new variant is scheduled to be inserted between `OPEN` and `PAID` with its own code. With this change, that insertion silently shifts `PAID` to 12 and `CLOSED` to 13, breaking every consumer relying on the published codes — with no compile error and no test failure unless a pinning test exists. Even without the scheduled change, any reorder (e.g. alphabetizing, IDE refactor) would corrupt the protocol. `ordinal()` is explicitly documented as unsuitable for persistent/wire values. The fact that current output is identical does not make this a safe refactor; it converts a data contract into an implicit coupling.

Required instead: Keep an explicit, per-constant mapping. Preferred form is a constructor field so each code is declared next to its constant and cannot drift:

```java
enum Status {
    OPEN(10), PAID(11), CLOSED(12);
    private final int wire;
    Status(int wire) { this.wire = wire; }
    int wire() { return wire; }
}
```

This is still shorter than the original switch, satisfies the "shorten" goal, and makes the upcoming insertion trivial (`NEW_STATE(13)` placed wherever the author likes). Also add a small test asserting `OPEN.wire()==10`, `PAID.wire()==11`, `CLOSED.wire()==12` so any future regression is caught.

**Verdict:** Block. The change is functionally equivalent today but replaces a stable contract with an ordinal dependency that the already-planned enum insertion will break.
