What I checked:

**Classification truth table** for `apply(ident, delta)`:

| `ident in _seen` | action | `_seen` after | `_value` after |
|---|---|---|---|
| no | add `delta`, record `ident` | ∪ {ident} | +delta |
| yes | no-op | unchanged | unchanged |

Both rows are implemented, and there is no third/ambiguous state.

**Owner and atomicity of the transition.** `_lock` is the single owner of both `_seen` and `_value`. The check (`ident not in _seen`), the write (`_value += delta`), and the record (`_seen.add`) all happen inside the same critical section, so there is no check-then-act window between "is it new?" and "mark it applied." There are no writers to either field outside the lock. `value()` also reads under the lock. Lock is non-reentrant but nothing nests, so no self-deadlock.

**Concurrent/repeated runs.** 32 concurrent deliveries of `e1` across 8 workers serialize on the lock; exactly one takes the "new" row, the other 31 take the "seen" row. Repeated sequential calls behave the same. The `check()` assertions (`values == [1]*32` and final value `1`) are real assertions, not optional guards.

**Invalid intermediate states.** If `_value += delta` raises (e.g. non-numeric `delta`), the exception propagates before `_seen.add(ident)`, so a failed apply does not poison the ident as "seen." The state is either fully applied or untouched.

**Considered and not raised**, given the stated contract in the reviewer notes:
- Same `ident` with a different `delta` is silently treated as a duplicate rather than rejected. The notes assert the ID→delta binding is immutable upstream, so this is by contract, not a defect here.
- `_seen` grows without bound and is lost on restart. Notes explicitly place persistence/restart outside this store's contract; growth is inherent to an in-memory dedupe set with no retention policy in scope.
