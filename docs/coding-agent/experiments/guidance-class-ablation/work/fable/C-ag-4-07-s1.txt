**Findings**

1. **`lib.rs`, `after_prefix` — unit mismatch: byte length passed as a scalar index (blocking).**
   `at_scalar` is defined (and documented downstream) as indexing by Unicode scalar value (`chars().nth`). `after_prefix` feeds it `prefix.len()`, which is the UTF-8 *byte* length. These only coincide for pure-ASCII prefixes, which is why the ASCII examples passed. For any non-ASCII prefix the index is too large: `after_prefix("éa", "é")` computes `at_scalar("éa", 2)` → `None` instead of `Some('a')`; `after_prefix("日本語", "日")` → `at_scalar(_, 3)` → `None` instead of `Some('本')`. Worse than a panic — it silently returns a wrong value that is indistinguishable from the legitimate "nothing after prefix" case. The boundary between the two functions mixes two index spaces, violating the "preserve scalar semantics for non-ASCII" requirement.
   Require: keep the boundary in one unit. Either convert to scalar space explicitly — `at_scalar(text, prefix.chars().count())` — or, preferably, stay in byte space where the prefix relationship actually lives and never route through `at_scalar` for this: `text.strip_prefix(prefix)?.chars().next()`. The latter is O(prefix) instead of O(text), can't drift out of sync with `at_scalar`, and is correct by construction. Add tests with multi-byte prefixes (2-, 3-, 4-byte scalars, and combining sequences) so this can't regress on ASCII-only fixtures.

2. **`lib.rs`, `after_prefix` — precondition "prefix is a validated prefix of `text`" is implicit and unenforced.**
   The function accepts any `prefix` and returns `Some(char)` for inputs where `prefix` is not a prefix at all (`after_prefix("abcd", "xy")` → `Some('c')`), and returns `None` both when the prefix is wrong and when the text ends exactly at the prefix. The success/failure contract is therefore ambiguous at the API boundary, relying on a caller-side invariant that is not visible in the signature or docs. Using `strip_prefix` as in (1) makes the precondition part of the function's own behavior (`None` on non-prefix). If the current pass-through behavior is intended, document the precondition on the function and state that the result is unspecified otherwise — but I would not accept the unstated version.

**Impact classification:** additive (two new public functions, no existing consumers), but as written the second function has a latent correctness bug for non-ASCII input that would become a breaking fix later once callers depend on it; better to land it correct now.
