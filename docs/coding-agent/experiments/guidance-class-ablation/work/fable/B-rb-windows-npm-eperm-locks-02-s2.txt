**Cause**

`npm install` needs to replace `node_modules\sharp\build\Release\sharp-win32-x64.node`, but Windows won't allow unlinking a DLL that is mapped into a live process. `tasklist /m` shows exactly one holder: `node.exe` PID 4102, an image worker launched from `C:/work/npm-lock/workers/images.js` (owned by this repo). It survived its terminal disconnecting, which is why "close the terminal" didn't free the lock. This is not a permissions, lockfile, registry, or cache problem — the probe file beside the module can be created/removed fine, so it's purely a file-in-use lock.

**Smallest safe remediation**

Stop that one worker; don't kill node processes broadly.

1. Try a graceful stop first if you have a mechanism (Ctrl+C in its session, a shutdown endpoint, or `taskkill /PID 4102` without `/F`).
2. If it doesn't exit:
   ```
   taskkill /PID 4102 /F
   ```
3. Re-run:
   ```
   npm install
   ```

No need for `rm -rf node_modules`, cache cleaning, or reboots.

**Confirmation**

- `tasklist /m sharp-win32-x64.node` returns "INFO: No tasks are running which match the specified criteria" (no holder).
- `tasklist | findstr node` shows nothing else from this repo still holding the tree (fine if unrelated node processes remain — they didn't appear in the `/m` output).
- `npm install` exits 0 with no EBUSY/EPERM.
- Optional sanity: `node -e "console.log(require('sharp').versions)"` loads the rebuilt/reinstalled binary.
- Restart `workers/images.js` afterward — note it will now load the new binary, which is the correct outcome.

**Evidence to keep**: the original stderr (path + errno -4082), the `tasklist /m` output naming PID 4102, the `taskkill` result, and the retry's exit code.

**Prevention note**: since the worker outlives its terminal, treat it as a service — stop it explicitly (or via a script/task target) before any `npm install`/`npm ci` on this checkout.
