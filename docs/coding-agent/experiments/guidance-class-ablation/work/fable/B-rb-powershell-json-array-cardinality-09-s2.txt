## Cause

Not a workspace problem. `data.json` is valid and correctly framed (`  [true]  `), and the contract says singleton arrays must pass. The failure is a bug in the checker itself: line 5 pipes the parsed result through `| Write-Output`, and the PowerShell pipeline unrolls a one-element collection into its single element. So `$parsed` arrives as a bare `System.Boolean`, and `-isnot [array]` on line 10 throws. The `-is [array]` check is measuring pipeline unrolling, not the wire framing — that's why it would pass for `[true,false]` and fail for `[true]` with the same JSON shape.

`ConvertFrom-Json -NoEnumerate` isn't available on Windows PowerShell 5.1.22621, so the correct fix here is to assert framing on the raw serialized text.

## Smallest safe remediation

Replace the parse line and the assertion in `probes/cardinality.ps1`:

```powershell
$raw = Get-Content -Raw data.json
$parsed = ConvertFrom-Json -InputObject $raw   # still parsed for validity; no re-piping
...
$trimmed = $raw.Trim()
if (-not ($trimmed.StartsWith('[') -and $trimmed.EndsWith(']'))) { throw 'Expected JSON array' }
```

This accepts `[]`, `[true]`, and `[true,false]` and rejects scalars like `true` or `"x"`, independent of element count. Don't "fix" it with `@(...)` around the parse — that would coerce a scalar wire value into a one-element array and make the check accept things the contract must reject.

2. Negative check: temporarily set `data.json` to `true` (scalar) — expect the throw and exit code 1.
3. Cardinality sweep: `[]`, `[true]`, `[true,false]` — all three should exit 0, confirming the result no longer depends on element count.
