## Cause

This is a workspace (script logic) problem, not an environment problem. PowerShell 7.4.6 is present and `-NoEnumerate` is supported.

The bug is a **re-enumeration across the function boundary**. Inside `Parse`, `ConvertFrom-Json -NoEnumerate` correctly stores a 1-element array in `$items`. But the bare `$items` on the next line writes that array to the function's *output stream*, which unrolls it. Because the array has a single element, the caller receives the scalar `7`, so `$parsed` becomes `System.Int64` and the `-isnot [array]` assertion fires.

This matches the reference note: `-NoEnumerate` preserves the array *unless re-piped* — and returning it via the function output stream is exactly such a re-emission.

## Smallest safe remediation

Suppress enumeration on the function's return value with the unary comma (array-wrapping) operator:

```powershell
function Parse { $items = $raw | ConvertFrom-Json -NoEnumerate; ,$items }; $parsed = Parse
```

(Equivalently `return ,$items`, or eliminate the function and assign `$parsed = $raw | ConvertFrom-Json -NoEnumerate` directly, since assignment does not unroll.) The comma-operator change is the minimal edit and preserves the empty/singleton/multiple-element contract.

Note: even after this fix, a post-pipeline `-is [array]` test proves the parsed *object shape*, not the on-the-wire framing. If the contract really means "reject scalar wire values," the robust check is on the trimmed raw text — that it starts with `[` and ends with `]` (a framing check, not a JSON syntax validator) — alongside the element count.
