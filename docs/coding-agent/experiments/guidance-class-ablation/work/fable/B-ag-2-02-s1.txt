**Verdict: Block.**

## Findings

### 1. `Order.java` — domain record now imports `jakarta.servlet.http.HttpServletRequest`

**What's wrong:** The diff adds a direct dependency from `Order` (domain) to the Servlet API (transport/delivery layer). This inverts the dependency direction: the stable inner type now depends on a volatile outer framework detail.

**Why it matters:**
- Per the reviewer notes, `Order` is explicitly transport-independent and is reused by batch jobs. Batch jobs have no `HttpServletRequest`, yet after this change they must have the Servlet API on the classpath just to compile/load `Order`. That's a build/packaging coupling that shouldn't exist.
- The Servlet API is installed in the outer Spring application, not in the domain module. If the domain is a separate module (as the notes imply), this either fails to compile or forces the domain module to pick up a servlet dependency it has no business owning.
- It creates a circular-in-spirit relationship: the web layer depends on `Order`; `Order` now depends on the web layer's framework.
- The `"tenant"` attribute name and the `(String)` cast encode the authentication middleware's contract inside the domain. The note says the middleware *guarantees* a validated String — fine, but that guarantee belongs to the middleware/adapter, not the domain. If the attribute key or type changes, the domain breaks for a reason unrelated to orders.

**What I'd require instead:**
- Revert `Order` to `public record Order(String tenant) {}` with no servlet import.
- Put the extraction in the web adapter layer, e.g. a controller helper, a `HandlerMethodArgumentResolver`, or a small `OrderRequestMapper` in the Spring module:
  ```java
  // web layer
  static Order orderFrom(HttpServletRequest request) {
      return new Order((String) request.getAttribute("tenant"));
  }
  ```
- If the intent is a reusable seam, define it in terms the domain owns (e.g. `Order.from(TenantContext ctx)` where `TenantContext` is a domain-level abstraction), and have the servlet adapter implement/produce `TenantContext`. The domain never sees the request type.

### 2. `Order.java` — factory hides an unchecked cast with no null/type handling (minor, secondary)

**What's wrong:** `(String) request.getAttribute("tenant")` will throw `ClassCastException` if the attribute is not a String, and silently produce `Order(null)` if it's absent.

**Why it matters:** The notes say the middleware guarantees a validated String, so on the happy path this is fine. But once the extraction lives in the adapter, that's where the guard belongs — an explicit `Objects.requireNonNull` or a clear failure if the middleware didn't run (misconfigured filter ordering, a route that skips auth). A domain record silently accepting `null` tenant is a worse failure mode than a loud one at the boundary.

**What I'd require:** In the adapter, fail fast on a missing/mistyped attribute rather than propagating a null tenant into the domain. This is not blocking on its own; it's a follow-on once finding 1 is addressed.

---

Summary: the change does what the commit message says functionally, but places the logic in the wrong layer. Move the request-to-`Order` mapping into the Spring/web module and keep the domain record free of `jakarta.servlet`.
