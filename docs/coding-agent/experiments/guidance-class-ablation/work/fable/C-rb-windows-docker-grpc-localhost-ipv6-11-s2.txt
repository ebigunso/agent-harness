**Cause**

Not a probe, dependency, or server defect. `localhost` resolves `::1` before `127.0.0.1`, so the failed channel dialed `[::1]:50051`. Docker Desktop's published-port proxy on the IPv6 loopback accepts the TCP connection but never returns HTTP/2 (h2c) response headers, so the bidi stream stalls until the 2 s deadline → `DEADLINE_EXCEEDED`, exit 2, and no entry in the server interceptor log (the request never reached the handler).

The discriminating evidence is the address-only comparison, not the REST check: same method, payload, deadline, server, container, and config, only the target changed to `127.0.0.1:50051`, and it returned `pong 1`/`pong 2` with the service log showing `invoked=true completed=true`. The `curl` result to `localhost:50080` (200 in 0.012 s) only shows that HTTP/1.1 on the sibling port is fine through the same proxy; it does not exercise h2c on 50051, so it rules out "container down" but does not on its own explain the hang.

**Smallest safe remediation**

Change the local target from `localhost:50051` to `127.0.0.1:50051` in the local probe/config used for this workspace. Nothing else: don't touch the service, port mappings, container, Docker Desktop networking, or system-wide IPv6/hosts settings.

**Confirmation**

1. `dart run probes/bidi.dart --target 127.0.0.1:50051 --timeout 2` → expect exit 0, stdout `pong 1` / `pong 2`, empty stderr. (Already observed.)
2. Service interceptor log shows `probe method="bidirectional Echo" transport=h2c invoked=true completed=true` for that run.
3. Optionally re-run once more against `localhost:50051` to confirm the failure still reproduces there, so the only delta is the address.
4. Record: targets and port (`[::1]:50051` fail / `127.0.0.1:50051` ok), the deadline output (`DEADLINE_EXCEEDED: deadline expired after 2s`, exit 2), REST timing (`localhost:50080` 200, 0.012 s), and the IPv4 retry result.

**Is this a workspace problem?**

The workspace files, deps, and build are fine; the failure is a local Docker Desktop environment behavior (IPv6 loopback proxy stalling HTTP/2 on the published port). The fix is a local config change, not a code fix. If both addresses had failed, the next step would be inspecting the service, published ports, and container health — but that branch doesn't apply here.
