**Findings**

1. **`Money.cs`, `Money` constructor (line 4) — invariant is declared but not enforced.**
   `Money.Create` validates `amount >= 0`, but the constructor is `public` and does no validation. Per the reviewer notes, import and API adapters call the constructor directly, so `new Money(-50m)` is a legal, trust-boundary-reachable value. `Ledger.Debit` then silently turns a "debit" into a credit (`balance - (-50) = balance + 50`). The nonnegative-magnitude invariant that `Debit` relies on is therefore not actually guaranteed anywhere; it only holds if callers happen to choose the factory. This is the exact failure the "protect invariants" guideline is about: the check exists but isn't at the boundary that matters.
   **Require:** either make the constructor `private` so `Create` is the only entry point, or move the `amount < 0` check into the constructor (and have `Create` just delegate). Do not ship two construction paths with different guarantees.

2. **`Money.cs`, `Ledger.Debit` (line 11) — no null guard on `money`.** Minor, but since this is the new public API and the file shows no nullable-context enablement, a `null` argument surfaces as a `NullReferenceException` inside the method rather than an actionable `ArgumentNullException` at the boundary. **Require:** `ArgumentNullException.ThrowIfNull(money)` (or enable nullable and annotate), so misuse fails early with a clear message.

Finding 1 is blocking; finding 2 I'd flag but not block on alone.
