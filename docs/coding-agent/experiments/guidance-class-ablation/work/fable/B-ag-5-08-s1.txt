**Findings**

1. **`lib.rs`, `remove` body — ordering breaks the registry invariant on cleanup failure (blocker).**
   The sequence is `resources.remove` → `cleanup()?` → `registry.remove`. If `cleanup` returns `Err`, the `?` returns early with the resource bytes already gone but the ID still in `registry`. The stated invariant ("every advertised ID must resolve to a live resource") is now violated and observable to anyone reading the registry: they will look up `id` in `resources` and get `None`. This is exactly the anti-pattern of a state transition that admits an invalid intermediate state and then leaves it there permanently on the error path. It is also not self-healing: a retry re-runs `cleanup` (which may not be idempotent) on an already-released resource before ever fixing the registry.
   Require: make the registry (the authoritative advertisement) the *first* thing to change, so no window exists in which an advertised ID has no backing resource:
   ```rust
   registry.remove(&id);      // stop advertising before anything can disappear
   resources.remove(&id);     // release
   cleanup()?;                // fallible follow-up; failure leaves state consistent
   Ok(())
   ```
   With this order, a cleanup failure leaves the ID unadvertised and the resource released — consistent by the stated invariant — and the caller gets the error for the cleanup step only. If the design instead requires that a cleanup failure roll everything back, then `cleanup` must run *before* either mutation (or the resource must be re-inserted on `Err`); pick one and document it, but the current order is not acceptable under either interpretation.

2. **`lib.rs` — `remove` return values silently discarded (flag).**
   `resources.remove(&id)` and `registry.remove(&id)` both return whether anything was present, and the function ignores both. Given the invariant, `registry.contains(&id) && !resources.contains_key(&id)` on entry is a pre-existing corruption, and this function is the natural enforcement point to detect it rather than paper over it. It also leaves the idempotency contract undefined: is calling `remove` for an unknown ID a no-op, or an error? Right now it runs `cleanup()` regardless, which for an unknown/already-removed ID may be wrong.
   Require: decide the contract explicitly. At minimum, check the results — e.g. return `Err` (or `debug_assert!`) if the registry had the ID but the resource map did not, and skip `cleanup` (or return a distinct result) when nothing was actually released.

The change is not acceptable as-is; finding 1 must be fixed before merge.
