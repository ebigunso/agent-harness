**Findings**

1. **`preview.cpp`, `format_preview` — `next_id++` mutates shared allocator state from a rendering function.**
   - *What's wrong:* `format_preview` is documented/expected to be observational, but the change post-increments `next_id`, the same counter `allocate_id()` consumes. Every preview now silently allocates (and discards) an ID.
   - *Why it matters:* Rendering a preview changes what the next real `allocate_id()` returns, so the "hint" is wrong the moment it's shown (that ID will never be allocated to anything), and previewing twice yields different output for identical input. It also breaks local reasoning: nothing in the name or signature of `format_preview` suggests it has side effects, and the mutation bypasses `allocate_id()` so there are now two writers to the counter. Uniqueness isn't violated in a single-threaded session, but the behavior is still incorrect for the stated purpose and is a hidden-coupling trap for the next reader.
   - *Require instead:* Read the counter without modifying it, e.g. `return name + ":" + std::to_string(next_id);`. Preferably expose a small read-only accessor (`unsigned peek_next_id() { return next_id; }`) so `format_preview` doesn't touch the global directly and `allocate_id()` remains the sole writer. If the intent was actually to reserve an ID at preview time, that must be made explicit in the function's name/contract and the reserved ID returned to the caller—not left as an incidental side effect of formatting.

No other issues; the change is not acceptable as-is because of the above.
