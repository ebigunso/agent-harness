**Cause: not a workspace problem — it's a script bug (pipeline enumeration).**

In PowerShell 7, `ConvertFrom-Json` *enumerates* a top-level JSON array into the pipeline by default. `'[null]' | ConvertFrom-Json` therefore emits the array's single element, `$null`, and that is what gets assigned to `$parsed`. The one-element array is never seen by the script, so `parsed type=<null>` and the `-isnot [array]` check throws. The same defect would misreport `[]` (emits nothing → `$null`) and `[1]` (emits `Int64 1`, a scalar). The runtime, execution policy, and file are all fine; the input JSON is valid.

**Smallest safe remediation:** keep the array intact with `-NoEnumerate` (line 5):

```powershell
$parsed = $raw | ConvertFrom-Json -NoEnumerate
```

Don't "fix" it with `@(...)` around the result: `@($null)` is a one-element array, so a scalar wire value of `null` would be accepted, violating the contract that rejects scalars. `-NoEnumerate` preserves the distinction the contract needs: `[]` → empty `Object[]`, `[null]` → `Object[]` of length 1 containing `$null`, `null`/`1` → scalar → rejected.

1. Rerun `pwsh -NoProfile -File probes/cardinality.ps1` → exit code 0, output shows `parsed type=System.Object[]`, no stderr.
2. Spot-check the contract boundaries in a shell:

   ('null'   | ConvertFrom-Json -NoEnumerate) -is [array]   # False → script would throw (correct)
