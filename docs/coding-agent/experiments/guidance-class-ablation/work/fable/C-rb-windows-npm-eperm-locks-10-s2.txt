## Cause

This is a workspace problem, not an npm/registry/lockfile issue. `npm ci` must remove `node_modules` before reinstalling, and Windows refuses to `unlink` a native addon (`.node` is a DLL) that is mapped into a running process → `EPERM -4048`. The holder is confirmed:

```
Code.exe   PID 4110   better_sqlite3.node
```

PID 4110 is the editor's integrated test host, and the test-host log records the same PID loading exactly `C:\work\npm-lock\node_modules\better-sqlite3\build\Release\better_sqlite3.node`. Permissions and lockfile sync are ruled out (probe file create/delete works beside the module, no ACL denial, lock and manifest match).

## Smallest safe remediation

1. **Release the module gracefully** — stop the editor's test integration / test run for this workspace (or "Developer: Reload Window" / close the workspace window in the editor). That ends the extension host that has the addon loaded. Do **not** delete `node_modules` by hand or take ownership/ACL changes — the file isn't permission-locked, it's in use.
2. **Verify it's released:**
   ```powershell
   tasklist /m better_sqlite3.node
   ```
   Expected: `INFO: No tasks are running which match the specified criteria.`
3. **Retry the original command:**
   ```powershell
   npm ci
   ```
4. **Last resort only** if step 2 still shows PID 4110 after the graceful stop and you've confirmed via the test-host log that this PID is the workspace's test host (it is, per the observations):
   ```powershell
   taskkill /PID 4110 /F
   ```
   then repeat steps 2–3.

## Confirmation

- `tasklist /m better_sqlite3.node` returns no processes before the retry.
- `npm ci` exits 0 with no `EPERM`/`unlink` in stderr.
- `node_modules\better-sqlite3\build\Release\better_sqlite3.node` exists with a new timestamp, and a quick load check works:
  ```powershell
  node -e "require('better-sqlite3')(':memory:').prepare('select 1 as x').get()"
  ```
- If the retry fails anyway, capture the new module path from the error and `tasklist | findstr node` to find the next holder.

One follow-on caveat (not part of the fix): the pre-existing binary was an **editor-runtime source build** (compiled against the editor's Electron ABI). `npm ci` will rebuild it for Node 20.18.0. When you restart the editor test integration, it may need its own rebuild step (e.g. `electron-rebuild`/the extension's rebuild script) or it will fail to load the Node-ABI addon.
