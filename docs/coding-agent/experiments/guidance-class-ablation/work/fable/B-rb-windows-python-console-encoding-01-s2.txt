**Cause**

`print(summary)` raised at output time, not during computation. `summary` is `'Summary \u2014 complete'`; the em-dash at index 8 matches the traceback's "position 8". Under CPython 3.12 on Windows, when stdout is not a console (here a pipe), `sys.stdout` is encoded with the ANSI/locale code page — cp932 on this machine — and cp932 has no mapping for U+2014, so the codec raises. `sys.stdout.encoding = cp932` and `utf8_mode = 0` confirm nothing overrode the default.

One nuance vs. the reference note: since stdout is a pipe, this isn't the *console* code page but the process's locale code page; the mechanism and fix are the same. This is an environment/output-encoding issue, not a workspace or data problem — the report itself was produced correctly.

**Smallest safe remediation**

Rerun with the I/O encoding override (PowerShell 7):

```powershell
$env:PYTHONIOENCODING = 'utf-8'; python report.py
```

(`$env:PYTHONUTF8 = '1'` is an equivalent alternative that enables UTF-8 mode more broadly.)

There's nothing to clean up: the script is read-only and writes no files, and the failure occurred after the summary was computed, so the failed attempt left no partial side effects.

**Confirmation**

- Exit code 0 and stdout contains `Summary — complete`; if the consumer is byte-oriented, the em-dash should appear as `E2 80 94`.
- Optionally, `python -c "import sys; print(sys.stdout.encoding)"` in the same env prints `utf-8`.

**Durable fix (if you own `report.py`)**

Don't depend on the caller's environment: add `sys.stdout.reconfigure(encoding="utf-8")` at startup (works for both console and piped stdout), so the script prints correctly regardless of locale. Note that the env-var approach only applies to invocations that set it; any other caller (scheduler, CI step, another shell) will hit the same error until the script fixes its own output encoding.
