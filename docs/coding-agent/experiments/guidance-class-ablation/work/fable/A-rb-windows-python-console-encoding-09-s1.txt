**Cause**

This is an environment problem, not a logic failure. The script's checks all passed; it died on the final `print('PASS ' + symbol)`. Because stdout is a pipe (not a Windows console), CPython 3.12 with UTF-8 mode off (`sys.flags.utf8_mode = 0`) uses the ANSI code page for `sys.stdout` — here cp1252. U+2713 CHECK MARK has no mapping in cp1252, so the `charmap` encoder raises `UnicodeEncodeError` before anything is written (hence empty stdout) and the interpreter exits 1.

Run interactively in a console it would have worked (the console uses UTF-16 via `WriteConsoleW`), which is why this only bites under capture/CI.

**Smallest safe remediation**

Enable UTF-8 mode for the invocation only; no code change, no machine-wide setting:

```powershell
$env:PYTHONUTF8 = 1; python check.py
```

or equivalently `python -X utf8 check.py`. This makes `sys.stdout`/`stderr` UTF-8 regardless of the console/pipe state (and also makes `open()` default to UTF-8, which is the intended Python 3.15 behavior anyway).

If you'd rather fix it in the script so every caller benefits, the minimal equivalent is one line near the top of `check.py`:

```python
sys.stdout.reconfigure(encoding="utf-8")
```

Avoid the tempting alternatives: `errors="replace"` silently emits `?`, and swapping `✓` for ASCII changes the output contract for whatever consumes it.

**Confirmation**

1. Rerun under the same captured pipe: `python -X utf8 check.py; $LASTEXITCODE` → expect exit code `0`, stdout `PASS ✓`, empty stderr.
2. Verify the stream encoding in that same configuration: `python -X utf8 -c "import sys; print(sys.stdout.encoding)" | Out-String` → `utf-8`.
3. Optionally confirm the bytes on the wire: `python -X utf8 check.py | Format-Hex` should show `E2 9C 93` for the check mark, and the pipe consumer must be reading as UTF-8 (in PowerShell 7 that's the default; on 5.1 set `[Console]::OutputEncoding = [Text.Encoding]::UTF8`).
