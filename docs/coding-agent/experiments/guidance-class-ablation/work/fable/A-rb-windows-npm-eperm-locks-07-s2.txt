**Cause**

This is a workspace problem, but not a dependency/lockfile/permissions one. `npm ci` deletes `node_modules` before reinstalling, and the unlink of `node_modules\canvas\build\Release\canvas.node` failed with `EPERM` (errno -4048). On Windows, a loaded native addon (`.node` DLL) is mapped into the process's address space and cannot be unlinked while the process holds it. `tasklist /m canvas.node` shows exactly one holder: `node.exe` PID 4107, the chart-preview worker (`workers/chart-preview.js`) launched from this repository — a leftover child that outlived its parent script. Lockfile sync, ACLs, cache, and registry are all fine, so nothing else needs touching.

**Smallest safe remediation**

Stop the orphaned worker that this repo owns, then rerun the same command:

```powershell
Stop-Process -Id 4107          # add -Force only if it doesn't exit
npm ci
```

Don't reach for `rm -rf node_modules`, `--force`, cache clears, or running as Administrator — none of those address a file lock, and admin rights won't override an in-use DLL mapping anyway. Since the worker's parent already finished, killing the orphan is safe; if the worker is supposed to persist, restart it *after* `npm ci` so it loads the freshly installed binary.

**Confirmation**

1. `tasklist /m canvas.node` — should report "No tasks are running which match the specified criteria" (no remaining holders).
2. `Get-Process -Id 4107 -ErrorAction SilentlyContinue` — returns nothing.
3. `npm ci` exits 0 with `node_modules\canvas\build\Release\canvas.node` present, and `node -e "require('canvas')"` loads cleanly.

**Follow-up worth doing** (outside the immediate fix): make the parent script terminate the chart-preview child on exit (e.g., `child.kill()` in an `exit`/`SIGINT` handler, or spawn it non-detached), so the next `npm ci` doesn't hit the same lock.
