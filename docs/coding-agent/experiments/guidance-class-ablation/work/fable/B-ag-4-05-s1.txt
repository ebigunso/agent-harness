**Verdict: block.** The change ships the public entry point behind an untyped bag, which is exactly what Gate 4 prohibits.

## Findings

### 1. `query.ts:3` — `query(options: any)` is an implicit contract
- **What's wrong:** The only exported query takes `any`. Its real shape (`{ id: string; connection: Connection; view: BrowserView }`) is discoverable only by reading `screen()`.
- **Why it matters:** This is the Gate 4 anti-pattern verbatim — a contract communicated by call-site assumption. Any new caller can pass anything and the compiler will accept it; renaming a field breaks callers silently at runtime. "Inputs trusted" covers the current caller, not the contract.
- **Require:** A named, exported input type (interface or explicit parameters) and an explicit return type. No `any` on an exported signature.

### 2. `query.ts:3` — the query's boundary spans UI and database internals
- **What's wrong:** An "account lookup query" takes a `BrowserView` and performs rendering. The function's contract now depends on both a DB connection and a UI component; its return type is whatever `render` returns (a `string`, inferred from `any`, so effectively `any`).
- **Why it matters:** Boundary is neither minimal nor stable — any change to the view or connection API is a change to the query API. It also makes the query un-testable without a view and un-reusable outside the browser path. The reviewer note flags this correctly.
- **Require:** `query` should take an account id (plus, if injection is wanted, a narrow lookup interface — e.g. `{ lookup(id: string): Account }`) and return an `Account`. `screen()` composes `query` with `BrowserView.render`. Rendering does not belong in the query contract.

### 3. `query.ts:1–3` — failure semantics unmodeled
- **What's wrong:** `Connection.lookup` returns `{id}` for every input; there is no not-found, error, or invalid-id path, and `query` inherits that. Nothing in the signature tells a caller whether a miss is `undefined`, a throw, or a fabricated row.
- **Why it matters:** Gate 4 requires failure modes to be explicit. As written, a lookup that "fails" returns something that looks like success — an ambiguous success/failure signal. When the stub is replaced with a real data source, every caller's assumption will be wrong in some direction.
- **Require:** State the failure contract on the exported signature (e.g. `Account | undefined`, a `Result`, or a documented typed error) and have `screen()` handle it rather than passing an undefined into `render`.

### 4. `query.ts:1–2` vs. `:3` — public function, private parameter types
- **What's wrong:** `Connection` and `BrowserView` are module-private, but `query` is exported and needs them. Once `any` is removed (finding 1), no external caller can construct a valid argument.
- **Why it matters:** This is likely *why* `any` was used — it papers over an inconsistency in what's actually meant to be public.
- **Require:** Decide the boundary. Either export the minimal interfaces the query depends on, or (preferred, per finding 2) drop the dependency on these classes from the public signature entirely.

### 5. Commit / plan — no contract-impact scope stated
- **What's wrong:** The message "expose one account lookup query" doesn't state whether this is none/additive/breaking, nor what the exported surface is.
- **Why it matters:** Gate 4 evidence expectation; trivial to satisfy here (it's additive, new file) but it should be written down, especially since the export surface is the whole point of the change.
- **Require:** One line: "Additive: new exports `query`, `screen`; no existing consumers."
