**Cause**

This is an environment (stdout encoding) problem, not a bug in the audit logic. Because stdout is a pipe rather than an interactive console, Python 3.12 on Windows uses the locale ANSI code page for `sys.stdout` — here cp932 (`sys.stdout.encoding = cp932`, UTF-8 mode off). `print(path)` for `C:\reports\🧪.txt` then has to encode U+1F9EA, which cp932 cannot represent, so `print` raises `UnicodeEncodeError` on line 40. File I/O is unaffected (Windows paths are UTF-16 natively and the read succeeded); only the display fails.

**Smallest safe remediation**

Scope the fix to the stream encoding for this invocation only — don't touch the script or system locale:

```powershell
$env:PYTHONIOENCODING = 'utf-8'; python audit.py
```

`PYTHONIOENCODING` changes only stdin/stdout/stderr, so it cannot alter how `audit.py` reads files (unlike `-X utf8` / `PYTHONUTF8=1`, which also flips the default `open()` encoding and could misread any cp932-encoded inputs). If the pipe consumer is PowerShell itself, also set `[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()` in that session so it decodes the bytes correctly.

If you'd rather make the script robust regardless of caller, the minimal in-code equivalent is `sys.stdout.reconfigure(errors="backslashreplace")` near the top of `audit.py` — output stays cp932 but unencodable characters degrade to `\U0001f9ea` instead of crashing. Either is fine; prefer the env var if you don't want to edit the script.

**Confirmation**

1. `python -c "import sys; print(sys.stdout.encoding)" | Out-String` → prints `utf-8` (still piped, so it exercises the same path).
2. `python audit.py; $LASTEXITCODE` → exit code `0`, no traceback on stderr, and the output contains the `C:\reports\🧪.txt` line intact (or `\U0001f9ea` if you chose the `backslashreplace` variant).
3. Optionally run once without the variable to confirm it fails identically, proving the env var is the controlling factor.
