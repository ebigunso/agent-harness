**Verdict: not acceptable as-is. Two blocking defects, one flag.**

### 1. BLOCK — `charge.js` L5: `Idempotency-Key` is regenerated on every attempt

`randomUUID()` is evaluated inside the `for (;;)` body, so each retry sends a *different* idempotency key. The reviewer notes state the exact scenario this breaks: "a timeout can follow a committed charge." When the first request commits server-side but the client's 1 s deadline fires, the retry arrives with a fresh key, the server has no reason to dedupe it, and the customer is charged twice (or N times, given #2). This defeats the sole purpose of the header and makes the retry loop strictly worse than no retry.

Note this also applies when the timeout fires during `response.text()` after a 2xx header was already received — the charge is committed, and the retry must carry the same key to get the stored result back.

**Require:** hoist key generation out of the loop so one key covers all attempts of one logical charge:

```js
export async function charge(idempotencyKey = randomUUID()) {
  for (...) {
    await fetch(..., { headers: { "Idempotency-Key": idempotencyKey }, ... });
```

Prefer accepting the key as a parameter (with the caller persisting it) so a process crash between attempts doesn't also lose the key; the default is acceptable as a minimum.

### 2. BLOCK — `charge.js` L3: unbounded retry with no backoff

`for (;;)` retries forever on `TimeoutError` with zero delay between attempts. Against a payment provider that is slow or degraded, this (a) never returns control to the caller — a hung charge in a request path becomes a hung request indefinitely, and (b) hits the provider every ~1 s per stuck caller, amplifying the very outage that caused the timeout. This is the Gate 6 anti-pattern verbatim ("unbounded retries … in critical paths", "cascading failure paths without isolation boundaries").

**Require:** a bounded attempt count (e.g. 3) with exponential backoff and jitter, and rethrow the last `TimeoutError` when attempts are exhausted so the caller sees the failure rather than a silent hang. The caller can then decide whether to reconcile via the idempotency key.

### 3. FLAG — `charge.js` L5: 1000 ms deadline on a payment POST

A 1 s ceiling is tight for a payment authorization; it will produce timeouts (and therefore retries) under normal tail latency, not just outages. Combined with #1 that's duplicate charges; even after #1 is fixed it inflates provider load and false "timed out" outcomes. Not blocking on its own since the value may be a deliberate product constraint, but I'd want the number justified (provider p99, upstream request budget) or raised, and made a parameter rather than a literal.

### Not raised

- Only `TimeoutError` is retried and other failures propagate — correct and matches intent. `AbortSignal.timeout` in Node 24/undici rejects with the signal's reason (a `TimeoutError` DOMException), so the `error.name` check is sound for both header and body-read timeouts.
- Non-2xx → throw without retry is appropriate; a 5xx from a payments endpoint should not be blindly retried without knowing whether it's committed.
