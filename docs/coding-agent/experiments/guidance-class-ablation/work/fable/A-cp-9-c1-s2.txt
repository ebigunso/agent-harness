**Verdict: not acceptable as-is.** The wrapping is structurally sound (non-nil-interface return, `Unwrap` preserves the chain), but there are three things I'd require changes or answers on, plus one nit.

---

**1. `catalog/fetch.go` – `Timeout` is a lossy snapshot that only recognizes `context.DeadlineExceeded`.**

`Timeout: errors.Is(err, context.DeadlineExceeded)` misses every other way a store timeout is typed: `os.ErrDeadlineExceeded` (what `net.Conn` deadlines actually return, and it does *not* `errors.Is` `context.DeadlineExceeded`), `net.Error` implementations with `Timeout() == true`, driver-specific timeout sentinels, and the case where the store swallows the ctx error and returns its own error while `ctx.Err() == context.DeadlineExceeded`. In all of those the field is `false` while the wrapped `Cause` still says "timeout", so a caller that trusts the field disagrees with a caller that does `errors.Is`/`errors.As` on the same error. That is the opposite of "preserve typed timeout context."

Require one of:
- Drop the field entirely and have callers classify via `errors.Is`/`errors.As` through `Unwrap` (the chain is already preserved; the bool adds nothing but a chance to diverge), or
- Replace it with a method that computes from `Cause` and covers the real cases: `errors.Is(cause, context.DeadlineExceeded) || errors.Is(cause, os.ErrDeadlineExceeded) || (errors.As(cause, &netErr) && netErr.Timeout())`, and also consult `ctx.Err()` at the wrap site.

**2. `catalog/fetch.go` – `Error()` discards the cause, so ordinary logging loses the reason.**

`Operation + " failed"` means `log.Printf("%v", err)`, `fmt.Errorf("...: %w", err)` chains, and error-reporting middleware all now print `"fetch catalog failed"` and nothing else. Before this change the store error text reached the logs; after it, an operator cannot tell timeout from auth failure from connection refused without code that knows to `errors.As` into `*FetchFailure` and print `.Cause`. Reviewer notes state store errors are already sanitized at source, so there is no confidentiality reason to hide them here.

Require: `Error()` returns `e.Operation + ": " + e.Cause.Error()` (idiomatic and matches the stated sanitization guarantee). If the intent really is an opaque message for some external surface, that belongs in the HTTP layer, not in `Error()`.

**3. HTTP mapping – wrapping *every* store error as `*FetchFailure` risks collapsing distinct outcomes into 503.**

The notes say "HTTP maps the typed failure to 503." `Fetch` now wraps unconditionally, so `context.Canceled` (client disconnected — should not be a 503), and any store sentinels that were previously mapped differently (e.g. not-found → 404, permission → 403) will all match `errors.As(err, &fetchFailure)`. Whether this regresses depends on check ordering in the handler, which is not in the diff.

Require: either confirm (and add a test) that the HTTP layer checks specific sentinels/`context.Canceled` *before* the generic `*FetchFailure` → 503 mapping, or restrict the 503 mapping to `Timeout`/transient causes. As submitted this is a plausible behavior change with no evidence it was considered.

**4. Missing tests.**

The change introduces classification logic and a new public error type with no tests. Require table tests covering: `context.DeadlineExceeded` → timeout; `os.ErrDeadlineExceeded`/`net.Error` timeout → timeout (once #1 is fixed); non-timeout store error → not timeout; `errors.Is(err, <original sentinel>)` still true through the wrapper; success path unchanged.

**Nit:** struct fields aren't gofmt-aligned; run `gofmt`.
