**Verdict: workspace/runtime configuration problem (stdout encoding), not a code or data bug. Safe to rerun.**

## Cause

`print(row.description)` at `db_report.py:34` tries to write `"Launch 🚀"` to `sys.stdout`. Because stdout is a pipe (not a console) and `sys.flags.utf8_mode = 0`, CPython picks the Windows ANSI code page for the stream — here **cp932** (Japanese). cp932 has no mapping for U+1F680 (🚀, position 7 in the string — right after `"Launch "`), so the `.encode()` inside `print` raises `UnicodeEncodeError`.

The data path is fine: the driver already produced a correct `str`. The failure is purely at the output-encoding boundary.

## Partial-effect check (before rerunning)

- DB: read-only, nothing committed → nothing to undo.
- stdout: empty → no partial report was emitted to the consumer.
- Nothing else observed. Rerun is safe.

## Smallest safe remediation

Command-scoped override, no code change:

```powershell
# truly command-scoped (PowerShell has no inline VAR=x form; cmd /c isolates it)
cmd /c "set PYTHONIOENCODING=utf-8 && python db_report.py"
```

Equivalent and even simpler, also command-scoped:

```powershell
python -X utf8 db_report.py
```

One caveat for the confirmation step: if PowerShell itself is the pipe consumer (`$out = python ...` or `| Out-File`), it decodes native output using `[Console]::OutputEncoding`, which on this box is also cp932. Set `[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()` in that session first, otherwise you'll get mojibake instead of an error — which is a different symptom, not a fix.

If you own the script and want it to stop depending on the caller's environment (the durable fix, not the minimal one):

```python
import sys
sys.stdout.reconfigure(encoding="utf-8")   # top of db_report.py
# and any file output: open(path, "w", encoding="utf-8")
```

I would *not* "fix" this by stripping/replacing the emoji or setting `errors="replace"` — that silently corrupts report content.
