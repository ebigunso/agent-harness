## Cause

This is **not a workspace or tooling problem** — the script did exactly what it was written to do.

The probe's contract is "require array framing." It records the raw JSON, then asserts that the trimmed raw string both starts with `[` and ends with `]`. The input `{"id":7}` is a syntactically valid JSON **object**, not an array, so `$trimmed.StartsWith('[')` is `$false`, the guard's `-not (...)` is `$true`, and `throw 'Expected array framing'` fires. With `$ErrorActionPreference = 'Stop'`, that terminates with exit code 1.

Note the design is sound: the `ConvertFrom-Json` result is discarded (`$null = ...`), and the check is done against the raw trimmed string. That deliberately sidesteps the pipeline-unrolling trap — a post-parse `-is [array]` test would tell you nothing about wire framing here. The failure is a **correct negative assertion on the data**, not a defect in the script, runtime, or environment.

## Smallest safe remediation

Nothing in the workspace needs fixing. The action depends on what you actually intended:

- **If the input is supposed to be array-framed:** the fix is in the *data source*, not the probe. Supply array-framed JSON, e.g. change `$raw` to `'[{"id":7}]'` (or point the probe at input that is genuinely wire-framed as an array). The single-object payload is the thing that's wrong.
- **If a bare object is legitimately acceptable here:** then the probe is the wrong assertion to run — don't weaken it silently. Use a probe whose contract matches (object-or-array), rather than editing this one to pass.

Do not "fix" it by piping the parsed result and testing `-is [array]`; that would reintroduce the unroll ambiguity this probe is specifically avoiding.
