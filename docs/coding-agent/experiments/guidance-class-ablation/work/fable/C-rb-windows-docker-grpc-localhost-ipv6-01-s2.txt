## Cause

This is not a defect in the probe, the service, or the project's dependencies. It is a local Docker Desktop address-selection problem:

- `localhost` resolves to `::1` before `127.0.0.1`, so the failed channel dialed `[::1]:50051`.
- Docker Desktop's published-port proxy on `[::1]:50051` accepts the TCP connection but never carries the h2c stream: no HTTP/2 response headers arrived within 2 s, the probe's client-side deadline fired (exit 2, `DEADLINE_EXCEEDED: deadline expired after 2s`), and the service interceptor log shows no invocation — the request never reached the container.
- The controlled comparison isolates the variable: with only the target changed to `127.0.0.1:50051`, the same call returned `pong` in exit 0, and the service logged `invoked=true completed=true`.
- The REST sibling (`localhost:50080`, 200 in 0.012 s) is HTTP/1.1, which the proxy handles fine; it does not exercise the HTTP/2 path, so it is not evidence that the gRPC port is healthy over `::1`.

Not implicated: TLS/name checks (plaintext h2c, none configured), auth (would be exit 3), server load or method registration (server never saw the call).

## Smallest safe remediation

Point the local gRPC target at the IPv4 loopback explicitly:

```powershell
python probes/unary.py --target 127.0.0.1:50051 --timeout 2
```

and set `127.0.0.1:50051` (not `localhost:50051`) as the gRPC target in local config / scripts on this Windows host. No probe code change, no container or port-mapping change, no Docker Desktop reconfiguration needed.

Do not "fix" this by raising the timeout or adding retries — the `::1` path stalls indefinitely, so a longer deadline only delays the same failure.

## Confirmation

1. Re-run the unary probe with `--target 127.0.0.1:50051 --timeout 2`: expect exit 0, stdout `pong`, empty stderr.
2. Check the service log for the new call: expect `probe method="unary Echo" transport=h2c invoked=true completed=true`.
3. (Optional, to prove the variable) re-run once with `localhost:50051`: expect exit 2 with the deadline message and no interceptor log entry, confirming only the address differs.
4. Record for the ticket: both targets and port (50051), the deadline stderr line, the REST timing (`200`, 0.012 s on 50080), and the IPv4 retry result.

If step 1 had also failed on `127.0.0.1`, the next checks would be the container's health, the published-port mappings, and whether the service is actually listening on 50051 — but the captured comparison already rules that out here.
