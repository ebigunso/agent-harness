**Cause**

`npm ci` deletes `node_modules` before reinstalling. On Windows, a loaded native addon (`.node` DLL) cannot be unlinked while a process has it mapped, and the OS returns `EPERM` (errno -4048) regardless of ACLs. The current `tasklist /m` output shows exactly one holder: `node.exe` PID **4114**, the repository's own thumbnail watcher (`workers/thumbnails.js`), which has `sharp-win32-x64.node` loaded. This is not a permissions, lockfile, registry, or cache problem — the probe-file test and synced lockfile rule those out. The earlier `better_sqlite3.node` / PID 4113 entry is history only; 4113 is gone and is not the blocker now.

**Smallest safe remediation**

Stop the repo-owned watcher that holds the DLL, then rerun the install. Do not touch antivirus, ACLs, or delete `node_modules` by hand.

```powershell
# confirm it's still the same repo-owned process before killing
Get-CimInstance Win32_Process -Filter "ProcessId = 4114" | Select-Object ProcessId, CommandLine

Stop-Process -Id 4114          # add -Force only if a graceful stop doesn't succeed
npm ci
```

(If the watcher is normally launched by a task runner/dev script, stop it through that mechanism instead, so it doesn't respawn mid-install.)

**Confirmation**

1. `tasklist /m sharp-win32-x64.node` → prints "No tasks are running which match the specified criteria." (no remaining holders).
2. `npm ci` exits 0 with no `EPERM`/`unlink` lines in stderr.
3. `Test-Path node_modules\sharp\build\Release\sharp-win32-x64.node` → `True`, and `node -e "require('sharp')"` loads without error.
4. Restart the thumbnail watcher afterward so it picks up the freshly installed module.

If, after PID 4114 is gone, `tasklist /m` shows another holder, repeat the ownership check on that PID; if a *different* module path is named next time, treat it as a new incident rather than the same cause.
