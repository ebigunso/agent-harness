## Findings

### 1. `adapter.py` — both service failures collapsed into `200, None` (blocking)

```python
-    except NotFound: return 404, None
-    except Unavailable: return 503, None
+    except (NotFound, Unavailable): return 200, None
```

This is the core defect. The task was to *map* RPC results to HTTP; the change instead erases the mapping. After this diff:

- A not-found lookup, an unavailable backend, and a successful lookup whose value is legitimately `null` all produce the identical tuple `(200, None)`. The status code no longer carries any information about the outcome.
- The reviewer notes explicitly say "Client treats 404 as missing and 503 as retryable" — but the adapter never emits 404 or 503 anymore, so those semantics are unreachable. The notes describe a contract the diff does not implement.
- `Unavailable` is a transient condition that callers are supposed to retry. Reporting it as `200` means callers will treat a backend outage as a definitive successful empty result and never retry. That's silent data loss dressed up as success.

**Require:** restore the distinct mappings (`NotFound → 404`, `Unavailable → 503`). If there's a reason to change codes, do it deliberately on both sides, not by folding everything into the success path.

### 2. `client.ts` — `interpret` is now decoupled from what the adapter actually sends

```ts
if (status === 404) return "missing";
if (status === 503) return "retry";
```

Given finding 1, these branches are dead code. Worse, the `200` path returns `value`, which for both failure cases is `null` — so `interpret` hands `null` up as a valid result and the caller has no way to tell "found nothing," "backend down," and "found a null value" apart. The retry contract the client is supposed to enforce is silently dropped at the boundary.

This is exactly the "upstream/downstream disagree on schema and semantics" case. The client is written against the *old* adapter; the diff changes the adapter without touching the client, so the two halves now embody different contracts and nothing (types, tests, shared enum) catches it.

**Require:** fix the adapter per #1, and add a test that exercises each of the three outcomes end-to-end through both `lookup` and `interpret` so the mapping can't drift again without a failure.

### 3. `client.ts` — return type conflates sentinel strings with payload values (should fix)

`interpret` returns `"missing" | "retry" | unknown`, which flattens to `unknown`. A caller cannot distinguish a successful lookup whose value is the string `"missing"` from a 404 result. Sentinel-in-band signalling is the same class of shape drift as #1, just on the TypeScript side.

**Require:** return a discriminated union, e.g. `{ kind: "ok", value } | { kind: "missing" } | { kind: "retry" }`, so the outcome is in a separate channel from the payload.

### 4. Commit message / reviewer notes misstate the change (minor, but fix before merge)

"map rpc lookup results to http" and "only not-found and unavailable are service errors … client treats 404 as missing and 503 as retryable" describe the pre-change behavior. The diff does the opposite. Whoever reads the log later will be misled about what shipped.

**Require:** commit message and notes should describe what the code actually does; once #1 is fixed, the current wording becomes accurate.

---

**Verdict:** Not acceptable as-is. Finding #1 is a blocker — the change removes the mapping the task asked for and makes backend outages indistinguishable from successful empty results.
