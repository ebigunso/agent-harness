**Verdict: not a workspace problem.** This is a server-side stall in the service's database, not anything wrong with the probe, Docker, port mapping, name resolution, or the local toolchain.

**Cause**

- The RPC reaches the server: the interceptor records `method=Echo invoked=true`, so connectivity, h2c, and the 50051 mapping are fine. `127.0.0.1` and `localhost` behave identically, and the HTTP/1.1 sibling on 50080 answers in 12 ms, which rules out the Docker/WSL2 address asymmetry the scenario hints at.
- The handler then blocks at `phase=db-query waiting_on=lock-42`, and lock-42 is held by a stalled migration transaction. The handler never returns, so the client's 2 s deadline expires and the probe maps that to exit 2 with its normalized `DEADLINE_EXCEEDED` message. That message is correct behavior, not a bug.

Raising `--timeout`, retrying, or restarting Docker/the container would not help: every `Echo` call will queue behind the same lock until the holder releases it.

**Smallest safe remediation**

Release lock-42 by dealing with the stalled migration transaction on the database side, without touching the service or the workspace:

1. Confirm the holder is genuinely stalled (e.g. "idle in transaction" with no progress, not a long-running but active migration). For Postgres that is `pg_stat_activity` / `pg_locks`; the equivalent view for whatever engine is in use.
2. If it is stalled, terminate/roll back that one session (Postgres: `pg_terminate_backend(<pid>)`). Do not kill the gRPC service, do not restart the DB, and do not re-run the migration until you have checked which migration step it was on so it isn't left half-applied.

If the migration is actually still doing work, the correct action is to wait for it (or run it in a maintenance window) rather than kill it.

**Confirmation**

1. Re-run the original command unchanged: `python probes/unary.py --target 127.0.0.1:50051 --timeout 2`. Expect exit 0 and the response value on stdout, with nothing on stderr.
2. Check the handler trace / lock view: no session waiting on lock-42, and the interceptor shows the invocation completing rather than stuck in `db-query`.
3. Optionally re-run with `localhost:50051` to show the two addresses still behave the same, and verify the migration ledger reflects a consistent (fully applied or fully rolled back) state before any migration is re-attempted.
