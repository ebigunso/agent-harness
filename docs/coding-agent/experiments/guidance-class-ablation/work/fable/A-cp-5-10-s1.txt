**Finding 1 — `Search.kt`, `ingress`: raw input is stored without NFC normalization.**

`ingress` passes `raw` straight into `store.addCanonical(raw)`. Per the reviewer notes, the store's contract is that it holds *canonical NFC* keys, and input is explicitly *not* guaranteed to be normalized. So `"é"` submitted as precomposed U+00E9 and as `e` + U+0301 (NFD) will be inserted as two distinct entries in the `MutableSet`, violating the stated requirement that distinct normalization forms of the same text must share one key. This is the core of the task and it isn't implemented — the change is functionally a no-op with respect to "canonical."

Required: normalize at the boundary before insertion, e.g.

```kotlin
import java.text.Normalizer

fun ingress(raw: String, store: KeyStore) {
    store.addCanonical(Normalizer.normalize(raw, Normalizer.Form.NFC))
}
```

Do not lowercase or otherwise fold — case sensitivity is intentional. Add a test that inserts NFC and NFD spellings of the same string and asserts `keys.size == 1`.

**Finding 2 — `Search.kt`, `KeyStore.addCanonical`: the method name asserts a precondition it does not enforce.**

Nothing stops another caller from doing what `ingress` currently does. Since the store "owns" canonical keys, I'd want the invariant held where it can't be bypassed — either have `addCanonical` normalize (or `require` NFC via `Normalizer.isNormalized`), or make `keys` non-publicly-mutable (`private val` + read-only accessor) so that `ingress` is the only write path. As written, `keys` is a public `MutableSet`, so any code can insert unnormalized strings directly. Pick one enforcement point and make it the only one; I'd accept either approach but would block on having neither.

No other issues; the change is otherwise minimal and the omission of case folding is correct per the notes.
