## Diagnosis

**This is not a workspace, network, or Docker problem.** It is a server-side authorization rejection, and the failure is expected given the credentials supplied (none).

### Cause

The RPC reached the server and executed. The evidence rules out every transport/config hypothesis:

- **The server was actually called.** `invoked=true`, `policy=role-required`, `status=PERMISSION_DENIED`, and the policy interceptor *recorded* the request. A response cycle happened.
- **HTTP/2 transport works.** The call completed in ~15 ms and returned a real gRPC status, not a stall or reset.
- **The `localhost`→`::1` hang scenario from the reference material does not apply.** That pattern manifests as a `DEADLINE_EXCEEDED`/hang with no server call. Here `localhost:50051` and `127.0.0.1:50051` return the **identical** `PERMISSION_DENIED` with an identical exit code 3 — proving both IPv6 and IPv4 paths connect and are served. The IPv4 retry was already done and did not change the outcome, so address selection is not the issue.
- **The sibling health check is green** (`200 OK`, 12 ms), confirming published ports and container health.

The probe maps `PERMISSION_DENIED` to exit 3 exactly as specified. Exit 3 with `role required` means the server's policy interceptor rejected the call because the request carried no credential granting the required role. The gRPC/HTTP-2/Docker plumbing is functioning correctly.

### Smallest safe remediation

Nothing in the workspace should be changed. The fix is to **present the required authorization on the call** — i.e., attach the role-bearing credential (e.g., a bearer token / call credentials in request metadata) that the `role-required` policy expects for `Private`. If your account legitimately lacks that role, the correct action is to request the role grant from whoever owns the service policy, not to alter local config.

Do **not** switch addresses, edit `localhost` resolution, change ports, or touch Docker — those are all confirmed healthy and would mask nothing.

### How to confirm it worked

Re-run the same command with the credential attached:

```
java -jar probes/grpc-probe.jar --target 127.0.0.1:50051 --method Private --timeout 2 <auth flag/metadata>
```

Success criteria:
- **Exit code 0** (not 3).
- **stdout is non-empty** — the probe only prints response values after a successful call.
- **stderr empty**; no `PERMISSION_DENIED`.
- Server-side line changes to a granted/`OK` status for `method=Private`.

If, after supplying valid credentials, you instead see `DEADLINE_EXCEEDED`/a hang on `localhost` that clears on `127.0.0.1`, *then* the reference IPv6 scenario would be in play — but the current evidence shows the opposite, so that is not today's failure.
