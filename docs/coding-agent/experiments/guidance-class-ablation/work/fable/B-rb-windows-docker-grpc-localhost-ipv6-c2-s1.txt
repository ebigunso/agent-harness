**Cause: wrong port in the command, not a workspace or Docker networking problem.**

The probe targeted `50052`, but the service publishes only `50051/tcp` (gRPC h2c) and `50080/tcp` (HTTP health). Nothing listens on 50052 on the host, so the TCP connect is refused immediately and grpc-js reports `UNAVAILABLE: connection refused` (probe-mapped exit 2). The server invocation log is empty for these calls because no connection ever reached the service.

Why the loaded reference (`localhost` → `::1` IPv6 stall on Docker Desktop) does **not** apply here:
- That failure mode is a *hang until deadline* (`DEADLINE_EXCEEDED`), not a fast `connection refused`.
- Its distinguishing signal is an IPv4/IPv6 asymmetry; here `127.0.0.1:50052` fails identically to `localhost:50052`, so loopback resolution is ruled out.
- The REST sibling on 50080 succeeding just confirms the container and port proxy are healthy; it says nothing about 50052, which isn't mapped at all.
- Correctly targeted 50051 probes are already reported healthy.

**Smallest safe remediation:** fix the target port only.

```powershell
node probes/unary.mjs --target localhost:50051 --timeout 2
```

No change to Docker config, port publishing, probe code, or host resolution is needed. (If you later do see a hang-until-timeout on `localhost:50051` while `127.0.0.1:50051` works, *then* the reference guidance applies and you'd switch the connection string to `127.0.0.1`.)

**Confirmation:**
1. The command above exits `0`, prints the response values on stdout, and stderr is empty.
2. The server invocation log shows the corresponding unary call.
3. Optional sanity check that the earlier failure was purely the port: `docker port <container>` (or `docker compose ps`) lists `50051/tcp` and `50080/tcp` only — no `50052` — and `Test-NetConnection -ComputerName 127.0.0.1 -Port 50052` reports `TcpTestSucceeded : False` while `-Port 50051` reports `True`.

If the intent was genuinely to expose a second gRPC port on 50052, that's a deliberate config change (add `50052:50051` or a new listener), not a fix for this failure — the command as written simply pointed at an unpublished port.
