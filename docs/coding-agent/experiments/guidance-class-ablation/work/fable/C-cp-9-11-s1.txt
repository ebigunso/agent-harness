**Verdict: block.** The change replaces a visible failure with a permanent, invisible hang, which is the opposite of the stated task.

**Findings**

1. **`src/service.cpp`, `Service::process` — unbounded retry loop on `std::bad_alloc`.**
   - *What's wrong:* `for (;;) { try … catch (bad_alloc) { continue; } }` retries forever with no attempt limit, no backoff, and no condition that could change between attempts. Per the reviewer notes, validated input can legitimately require more than the fixed worker limit, and identical retries cannot shrink the allocation. For such input the loop can never exit.
   - *Why it matters:* This service has a single dispatch thread. When that thread enters the loop on an oversized input, the whole service stops processing all other work — permanently — while spinning at 100% CPU. That is exactly "wedging the service worker," which the task was supposed to prevent. The original code at least propagated `bad_alloc` so a caller/supervisor could see and act on it; this change is strictly worse.
   - *Require instead:* Either no retry at all (convert to an error result immediately), or a bounded retry (small fixed attempt count, with a short sleep/backoff between attempts so transient pressure has a chance to clear) that terminates in a failure path. Retry is safe here only because `allocate_and_run` releases partial resources and has no pre-success side effects — worth keeping that precondition in a comment if retry is kept.

2. **Same location — the failure is swallowed with no context and no visibility.**
   - *What's wrong:* The `catch` discards the exception silently. Nothing is logged, no metric is emitted, and no error `Result` is produced. Even if the loop were bounded, an operator would have no signal that inputs are exceeding the worker's memory limit.
   - *Why it matters:* "Handle boundary errors with context; never hide or blur failures." An allocation failure at the worker limit is a boundary condition that needs to be diagnosable (which input, requested size if available, attempt count, limit). Silently retrying blurs it into latency and CPU burn.
   - *Require instead:* On exhausting the retry budget (or immediately, if no retry), return an explicit failure `Result` (e.g. resource-exhausted / input-too-large) carrying the `bad_alloc` context and identifying information about the input, and log/emit a metric at that point. The caller must be able to distinguish "this input cannot be processed under the current limit" from a transient condition.

3. **Commit message "retry allocation until successful" describes the bug as the feature.**
   - *What's wrong:* It states the intent is to loop until success, which for over-limit inputs is never.
   - *Why it matters:* Anyone reading history will believe unbounded retry was deliberate and vetted.
   - *Require instead:* Message should reflect the actual (bounded, failing-with-context) behaviour once fixed.

**Not a finding:** The `<new>` include is already present in the header, so `std::bad_alloc` resolves; no include change needed.
