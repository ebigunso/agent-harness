## Review: `delete.go` — Delete account and recurring jobs

**Verdict: Block.** The change implements the happy path only and, per the reviewer notes, leaves the system in exactly the state the task says must never exist.

### Findings

**1. `delete.go:4` — Non-atomic two-step write leaves a deleted account with live billable jobs (blocking)**

`MarkDeleted` commits independently. If `CancelJobs` then fails, the error propagates but the account is already durably deleted while its recurring jobs remain scheduled and billable. That is the precise invariant the notes call out ("Deleted accounts must not retain billable jobs"), and this code violates it on any partial failure — a network blip, a lock timeout, a crash between the two calls.

Why it matters: the customer is billed for jobs on an account they believe is gone. That's a revenue/compliance defect, not a cosmetic one, and it's silent — the caller sees an error, but nothing is left in a state that anyone will notice or reconcile.

Require: the two mutations must be atomic at the authoritative boundary. Options, in order of preference:
- Add a single `Store.DeleteAccount(id)` that marks deleted and cancels jobs in one transaction. Move the "no billable jobs on a deleted account" rule into the store where it can actually be enforced.
- If the store genuinely cannot span both (separate systems), then (a) reverse the order — cancel jobs first, mark deleted second — so the failure-mode intermediate state is "active account with no jobs" rather than "deleted account with billable jobs", and (b) have the job runner/billing path check account state and refuse to execute or bill jobs for a deleted account, so the invariant is enforced where money moves, not only in this one caller.

**2. `delete.go:3-4` — `Delete` is not safely retryable; the interface contract doesn't guarantee idempotency**

The obvious recovery for a `CancelJobs` failure is "call `Delete` again." But nothing in the `Store` contract says `MarkDeleted` on an already-deleted account is a no-op rather than an error, and nothing says `CancelJobs` tolerates already-cancelled jobs. If either fails on repeat, the partial state from finding 1 becomes permanent — the retry path is closed. Concurrent double-submits (user double-clicks, two workers pick up the same deletion event) hit the same problem.

Require: document and test that both methods are idempotent (or that the composite `DeleteAccount` is), so a retry from any intermediate state converges to the terminal state. Add a test that exercises "MarkDeleted succeeds, CancelJobs fails, Delete called again" and asserts the end state is correct.

**3. `delete.go:3` — Invariant enforced only in an optional caller path**

Even once ordering/atomicity is fixed inside `Delete`, the rule lives in one Go function. Any other path that calls `MarkDeleted` directly — admin tooling, a batch purge, a future GDPR handler — bypasses job cancellation entirely. This is the Gate 5 anti-pattern verbatim.

Require: the store's `MarkDeleted` (or the transactional replacement) should own the invariant, and/or the scheduler must treat "account deleted" as a hard stop for execution and billing. `Delete` should be a thin convenience, not the sole guardian.

**4. No tests, no failure-path coverage**

The diff adds no tests. Given the notes explicitly identify the failure ordering, a test for the partial-failure case is the minimum bar to merge, and it would have caught finding 1.

### Minor (non-blocking, mention only)

- No `context.Context` on `Delete` or the interface methods. Cancellation/timeouts across two remote calls matter more once this becomes a multi-step operation; worth adding now rather than retrofitting.

### Summary of what I'd need to see

A single transactional store operation (or, failing that, cancel-before-delete plus enforcement at the job execution/billing boundary), an explicit idempotency contract with a retry test, and a test that reproduces the `CancelJobs`-fails-after-`MarkDeleted` scenario and asserts no billable jobs survive on a deleted account.
