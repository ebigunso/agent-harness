**Verdict: this is a workspace (host networking) problem, not a bug in the probe, the client library, or the service.**

**Cause**

`localhost` on this host resolves to `::1` first, so `Grpc.Net.Client` (via `SocketsHttpHandler`) connects to `[::1]:50051`. Docker Desktop's published-port forwarder accepts the TCP connection on the IPv6 loopback, so the client sees a successful connect and never falls back to `127.0.0.1` — but the h2c stream is never delivered to the container. Evidence:

- TCP connect to `[::1]:50051` succeeds, yet no HTTP/2 response headers arrive within 2 s.
- The service interceptor log shows **no invocation** for the failed call — the request never reached the service. A server-side hang would have shown `invoked=true completed=false`.
- The address-only control (`127.0.0.1:50051`, everything else identical) returns exit 0, `pong`, and the log shows `invoked=true completed=true`.

So the `DEADLINE_EXCEEDED` is the probe correctly reporting a dead half-open forward on the IPv6 loopback path, not a slow or broken service. Note the `curl` check is *not* a valid control for this: different port, HTTP/1.1 rather than h2c, and curl does its own address selection/fallback — its success only shows the container is up, which the 127.0.0.1 gRPC call already proves more directly.

**Smallest safe remediation**

Pin the probe target to the IPv4 loopback address:

```powershell
dotnet run --project probes/GrpcProbe -- --target 127.0.0.1:50051 --timeout 2
```

This is a one-argument change scoped to the invocation. Do **not** edit the hosts file, disable IPv6 machine-wide, or set `DOTNET_SYSTEM_NET_DISABLEIPV6` — those are broader than the problem and affect unrelated software. If you want the fix to survive in project config, the next-smallest step is publishing the port explicitly on IPv4 (`127.0.0.1:50051:50051` in the compose/`docker run` mapping), which makes `[::1]:50051` refuse the connection outright so any client falls back to IPv4 instead of hanging.

**Confirmation**

1. Run the command above: expect exit code `0`, stdout `pong`, empty stderr.
2. Check the service interceptor log for a new line `probe method="unary Echo" transport=h2c invoked=true completed=true` correlated with that run.
3. Optionally rerun the original `localhost:50051` command once to confirm it still fails with exit 2 / `DEADLINE_EXCEEDED` and no log entry — that demonstrates the address is the only variable. If you applied the explicit IPv4 port publish, that same rerun should instead succeed (connect to `::1` refused → fallback to `127.0.0.1`).
