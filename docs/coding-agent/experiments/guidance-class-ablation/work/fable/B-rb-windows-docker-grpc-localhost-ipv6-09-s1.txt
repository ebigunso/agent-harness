**Cause**

The failure is not a service or project problem. `localhost` resolves to `::1` first on this Windows host, so the Ruby gRPC channel connected to `[::1]:50051`. Docker Desktop's IPv6 port proxy accepted the TCP connect but never returned HTTP/2 response headers, so the h2c server-streaming Echo stalled at the transport layer until the probe's 2s deadline fired (`DEADLINE_EXCEEDED`, exit 2). The evidence lines up with the loaded reference note:

- REST on sibling port 50080 via `localhost` responded in 12 ms — but that is HTTP/1.1, which the IPv6 proxy handles fine.
- The service interceptor log shows no invocation for the failed call — the request never reached the service.
- The identical call to `127.0.0.1:50051` succeeded (`pong 1`, `pong 2`, exit 0) and was logged `invoked=true completed=true`.

The only variable between the failing and passing runs is the target address family. The service, port mappings, deadline, and probe code are all healthy.

**Smallest safe remediation**

Change the gRPC client target from `localhost:50051` to `127.0.0.1:50051` in the local connection string:

```powershell
ruby probes/stream.rb --target 127.0.0.1:50051 --timeout 2
```

Apply the same substitution wherever the project's local gRPC config/scripts reference `localhost:<port>` for Docker Desktop published ports. Do not touch the service, the port publishing, container health, or the probe's error mapping — none of those are at fault. Don't edit the hosts file or disable IPv6 system-wide; that's a broader change than needed.

**Confirmation**

1. Re-run the streaming probe against `127.0.0.1:50051` (already captured): exit 0, stdout `pong 1` / `pong 2`, empty stderr.
2. Check the service interceptor log shows `probe method="server-streaming Echo" transport=h2c invoked=true completed=true` for that run.
3. Optionally re-run against `localhost:50051` once more to confirm it still hangs with the same `DEADLINE_EXCEEDED` after 2s — this proves the asymmetry is address-only and reproducible, not a transient.
4. If any other gRPC probes (unary etc.) use `localhost`, run one of them against `127.0.0.1` as well to confirm the fix generalises.

Note: the probe deliberately does not fall back to a different address, so the `localhost` form will keep failing until the connection string is changed — this is expected, not a regression.
