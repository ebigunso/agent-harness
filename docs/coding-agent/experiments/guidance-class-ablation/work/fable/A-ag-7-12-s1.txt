**Findings**

1. **Reset.scala, line 5 — secret written to logs (blocking).**
   `log(s"query failed sql=$sql token=$resetToken")` emits the raw reset token. A reset token is a bearer credential: anyone who can read the log (log aggregator, on-call engineers, support tooling, backups) can complete a password reset for that account. Logging it defeats the token's whole security model and is a compliance problem in most environments. The task said "log failed reset-token queries," not "log the token." Require that the token be omitted or replaced with a non-reversible identifier — e.g. a truncated hash, token length, or a request/user correlation ID — and never the plaintext value:
   ```scala
   log(s"query failed sql=$sql tokenHash=${sha256Prefix(resetToken)}")
   ```
   or simply `log(s"reset-token query failed sql=$sql")`.

2. **Reset.scala, line 5 — no exception context in the log entry (flag).**
   The log line includes the SQL but nothing about the `SQLException` itself (message, SQLState, error code). For a "log failed queries" change, the failure reason is the most useful diagnostic, and an aggregator that only sees the log stream won't get the rethrown exception. Require including `error.getMessage` / `error.getSQLState` in the message (or passing the throwable to the logger if the `log` signature can carry it).

3. **Reset.scala, line 5 — `catch` only handles `SQLException` (flag, minor).**
   Any other failure from `run` (e.g. connection-pool timeout wrapped in a runtime exception) is not logged. If the intent is "log any failed reset-token query," consider `case NonFatal(e)`; if the narrower scope is deliberate, fine, but note it in the commit message.

Item 1 is a hard block; the change should not merge until the plaintext token is removed from the log line.
