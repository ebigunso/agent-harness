**Verdict: not acceptable as-is.** One blocking defect (timezone contract), several flags.

---

**1. `Inventory.java:4` — `schedule(LocalDateTime, …)` silently assumes UTC. (BLOCK)**
- **What:** `LocalDateTime` carries no zone. The method hard-codes `toInstant(ZoneOffset.UTC)`, so any caller whose `LocalDateTime` was produced in another zone (the reviewer note confirms these exist) gets an `Instant` that is off by that zone's offset — no error, no warning, just a wrong snapshot time in the queue.
- **Why it matters:** This is exactly an implicit, ambiguous input contract. The parameter type tells callers "any wall-clock time is fine" while the body requires "must already be UTC." The failure mode is silent data corruption at the queue boundary, and it will only be noticed when a snapshot fires hours early/late.
- **Require:** Make the zone part of the type or the signature. Preferred: `schedule(Instant at, …)` — the queue stores `Instant`, so accept `Instant` and push the conversion to the caller who actually knows the zone. Acceptable alternative: `schedule(ZonedDateTime at, …)` / `OffsetDateTime`, or `schedule(LocalDateTime wallClock, ZoneId zone, …)`. Do not keep a bare `LocalDateTime` overload. Update the non-UTC callers in the same change (producer/consumer sync), and note in the commit that this is a breaking signature change if `Inventory` already existed elsewhere.

**2. `Inventory.java:5` — `nightly(...)` does not schedule a nightly snapshot.**
- **What:** It schedules "now" (`LocalDateTime.now(UTC)` round-tripped back to an `Instant`). The name promises a night-time/next-midnight run; the body enqueues an immediate one.
- **Why:** Name and behaviour disagree; the next reader will assume the wrong thing. The `LocalDateTime` detour is also pointless — `Instant.now()` is the direct expression and avoids the zone question entirely.
- **Require:** Either rename to `now(...)`/`immediate(...)` and use `Instant.now()`, or implement the actual nightly semantics (next 00:00 in an explicit zone, using a `Clock` parameter for testability). Pick one and say which in the commit.

**3. `Inventory.java:4` — no explicit null/argument contract.**
- **What:** `input == null` or `queue == null` throws a bare `NullPointerException` from inside the method; a past `Instant` is accepted without comment.
- **Why:** Failure behaviour is undeclared. Callers can't tell whether null is rejected by design or by accident, or whether scheduling in the past is meaningful.
- **Require:** `Objects.requireNonNull(at, "at")`, `Objects.requireNonNull(queue, "queue")`, and a Javadoc line stating whether past instants are allowed (and if not, throw `IllegalArgumentException`).

**4. `Inventory.java:4` — output is a side effect on a caller-supplied raw `List`.**
- **What:** The "queue" is a `List<Instant>`; the method mutates it and returns `void`. `List.of(...)`/unmodifiable lists will throw `UnsupportedOperationException`; the caller gets no handle on what was scheduled.
- **Why:** The boundary is wider than it needs to be (all of `List`) and the success path is implicit.
- **Require (flag, not block):** Return the scheduled `Instant`, and narrow the parameter to what is actually needed — `Queue<Instant>`, `Collection<Instant>`, or a `Consumer<Instant>` sink — so the contract is "accepts an Instant" rather than "mutates your list."

**5. No tests.**
- **What:** New public API with zero coverage; the zone bug in #1 would have been caught by a single test passing a non-UTC time.
- **Require:** Tests for the UTC case, a non-UTC case (after fixing #1), null rejection, and `nightly`'s actual semantics (with an injected `Clock`).
