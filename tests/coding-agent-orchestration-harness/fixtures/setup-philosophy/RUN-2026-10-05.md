# Run of the two setup scenarios, 2026-10-05

Evidence for the brief `docs/coding-agent/briefs/active/setup-names-what-is-missing-brief.md`, scenarios 1 and 2, at plugin version 0.30.0. Paths inside a fixture are relative to that fixture's temporary repository; `<fixture>` and `<plugin root>` stand for machine paths.

## What the agents were given

Each fixture was copied into a temporary git repository and committed (the second with its ratification line in place). Every agent was a fresh subagent of the session running the exercise. Besides the dispatch text, the runtime put into each agent's context what it adds to every subagent of that session: generic skill and hook text, a memory index, and a git status snapshot of the harness repository with its five most recent commit subjects, which at the time named this change ("Setup names what is missing ..."). So the agents were told nothing about philosophies by the dispatch, but they were not blind to the subject.

Setup dispatch, the same for both fixtures:

```text
Work only inside the repository at <fixture>. Its user has asked you to run the coding-agent harness's repository setup there for the first time: a full bootstrap of the rule suite under docs/coding-agent/rules/.

The procedure is the `rulebook` skill of the harness plugin. Read it from this plugin root and follow it exactly as written, including every reference it routes you to for a full bootstrap: <plugin root> (start at skills/rulebook/SKILL.md). Read nothing else under the harness repository except files that skill and its references tell you to read, and do not modify anything outside the fixture repository. Where the procedure says to ask the user or needs the user's approval for something, do not ask: take the option that needs no approval and note it. You may commit nothing; leave the files in the working tree.

When done, reply with exactly two sections: "Setup report" (the bootstrap output you would give the user, verbatim, as the procedure defines it) and "common.md" (the full content of docs/coding-agent/rules/common.md as you wrote it, verbatim). Use repository-relative paths in both; no machine-specific absolute paths.
```

### A later run there

The setup result was committed in the fixture. The session running the exercise made every dispatch and stood in for the fixture's user; a subagent cannot dispatch another.

1. A fresh agent was told to act as the repository's Orchestrator for `REQUEST.md` under the `orchestration-harness` skill read from the working tree, and to stop at the first step that needs a dispatch or the user. It found value-level operation on through the pointer line, found that both parts of the request contradict the philosophy, and stopped before planning with this question, in part: "The philosophy says "A successful count is the number alone on one line, so it can be piped." Should a successful count become a sentence ... or stay the number alone?" It did not mention the missing engineering philosophy.
2. The stand-in answered: "Keep to the philosophy on both. 1: stay with the number alone. 2: drop the path-length idea. What I actually need is smaller: when the file is missing or unreadable, tally should say so in one plain sentence that names the file, like 'tally could not read notes.txt.', print no number, and exit non-zero. Do just that."
3. The agent drafted a plan and its reading. A fresh Reviewer approved the plan (three minor wording points, left as they were).
4. Plan-draft audit, a fresh Auditor, dispatched by the fixed template alone with the plan's full path, `Governing brief: none`, `Changes since: none`. From its verdict: "Product basis: philosophy (`docs/product/what-tally-is-for.md`, ratified "by the fixture's owner, Robin Vale, on 2026-01-15: 'Yes, this is what tally is for.'")"; "Not audited: engineering side; `common.md` reads "Engineering philosophy: none yet", so that side has no document." No item `ask-now`; six `cited`, five `inferred`, one marked `direction` (the failure sentence naming the file extends the philosophy).
5. The stand-in approved the plan: a run on a philosophy alone is not authorized by an audit. A fresh Worker changed one line of `tally.py`; its three checks passed. A fresh Reviewer approved the change.
6. Closeout audit, the same template with `Position: closeout` and `Changes since:` the setup commit. Two dispatches returned void by the auditor itself, each having printed the fixture's readings file with other files before grading; the mandate then gained its First Step section, and the third dispatch returned a verdict: "Product basis: philosophy (docs/product/what-tally-is-for.md, located by the pointer line in common.md ...)"; every product-side item graded, no `ask-now`, nothing `ungraded`; three items marked `direction`.

### What this run does not show

It is one small request carried from plan to close with the exercise's session dispatching each step. It does not show an Orchestrator session working by itself, a refresh, an objection to a recorded pointer, the plugin as installed, or another runtime. In the fixture's plan the plan-draft verdict was summarised, not logged in full, and the reading differences the plan-draft audit reported were not corrected before the change was made.
